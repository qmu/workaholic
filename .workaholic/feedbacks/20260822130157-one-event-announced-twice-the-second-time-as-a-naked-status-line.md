# One event, announced twice, the second time as a naked status line

A unit resolved to two feedback stems. One found its thread; the other matched nothing in either search, so the run took the documented not-found branch and posted a new keyed root. The channel carried the identical finish line twice within four seconds.

Three things are wrong, and only the first is the rule everyone would name.

The two stems were two records of one request — not two items with two audiences. The same ask had been captured twice by different seams, months apart. "Once per stem per event" then means "announce one event as many times as the corpus happens to hold records of it", which is a property of capture history rather than of who needs telling.

The fallback root is the shape this skill already rejected elsewhere. Every legitimate root in that channel opens with a marker, a linked title and a one-line description of the item. The finish-line root opens with a status emoji and a pull request number, gives a reader nothing to read and nothing to answer, and ends in a bare sixty-character machine key. That is the defect the description root was introduced to fix for the proposing command — and the skill states the fix is deliberately not extended to the implementing one, on the ground that the routine prompt does not name the shape.

Nothing renders the key. For the roots the proposing command writes the exact wording is specified; for this one it is not, so the shipped line did not match the formatting of every other root beside it.

Measured again the same day on a different post shape: a red alert rendered as
🔴 Blocked - `open-decision-unruled: d1-r2-vs-platform-no-guessing-stance`
— the developer's words were that a post like that is one nobody reading it can do anything about. The signature is the dedup key of the red-alert shape, so it is the same defect on a second template.

What should change: deduplicate per event rather than per stem — one finish line per unit per channel, threaded into the thread that was found, with any remaining stems getting a pointer or nothing; two records of one request must not become two announcements. If a keyless post is genuinely unacceptable, give this root the same readable shape the proposing command's root already has, or keep the key out of the rendered text. A message a human reads should not end in a machine identifier.
