# /moderate の記録の口が、定時実行では何も残さない

`/moderate` の手順 2（inbound-sweep）と手順 5（issue-triage）は、見つけたことを `feedback/scripts/create.sh` でフィードバック記録として書く。定時実行の器は基底から複製されて捨てられるので、git に載せただけの記録は器とともに消える。

三つの規則が定時実行の tick に対して同時に満たせない。(1) `workaholic:moderate` は `persist-log.sh` が `.workaholic/moderations/` を公開し「それ以外はどこにも書かない」と定めている。(2) `create.sh` は記録を git に載せて終わる。(3) 認められる枝の形は claim の形だけで、`hooks/guard-git-branch.sh` が `work-*` と `release/*` 以外を拒む — 記録を公開しうる `publish-tree-pr.sh` は `work-*` の枝を作るが、それは `/moderate` が作ってはいけないもの。tick が書いた記録から基底へ至る道が一本もない。

測ったこと（導入先リポジトリの tick 20260821-085204）: tick はインバウンドのイシュー 2 件について記録を書き、`persist-log.sh` は両方について filed／persisted と報告して 17 行の記録簿を main に載せた。しかし origin/main には tick の節だけがあり、記録は 1 件も無く、両方とも器の中に staged のまま残っていた。枝に退避しようとすると refusing off-policy branch creation で拒まれ、そのあと停止フックがどの口でも実行できない commit と push を求めた。

なぜ静かに失われるか: 重複判定が記録そのものではなく tick の記録簿を読むため。次の tick は inbound-sweep-filed と issue-triage-filed を読んで両方が存在すると信じ、同じ件を判定し直さない。所見は公開もされず再導出もされないまま、どの仕組みも成功を報告する。手順 2 の重要度の判定と手順 5 のずれの判定が毎時捨てられている。

直してほしい形: /moderate に、自分の手順が書いた成果物のための正規の公開経路を与える。persist-log.sh が既に使っている publish-tree-commit.sh の形 — 基底へ直接、枝も claim も作らない — を、moderations/ からその tick が同じ tick 内で書いた記録まで広げる。重い禁止（マージしない・work-* の枝を作らない・ストラテジを書き換えない）はそのまま残り、目的のない拒否だけが外れる。

もう一つの道は「定時実行では手順 2・5 で記録を書くのをやめ、所見を check-in の手順へ回す」。安いが、フィードバックの流れが inbound-sweep の分を失う。上を採れないときの次善。
