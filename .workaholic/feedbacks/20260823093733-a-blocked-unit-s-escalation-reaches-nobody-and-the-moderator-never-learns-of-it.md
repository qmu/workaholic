# A blocked unit's escalation reaches nobody and the moderator never learns of it

導入先リポジトリのループが11ティック連続で停止した。全ティックが正しく動作し、正しく blocked を報告し、2.1 agent-hours を消費して、外向きの信号は前日のフィードバック・ルートのスレッドへのメンション無し返信1本だけだった。

`↳ still failing - <signature>, first reported <time>, 10 ticks` + session URL。

メンショントークンが無いので Slack は誰にも通知しない。前日のスレッド内なのでチャンネル最上位にも出ない。開発者は「チャンネルが10時間更新されていない」ことに気づいて理由を尋ね、そのあとこう述べた — 「そのような通知をどこで僕は受けたのでしょうか？まったく気づけませんでした」。

正確な記述は「エスカレーションした」ではなく「誰にも見に行けと言われていない場所に文字列が存在した」である。

開発者が想定しているフロー: (1) 人が要る blocker はモデレーターの質問になる。(2) 名指しするので Slack が通知する。(3) 回答は Slack 上ではなく、質問が運ぶ Claude Code セッションのリンクから、モデレーターのセッションに入って行う。(4) モデレーターが解消し、ループが続く。

そのフローに対して欠けているもの:

- /implement の blocker が /moderate に一切届かない。tick の check-in は自分の10ステップが見つけたものしか訊かない。「claim された単位が N ティック停止している」を読む機構がどこにも無いので、人を名指しで訊く唯一の面が、訊くべきものがあることを知らない。
- どちらのアラート形も誰も名指ししない。🔴 Blocked も ↳ still failing も <@U…> を持たない設計で、誰も名指ししない投稿は誰にも通知しない。人に届くことが唯一の目的のアラートで、それは既定として誤り。
- 返信が item のスレッドに入る。単位のフィードバック・スレッドがどこであれそこに着地するので、数日前の誰も見ていないルートでありうる。
- 週末ゲートが重なる。停止は金曜夜に始まり、human-checkin は正しく翌営業日まで質問を保留した。保留は破棄ではなくその規則は正しいが、上の3つと合わさって週末が丸ごと、死んだループと無音のまま過ぎた。

「ループが止まっている」から「人が訊かれる」への経路が一本も無く、その間すべての個別機構が仕様どおりに動作していた。

直してほしい形: モデレーターに「止まっている仕事」の読み取りを与え、訊かせる。形はこのプラグインに既にある — strategy-pace ステップは別スキルのスクリプトを直接読む（/propose がツリーに何も書かないから受け渡しではなく読み取り。blocked な /implement も同じ）。何が claim され、何が blocked で、どれだけ続いているかを読み、長く止まっているものを check-in に候補として渡すステップは、同じ形の再演である。

その質問に人を名指しさせる。🙋 <@U…> の形は既に名指しし、既に session URL を運び、既に一度だけ訊く。乗り物は正しく、足りないのは載せる所見。

回答でループを閉じる。人はモデレーターのセッションで答えるので、次のティックはその質問が答えられたことを見て保留をやめられなければならない。何がそれを記録するにせよ、「回答済み」と「一度も訊いていない」を区別できなければならない。tick log が asked-once 台帳を既に持っており自然な置き場。

アラートを大きくする方向で直さないこと。失敗したのは音量ではなく方向であり、誰にも宛てていない投稿を大きくするのは、このリポジトリが二度退役させたステータス行である。
