# Every open proposal conflicts on the generated feedbacks index

Source: https://github.com/qmu/workaholic/issues/780

kind: instruction / source: development / subject: person:a@qmu.jp

Measured 2026-08-31 on a consuming repository. Three open proposal pull requests — every
open proposal there was — each carried exactly one conflict, and it was the same file in
all three: `.workaholic/feedbacks/index.md`. Nothing about the three asks disagreed. The
index is generated by `skills/okf/scripts/refresh-index.sh` from what is on disk, so every
branch that adds a feedback record rewrites the same generated region, and each new record
reaching the base conflicts with every branch that has one of its own.

The repair was mechanical and total: merge the base, run `refresh-index.sh`, commit.
Applied by hand to all three; each came out MERGEABLE/CLEAN, and no judgement was made
about anything.

What the loop did instead was file tickets. Two were sitting in `tickets/todo/` — one to
stop the generated index conflicting every open proposal, one to bring the three stranded
pull requests back to mergeable — while `/moderate` reported `merge-conflicts` and
`stuck-prs` every hour and the pull requests stayed stranded. The work waiting behind them
was the same day feedback, so the tick was reporting a live blockage it had already
ticketed and could have cleared.

Two defects, separable. First, a generated file is committed, so it is a conflict
generator: every branch open at once collides on it by construction, and a conflict in a
file with one deterministic producer carries no information — it is never a disagreement
between two authors, only a stale regeneration. Second, the tick classifies a repair it can
perform as a finding to report: `catchup-blocked` and `merge-conflicts` treat `content`
mergeability as needing a person, and for this file it does not — the resolution is "run the
generator", and the generator already ships in this plugin. The `content` verdict is right
about the git fact and wrong about who it is for.

What would settle the first, stated as shapes to weigh rather than a menu: regenerate the
index during the merge rather than storing merged bytes (a merge driver, or a post-merge
step the loop already owns), or stop committing the generated region at all and produce it
where it is read. Either one also removes the second defect most frequent instance, but not
the second defect: a mechanically repairable conflict being reported rather than repaired is
the general shape, and this file is one occasion of it.
