# A proved residue clear restores to HEAD while its proof is against the base, and the index generator re-creates the residue

Measured on this checkout on 2026-09-09, during and before moderation tick `20260909-110700`.

Two independent defects produce one outcome: a checkout whose residue re-forms after every
proved clear, so `sync-main.sh` refuses `dirty_workspace` forever and no `[Implement]` run
ever reaches its survey. The mission `clear-the-residue-the-base-already-holds-and-never-stop-silently`
shipped the mechanism that is supposed to end exactly this stall; both defects are in what it
shipped, and neither is filed.

## 1. The clear restores to `HEAD` while the classification proves against the base

`branching/scripts/classify-residue.sh` resolves its base to `origin/<base>` (its own
`--- The base branch ---` block) and defines `on_base` as *both the index entry and the
working-tree file byte-identical to `<base>:<path>`*.

`branching/scripts/clear-proved-residue.sh` then restores each such path with
`git restore --source=HEAD --staged --worktree -- <path>` (its header, and the restore
function around line 192).

The two refs are the same only while `HEAD` is level with `origin/main`. When the checkout
is behind the base — which is the ordinary state of a long-running local loop container, and
was the measured state here (2 commits behind) — a path proved byte-identical to
`origin/main:<path>` is restored to `HEAD`'s different content. The script reports `cleared`,
the tree is still dirty against the base, the freshen refuses `dirty_workspace` again, and
`/drive` §1's "run once, re-freshen once" rule correctly declines to spin. Measured
consequence here: two consecutive `[Implement]` runs never reached `plan-units.sh`.

The repair the finding names: the clear must restore from the same ref the classification
proved against — the reader already reports it as `base` on every reading, and the clearer
already parses that field into `BASE` for its own output but never uses it as a restore
source.

## 2. `refresh-index.sh` writes a `moderations/` line the base can never carry

`okf/scripts/refresh-index.sh` enumerates areas with `[ -d "$dir" ] || continue` (its
`for area in tickets moderations stories ...` loop) and emits a `moderations/` bullet
whenever `.workaholic/moderations/` exists on disk.

`.workaholic/moderations/` is git-ignored (`.gitignore:48`) and, since the log stopped being
committed anywhere, it exists in every persistent checkout and in no fresh clone. So:

- `origin/main:.workaholic/index.md` carries no `moderations/` line and never will, because
  the publish tree is a fresh clone of the base where the directory does not exist;
- every seam that refreshes the indexes in the *caller's* checkout — `feedback/scripts/create.sh`
  among them — writes that line into `.workaholic/index.md` and stages it.

Verified on this checkout: `git show HEAD:.workaholic/index.md` has no such line, and the
generator's area loop emits one unconditionally on directory presence.

So every knowledge write the loop makes locally manufactures one line of residue that the base
cannot hold. Combined with defect 1 it is self-sustaining: the residue is regenerated by the
next write and never provably cleared.

The repair the finding names: gate the `moderations/` bullet on the path being tracked (or
simply drop it — the area is an operational log the root index describes in prose anyway),
rather than on the directory existing.
