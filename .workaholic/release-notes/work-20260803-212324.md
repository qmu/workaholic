# Acceptance ticking measures satisfaction, not marker shape

## Summary

A mission's acceptance checklist was ticked by matching an archived ticket's filename against marker text, so an item without the right `(#<filename>)` marker could never be ticked and `0/N` was indistinguishable from stalled work. The link between an acceptance item and its ticket is now an explicit contract: stamped by the seam that emits the ticket set, verified by the ticker, and reported when absent.

## Key Changes

- `link-acceptance.sh` is the only writer of an acceptance item's `(#<filename>)` link, called by the emitting seams (Creation Interrogation, replan, `/propose`) with the pairing decided by the caller.
- `tick-acceptance.sh` distinguishes `unlinked_items` from `no_unchecked_match`, and `progress.sh` reports an `unlinked` count beside `checked`/`total` — an unaddressable board no longer reads as unfinished work (six missions measured at 37 unlinked items to zero linked).
- Ticking means satisfaction: an item ticks when its linked artifact lands, not when a filename happens to appear in the marker text.

## Changes

### Changed
- The mission skill's schema reference states the link contract; the emitting seams close the loop at emission time; the ticker and progress reader report link health instead of silently failing to match.
