# `/request`'s backstop matches an identifier, not a substring

A repository whose name is an ordinary English word could not submit any request whose
body listed paths embedding that word — including directories belonging to the *target*
repository. The refusal was unconditional, arrived after the developer had already
confirmed the body verbatim, and told them to "mask" something that could not be removed.

## Fixed

- The bare-name check now matches the repository name only where it is **not glued to a
  neighbouring identifier character**, so `docs/<name>-reports/x.md` and `docs/site-<name>/x.md`
  submit while a standalone mention is still refused.
- Every refusal now **cites the matched text and its line**, so a future false positive is
  diagnosable instead of mysterious.

## Added

- Two exact checks that the substring rule had been catching only incidentally: the
  repository's **`owner/name` remote form** and its **clone URL**. Narrowing adjacency
  without these would have lost true positives rather than being neutral.

The absolute-path check is byte-identical — it is an exact match with no false-positive
mode, and it is the check that carries the real weight. This backstop remains mechanics,
not assurance: the developer's verbatim confirmation is still what masks customer context.
