# Allocate each development tick from current work and machine capacity

## Summary

The development loop now decides each tick's allocation from the work it just read instead
of assuming one fixed runner. It can fan out independently claimable implementation work,
capture newly ingested asks in the same tick, and explain why it ran or waited.

## Key Changes

- Read independently claimable work through the executor's existing survey.
- Read CPU count and load without inventing a usable value when the machine cannot be measured.
- Fan out implementation runners up to the operator-declared bound while preserving claim arbitration.
- Run ingest from the tick's own capture and keep strategy proposal on its separate cadence.
- Defer redundant proposal attempts only for bounded, previously reported `work_waiting` outcomes.
- Report the chosen allocation and its reasons on every tick.

## Operational Notes

- `WORKAHOLIC_IMPLEMENT_FANOUT` remains an operator-owned bound; when absent, fan-out stays at 1.
- The machine-load reader is available, but refusing excess fan-out still requires the queued
  load-threshold wiring and `WORKAHOLIC_MAX_LOAD_PER_CORE` policy choice.
- The claimable-work survey costs roughly 70 seconds on the measured machine and is intentionally
  reused rather than replaced with a cheaper count the executor would reject.
