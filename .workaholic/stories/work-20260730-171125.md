## 1. Overview

Artifact creation stops cutting git refs. `/ticket` and `/mission` now write into a dedicated **publish tree** — a checkout of `origin/main` at the git-ignored `.publish/` — commit through the shared wrapper, and push to `main`, leaving the developer's branch and uncommitted work byte-identical. `/drive` fast-forwards its checkout before surveying, so a runner never reads yesterday's queue. Together these complete decision I6: the executor's claim is now the only thing in the plugin that creates a branch or a worktree.

**Highlights:**

1. **A ticket or mission is visible the moment it exists** — to every runner, every machine, and every fresh clone — instead of being stranded on a local unpushed ref that `plan-units.sh` could not survey.
2. **Publication never touches the caller's checkout.** A developer can type `/ticket` mid-edit on a dirty feature branch; branch, staged set, untracked set, and file contents are unchanged. This is asserted by a named test, not only observed.
3. **The stale-survey defect reproduced during this very run** — the opening survey ran nine commits behind `origin/main` and silently missed two claimable units — which is the strongest available evidence for why the freshness step and the `current` flag had to exist.

## 2. Motivation

`/ticket` called `create.sh` whenever it found itself on `main`, and `/mission` built `.worktrees/<slug>/` and performed every write inside it. Neither pushed. So the two human-facing sources produced artifacts that existed only on a local ref — which is exactly why `docs/drive-loop-runbook.md` §6 listed "approved missions exist but nothing is claimed" with the cause "its tickets live in an unmerged worktree", and why `claim.sh` carried a comment tolerating a mission with no `mission.md` in the main tree. The repository had already settled the argument on the executor side (decision I6: worktrees are claim-born and ship-torn) and `/propose` already shipped as the working proof that a mission artifact needs no worktree at all; `commands/mission.md` was the unimplemented half.

The branch could not simply reuse `/propose`'s guard. A headless batch may abort on "not on `main` with a clean tree"; a developer types `/ticket` and `/mission` at any moment, most often mid-work on a dirty branch, and aborting there would make the sources unusable exactly when they are most useful. Hence the publish tree: publication that depends on nothing about the caller's checkout and disturbs nothing in it.

The order is the dependency chain. The primitive lands first with no caller, then each source is moved onto it, then the executor is taught to read the base the sources now write to. Every step is verified against a throwaway clone whose `origin` is a local bare mirror, so no rehearsal commit could reach the real remote.

### 3-1. Add the publish-tree primitive ([1179d916](https://github.com/qmu/workaholic/commit/1179d916))

Adds `sync-main.sh` (fast-forward only, never merges or resets) and the three publish-tree scripts — `open-publish-tree.sh`, `publish-tree-commit.sh`, `close-publish-tree.sh` — plus the `.publish/` exclude line in the shared `lib/ensure-git-excludes.sh` seam. Records decisions J1–J3 in `docs/loop-engineering-workflow.md`, defines the term in `branching/SKILL.md`, and replaces `commands/propose.md`'s inline git guard with `sync-main.sh`. No command's behaviour changes yet.

### 3-2. Publish tickets to main from /ticket ([7483be42](https://github.com/qmu/workaholic/commit/7483be42))

Replaces `/ticket`'s branch cut with a publish-tree open, routes the stray sweep and the ticket writes into that tree, and publishes-and-closes in Step 2. Deletes the Step 0 worktree guard — one `AskUserQuestion` fewer — recording in its place why a prompt whose every answer produces the same outcome is worse than no prompt. Summary mode keeps reading the caller's own checkout, deliberately, and `check-worktrees.sh` stops counting the publish tree.

### 3-3. Publish missions to main from /mission ([e7be1bf2](https://github.com/qmu/workaholic/commit/e7be1bf2))

Moves all four mission write paths — create, replan, approve, close — onto the publish tree. The creation batch publishes as **one** commit, because a mission whose statement reached `main` without its tickets is a mission `/drive` would survey as approved with an empty queue; an abandoned interrogation publishes nothing. Step 6 reports the mission's path on `main` instead of a worktree the developer cannot enter, and the stale close-time-teardown prose in `close.sh` and `cleanup-mission-worktree.sh` is corrected. The mission scripts themselves are untouched.

### 3-4. Survey a current main in /drive ([5a77dc50](https://github.com/qmu/workaholic/commit/5a77dc50))

Adds step 0 to `commands/drive.md` — `sync-main.sh` before the survey, with every `ok: false` reason decided as a reported outcome and no prompt anywhere. `plan-units.sh` stays a pure reader and now states its own freshness (`surveyed_sha`, `base_sha`, `current`); `current: false` forbids the `ok` token. `claim.sh`'s stranded-artifact tolerance becomes a named `mission_missing` refusal, while its in-worktree re-resolution is verified, kept, and given its real reason. Runbook §6's now-impossible cause is replaced by the five that can occur.

## 4. Outcome

The publication model is coherent end to end. A source writes to `main` from any checkout; the executor claims from `main` into a worktree it creates; ship or an explicit release tears that worktree down. `claim.sh` is the only branch-and-worktree creator left in the plugin, and a named test asserts it is the only invoker of `create-mission-worktree.sh`.

The suite grew from 1331 to 1436 assertions, and the new coverage is aimed at the invariants rather than the outputs: publication leaves the caller's checkout byte-identical; a batch reaches `origin/main` in one commit and is surveyed as claimable by a *second* clone; two runners over one freshly published unit produce exactly one claim; a deliberately-behind clone misses the artifact and *says so* before the freshness step fixes it. Three tests that encoded the old invariants were inverted rather than deleted, and the mission-lens case was re-pinned because a worktree's meaning changed from "this mission exists" to "a runner has claimed it".

Four rehearsals ran against throwaway clones of this repository with `origin` re-pointed at a local bare mirror. Two of them found defects the hermetic tests had not: a swept ticket's old path aborting a whole publish, and untracked ticket files silently missing from the mission publish commit.

## 5. Historical Analysis

This placement has been revised twice before, and each revision narrowed the same thing. `20260129012614-auto-branch-on-ticket.md` introduced `/ticket`'s auto-branch-on-main — the behaviour this branch reverses. `20260714011847-mission-create-worktree-kickoff.md` made `/mission create` spin up a worktree, itself superseding an earlier in-tree branch-on-create step. Then the 2026-07-28 round introduced claims (G3) and ruled worktrees claim-born and ship-torn (I6), which left creation-time branching as the surviving remnant of a design that no longer existed. `20260728210302-add-proposal-batch-command-and-skill.md` shipped `/propose` as the working precedent: scaffold into the main checkout, commit, push, never prompt.

The pattern across all three is that coordination state kept migrating toward git refs and away from local convention. `20260717152506-mission-resolution-follows-the-ticket-not-cwd.md` and `20260718191500-validate-ticket-resolves-mission-in-tickets-checkout.md` built cross-checkout resolution as workarounds for missions living in worktrees — and that machinery turned out to be exactly what makes the publish tree work, since both derive their root from the artifact's own path rather than from cwd. A workaround for one model became the mechanism of its successor.

## 6. Concerns

### The four tickets merged as one PR-unit, as an open stream concern predicted

- **Severity:** moderate
- **Description:** The open concern `the-depends-on-chain-will-batch` predicted exactly this: the `depends_on` chain makes all four tickets one PR-unit, and `drive/SKILL.md` names `depends_on` as "the one signal strong enough to group on by itself". So this PR rewrites branching, `/ticket`, `/mission`, and `/drive` together — the shape that section warns a reviewer cannot review as one thing. Tickets 2–4 each carry a gate item reading "the dependency is merged first", which a single combined PR cannot literally satisfy (see [1179d916](https://github.com/qmu/workaholic/commit/1179d916) through [5a77dc50](https://github.com/qmu/workaholic/commit/5a77dc50)). The mitigation is ordering rather than partitioning: each commit is self-contained and the dependency precedes its callers at every commit, so the intent behind "merged first" — the primitive exists before anything uses it — holds commit-by-commit and can be reviewed that way.
- **How to Fix:** Review commit-by-commit rather than as one diff, and if the foundation should land separately, ask for a split: reverting to `1179d916` leaves a working repository with an unused primitive. Longer term, decide deliberately whether a `depends_on` chain longer than two should be capped at one unit — the grouping rule and the reviewable-PR rule genuinely conflict here, and one of them has to yield.

### The foundation commit is 772 changed lines, over the per-commit ceiling

- **Severity:** moderate
- **Description:** The release scan blocks at `override` tier: [1179d916](https://github.com/qmu/workaholic/commit/1179d916) is 772 non-generated changed lines against a 500 ceiling. Unlike the spec-commit case already in the stream (`the-ticket-batch-convention-structurally-collides`), this is an implementation commit — four new scripts, the decision record, the skill section, and ~200 lines of hermetic tests — so the ceiling is measuring what it was built to measure and the commit genuinely exceeds it. The unit routes to a PR regardless of the finding (all four members are `merge_policy: review`), so the block changed nothing about the route; it is recorded rather than overridden silently.
- **How to Fix:** Split a primitive-plus-tests commit at the seam between the scripts and their coverage next time — the tests are independently reviewable and would have kept both halves under the ceiling. If that split is not wanted, the honest alternative is raising `MAX_COMMIT_CHANGED_LINES` with a stated reason, not overriding it per commit.

### `/fb` still commits without pushing, so its records remain invisible to `/propose`

- **Severity:** moderate
- **Description:** The primitive the open concern `fb-still-commits-without-pushing-so` was waiting for now exists, but `/fb` is unchanged: `commands/fb.md` step 4 still commits without pushing and never guards on `main`, so a feedback registered from a work branch never reaches `/propose`'s cursor, which reads records merged to `main` (see [1179d916](https://github.com/qmu/workaholic/commit/1179d916) in `plugins/workaholic/skills/branching/scripts/open-publish-tree.sh`). Both source tickets declared it out of scope, correctly — the request was tickets and missions — but the gap is now the only remaining instance of the defect this branch exists to remove.
- **How to Fix:** Write the fifth ticket both source tickets name: route `/fb`'s write through the publish tree exactly as `/ticket` does. It is a small change now that the primitive and its rehearsal pattern exist.

### The publish tree is a new recoverable-state location nothing garbage-collects

- **Severity:** low
- **Description:** A failed publish deliberately leaves the commit intact on `publish-main` inside `.publish/`, and both `open` and `close` refuse to destroy it (`dirty_publish_tree`, `unpublished_commits`) — see [1179d916](https://github.com/qmu/workaholic/commit/1179d916) in `plugins/workaholic/skills/branching/scripts/close-publish-tree.sh`. That is the right default, but it means a `diverged` publish leaves a tidy-looking directory holding the only copy of an artifact, and nothing surfaces it later: the claim reader reports claims, not publish trees, and `.publish/` is git-ignored so `git status` says nothing.
- **How to Fix:** Add a one-line publish-tree check to the same surfaces that already report in-flight claims — `/mission`'s bare view or `/drive`'s survey report — stating "a publish tree holds N unpublished commits" when `publish-main` is not an ancestor of the base. A refusal that nobody is told about is a refusal that ages into a lost artifact.

### The rebase-and-retry bound is untested under real contention

- **Severity:** low
- **Description:** `publish-tree-commit.sh` answers a non-fast-forward with exactly one rebase-and-retry and then reports `diverged` (see [1179d916](https://github.com/qmu/workaholic/commit/1179d916) in `plugins/workaholic/skills/branching/scripts/publish-tree-commit.sh`). The bound is deliberate — an unbounded loop hides sustained divergence a human should see — and the single-retry path is covered by a two-clone test. What is not known is how often the *second* attempt loses in practice once two crons and interactive sessions all publish to one `main`.
- **How to Fix:** Watch for `diverged` in the loop logs. If it appears, revisit the bound with the observed contention rate rather than raising it blindly; a second retry is cheap, an unbounded loop is not.

## 7. Successful Development Patterns

- **Rehearsing against a throwaway clone with `origin` re-pointed at a local bare mirror caught two defects the hermetic suite did not.** The mirror makes the rehearsal safe (no scratch commit can reach the real remote) while keeping the *real* repository content — real `.gitignore`, real hooks, real `.workaholic/` tree. Both misses were interaction defects between steps that only co-occur in a real flow: naming a swept ticket's old path aborts the whole publish, and untracked ticket files never reach a `git add -u` commit. Hermetic fixtures test a script; a rehearsal tests a sequence.
- **Writing the test assertion from the documented wording, before the code, caught a semantic error in a new field.** `current` was first implemented as a sha comparison, which reports `true` for an offline runner matching its own last-known ref. The assertion "and cannot claim to be current" came from the phrase *known* current in the skill prose, and failed — so the field now requires `fetched` too. Prose that states a property precisely enough is a test oracle.
- **Inverting a test rather than deleting it makes a model change auditable.** Three tests encoded "the mission lives in a worktree and is absent from main". Deleting them would have left no record that the invariant had a previous form; inverting each assertion in place makes the flip visible in one diff, and the two rewritten test names now carry the decision letter (`J1`) that caused it.
- **Deciding a caller-less script's fate by consumer census, not by tidiness.** Both `check-worktrees.sh` and `create-mission-worktree.sh` lost callers this branch. Neither was deleted or renamed, because both ship in the generated `outputs/workflows` bundle where a name is public API to cross-agent consumers — but `check-worktrees.sh` was *fixed* (it would have counted the publish tree) and `create-mission-worktree.sh` got a header stating it is claim-side only. Correctness first, deletion only with a census.
- **Reporting a condition rather than repairing it, when the repair belongs to a different layer.** `plan-units.sh` could have fast-forwarded before reading, and that would have been a survey script with a surprise side effect, unusable inside a claim worktree. Splitting it — the command mutates, the script reports `current` — kept the reader pure and still made the staleness impossible to miss.

## 8. Release Preparation

**Verdict**: Needs attention before release

### 8-1. Concerns

- The branch changes the plugin's own critical path (`/ticket`, `/mission`, `/drive`). Until the installed marketplace copy refreshes, a session runs the *old* flow — this aggravates the open stream concerns `installed-plugin-lag-now-includes-commands` and `a-stale-installed-plugin-now-offers`.
- The release scan blocks at `override` tier on commit size. The unit is `merge_policy: review`, so it stops at this PR regardless and no gate was overridden.
- The composed unattended chain (claim → drive → auto-ship → teardown) still has not run end to end; the open concern `the-full-unattended-chain-claim-drive` remains active and this branch does not close it.

### 8-2. Pre-release Instructions

- Review commit-by-commit, in dependency order, per the first concern in section 6.
- No version bump is included in this branch. If one is wanted, check that `main` has not already reached the target version — a colliding merge silently goes unreleased.

### 8-3. Post-release Instructions

- **Refresh the installed plugin** before relying on `/ticket` or `/mission`: a pre-refresh session still cuts a branch and builds a worktree at creation, and its `/drive` will not fast-forward before surveying.
- Confirm the 5-minute `/drive` runner's checkout is a clean `main`. The freshness step now terminates `pending` on `not_on_main` / `dirty_workspace` / `diverged` rather than surveying the wrong queue — which is correct, but a runner checkout used for other work will now stop instead of quietly doing nothing.
