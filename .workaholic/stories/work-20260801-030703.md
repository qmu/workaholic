## 1. Overview

Routines are how this project runs — the 5-minute drive loop, the 15-minute proposal loop — yet nothing recorded which routines a repository wants, and nothing reported which are installed. `/workaholify` now does both, because wiring a repository to the way we work is what that command already means.

**Highlights:**

1. The repository declares its routines in `.workaholic/routines/` (registered as a lockstep amendment); the invoking user's crontab is read back for what is actually installed.
2. `install-routine.sh` **refuses to write outside an interactive context** — the runbooks' "never install a crontab from an agent session" is unchanged and now enforced in code.
3. A non-blocking hook nudges once per session when the two disagree, and is silent otherwise.

## 2. Motivation

The configuration lived in one person's account, so *"what runs against this repo"* could only be answered by asking them, and a developer joining had no path to the same setup. Provisioning also drifts in one direction nobody notices: a routine added after someone set up their machine never reaches it, nothing fails, and the routine simply does not run — which looks like a quiet week.

## 3. Changes

### 3-1. Make /workaholify provision the loop-engineering environment ([592c963b](https://github.com/qmu/workaholic/commit/592c963b))

Two scripts (`survey-routines.sh`, `install-routine.sh`), one hook (`routines-lens.sh`), the `.workaholic/routines/` registration in both sources of truth, this repository's own two declarations, and the command step that shows the exact crontab line before installing it. Both runbooks now point at their declaration rather than defining the schedule themselves.

## 4. Outcome

`survey-routines.sh` answers "what runs against this repo, for me, on this machine" in one read-only command, and names *which* thing is wrong — `not_installed`, `schedule_drift`, `missing_env`, or `incomplete_declaration` — rather than collapsing them. Measured on this machine right now: two routines declared, both `not_installed` for this user.

## 5. Historical Analysis

The decision shape repeats today's earlier one exactly. The mission-size norms split on *who holds the pen*: report for a human author, enforce for the unattended batch. The routine installer splits the same way — a developer who typed `/workaholify` is present and may install; a cron tick has nobody to ask and may not. Neither rule was weakened; both were read precisely enough to locate the boundary.

## 6. Concerns

### The unattended-write refusal is the thing most likely to be eroded

- **Severity:** moderate
- **Description:** Someone will want `/drive` to self-heal its own routine, and the refusal is one `[ ! -t 0 ]` away from being removed (`plugins/workaholic/skills/workaholify/scripts/install-routine.sh`).
- **How to Fix:** It is enforced in the script with a test asserting `not_interactive`, so crossing it requires deleting both — which is the point. If a genuine need appears, the honest change is an explicit, recorded opt-in, not quietly dropping the check.

### The survey sees only the invoking user's crontab

- **Severity:** low
- **Description:** A routine installed under a different account, or by a system-level scheduler, is invisible — the survey would report `not_installed` for a routine that is in fact running (`survey-routines.sh`).
- **How to Fix:** The report carries `user` and the command says "for this user on this machine", which makes the limit legible rather than hidden. Widening it would mean reading other users' crontabs, which is not something this should do.

### This machine runs no crontab at all

- **Severity:** low
- **Description:** The survey reports `crontab: false` here, yet the loops have been running — so they are driven from somewhere the survey cannot see (Claude Code Web), which is precisely the situation the ticket set out to fix and does not yet fully cover.
- **How to Fix:** Either provision the routines locally via the new path, or extend the declaration format to describe a non-cron runner. The second is a real design question, not an oversight.

### The archive commit is over the changed-lines ceiling again

- **Severity:** low
- **Description:** 623 non-generated lines against 500 on [592c963b](https://github.com/qmu/workaholic/commit/592c963b) — the third consecutive branch, since `archive.sh` emits one commit per ticket.
- **How to Fix:** Belongs to the open mission *Make the per-commit changed-lines ceiling a rule that holds*; three branches in a row is now a pattern rather than an anecdote.

## 7. Successful Development Patterns

- Resolving an apparent conflict by reading the existing rule precisely instead of amending it. "Do not install a crontab from an agent session" looked like it blocked this ticket; it targets the *unattended* case, and encoding exactly that as `[ ! -t 0 ]` satisfied both the rule and the request.
- Letting the suite adjudicate a design detail. The nudge surfaced a fixture whose declaration lacked a `schedule` and reported `not_installed` — pointing a developer at their crontab for a fault in a committed file. That produced `incomplete_declaration` as its own reason, which no amount of reading the code would have prompted.
- Registering a closed-layout amendment in the same commit as the first write, and asserting it in a test. `layout-doctor` reports `conforming: true` because `routines/` reached both the allowlist and the rules table together — the drift the policy exists to prevent.
