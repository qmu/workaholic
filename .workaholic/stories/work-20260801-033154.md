## 1. Overview

`/workaholify` can now tell you which routines run against this repository, how they differ from the templates the plugin ships, and refresh them after showing you exactly what it will write. This is the second attempt: the first targeted crontab and was withdrawn whole.

**Highlights:**

1. Routines are **Claude Code Web routines** reached through `RemoteTrigger` — not cron, which the withdrawn design assumed.
2. The plugin holds **one set of three templates** (`fb`, `merged-pr`, `drive`) applied to whichever repository the command runs in. No per-repository routine file; `.workaholic/` gains nothing.
3. Drift is reported **per field, across every repository that carries a workaholic routine** — not just this checkout — and creating or refreshing one is confirmed **verbatim, one at a time**.
4. Two preconditions are checked before scheduling: the account's Slack connector, and whether `dev-<repo>` exists — with "could not check" kept strictly distinct from "does not exist".
5. **The web bootstrap is installed and checked** — without it every cloud routine is configured but cannot work, which is the state this repository was in.

## 2. Motivation

Configuration lives in one person's account, so *"what runs against this repo"* could only be answered by asking them. Measured live: 16 routines, three patterns replicated across seven repositories, with the `[FB]` and `Merged PR` prompts byte-identical everywhere — and already drifting (`Merged PR qmu-co-jp` and `[FB] coop-csnet` carry no `model`; `[FB] data-platform` has an extra prompt line).

## 3. Changes

### 3-1. Make /workaholify provision Claude Code Web routines ([56fddd3a](https://github.com/qmu/workaholic/commit/56fddd3a))

Three templates captured verbatim from the live routines, three scripts (`list-routine-templates.sh`, `render-routine.sh`, `compare-routines.sh`), and the command steps that survey, render, confirm, and apply. Scripts own the templates and the comparison; the command owns the API and the confirmation, because a shell script cannot call `RemoteTrigger` — which is also what makes the comparison testable against fixtures.

## 4. Outcome

Running `/workaholify` in a repository now answers "what runs against this, and does it match what we ship" without asking anyone. The templates are provably faithful: rendering them reproduces the live prompts byte-for-byte, which the tests assert as an empty drift rather than by inspection.

## 5. Historical Analysis

The withdrawn attempt is the useful history here. It built a crontab provisioner, and its own survey reported `crontab: false` on a machine where the loops run hourly. That contradiction was written into the branch story as a low-severity concern and shipped past, when it was in fact a refutation of the premise — the originating feedback says *"a `/setup-routines` skill **in Claude Code Web**"* in its first sentence.

### 3-2. Survey the whole fleet, and check the Slack preconditions ([later commits](https://github.com/qmu/workaholic/pull/138))

`compare-routines.sh` now reports `this_repo` (missing **and** drifted) alongside `other_repos` (drifted only, over routines that already exist) — because the templates are one set applied to many repositories, so a defect replicated across seven repos is still one defect and should not need seven visits to find. A missing Slack connector counts as drift, since every template posts to `dev-<repo>` and a routine without it runs, works, and fails silently at the last step.

`check-slack-channel.sh` probes the channel and **refuses to conflate "cannot check" with "does not exist"**: on a locked qfs credential store both return the identical `slack_auth` error, so a naive success test would mark every channel missing.

### 3-3. Install the web bootstrap, and check it first ([later commits](https://github.com/qmu/workaholic/pull/138))

Claude Code on the web starts each session in a fresh container where `enabledPlugins` installs nothing, so a repository without `.claude/hooks/session-start.sh` schedules its routines, fires them on time, and stops at the `[Drive]` prompt's own *"the workaholic plugin must be loaded … post the failure and stop"* precondition. **This repository was in exactly that state** — all four checks failed — while its hourly routine looked healthy in the routines list.

The canonical hook carries the corrections from qmu/workaholic#126, whose review had been recorded and then never implemented anywhere: it fails open with no `set -e`, status-checks each step instead of a `{ … } || echo FAILED` group that reported success on total failure, drops the invalid `marketplace add --scope user`, and is idempotent. `check-bootstrap.sh` names each problem separately, and compares the installed copy against the canonical one so an older copy is drift rather than presence.

## 6. Concerns

### Prompt comparison is exact, so reformatting a template flags every repository at once

- **Severity:** low
- **Description:** `compare-routines.sh` compares prompts after trimming and nothing else. Any future edit to a template — including whitespace — reports drift for every repository that has that routine.
- **How to Fix:** Nothing; this is the intended trade. Fuzzy matching would hide the single-line drift this exists to detect. Worth knowing before editing a template casually.

### The Drive template is still a pilot

- **Severity:** low
- **Description:** Its name carries `(pilot)` and its prompt bounds a tick to two units. It exists for exactly one repository today.
- **How to Fix:** Applying it to a second repository should be a deliberate decision, not a default of "provision everything". The command offers each routine separately for this reason.

### Only this repository is bootstrapped

- **Severity:** moderate
- **Description:** The check and the canonical hook now exist, and workaholic itself is wired, but every other repository carrying a workaholic routine is presumably still unbootstrapped — its routines firing hourly and doing nothing.
- **How to Fix:** Run `/workaholify` in each. The check is per-repository by design; nothing here reaches into another repository, which is the confinement rule.

### The bootstrap has never been observed working on the web

- **Severity:** moderate
- **Description:** The hook is verified by its contract (POSIX, fail-open, idempotent, correct flags) and is a no-op locally by construction — but no test can exercise the path that matters, because that path only exists inside a Claude Code Web container. Issue #126 lists two platform facts still unconfirmed: whether sandbox git can clone a *different* private repo than the session's own, and the actual `claude plugin install` flag set.
- **How to Fix:** The next hourly `[Drive]` run is the observation. Read `${TMPDIR}/bootstrap-workaholic.log` in that session, or watch whether the run stops at its plugin precondition. Until then this is unproven, not proven.

### The channel check cannot run on a locked credential store

- **Severity:** moderate
- **Description:** `check-slack-channel.sh` returns `checked: false, reason: "slack_locked"` whenever qfs's store is locked — which is every non-interactive session, and any interactive one where the developer has not run `qfs auth`. The precondition is therefore unverified in exactly the automated contexts where a mistake would go unnoticed.
- **How to Fix:** Correct as-is: reporting honestly beats guessing, and the check is advisory by design. If channel verification becomes load-bearing, the fix is a check that does not depend on the developer's local credential store — reading the channel through the same Slack connector the routines already use.

### Nothing reconciles a routine that was deleted outside this flow

- **Severity:** low
- **Description:** `RemoteTrigger` has no delete, so this flow can add and refresh but never remove. A routine deleted at claude.ai simply reappears as `missing` on the next survey.
- **How to Fix:** Correct as-is — the survey reports, the developer decides. Only worth revisiting if deliberate removals become common enough that the repeated `missing` report becomes noise.

## 7. Successful Development Patterns

- Comparing a rendered template field-by-field against the live original before writing anything else. The very first render produced `[FB] https://github.com/qmu/workaholic` as a routine name; the live listing said `[FB] workaholic`, which surfaced a needed third substitution in seconds.
- Asserting an **empty** drift against the real shapes. "The template looks right" is not checkable; "rendering it reproduces the live prompt byte-for-byte" is, and a paraphrase fails it immediately.
- Splitting on what each layer *can* do rather than on taste. A shell script cannot call `RemoteTrigger`, so scripts got the templates and the comparison and the command got the API and the confirmation — which incidentally made the comparison drivable from fixtures with no account access.
