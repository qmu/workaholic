# Stop resuming a unit that already finished

## 1. Overview

Claim resumption shipped this morning and the hourly runner started using it within the
hour — including on units that were already done. A `review` unit stops at its pull
request by design, so its branch stays unmerged, its tip stops advancing, and its
heartbeat lapses in exactly the way an abandoned run's does. The verdict could not tell
the two apart, so every tick re-took the finished unit, added an empty `Resume` commit
to a branch a human was reviewing, and stopped. This branch teaches the verdict the
difference.

**Highlights:**

1. A third resumption condition: something must still be left to drive on that branch.
2. `queue_drained` and `claimed_reported` — the state gets its own words, because it implies a different action.
3. A batch and a mission answer "what is left" from opposite directions; one rule for both would have disabled mission recovery entirely.
4. The recovery path is untouched — a unit with undriven tickets still resumes.

## 2. Motivation

Measured on the live loop, not inferred. On `work-20260731-185904` the runner published
`Resume batch-20260731185901` three times — 21:57, 22:57 and 00:58 UTC — and only the
first pass did any work (it reconciled with `main`, queued a ticket, recorded a
concern). The second and third added an empty commit and nothing else. The same pattern
ran on `batch-20260731220959`.

Nothing stops it: a review PR can sit for days, and each tick costs a PR-unit slot and
forces the run to report `pending`. The underlying error is narrow and worth naming
precisely — **the verdict answered "is anyone working this?" when it also had to answer
"is there anything left to work on?"**. The unit-outcome vocabulary had already drawn
that exact line for `handoff` versus "a review unit at a PR"; resumability had simply
never learned it.

One pass. The detection reuses a mapping the scan already computed and was discarding
half of; the naming follows the vocabulary rule this file has now applied twice.

### 3-1. Stop resuming a unit that already finished ([40f937f1](https://github.com/qmu/workaholic/commit/40f937f1))

`lib/claims.sh` gains `claims_has_work`, called as the third and last resumption
condition (last because it is the only one that costs git calls). `list-claims.sh`
reports `queue_drained`; `plan-units.sh` excludes such a unit as `claimed_reported` and
keeps it out of `resumable[]`; `claim.sh resume` refuses it with a message naming what
it is actually waiting for. `drive/SKILL.md`'s *Claims* section now states three
conditions rather than two.

## 4. Outcome

A finished unit is left alone, and the hourly no-op cycle stops. The recovery path this
is built on top of is deliberately unchanged: a unit with undriven tickets is still
offered and still resumed once its heartbeat lapses — the new test proves both halves,
including the partly-driven case in between.

## 5. Historical Analysis

This is the second defect in the same verdict inside one day. The first was an empty TSV
field collapsing under `read`; both were invisible without an assertion aimed at the
specific thing that broke, and both were caught by checking a *derived set* rather than
a single field. Two occurrences in one file is a pattern, and it argues for asserting
the shape of every scan row and the membership of every offered set, not individual
values.

The reason vocabulary has now split twice for the same principle: `claimed` became three
names when resumption landed, and four here. Each split happened at the point where two
states implied different operator actions — which is a usable rule for the next one.

## 6. Concerns

### A blocked ticket keeps its unit permanently resumable

- **Severity:** moderate
- **Description:** The new condition asks whether anything is left to drive, and a ticket that is *blocked* is still undriven — so a unit holding one never drains and stays resumable forever. That is correct as far as this rule goes, but it means a blocked ticket produces a loop that looks like the one just fixed while having a different cause (`plugins/workaholic/skills/drive/scripts/lib/claims.sh`).
- **How to Fix:** The answer to a blocked ticket is the icebox, which is a developer act by design. Keep the two causes distinguishable in the runbook so a cron log is not misread; if it recurs, consider whether a ticket whose last drive recorded `blocked` should be excluded from the drivable count.

### The mission half of the queue test is O(tickets) git calls per claim

- **Severity:** low
- **Description:** For a mission unit the check reads each `todo/` ticket's frontmatter at the branch tip through `git show`, once per claim per scan. Claims are few and tickets are few, so it is currently cheap, but the scan runs on every survey and every claim attempt (`plugins/workaholic/skills/drive/scripts/lib/claims.sh`).
- **How to Fix:** If it ever bites, read the whole tree once with `git grep -l` against the branch ref rather than per-file `git show`.

## 7. Successful Development Patterns

- Check whether a new signal can distinguish the states it will actually meet, not just the state it was designed for. Resumability was built against "the runner died" and was correct there; it met "the unit finished" the same night and could not tell the difference. Enumerating the *other* ways a branch can go quiet would have caught this at design time.
- When one rule must cover two artifact kinds, check the inverted case before writing it. The obvious path test — "is any artifact still under `todo/`?" — is right for a batch and silently wrong for a mission, where it would have declared every unit drained and disabled recovery outright: a worse failure than the one being fixed.
- Split a vocabulary exactly when two states imply different next actions. `claimed_active` and `claimed_reported` both mean "not yours to take", but one says wait for a runner and the other says go review a PR, and the person reading it is looking at a cron log.
