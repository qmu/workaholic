## 1. Overview

`CLAUDE.md` and `drive/SKILL.md` both stated an absolute invariant — **"`main` never shows a
claim"** — and it was false. This branch replaces it with the true one and records why the
obvious repair is the wrong one.

**Decision M1**: a `claim:` stamp that reaches the base is **history, never a claim**; the
unmerged-branch scan (`list-claims.sh`) is the only oracle.

## 2. Motivation

Merging PR #153 — a **handoff** PR for a `blocked` unit — published
`claim: work-20260731-221002` onto a ticket still sitting in `todo/`.

Both protocols were individually correct, which is why nobody caught it. The claim protocol
assumed a branch merges only *after* `archive.sh` has renamed every ticket out of `todo/`,
where the stamp is honest history. Then §7 made `handoff`/`blocked` a terminal state whose
unit *"opens or updates its PR even when the work is incomplete"* — and merging while still
queued became routine. `drive/SKILL.md` ended up holding both statements in one file.

Nothing was broken by it: `plan-units.sh` subtracts claims from the scan and never from
frontmatter, so the ticket was correctly re-offered after the merge. That makes this a
**correctness-of-record** defect — and the fix is to make the record true, cheaply, before
someone builds on the false sentence.

## 3. Changes

### 3-1. Rule that a merged claim stamp is history ([9da58c0c](https://github.com/qmu/workaholic/commit/9da58c0c))

**The decision first.** `docs/loop-engineering-workflow.md` gains an eighth round (M1/M1a/M1b).

**The invariant is narrowed, not deleted.** `CLAUDE.md` keeps the half that is still true —
the stamp is written only in the worktree, so the runner's main checkout stays clean between
ticks, which `/propose` depends on — and replaces the false half. `drive/SKILL.md`'s **Claims**
bullet now names the handoff/blocked merge as the ordinary case that produces a base-side
stamp, and §7 points back, so the two passages agree in both directions rather than one.

**The ticket's own recommendation was rejected on evidence (M1a).** It proposed stripping
`claim:` from tickets still in `todo/` in the handoff PR's final commit. Reading
`lib/claims.sh` first showed why that cannot work: a claim's artifacts are *the files the
claim commit touched that still carry `claim: <branch>` **at the tip***, so removing a stamp
drops that artifact — deliberately, and pinned by tests. Stripping at handoff time would
un-claim a ticket **while its PR is still open**, offering in-flight work as fresh backlog.
That is the double-pick the protocol exists to prevent, observed live on 2026-07-30 and again
on 2026-08-04.

**Also rejected (M1b):** re-sourcing the reader from the claim commit instead of the tip
(reverses deliberate, tested behaviour — needs its own ticket and a human, not a side effect
of a record fix), and a sweep over the base (two writers of claim state is what the single
shared scan prevents). Validating `claim:` in a hook stays rejected on its original grounds.

**The missing test now exists.** `testMergedStampIsHistoryNotAClaim` merges a branch whose
ticket is still in `todo/` and asserts all three halves of M1: the stamp *does* reach the
base, the scan reports the claim released, and the survey re-offers the ticket. Its second
half then asserts **M1a's failure mode directly** — strip the stamp on an unmerged branch and
watch the ticket fall out of its own claim — so the rejected fix cannot be re-proposed
without seeing it fail.

## 5. Concerns

### One acceptance bullet is superseded rather than met

The ticket asked that "the live stale stamp on `20260724094304` is gone from `main`". That
bullet was written assuming option (a) would win; under M1 removing it would delete exactly
the history the ruling legitimizes. The file has also since been **iced** by the developer
(`.workaholic/tickets/icebox/`), which is developer-curated space `/drive` must not edit. Left
in place deliberately, and recorded here rather than silently dropped.

### M1b names a real change that nobody has costed

Re-sourcing the reader from the claim commit would make a base-side stamp impossible *and*
keep the ticket claimed while its PR is open — strictly better than M1 on both counts. It is
deferred only because it reverses a deliberate, tested behaviour ("a stamp removal releases
that artifact") that some caller may rely on. Nobody has checked whether any caller actually
does. If this area is revisited, that is the question to answer first.

## 6. Successful Development Patterns

**Read the mechanism before implementing your own recommendation.** This ticket was written by
an earlier session of this same routine, with a confident "Recommended" on option (a). Ten
minutes in `lib/claims.sh` showed (a) would reintroduce the exact defect the file's comments
describe being fixed twice. A recommendation carried across sessions is evidence about what
someone once thought, not about what the code does.

**When a new terminal state is added, re-check what the other protocols assumed about
timing.** The `handoff` state did not contradict anything the claim protocol *says*; it
changed *when a branch merges*, which is what the claim protocol silently assumed. Both
documents stayed internally consistent all the way to the defect.

**Pin the rejected fix as a passing test.** M1a is a paragraph anyone can skim past. The
assertion that stripping a stamp un-claims an open PR's ticket is not skippable — it fails
loudly the moment someone tries.
