## 1. Overview

This branch closes a loop-stopping defect in which an **installed plugin older than the checkout** silently ran a retired data migration backwards, staged the result, and thereby aborted every hourly `/drive` tick before it could survey. The fix is deliberately split between making the condition **legible** and making the migration **structurally incapable** of repeating it: `check-deps` now reports the loaded version beside the version the checkout wants, and the mission status fold is pinned as a whitelist that leaves an unrecognised (newer) status word byte-identical and unstaged.

**Highlights:**

1. `check-deps/scripts/check.sh` gained `checkout_version` and `version_drift` beside the existing `version`, so a mismatch is a fact a reader can act on rather than a version string that reads as healthy
2. Recorded the **decision** that drift is a warning and never a stop, with the reason — the hard stop already exists where drift actually bites (`sync-main.sh` → `dirty_workspace`)
3. Pinned `resolve.sh`'s status fold as a whitelist and explained why that is the durable guard: **unknown means newer**, so an older build cannot rewrite a vocabulary invented after it shipped
4. Answered the open question about long-lived sessions — the bootstrap does **not** refresh mid-session, by decision — and named the one thing the version gate still cannot see
5. Added a fixture test with teeth: an unknown status word must survive **byte-identical and unstaged**, not merely keep its word

## 2. Motivation

On 2026-08-02〜04 the hourly cloud runner fired on time and did nothing, for two days, while reading as healthy from the routines list. The cause was that `hooks/mission-lens.sh` runs on essentially every turn and runs from the **installed** plugin, not the checkout. A container image had baked in a plugin build predating decision K1, whose living migration folded `active` → `draft` — the exact inverse of the direction K1 established. So every turn rewrote every active mission, `git add`ed the result, and left a dirty tree; `/drive`'s own freshness step treats `dirty_workspace` as terminal, so each tick died before it learned what was queued.

Two properties made it durable rather than merely annoying. The rewrite was **staged**, so any `git add -A` commit would have swept a K1 reversal into unrelated work. And it was **invisible without `git status`** — the lens printed its ordinary roster line either way, and `check.sh` reported a plausible `"version": "1.0.112"` that means nothing to a reader who does not happen to know what the repository is on.

The ticket's framing held up under implementation, with one correction worth recording: the same drift **recurred while this ticket was being driven**, and supplied the measurement in §4.

## 3. Changes

### 3-1. A session that outlives a plugin version bump runs stale always-on hooks, dirties the workspace, and halts `/drive` before it can survey ([f079f837](https://github.com/qmu/workaholic/commit/f079f837))

- **Made the drift visible where it was already measurable.** `check.sh` reads the checkout's `.claude-plugin/marketplace.json` (via `CLAUDE_PROJECT_DIR`, then the git toplevel, then cwd) and emits `checkout_version` plus `version_drift`. Drift requires **both** numbers — one unknown side is silence, never an accusation — so a consuming repository, which carries no marketplace manifest, reports `checkout_version: ""` and `version_drift: false` rather than a false alarm.
- **Decided drift is a warning, not a stop,** and recorded the reason in the script, the skill, and the runbook. A runner that refuses to work because its plugin is old is as useless as one that works wrongly.
- **Pinned the status fold as a whitelist** in `mission/scripts/lib/resolve.sh`, with the rule stated for the next person: when a future decision retires another word, *add it to the case* — never invert the direction, never widen to a catch-all.
- **Answered the session-refresh question** in `session-start.sh`: it installs at SessionStart and nowhere else, deliberately, because swapping the plugin under already-loaded skills and always-on hooks mid-turn is worse than being one version behind.
- **Added the runbook rows** (two: the dirty-tree symptom with its targeted-`git restore` recovery, and the benign-drift row), plus the doc updates in `check-deps/SKILL.md`, `drive/SKILL.md`, `commands/ticket.md`, and `CLAUDE.md`.
- **Re-synced `.claude/hooks/session-start.sh`**, this repository's own installed mirror of the canonical bootstrap, which `check-bootstrap.sh` compares byte-for-byte.

## 4. Outcome

The defect is fixed in the two places that matter and measured in a third.

**The drift is now legible.** `check.sh` was exercised against three fixtures: matching versions (`version_drift: false`), a simulated stale install (`1.0.112` loaded against a `1.0.126` checkout → `version_drift: true`), and a consuming repository with no marketplace manifest (`checkout_version: ""`, no false drift).

**The migration cannot run backwards.** The new test seeds four missions — `draft`, `approved`, `active`, and `chartered` (a word from a hypothetical future vocabulary this build has never heard of) — and asserts the two retired words fold forward while the live and unknown words stay **byte-identical with nothing staged**.

**The condition recurred during implementation, and was measured.** The session driving this ticket started with a `1.0.112` plugin cache while the checkout wanted `1.0.126`. That cache was not merely a version behind: it was missing entire scripts the checkout has (`heartbeat.sh`, `link-acceptance.sh`, `survey-worktrees.sh`, the whole `workaholify/routines/`) while still carrying the retired `approve.sh` and the retired `not_approved` exclusion. Running the survey from each in turn produced **materially different answers** — the stale copy reported `claimed: []` and excluded two missions as `not_approved`; the checkout copy reported a live claim on `work-20260804-084744` and the real exclusion reasons. A runner trusting the stale copy would have double-picked a claimed unit, which is precisely the failure the claim protocol exists to prevent. This is the concrete argument for reporting **both** numbers rather than a boolean: the reader needs to know which build answered.

**Suite:** 2107 passed, 3 failed — the same 3 failures the unmodified `main` checkout produces in this sandbox (2099 passed, 3 failed), all caused by the container's git remote being a local proxy rather than `github.com`, which `resolve-repo-url.sh` and `submit-request.sh` assert on. No new failure; the 8 new assertions all pass. `build.mjs`, `verify.mjs`, `validate-metadata.mjs` and `layout-doctor.sh` (`conforming: true`) are all green, and the branch-safety scan returns `pass`.

## 5. Concerns

### The drift check can be defeated by a stale checkout, and is not repaired here

**Severity:** medium

`checkout_version` is read from the checkout as it stands at that moment, and `/drive` calls `check-deps` **before** `sync-main.sh` fast-forwards. A runner whose clone is itself behind the base therefore compares against a stale wanted-version — and a stale clone plus a stale baked-in install *agree*, so both the bootstrap's fast path and this new drift check see a match exactly when they should not. That is not hypothetical: it is how this container reached a matching `1.0.112`/`1.0.112` pair while `origin/main` was on `1.0.126`.

It is recorded as a named limit in `check-deps/SKILL.md`, `session-start.sh` and `CLAUDE.md` rather than fixed, for two stated reasons: a diagnostic must not mutate the checkout (the same principle that makes `plan-units.sh` report `current` rather than repairing it), and SessionStart must never block a session on the network. The practical consequence is a one-tick delay — the drift surfaces on the tick *after* the fast-forward. Reordering `/drive` so the freshness step precedes the dependency check would close it, but that means trusting a possibly-broken install to run `sync-main.sh`, which is the reason the current order exists. Worth a deliberate decision rather than a drive-by reorder.

### The fix cannot reach the build that is actually broken

**Severity:** low

Nothing in this repository can alter a plugin cache outside it, so the guard added to `resolve.sh` protects against the *next* vocabulary reversal, not the `1.0.112` copies already baked into container images. Those are repaired only by `plugin update` or a fresh session. The ticket's manual check — "with the 1.0.112 cache in place, a turn no longer leaves four staged mission files" — is therefore satisfied only weakly here: the tree stayed clean all session and both active missions still read `status: active`, but the session's active build turned out to be `1.0.126`, so the backwards fold never had the chance to run. The durable proof is the fixture test, which is why the quality gate asked for one.

### An always-on lens that writes at all is the deeper question

**Severity:** low

The ticket raised, and this branch does not settle, whether a hook that fires on every prompt should ever `git add`. The staging is what turned a cosmetic rewrite into a loop-stopping condition, and the new test asserts against it for the unknown-word case — but a *correct* forward migration still stages, by design, so the lens can carry the fold. Whether that is the right seam for a living migration at all is a design question worth its own ticket rather than an opportunistic change here.

## 6. Successful Development Patterns

**The bug reproduced itself during its own fix, and the run measured it instead of narrating it.** Rather than trusting the ticket's account, the drive ran the same survey script from both the stale cache and the checkout and diffed the answers. That turned "the install is old" into "the two builds disagree about whether a unit is claimed" — a far stronger argument for the chosen design, and the reason the output reports both version numbers rather than a boolean.

**The test asserts the shape, not only the behavior.** Behavior can be preserved while the structure drifts, so alongside the byte-identity assertions the test greps the source for the explicit `draft | approved)` word list. A future refactor that quietly widens the match to a catch-all fails even if every status word still comes out right — which is exactly how the original defect shipped.

**Staging was asserted separately from content.** The two halves of the harm are separable: a rewrite that left files merely modified would be wrong but not loop-stopping. Asserting an empty staged set as its own row means a change that reintroduces staging fails even if it gets the status word right.

**Decisions were written where enforcement lives.** The warning-not-stop ruling sits in the script that implements it, the whitelist invariant in the function it governs, and the no-mid-session-refresh answer in the hook it constrains — each next to the code a future reader would otherwise have to reverse-engineer.
