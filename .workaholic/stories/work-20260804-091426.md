## 1. Overview

`plan-units.sh` reported two opposite states with one reason word. A mission whose ticket set was never emitted and a mission whose every ticket was driven both came out as `no_tickets` — so the survey said *no plan* about work that was finished, every tick, forever.

`queue_drained` is now a distinct reason in the survey and on the developer-facing roadmap.

## 2. Motivation

Measured on `main` at `ee78c9dd`: four active missions, **15 archived tickets and 4.66 recorded agent-hours** between them, every one reported `no_tickets`. The state held for four days across every hourly tick.

It survived that long because **two independent failures agreed on a wrong story**. Each of those missions also had zero linked acceptance items, so the roadmap showed `0/8`, `0/3`, `0/3`, `0/7` — which reads as *no work done* — while the survey said `no_tickets` — which reads as *no plan*. Neither signal was individually suspicious, and the true state (finished, unclosed) was visible from neither. The acceptance-link half landed 2026-08-03; this is the survey half.

## 3. Changes

### 3-1. Tell a drained mission from an unplanned one ([c96e7cc3](https://github.com/qmu/workaholic/commit/c96e7cc3))

**The signal already existed, and step 2 of the ticket dissolved.** The ticket proposed extending `queue-size.sh` to report both counts, preferring that over a second reader. It already reported `todo`, `archive` and `total` — the archive count has been there since the script was written for the drivability floors. `plan-units.sh` simply read only `todo`. So this is a verdict on counts already in hand: no new script, no second reader, and the rejected alternative never had to be weighed.

**Both consumers, because they answer to different people.** `plan-units.sh` gains the `excluded[]` reason a runner reads out of a cron log; `list.sh` gains the matching `ready_reason`, because "decide the close" is a *human* action and the roadmap is where a human looks. Reporting it in only one would have left the other still saying the wrong thing.

**Neither state is claimable — only the reason changes.** A drained mission has nothing to drive, and the close stays a human judgment. That is not caution for its own sake: of the four missions closed on 2026-08-04, one (`make-the-branch-story-concise-by-default`) turned out **not** to be achieved — its stories measurably got longer — so an automated close would have recorded it wrongly. That instance is in the code comment, not just here.

Prose updated in the same change: `drive/SKILL.md`'s reason list and its "deliberately distinct" sentence, and `CLAUDE.md`'s drivability sentence.

What the live run proves is the discriminating half: `make-the-branch-story-measurably-shorter`, a carried successor that never had a ticket, still reports `no_tickets`. The change did not relabel every empty queue. The drained side is covered hermetically.

## 5. Concerns

### The roadmap marks the state but does not rank it

`list.sh` reports `queue_drained` in `ready_reason`, and a drained mission still reads as `ready: true` — it has a plan; it finished it. Whether the bare `/mission` view should *sort* or visually separate drained missions is a presentation decision this ticket did not make. If several missions drain at once the developer sees several ordinary-looking rows with one differing field.

### The companion defect is fixed but its instances are not audited

The acceptance-link contract landed 2026-08-03, so newly emitted ticket sets link their items. Nothing swept the missions that were already unlinked when it landed. A mission can still be drained *and* unlinked — the exact state the four were in — and `progress.sh` reports `unlinked` today, but no consumer surfaces it alongside the new reason. The ticket's own Considerations flagged this; it is left for whoever picks up the audit.

## 6. Successful Development Patterns

**Before adding a reader, check what the existing one already publishes.** `queue-size.sh`'s header explicitly says two consumers ask different questions and *both numbers are therefore reported* — and then the caller read one field. A script that deliberately publishes more than its current caller needs is telling you something; read the header before extending it.

**Two wrong signals that agree are harder to see than one contradiction.** `0/N` progress and `no_tickets` told a consistent, plausible, wrong story for four days. When a state "looks explainable", check whether the explanation is being supplied by a second defect.

**Fix the reason word in every consumer at once, or you have moved the confusion rather than removed it.** The runner reads cron logs and the developer reads the roadmap; a distinction present in one and absent in the other just relocates who gets misled.
