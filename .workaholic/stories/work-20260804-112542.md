## 1. Overview

The whole `make-routine-notifications-one-semantic-story` mission: the scheduled routines' outward voice becomes one Slack thread per feedback item, on one surface, filtered to what a developer acts on — and the `[Drive]` template stops asserting a resumption gap that closed three days ago. Four tickets, `## Acceptance` 3/3, template and documentation only.

## 2. Motivation

Four Slack instructions from 2026-08-04 asked for one thing: **a developer following a feedback item should read its whole life in one place, and read nothing that is not worth reading.** What they had instead was per-step top-level posts that threaded to nothing, the same event pushed twice on two surfaces, FB issues swinging between heading-heavy filler and shapeless prose, and a routine template whose stated model of the system was three days out of date — with a live scheduling rule resting on the stale part.

## 3. Changes

### 3-1. Truth up the drive template's resumption model ([87fb93b9](https://github.com/qmu/workaholic/commit/87fb93b9))

§5 opened with *"this routine cannot resume its own unfinished work … a claimed unit is excluded from every later survey"*, false since `claim.sh resume` and `plan-units.sh`'s `resumable[]` shipped on 2026-08-01. It now states the shipped model: an unfinished claim is offered back once the branch-tip heartbeat lapses past `WORKAHOLIC_CLAIM_HEARTBEAT_STALE_MINUTES` **and** the claim commit's author is this runner's own identity, and `claim.sh resume` re-creates the worktree at the branch tip. The handoff is reframed from rescue to **information**: the next tick reaches the code either way, and what it cannot reconstruct is what the previous session knew.

**§1's one-unit-at-a-time rule survives on a re-derived reason.** It had cited the retired impossibility as its whole justification. The cost argument still supports it — an orphaned claim waits out a heartbeat lapse plus a resume round trip, so claiming N units puts N-1 through that wait against the sequential loop's at-most-one — so the rule stands with a measurable delay behind it instead of a dead end. Step 4's do-not-release warning and the yellow handoff line were corrected to match.

### 3-2. Thread the FB lifecycle into one story ([1e515a75](https://github.com/qmu/workaholic/commit/1e515a75))

The threading model is stated **once** in `workaholify/SKILL.md` and referenced by all three templates. `fb.md` founds the thread root ("🟢 Proposed to @dev", a `[Proposal]`/`[提案]` PR-title prefix, the key, the session URL) and emits no separate PR-opened line; `merged-pr.md` replies in-thread ("🟣 Proposal merged by @dev"); `drive.md` routes its outcomes there with the reporter's four-outcome vocabulary (🟢 merge requested / 🟣 merged by dev / 🚀 auto merge / 🟡 handoff).

**The key is the feedback record's filename stem, and that choice is the ticket's one real decision.** The GitHub issue number is what a human reads, but only the filename appears **in the repository** — a mission's `feedback:`, a record's `supersedes`, a publishing PR's own diff — so a later session derives the key from the artifact it is already holding rather than from a channel post it would first have to find. The session URL resolved the same way: it is the URL the harness already hands the session for its `Claude-Session:` commit trailer, which answers the ticket's open question about availability with a mechanism rather than a hope.

### 3-3. Make Slack the only notification surface ([e245d885](https://github.com/qmu/workaholic/commit/e245d885))

The surface-and-filter doctrine, once, in `workaholify/SKILL.md`: Slack only; the default for an event is silence; two precedents reused rather than reinvented (**drop the low tier**, as the PR body drops `low` concerns from the story that keeps them all; **dedupe a repeat by failure signature**, as the red alert already does); and a bright line — post a run started, a proposal opened, a merge, a handoff, a blocked precondition; post nothing for a survey, a claim, a heartbeat, an archived ticket, a pushed commit or a passing build. **An idle tick is silent, and that silence is the report.** All three templates state the surface rule and name their own postable events.

**The mobile push was identified, not assumed, and the answer was "cannot".** A live routine record carries no notification field of any kind — `list-routines.sh`'s documented shape and `compare_routines.py`'s compared set (prompt, model, schedule, `enabled`, Slack connector) exhaust it. So the duplicate push is account-level, unreachable from a template, a script, or the drift report. The deliverable split accordingly: the session-controlled half went into the three prompts, and the account-level half became a **stated limit** in `/setup-routines` — *"this command cannot do it for you"* — because a report that silently omitted a field it cannot see would let a developer conclude the duplicate was handled.

### 3-4. Balance structure and prose in FB authoring ([dd2e0588](https://github.com/qmu/workaholic/commit/dd2e0588))

`feedback/SKILL.md` gains a **Body style** section: prose by default; a short list or small table only where a genuinely multi-step or multi-item ask reads better as one; no deep headings; no content-free items. Plus the licence the FB asked for — **correct apparent wording slips and fill the gaps a standalone reader needs**, rather than transcribing a Slack message verbatim. Both shipped failure modes are named as the rationale (the heading-heavy era; `20260804101847`'s flat-prose overcorrection), so the rule reads as a midpoint rather than a swing back. The `[FB]` template references it with one positive and one negative example.

## 5. Concerns

### The whole mission is unverifiable until the fleet is refreshed, and that is a human act

Every change here edits a **template**. The live routines still carry the old prompts, so nothing in this branch changes a single Slack post until `/workaholify` or `/setup-routines` refreshes each routine, one at a time, verbatim-confirmed — which an unattended run cannot do at all. The drift report flagging all of them after this merges is the intended signal. Until then the repository states one model and the account runs another, and the gap is invisible to anyone reading only the channel.

### The filter is a model judgment at post time, not a gate

Nothing checks that a session obeyed the bright line; a prompt asks it to. The line and the tie-goes-to-silence rule are as far as prose can go, and the failure mode is gradual — one justifiable post at a time until the channel is noise again. If it recurs, the fix is a narrower enumeration, not a stricter adjective.

### Thread discovery is eventually consistent, and its fallback duplicates roots

A channel search that misses posts a second root carrying the same key. That is deliberate — a keyless post is unattributable forever, while two roots are a repairable mess — but nothing reconciles them, so an item can end up with its life split across two threads and no routine will notice.

### The new authoring licence brushes against an older rule in the same file

`feedback/SKILL.md` already said *"record faithfully; do not editorialize"*. The boundary is now stated explicitly — repairing an expression changes **how** the ask is written, adding a cause or a severity changes **what it claims** — but two adjacent paragraphs governing the same act is a shape that invites the next editor to soften one of them.

## 6. Successful Development Patterns

**"Identify the mechanism, do not assume it" is worth writing into a ticket, because the honest answer is sometimes "cannot".** The mobile-push step could have been satisfied with a plausible template line that silently did nothing. Reading the routine record's actual field set turned it into a documented limit plus a developer instruction — less impressive and true.

**A stale premise is most dangerous when something still cites it.** §1's rule was correct and its stated reason was not, so a reader checking the reason would have found a dead end and might have dissolved a rule that a cost argument still supports. Re-deriving beat deleting.

**Pick the identifier that lives where the reader already is.** The thread key could have been the GitHub issue number a human sees. Choosing the filename stem — which sits in the mission's `feedback:` field, in the record's `supersedes`, and in the publishing PR's diff — means a session derives it from the artifact in its hands instead of searching for it.
