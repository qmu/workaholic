## 1. Overview

The branch-safety scan's `secret` rule — the one tier with no override — was hard-blocking
branches over content that had been on `main` for weeks. The trigger was not a credential
but a *build*: when `build.mjs` grows a bundle's closure, it copies whole tracked files
into new `outputs/` paths, and `git diff <base>..HEAD` reports a file arriving at a new
path as wholly added. Every copied line therefore read as authored.

This change filters generated paths out of the `secret` rule's input, through the same
`is_generated_path` predicate the per-commit size rule already uses.

## 2. Motivation

Observed while driving `20260805033616-drive-land-unit-now.md`: `land-unit.sh` composed
`catchup-main.sh`, which pulled `ship/scripts/` into two more bundles, and the scan
returned a hard block citing

```
outputs/workflows/skills/{create-ticket,drive}/ship/scripts/record-evidence.sh:19
```

Line 19 is a **comment**, and specifically the comment documenting the secret guard:

```
# (cloud keys, GitHub/Slack tokens, bearer/basic auth, PEM keys, password=/token=
```

It parses as a hit because `password=` is followed by `/token=` — seven value characters
running to end of line, which is exactly the rule's "bare literal" shape. The rule matches
on the value rather than the key name by design, and English prose satisfied it.

Two properties made this worth fixing rather than working around. First, `secret` is
non-overridable, so the unit that discovered it simply could not ship. Second, the trigger
is "a skill gained a cross-skill script reference", so **any** future closure growth
inherited the same permanent block on a branch introducing no credential at all.

The reasoning already existed one file away: `commit-size.sh` had worked this class
through for the size rule — *"it counts additions only, so a relocation is not charged
twice for moving content"* — and the `secret` rule inherited none of it. The allowlist had
also already made the fix surgically for exactly one path
(`outputs/workflows/skills/*/release-scan/**`). This generalizes what both had concluded.

## 3. Changes

`scan-branch-safety.sh` now partitions `added_lines` before the secret pass, dropping rows
whose file is a generated path. The predicate is resolved once per distinct path rather
than per line. `size` and `leak` are untouched, and `.workaholic/scan-allow` remains the
way to drop a path from the *whole* scan — which is why the release-scan allowlist entry
stays: it does strictly more than this rule.

Five regression cases were added, built around the real `record-evidence.sh:19` line.

## 4. Outcome

The reported block is gone and the coverage it stood for is measured rather than assumed:

- a generated copy of a tracked file → `pass` (was: hard block, verified against the
  pre-fix script on the same fixture)
- a credential under a non-generated path → still a hard finding
- a credential carried into the bundle by a build → still caught at its source
- a generated path → still scanned by the `leak` rule

Suite: 2252 passed, 0 failed. `build.mjs`, `verify.mjs`, `validate-metadata.mjs` and
`layout-doctor.sh` clean; `scan-branch-safety.sh` on this branch returns `pass`.

## 5. Concerns

### A hand-planted credential in a generated path is no longer reported by this rule

**Severity: medium.** This is the exemption's real cost, and it is measured rather than
inferred — case 4 of the new test pins it. A credential that reaches `outputs/` through a
build also sits in its source and is still caught there; one written into `outputs/` *by
hand*, with no source counterpart, is not.

What catches that case is the `Outputs Freshness` CI workflow, which rebuilds `outputs/`
and fails on any diff — so a hand-edit of a generated tree cannot reach a merge whether or
not it holds a credential. That backstop is now load-bearing for a security property it
was not designed for, which is why the dependency is written into the script, the SKILL
and `CLAUDE.md` rather than left as folklore. If `Outputs Freshness` is ever relaxed to
tolerate diffs, this exemption must be revisited in the same change.

### The generic-assignment rule still matches prose

**Severity: low.** Option 3 from the ticket — narrowing the rule so a `#`-comment line
cannot match — was deliberately **not** taken. A real credential in a comment is still a
leaked credential, and the ticket says so. The consequence is that the *source* file's
line 19 would still be flagged if that file were ever edited; today it is covered by the
allowlist's `release-scan/**` and `plugins/**`-adjacent entries only incidentally. Worth
revisiting only with a rule that can tell prose from an assignment, which is not this
change.

### Option 2 was not implemented and remains the more general fix

**Severity: low.** "Do not flag an added line whose content already exists on the base, at
any path" would cover hand-made relocations too, not just generated ones. It costs a
base-side lookup per candidate finding, was not needed for this defect, and should be
measured before adoption. Recorded so the narrower fix here is not mistaken for the
complete one.

## 6. Successful Development Patterns

**Reproduce against the pre-fix script, not just the fixed one.** The fixture was run
through the version on `main` first and confirmed to block, then through the fixed version
and confirmed to pass. Without the first half, "the test passes" would not have
distinguished a real fix from a fixture that never exercised the defect.

**Pin the cost, not only the benefit.** The exemption's blind spot is a test case that
asserts the scan stays *silent*, with a comment naming what covers it instead. A limit
that lives only in prose is a limit the next reader discovers by being bitten.

**Reuse the predicate the neighbouring rule already had.** `is_generated_path` was
right there, carrying the same reasoning for the size rule. Two rules reading one diff
will keep diverging unless the shared question has a single implementation.
