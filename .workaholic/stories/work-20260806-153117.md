## 1. Overview

`/setup-routines` was built to manage routines through the API. It managed the half the API exposes while blind to the half that decides whether a routine runs at all — the GitHub trigger, which is web-UI-only. It is now a **setup sheet renderer**, and the management machinery is deleted.

**Highlights:**

1. Each template declares its trigger as structured data; the sheet's UI steps are **derived** from it, so they cannot drift.
2. Seven scripts and ~1370 lines removed, with their tests — the command makes no `RemoteTrigger` call.
3. What the machinery got right is preserved as prose, so nobody restores it to recover the principle.

## 2. Motivation

The measured cost of managing half a routine, on one day: a paginated `list` (20 rows, `has_more` unread) was surveyed as the whole account; six duplicate records were carefully refreshed through the digest gate; and the real, wired `[Propose]` ran a stale prompt beyond page one. A "drift-free fleet" was reported both times. A tool authoritative about the parts that do not matter and silent about the part that does misleads more than it helps.

## 3. Changes

### 3-1. Render setup sheets from trigger declarations ([9821b2b1](https://github.com/qmu/workaholic/commit/9821b2b1))

Templates gain `trigger_kind` / `trigger_event` / `trigger_filters`; `render-setup-sheet.sh` derives the UI steps from them and emits the prompt verbatim through the existing renderer, so a sheet can never disagree with its template. `/setup-routines` becomes the renderer plus the two preconditions, with no account call and no prompt.

### 3-2. Retire the routine management machinery ([f4fe6a81](https://github.com/qmu/workaholic/commit/f4fe6a81))

The digest gate and the drift reporting are deleted with their tests. `/workaholify` no longer surveys the account or offers to create routines; the proposal runbook describes creating one by hand. The retirement reached four documents and two analogies beyond the scripts themselves.

## 4. Outcome

Both acceptance criteria are met. A developer runs `/setup-routines`, gets one paste-ready sheet per routine, and creates them in their own browser — and the repository no longer claims to know what the account holds.

## 5. Concerns

### Nothing can now report what actually runs against a repository

- **Severity:** moderate
- **Description:** That is deliberate — the report that claimed to was silent about the trigger — but the question a developer asks ("is my fleet wired?") has no answer in the plugin at all now.
- **How to Fix:** Answer it from what routines produce (an issue, a PR, a channel post), never from the account. The SKILL says not to reintroduce a reader for it.

## 6. Successful Development Patterns

- Sweeping for the deleted scripts by **name**, not by caller: two analogies cited `authorize-routine-change.sh` as the canonical "cannot prove a human was present" example — one inside `land-unit.sh`'s header, in the drive critical path — and neither would have broken anything, only sent the next reader to a file that is gone.
- Preserving a deleted gate's *reasoning* beside its retirement, so the principle survives without the machinery.
