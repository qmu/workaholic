# Right-size /report to single-ticket-per-PR granularity

## 1. Overview

Right-sized `/report`'s Phase 2 to the single-ticket-per-PR granularity the loop now merges at. A scale gate on Phase 0's `archived_tickets` count routes a branch of 2 tickets or fewer to one combined opus worker with no mermaid Journey, while a Story-shaped batch of more than 2 keeps the original 3-worker parallel fan-out unchanged. The result record and the FB → Proposal → Implementation → Report relations are untouched on both paths, because they are Phase 3/4/5 output that neither path reshapes.

**Highlights:**

1. Phase 2 now branches on `archived_tickets` count: ≤2 runs one combined worker (release-readiness + review-sections + Overview/Highlights/Motivation), >2 keeps the 3-worker fan-out
2. The mermaid Journey is full-path-only — skipped outright on the lite path, with the Changes section opening directly on the per-ticket subsections
3. Docs updated in the same change (`SKILL.md`, `orchestration.md`, `story-structure.md`, `CLAUDE.md`'s `/report` row) and `outputs/workflows` regenerated in lockstep

## 2. Motivation

The loop's merge granularity moved from a whole Story's batch of tickets to a single ticket or a small mission batch per pull request (`docs/loop-engineering-workflow.md` G1/P1), but `/report`'s per-run procedure did not move with it: Phase 2 spawned a fixed three-subagent fan-out and synthesized a mermaid flowchart of the work's progression regardless of whether the branch carried one ticket or ten. On a one-ticket branch that costs more time and output than the unit being reported on — a flowchart earns its keep only once there is a multi-phase progression worth diagramming. The design half of this mission established that the oversized thing was the procedure rather than the unit of work (one report per branch/PR is still right), and that the constraint from the source feedback — preserve the result record and the cross-document relations — is satisfied by construction, since both are produced by Phase 3, 4 and 5, which the split does not touch. The gate keys on a count Phase 0 already returns, so nothing new is measured to decide the path.

## 5. Concerns

### The lite/full scale gate is unenforced prose with no test coverage

- **Severity:** low
- **Description:** The `≤2` boundary lives only in skill markdown (`plugins/workaholic/skills/report/reference/orchestration.md` Phase 2, restated in `SKILL.md` and `CLAUDE.md`, landed in [0419cf4c](https://github.com/qmu/workaholic/commit/0419cf4c)). Nothing scripts or asserts it, so a run that spawns the full fan-out on a 1-ticket branch — or skips a Journey a 5-ticket branch should have — fails silently as a cost regression rather than an error.
- **How to Fix:** If path selection drifts in practice, move the count comparison into a small script the orchestration calls (returning `lite`/`full`) so `test-workflow-scripts.mjs` can pin the boundary, and have `/report` report which path it took.

## 6. Successful Development Patterns

- Audit a workflow's fixed fan-out arity against the unit's *current* granularity before trimming its checks: here the disproportionate cost was three LLM subagents plus flowchart synthesis, while the branch-safety scan and doc-drift backstop were already cheap script calls that stayed on both paths.
- Scale a procedure on a value an earlier phase already returns (`archived_tickets` from Phase 0's `git-context.sh`) — the gate adds a branch, not a measurement step, so it cannot itself become a cost.
- Split a right-sizing into a design ticket that names what must survive and an implementation ticket that only builds it: the two preservation requirements (result record, cross-document relations) were then verifiable by tracing which phases the diff touched, with no re-litigation mid-implementation.
