# Legibly report the unbound-plugin no-reload gap

## 1. Overview

Investigated why a plugin installed by a SessionStart hook is not invocable until a human types `/reload-plugins`, a command no unattended routine ever runs. Confirmed against Claude Code's own documentation that no harness mechanism exists to make a SessionStart-time install effective mid-session, so the deliverable is legibility rather than a fix: `check-deps/scripts/check.sh` now reports `claude_session_detected`, `registry_has_install` and `unbound_in_claude_session`, and `/drive` terminates `pending` on the last of these before surveying. The condition was reproduced live in the session that drove the ticket, and the new detector was verified firing against that exact state.

**Highlights:**

1. `check.sh` gained a third drift axis — `unbound_in_claude_session`, true only when a genuine Claude Code session has a registry-confirmed install yet never bound a plugin root
2. `/drive` §1 and its `reference/survey.md` terminate `pending` on the new field, with a matching row in the §7 terminal-token table, identical in shape to the registry-drift stop
3. Documented the no-fix finding in `CLAUDE.md`, `workaholify/SKILL.md` and `check-deps/SKILL.md` ("Two drift axes" → "Three drift axes"), plus four new hermetic gates in `test-workflow-scripts.mjs`

## 2. Motivation

An unattended `[Implement]` routine runs in a fresh container where the SessionStart bootstrap installs the plugin, but the harness binds nothing new for the rest of that session — so the very next `Skill({skill: "workaholic:drive"})` call fails `Unknown skill`, and the tick proceeds with zero workaholic surface while still reading as a healthy run. That is worse than a stale binding: it is no binding at all, and the only documented remedy, `/reload-plugins`, is a manual command an unattended routine never types. The investigation therefore had two possible outcomes and had to establish which one applied before writing any code — a harness mechanism to wire up, or none, in which case the honest deliverable is to make the condition impossible to mistake for an idle tick. Claude Code's plugin reference settled it: hooks, MCP servers and LSP servers keep the previous binding until a human reloads, and no environment variable, CLI flag or alternate hook event changes that. What remained was to detect the state cheaply and stop on it, so a routine that cannot possibly do its job says so instead of silently doing nothing.

This is the third binding-related gap this repository has investigated and the second to end in "no fix inside the plugin." The superseded-cached-binding case (closed 2026-08-05) established the precedent followed here: when the failing mechanism belongs entirely to the harness — the cache layout, the registry, the moment of binding — the plugin's only honest move is to make the condition legible and let the run stop, rather than to invent a workaround that repairs nothing. That precedent shaped both the shape of this change (a new reported field plus a `pending` stop, matching `loaded_version_behind_registry` line for line) and its scope: the ticket explicitly forbade re-litigating the earlier axis, and the two are documented side by side as distinct questions — a stale binding versus no binding.

## 5. Concerns

### The `loaded_root_source: "none"` branch now carries a hard stop

- **Severity:** moderate
- **Description:** `none` used to mean silence; it now means `pending` for `/drive` whenever a session marker and a registry entry are present (see [60f8dec6](https://github.com/qmu/workaholic/commit/60f8dec6) in `plugins/workaholic/skills/check-deps/scripts/check.sh`). A root is recognised only via the `CLAUDE_PLUGIN_ROOT` env var or a path under `~/.claude/plugins/cache`, so any legitimately-bound session resolving elsewhere — a locally-sourced marketplace entry, a direct literal-path invocation — is reported unbound and stops.
- **How to Fix:** Confirm which roots a local marketplace install actually resolves to and widen the recognised prefixes (or key the stop on a positive "nothing bound" signal rather than the absence of a known prefix), so the stop cannot fire on a session that is working.

## 6. Successful Development Patterns

- Verify a harness-condition detector against the very session that exhibits the condition: this ticket was driven inside a session the bootstrap had left unbound, so running the patched `check.sh` there proved it fires on the real state rather than on a simulated one — a state that is by construction unobservable from a healthy session.
- Keep every operand of a binding diagnostic a harness fact (the session marker, the harness registry, the resolved root) and never plugin content: a plugin that diagnoses its own binding from its own files can only ever agree with itself, which is the failure mode the registry axis was originally built to avoid.
