## 1. Overview

FB issues stayed open after their "[Proposal]" pull request merged, because the proposal pipeline never captured the triggering GitHub issue's number and so never emitted GitHub's native `Closes #<N>` keyword. This branch threads that number through and confirms live that merging now auto-closes the issue.

**Highlights:**

1. `propose/scripts/extract-issue-number.sh` captures the issue number from `CCR_TRIGGER_ISSUE_NUMBER` (a routine) or a `#<N>`/URL in the argument (a hand-typed `/propose`).
2. `publish-tree-pr.sh` threads it into the PR body as a validated `Closes #<N>` line via `WORKAHOLIC_CLOSES_ISSUE`, never laundering a non-numeric value into a public body.
3. Live-verified end to end against a disposable issue/PR in this repository: a squash merge via the GitHub MCP tool auto-closed the issue.

## 2. Motivation

The developer reported that "[FB] ***" issues were not auto-closing on merge, believing a mechanism already existed. Investigation found none: no script called `gh issue close`, and no generated PR body ever carried a closing keyword — the proposal pipeline threaded a local feedback-record filename through `feedback:` frontmatter, which has no relation to a GitHub issue number at all. The fix is additive: capture the number where it is already available (a routine's trigger env var, or the ask's own argument) and let GitHub's own native behavior do the closing, rather than adding a second, redundant `gh issue close` call.

## 3. Changes

### 3-1. Auto-close FB issues when their Proposal PR merges ([89063da1](https://github.com/qmu/workaholic/commit/89063da1))

Added `extract-issue-number.sh` to the propose workflow's step 1 and a validated `WORKAHOLIC_CLOSES_ISSUE` env var to `publish-tree-pr.sh`'s step 9, so a proposal's pull request body carries a native `Closes #<N>` line whenever the triggering issue's number is in hand. Documented the same line for the hand-opened-PR fallback path (`gh` is unavailable in this environment, so that path — not the scripted `gh pr create` — is what actually runs here today).

## 4. Outcome

A merged "[Proposal]" pull request now auto-closes the "[FB] ***" issue it addresses whenever the ask carried a GitHub issue number, confirmed live against a disposable issue/PR pair (squash-merged via the GitHub MCP tool) rather than inferred from GitHub's documentation. An ask with no issue number in hand is unaffected — same PR body shape as before.

## 5. Concerns

### The scripted `gh pr create` path is effectively unexercised in this environment

- **Severity:** low
- **Description:** `gh` is unavailable here (see [89063da1](https://github.com/qmu/workaholic/commit/89063da1) in `publish-tree-pr.sh`), so real `/propose` runs open the pull request by hand over MCP instead of through the script's own `gh pr create` call that emits `Closes #<N>`.
- **How to Fix:** No code fix — the hand-opened fallback now carries the same instruction (`workflow.md` step 9), and the hermetic suite covers body assembly directly, independent of `gh`.

## 6. Successful Development Patterns

- Give each `WORKAHOLIC_CLOSES_ISSUE` hermetic scenario its own fixture/origin rather than reusing one publish tree across sequential `publish-tree-pr.sh` calls — the work-branch name is second-granularity, so two calls against the same origin within the same wall-clock second collide (`branch_collision`); the first version of this test hit exactly that (2 failures), and independent origins fixed it without a sleep.
