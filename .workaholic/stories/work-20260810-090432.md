## 1. Overview

Moved the `[Implement]` Claude Code Web routine off its merged-`[Proposal]`-pull-request webhook onto a fixed 30-minute schedule (`0,30 * * * *`), returning the unattended executor to a loop-engineering cadence instead of instant event reaction. `[Propose]` was deliberately left on its GitHub trigger, because `/propose`'s whole design is the ask in hand and a clock fire supplies none. The companion "revive `/set-routines`" ask was answered by re-verification rather than new code: no session tool can read or write a routine's trigger, so `/setup-routines`'s existing `cron_expression` rendering is the whole answer.

**Highlights:**

1. `implement.md` now declares `trigger_kind: schedule` / `cron_expression: 0,30 * * * *`, replacing the `pull_request.closed` webhook trigger
2. `fb.md` (`[Propose]`) stays event-triggered, with the *ask in hand* reasoning recorded in the template, `reference/routines.md`, and `CLAUDE.md`
3. `ToolSearch` found no `RemoteTrigger`-family tool in this session's surface, so `/setup-routines`'s pre-existing `cron_expression` branch is the whole answer — no `/set-routines` command was added

## 2. Motivation

FB `20260810085032` (GitHub issue #336) asked that `[Propose]` and `[Implement]` stop reacting instantly to webhooks and return to a fixed-interval loop-engineering cadence — a bounded, predictable tick rather than reactive execution. The 2026-08-06 ruling that had settled `[Implement]` on the merge event argued that its survey already answers the clock case, since every merge-started run offers everything claimable; but that argument shows the survey *can* substitute for a timer, not that instant reaction is the better cadence, and the loop-engineering premise this repository was built on prefers the timer. `[Implement]` is survey-driven rather than event-driven, so nothing depended on the merge event for correctness and the move costs only the instant start. `[Propose]` is the opposite case: its entire design is the ask in hand, answering `nothing_in_hand` when there is none, and a schedule fire carries no issue number and no assignee at all, so converting it would either report `nothing_in_hand` every tick or resurrect the swept-backlog `[Propose Batch]` design already retired for sweeping instead of receiving an ask. The second half of the ask — reviving a `/set-routines` command — turned on a premise worth checking rather than inheriting: unlike a GitHub event, `cron_expression` is a genuine API-visible field on a routine record, so the 2026-08-06 "manages nothing" retirement did not obviously carry over; re-verifying it directly is what closed the question.

This branch deliberately revisits two decisions the repository had already settled, which is why each move is recorded with its reasoning rather than simply applied. On 2026-08-06 the routine account-management surface was retired in favour of a read-only copy-paste sheet, because a routine's GitHub trigger is UI-only and unreadable from the API — a tool that manages what it cannot verify misled more than it helped. The same period retired `[Propose Batch]` for sweeping the backlog instead of receiving an ask, which is precisely why `/propose` was rebuilt around the ask in hand. Both shaped this work: the schedule question was re-verified per-field instead of assumed to inherit the event trigger's answer, and when the verification came back negative the response was to document the finding and lean on the existing setup sheet — not to fabricate a management command the earlier retirement had already ruled out.

## 5. Concerns

### The live [Implement] routines keep their old trigger until a human rewires them

- **Severity:** moderate
- **Description:** This branch changes a template declaration and its documentation only; no tool in a session can write a routine's `cron_expression` (see [9e1d1745](https://github.com/qmu/workaholic/commit/9e1d1745) in `.workaholic/tickets/archive/work-20260810-090432/20260810085351-revive-set-routines-to-provision-the-routines-fixed-interval-trigger.md`), so every already-created `[Implement]` routine keeps firing on `pull_request.closed` while the repository documents a 30-minute schedule.
- **How to Fix:** After merge, run `/setup-routines` and apply the rendered Schedule step by hand to each live `[Implement]` routine.

### FB 20260810085032 is only half applied by design

- **Severity:** moderate
- **Description:** Issue #336 asked for both routines to move to a schedule; only `[Implement]` did, because `/propose` has no ask in hand on a clock fire (see [fd492266](https://github.com/qmu/workaholic/commit/fd492266) in `plugins/workaholic/skills/workaholify/routines/fb.md`).
- **How to Fix:** Close #336 on the recorded split, or raise a separate ticket to redesign how `/propose` discovers an ask under a clock — a design change, not a frontmatter edit.

### The no-RemoteTrigger finding is scoped to an unattended session

- **Severity:** low
- **Description:** The tool-surface probe ran inside a routine-fired, unattended session only (see [9e1d1745](https://github.com/qmu/workaholic/commit/9e1d1745) in `plugins/workaholic/skills/workaholify/reference/routines.md`), and says nothing about a developer's own interactive session.
- **How to Fix:** If provisioning from a session ever matters, re-run the same probe from an interactive session and record that result beside this one.

## 6. Successful Development Patterns

- Re-verify a retired decision per field before inheriting its conclusion: `cron_expression` is API-visible where a GitHub event has no field at all, so the two only looked like the same case.
- A name match is not evidence of capability: `CronCreate`/`CronList`/`CronDelete` read as the exact tool sought and are session-local and in-memory; the distinguishing test for an account-level resource is persistence across sessions.
- Declarative template frontmatter that a renderer already derives its UI steps from meant a trigger change was a data edit with no script change.
- When a ticket's literal instruction conflicts with a command's design, do the narrower change and record the deviation with its reasoning in the artifact itself.
