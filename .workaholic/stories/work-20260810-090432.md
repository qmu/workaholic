## 1. Overview

Moved both `[Propose]` and `[Implement]`, the Claude Code Web routines, off their GitHub event triggers onto the same fixed 30-minute schedule (`0,30 * * * *`), returning them to a loop-engineering cadence instead of instant event reaction. A first pass moved only `[Implement]` — `[Propose]`'s whole design is *the ask in hand*, and a schedule fire alone supplies none — but the developer's ask covered both routines from the start and said so again live on this PR, so `[Propose]` moved too, with the resulting gap (a pure clock tick still finds nothing to act on) stated rather than hidden. The companion "revive `/set-routines`" ask was answered by re-verification rather than new code: no session tool can read or write a routine's trigger, so `/setup-routines`'s existing `cron_expression` rendering is the whole answer.

**Highlights:**

1. `implement.md` and `fb.md` both now declare `trigger_kind: schedule` / `cron_expression: 0,30 * * * *`, replacing their `pull_request.closed` / `issues.assigned` webhook triggers
2. `[Propose]`'s move carries an open cost: a schedule fire alone gives `/propose` no ask in hand, so a pure clock tick still reports `nothing_in_hand` — recorded in the template, `reference/routines.md`, and `CLAUDE.md` rather than silently assumed solved
3. `ToolSearch` found no `RemoteTrigger`-family tool in this session's surface, so `/setup-routines`'s pre-existing `cron_expression` branch is the whole answer — no `/set-routines` command was added

## 2. Motivation

FB `20260810085032` (GitHub issue #336) asked that `[Propose]` and `[Implement]` stop reacting instantly to webhooks and return to a fixed-interval loop-engineering cadence — a bounded, predictable tick rather than reactive execution. The 2026-08-06 ruling that had settled `[Implement]` on the merge event argued that its survey already answers the clock case, since every merge-started run offers everything claimable; but that argument shows the survey *can* substitute for a timer, not that instant reaction is the better cadence, and the loop-engineering premise this repository was built on prefers the timer. `[Implement]` is survey-driven rather than event-driven, so nothing depended on the merge event for correctness and the move costs only the instant start. `[Propose]` is the harder case: its entire design is the ask in hand, answering `nothing_in_hand` when there is none, and a schedule fire carries no issue number and no assignee at all — an earlier pass of this branch read that conflict as grounds to leave `[Propose]` on its event trigger, deferring the redesign. The developer corrected that live: the ask was always for both routines, and the unresolved discovery question does not block moving the trigger — it only means the schedule does not yet give `/propose` anything new to act on. The second half of the ask — reviving a `/set-routines` command — turned on a premise worth checking rather than inheriting: unlike a GitHub event, `cron_expression` is a genuine API-visible field on a routine record, so the 2026-08-06 "manages nothing" retirement did not obviously carry over; re-verifying it directly is what closed the question.

This branch deliberately revisits decisions the repository had already settled, which is why each move is recorded with its reasoning rather than simply applied. On 2026-08-06 the routine account-management surface was retired in favour of a read-only copy-paste sheet, because a routine's GitHub trigger is UI-only and unreadable from the API — a tool that manages what it cannot verify misled more than it helped. The same period retired `[Propose Batch]` for sweeping the backlog instead of receiving an ask, which is precisely why `/propose` was rebuilt around the ask in hand; moving `[Propose]`'s trigger to a schedule does not reintroduce that sweep — the command still only acts on an ask handed to it, it just now checks periodically instead of on assignment.

## 4. Outcome

- `[Implement]` and `[Propose]` now both fire on a fixed 30-minute schedule (`0,30 * * * *`) instead of their respective webhook triggers, and `[Implement]`'s prompt resolves a reply thread per claimed unit rather than per triggering pull request.
- `[Propose]`'s open gap is recorded, not hidden: a pure schedule tick with nothing else in hand still reports `nothing_in_hand`, since the schedule is a periodic check, not a new ask-discovery mechanism.
- The "revive `/set-routines`" ask was closed by re-verification rather than new code: no `RemoteTrigger`-family tool exists in this session's surface, and `/setup-routines` already derives a Schedule step from `cron_expression`.

## 5. Concerns

### The live routines keep their old triggers until a human rewires them

- **Severity:** moderate
- **Description:** This branch changes template declarations and documentation only; no tool in a session can write a routine's `cron_expression` (see [9e1d1745](https://github.com/qmu/workaholic/commit/9e1d1745) in `.workaholic/tickets/archive/work-20260810-090432/20260810085351-revive-set-routines-to-provision-the-routines-fixed-interval-trigger.md`), so every already-created `[Implement]`/`[Propose]` routine keeps firing on its old webhook while the repository documents a 30-minute schedule.
- **How to Fix:** After merge, run `/setup-routines` and apply the rendered Schedule step by hand to each live routine.

### [Propose] on a schedule still has nothing to act on by itself

- **Severity:** moderate
- **Description:** `/propose`'s design requires an ask in hand; a schedule fire alone supplies none, so a `[Propose]` tick fired purely by the clock reports `nothing_in_hand` and ends (see [3bbd3664](https://github.com/qmu/workaholic/commit/3bbd3664) in `plugins/workaholic/skills/workaholify/routines/fb.md`). The trigger moved on the developer's explicit instruction; the discovery gap it exposes was not redesigned here.
- **How to Fix:** Raise a separate ticket to redesign how `/propose` discovers an ask under a clock, if a working schedule-driven `[Propose]` matters — a design change, not a frontmatter edit.

### The no-RemoteTrigger finding is scoped to an unattended session

- **Severity:** low
- **Description:** The tool-surface probe ran inside a routine-fired, unattended session only (see [9e1d1745](https://github.com/qmu/workaholic/commit/9e1d1745) in `plugins/workaholic/skills/workaholify/reference/routines.md`), and says nothing about a developer's own interactive session.
- **How to Fix:** If provisioning from a session ever matters, re-run the same probe from an interactive session and record that result beside this one.

## 6. Successful Development Patterns

- Re-verify a retired decision per field before inheriting its conclusion: `cron_expression` is API-visible where a GitHub event has no field at all, so the two only looked like the same case.
- A name match is not evidence of capability: `CronCreate`/`CronList`/`CronDelete` read as the exact tool sought and are session-local and in-memory; the distinguishing test for an account-level resource is persistence across sessions.
- Declarative template frontmatter that a renderer already derives its UI steps from meant a trigger change was mostly a data edit with little script change.
- A scoped deviation from a literal instruction is worth recording, but worth surfacing to the requester too: the first pass's "keep `[Propose]` event-triggered" reasoning was sound in isolation and still wrong against what was actually asked — recording a decision in the artifact does not substitute for checking it against the request when the two might conflict.
