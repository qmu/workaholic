## 1. Overview

`workaholic:notify`'s stateless thread lookup sometimes posted a brand-new Slack root instead of finding an item's real thread, because both of its exact-string search queries could miss. This branch adds a persisted `thread_ref` pointer to the feedback record itself, checked before either search runs, with the existing search kept as the fallback for anything written before this change.

**Highlights:**

1. Added a write-once `thread_ref` frontmatter field to `.workaholic/feedbacks/` records, with `feedback/scripts/set-thread-ref.sh` as its sole, refuse-on-repeat mutator.
2. Wired the field as the primary lookup path in `workaholic:notify`, ahead of the `fb:<stem>`/Issue-URL searches, in both `[Propose]`'s and `/implement`'s root-posting flows.
3. Bumped the plugin to v1.0.156 and regenerated `outputs/workflows`, whose `drive`/`create-ticket` bundles now carry `feedback/scripts/set-thread-ref.sh` in their closure for the first time.

## 2. Motivation

Issue #360 (feedback `20260810163347`) and a related earlier report (feedback `20260808030816`, issue #306) both measured the same symptom: a routine's search for an item's existing thread came up empty and it posted a new root instead of replying where the conversation actually was. The ticket's own note flagged the tension this reopens: Q1 (2026-08-07) retired an earlier carried-target mechanism specifically because it embedded a Slack thread URL in a public pull-request body. This branch is deliberately narrower — nothing is carried in a public body; the pointer lives on the item's own already-private feedback record, the same record every routine already reads to get `fb:<stem>`. A stale or unwritten key degrades to exactly the pre-existing search, never to a guess.

## 3. Changes

### 3-1. Persist the notify thread key at root-post time instead of re-deriving it by search ([afefc277](https://github.com/qmu/workaholic/commit/afefc277))

Added the `thread_ref` field, its sanctioned mutator script, and reordered the lookup in `workaholic:notify`, `workaholic:drive`, and `workaholic:propose` so a persisted key is read before any search runs.

## 4. Outcome

A record that has posted a Slack thread root now carries a pointer to it (`<channel-id>:<ts>`), and every later event for that item — under `/implement` or `[Propose]` — reads that pointer directly instead of re-running the two-query search. A record predating this change, or one whose write failed, is unaffected: it falls back to the identical search that was the whole mechanism before this branch.

## 5. Concerns

### `notify` has no scripts of its own, so a new script reference had to live elsewhere

- **Severity:** low
- **Description:** `workaholic:notify` carries no `scripts/` directory and is not a `build.mjs` target, so it never enters the generated `outputs/workflows` bundle on its own (see [afefc277](https://github.com/qmu/workaholic/commit/afefc277) in `plugins/workaholic/skills/notify/SKILL.md`). The instruction to call `feedback/scripts/set-thread-ref.sh` after a fresh root post therefore had to be added to `drive/reference/routing.md` and `propose/reference/workflow.md` — both already in a built target's closure — rather than to `notify/SKILL.md` itself.
- **How to Fix:** No action needed now; noted so a future edit to `notify/SKILL.md` that adds a cross-skill script call remembers to also add it to a closure-reachable file, or the built `drive`/`create-ticket` bundles will carry an unresolvable reference.

## 6. Successful Development Patterns

- Modeling `set-thread-ref.sh`'s refusal-channel convention (argument/file errors to stderr, business-logic refusals to stdout) on the existing mission mutators (`record-run-hours.sh`, `link-acceptance.sh`) rather than on `feedback/scripts/create.sh`'s all-to-stdout convention worked well: it matches the pattern of the class of script it actually is (a mutator of an existing file, not a first write), and the mismatch surfaced immediately as a test failure rather than silently.
