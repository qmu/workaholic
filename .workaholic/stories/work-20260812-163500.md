## 1. Overview

A run no longer depends on the plugin root the harness happened to bind. A new resolver,
`check-deps/scripts/plugin-src.sh`, returns the **newest plugin tree present on the
machine** — checkout, registry install path, clone, binding, ties to the checkout — and
the run executes every script from it. `loaded_version_behind_registry` stops being a
terminal gate and becomes a reported source-selection fact.

**Highlights:**

1. Twelve consecutive `[Implement]` ticks had been terminating before surveying, with claimable work queued and a current checkout on disk.
2. The root cause is a **two-scope registry**: the container binds an image-baked *project*-scope install while the bootstrap updates only the *user* scope.
3. Picking the newest tree can only move a run forward on the staleness axis — the exact property the demoted gate existed to protect.

## 2. Motivation

`/drive` §1 terminated `pending` on `loaded_version_behind_registry` because a superseded
binding once changed the survey's *answer*: a stale `claims.sh` offered five
already-driven tickets as fresh backlog and a tick claimed one (2026-08-04). That gate
was correct about the danger and wrong about the remedy — it treated "the binding is
dated" as "the run must not proceed", when what actually mattered was which scripts the
run executes.

The cost came due on 2026-08-12. Measured live in this session: `installed_plugins.json`
carries **two** entries — a `project`-scope install pinned at v1.0.133 (image commit
`77c462d`, 2026-08-06) and a `user`-scope one — and the SessionStart bootstrap's
`claude plugin update` reports "√ Plugin updated from 1.0.133 to 1.0.159 **for scope
user**", leaving the project-scope pin, which is what the session binds, untouched. Every
tick is a fresh container off that same image, so the condition reproduced hourly and
could never self-heal. The channel record shows it: a `⚪ Paused` root on 2026-08-10,
escalated to `🔴 Blocked` on 2026-08-12, then eleven `↳ still failing` replies.

The developer's ruling, live: the harness binding is not something the loop may depend
on — a current copy of the plugin was present on the VM in every one of those failures.
This is the reasoning already recorded for `unbound_in_claude_session` (FB
`20260810070110`), finally applied to the axis it had been withheld from.

### 3-1. Stop making the harness plugin binding a precondition ([fff1540](https://github.com/qmu/workaholic/commit/fff1540))

Added `plugin-src.sh` (POSIX `sh`, `jq`-optional, 216 lines): four candidates, compared
by `sort -V` — the same comparator `check.sh` uses for its behind/ahead decision, so the
two scripts cannot disagree about which version is newer — with ties falling to the
checkout, the tree a developer can actually inspect. The registry candidate is read for
its `installPath` rather than its version number, because that tree is already downloaded:
no network is involved in the repair.

The gate was then demoted across `/drive` §1, `reference/survey.md` and the
failure-contract table, and `check-deps/SKILL.md` gained a *Resolving the source to run
from* section. `rules/general.md`'s bullet was rewritten from "an unbound skill surface is
not, by itself, a reason to stop" to "the harness's plugin binding is an input, never a
precondition", so both axes resolve identically. Both routine templates gained a bootstrap
preamble that reads `<src>/commands/<name>.md` when the command itself never bound;
`notify`'s precondition-stop class narrowed to `no_plugin_source`, the only stop left.
Finally, `session-start.sh`'s header — which recorded, wrongly, that the registry "carries
exactly ONE entry for the plugin" — was corrected, since that error is what kept the
diagnosis parked at "the image is behind".

## 6. Concerns

- **Merging this does not by itself unblock the fleet** (medium). A tick's `/implement`
  body comes from the *bound* plugin, so a container still binding an old build reads the
  old rule. The live routine prompts carry the fallback and are what actually break the
  loop — and `RemoteTrigger` is not exposed to a routine-fired session, so applying them
  is a developer act in the routines UI, or `/setup-routines` from an attended session.
- **A degraded run does not repair hooks** (low). PreToolUse guards and the
  UserPromptSubmit policy lens belong to whatever the harness bound: a degraded run keeps
  the older guards (`guards_present` reports whether they are registered at all) and must
  load `hooks/policy-index.md` from `src` explicitly. Stated in the skills rather than
  papered over.
- **The project-scope install is left alone** (low). The bootstrap cannot help the session
  it runs in, and every tick is a fresh container, so updating or removing that entry was
  judged out of scope — but it remains the mechanical origin of the outage and may deserve
  its own ask upstream (qmu/workaholic#380).

## 7. Successful Development Patterns

- **Read the evidence file, then distrust it.** `session-start.sh`'s header carried a
  careful, dated, measured analysis — and one of its facts had silently gone stale
  ("exactly ONE entry"). Re-measuring the claim rather than inheriting it is what moved
  the diagnosis from "the image is behind" to "the hook updates a scope nobody binds".
- **Ask what the gate was protecting, not whether it fired correctly.** The gate was
  detecting its condition perfectly; it was the remedy that was wrong. Naming the protected
  property (the scripts actually run are current) made the replacement obvious and provable.
