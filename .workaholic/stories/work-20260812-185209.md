## 1. Overview

`/catch` could not render a report at all on a repository with a large ticket corpus:
`scan-window.sh` handed the whole serialized tickets array to `jq` as a single argument and
Linux caps one argv entry at 128 KiB, so the scan aborted with `Argument list too long` and
emitted nothing. The two values that grow with the corpus now travel by file.

**Highlights:**

1. Reproduced at 900 ticket files (217,691-byte tickets array) and localized to `MAX_ARG_STRLEN`, not total `ARG_MAX`.
2. `$TICKETS` and `$MLIST` go through a private `mktemp -d` read with `--slurpfile`; the `jq` filter body is byte-identical.
3. The envelope diffs byte-identical on a corpus that already worked, and no temp directory survives success, a mid-run abort, or a signal.

## 2. Motivation

The failure mode was total rather than degraded: non-zero exit with empty stdout, so
`/catch` had nothing to render — permanently broken on exactly the mature repositories it is
most useful for. Reported at qmu/workaholic#387 against a ~1,600-file corpus; this
repository is already near 740 ticket files, so the ceiling was on the near path here too.

The distinction that decided the fix is one the report asserted and this work verified:
`ARG_MAX` here is 2 MiB and nowhere near exhausted, while `MAX_ARG_STRLEN` — 32 pages,
131,072 bytes — caps a *single* argument. A 130 KiB lone argument fails `E2BIG` while
400 KiB spread over 400 arguments succeeds, so neither raising a limit nor splitting the
call would have helped; only removing the value from argv does.

## 3. Changes

### 3-1. Pass scan-window's large JSON through files, not argv ([b1d36e75](https://github.com/qmu/workaholic/commit/b1d36e75))

A private `mktemp -d` with `trap` on `EXIT`/`INT`/`TERM`/`HUP` holds the mission list and
the tickets array, which `jq` reads with `--slurpfile`. Two `as` bindings unwrap the array
`--slurpfile` returns so the filter body below them is unchanged, and every other `jq` call
in the script was audited and classified rather than assumed safe.

## 4. Outcome

A 900-file corpus now completes with all eight envelope keys and the mission join computed,
where it previously produced nothing. The audit corrected the report on one point: `$MLIST`
is not a bounded scalar either — roughly 300 bytes per mission — so it moved to a file too,
well before it could reach the ceiling.

## 5. Concerns

### Corpus growth itself is unaddressed

- **Severity:** low
- **Description:** The fix is a transport change; the scan still walks and serializes every ticket file, so the cost grows linearly with the corpus (see [b1d36e75](https://github.com/qmu/workaholic/commit/b1d36e75) in `plugins/workaholic/skills/catch/scripts/scan-window.sh`). The ticket scoped this out deliberately.
- **How to Fix:** If `/catch` becomes slow rather than broken at several times today's corpus, that is a separate observation for the feedback stream — window-scoping the ticket walk would be the place to start.

## 6. Successful Development Patterns

- Proving the limit with a direct experiment — one 130 KiB argument versus 400 KiB spread over 400 arguments — turned an inherited diagnosis into a measured one and ruled out the tempting "split the call" fix in a single step.
- Sizing the test fixture from `MAX_ARG_STRLEN` rather than a file count, and asserting the fixture crosses the ceiling before asserting the scan survives it, keeps the pin honest as the real corpus grows.
