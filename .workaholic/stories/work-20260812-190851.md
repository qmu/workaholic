## 1. Overview

The last four workflow scripts reaching GitHub through GraphQL-backed `gh` subcommands
now go through the one REST transport, and a hermetic check makes the dependency
unable to return silently. This completes the mission at 3/3 acceptance.

**Highlights:**

1. Converted `report/create-or-update.sh`, `mission/list-related-prs.sh`, `feedback/open-issue.sh` and `branching/list-worktrees.sh` — the last of which no ticket named and only the sweep found.
2. `search/issues`, the obvious REST translation of the slug search, is **also** refused in a bound session; the query moved to a repository-scoped endpoint with local matching.
3. The suite now fails on any non-comment `gh issue|pr|repo <verb>`, with an empty allowlist and a planted violation proving the check bites.

## 2. Motivation

The mission exists because a Claude Code Web session is not guaranteed to serve the
GraphQL surface those subcommands are built on — measured 2026-08-12 17:19 UTC, when this
repository's own `[Propose]` tick pushed its branch and then could not open the pull
request. Its first two tickets converted discovery and publishing. This one closes the
loop the other two opened: with four call sites left, the same stop simply moves to
`/report`, `/mission` and `/fb`'s crossing.

The closing argument for the check rather than another list is that the list was already
wrong. The mission enumerated seven scripts across five skills; the sweep this ticket
mandated found an eighth, `branching/scripts/list-worktrees.sh`, whose `has_pr` result
routes `/report`'s worktree context. A list of call sites goes stale silently. A check
does not.

## 3. Changes

### 3-1. Cover the remaining gh readers and pin the dependency ([32767de1](https://github.com/qmu/workaholic/commit/32767de1))

Four scripts converted to `gather/scripts/gh-rest.sh`, the regression check added to the

## 4. Outcome

Every workflow script now reaches GitHub through one always-available transport, and the
mission's third acceptance item — a suite that fails if the dependency returns — is met.
The measured proof is the live comparison in this very session: the converted
`list-related-prs.sh` reports `available: true` against this repository while the previous
version reports `available: false`, in the same restricted session, on the same data.

## 5. Concerns

### The slug match now reads one page instead of paginating

- **Severity:** low
- **Description:** `list-related-prs.sh` reads `per_page=100` of open pull requests and matches locally, where the server-side search paginated over all of them (see [32767de1](https://github.com/qmu/workaholic/commit/32767de1) in `plugins/workaholic/skills/mission/scripts/list-related-prs.sh`). A repository with more than 100 open PRs would see only the newest.
- **How to Fix:** Follow the `Link: rel="next"` header if a repository ever runs that many open PRs; the script states the bound rather than hiding it, so the symptom would be a missed duplicate-work warning rather than a wrong answer.

### The GraphQL check strips full-line comments only

- **Severity:** low
- **Description:** `testNoGraphqlGhCalls` would flag a subcommand named inside a string literal or a trailing comment (see [32767de1](https://github.com/qmu/workaholic/commit/32767de1) in `scripts/test-workflow-scripts.mjs`). `ship/scripts/publish-release.sh` already holds such a string for `gh release`, which is why that family is out of scope rather than allowlisted.
- **How to Fix:** Nothing pre-emptively — a false positive fails loudly and has a documented escape. The allowlist must stay empty; if it grows to hold most call sites the check has become theatre and should be reconsidered rather than extended.

## 6. Successful Development Patterns

- Measuring the obvious translation against the live session *before* adopting it caught that `search/issues` is refused one layer further out than GraphQL — the mission's own premise sentence ("REST answers in both") turned out to be narrower than written, and only an actual call could have shown that.
- Writing the check so it plants a violation next to a comment naming the same command proves both halves at once: that the rule bites, and that it does not fire on prose.
