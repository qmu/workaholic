## 1. Overview

`/setup-routines` now has one job — configure the routines — and one named failure mode. It attempts the configuration every time; when the session can reach no account routine it reports `no_transport: RemoteTrigger-family tool` and renders the copy-paste sheet as that refusal's recovery path, instead of falling through to sheet-rendering as an ordinary outcome.

**Highlights:**

1. The contract no longer reads as two equal branches keyed on tool detection.
2. The absence of a second transport is measured and written down, so the refusal is honest.
3. A session that does configure the routines states that as its job, never as luck.

## 2. Motivation

A developer ran the command in another repository and the session announced its own success as an accident — "a tool happened to be available, so I registered them instead of printing the sheet" (issue #408). Nothing misbehaved: both paths did the right thing. What produced that narration was the contract's shape, which led with detection and gave the sheet equal standing, so the session reported the structure it had been given.

The earlier instruction (FB `20260810214929`) had asked for direct-apply, and direct-apply landed — as a branch. This closes the gap between what was asked for and what the text says the command is.

## 3. Changes

### 3-1. Make /setup-routines always try to configure ([370c4cf8](https://github.com/qmu/workaholic/commit/370c4cf8))

Diagnosed before designing: the ticket demanded evidence about whether a tool-less session has any other transport, and the answer is no — no `RemoteTrigger`-family tool on this session's surface, the `CronCreate` family documented as session-only and in-memory (it cannot touch an account routine), no routine subcommand on the `claude` CLI, and no routines-API credential. So the fix is the contract, not a new mechanism: attempt, converge, or refuse by name with the sheet as the recovery path — mirrored in the command description, `workaholify/SKILL.md` §5, `reference/routines.md` and `CLAUDE.md`'s row.

## 4. Outcome

The command's purpose is now contingent on nothing; only its reachability is, and that is reported as a refusal with the thing it looked for named. The setup sheet is unchanged byte for byte — what changed is that a developer receiving one knows a repair is being handed to them.

## 5. Concerns

### The refusal path cannot be exercised from the class that can configure

- **Severity:** low
- **Description:** The measurement behind `no_transport` was taken in the routine-fired class, which is precisely the class that can never take the success path (see [370c4cf8](https://github.com/qmu/workaholic/commit/370c4cf8) in `plugins/workaholic/skills/workaholify/SKILL.md`). The converge path's wording is reasoned, not observed.
- **How to Fix:** Next interactive `/setup-routines` run, check that the report reads as configuration rather than as a lucky branch, and correct the wording from that observation.

## 6. Successful Development Patterns

- A capability probe should name a refusal, not select between outcomes of equal standing — otherwise the session narrates the structure it was given, which is how a success comes to be reported as luck.
- `CronCreate` is a permanent near-miss for this question (right name, right cron syntax, wrong scope), so its exclusion is kept written next to the transport rule rather than re-derived by each session that searches "cron".
