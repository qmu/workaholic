## 1. Overview

`loop-drill.sh verify-propose` reported `fail` on a proposal stage that had actually passed: its ticket lookup only ever described the loose-ticket shape, so a mission-shaped proposal read as a missing ticket. The verifier now follows record → `mission.feedback` → `ticket.mission`, names the shape it found, and treats a record-alone proposal as a judgment rather than an absence.

**Highlights:**

1. `verify-propose 406` goes from `fail` (2 false rows) to `pass` against the real base.
2. A second defect surfaced during the reproduction: the assignee row demanded a GitHub login where the artifact carries a git email.
3. Four hermetic scenarios pin all three proposal shapes and the identity bridge.

## 2. Motivation

A drill that reports red on a green run teaches the operator to ignore red — which is the failure mode the script's own `pending`-vs-`fail` rule already argues against, applied here to its own row set rather than to a colleague's claim. The first live run of the freshly delivered drill hit it immediately, on the mission-shaped PR #407.

## 3. Changes

### 3-1. Teach verify-propose the mission-shaped proposal ([1c9bcdc5](https://github.com/qmu/workaholic/commit/1c9bcdc5))

Localization confirmed the single `main_grep ".workaholic/tickets" "$stem"` lookup as the whole cause — every other row passed on the failing run. The mission hops are anchored to the line-leading frontmatter keys and read off the base through the same readers, the loose lookup is byte-identical so it cannot regress, and `proposal_form` reports which shape was found without grading it. Fixing the mission hop then exposed the assignee row comparing an issue's GitHub login against a ticket carrying the git email `.claude/git-identities` maps it to; either spelling now satisfies it.

## 4. Outcome

The drill agrees with reality on all three sanctioned proposal shapes, and the one shape that stays load-bearing and red — a mission naming the record with no ticket carrying its relation — is a real defect, since a mission is not a mission under two tickets.

## 5. Concerns

### A record-alone proposal can no longer fail the propose stage

- **Severity:** low
- **Description:** Making `ticket_feedback_ref` advisory when nothing names the record means a run that *should* have emitted a ticket and didn't now passes the drill (see [1c9bcdc5](https://github.com/qmu/workaholic/commit/1c9bcdc5) in `scripts/e2e/loop-drill.sh`). The trade was taken deliberately: the drill can see the form emitted, never the form the ask warranted.
- **How to Fix:** If a real run is ever seen dropping a warranted ticket, add a seeded-ask variant to the drill whose expected form is known from the seed, rather than grading the general case.

## 6. Successful Development Patterns

- Reproducing before designing paid twice here: the before-state JSON both confirmed the stated cause and, once fixed, surfaced the assignee defect that was hiding behind the first failing row.
- Identity has two spellings in this repository — GitHub logins on issues, git emails on artifacts — and `.claude/git-identities` is the only bridge. Any check comparing an issue field with an artifact field has to cross it.
