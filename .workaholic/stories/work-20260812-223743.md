## 1. Overview

`plugin-src.sh` resolved the tree a run executes *before* `sync-main.sh` moved the working
tree, and broke a version tie toward the checkout — the one candidate the freshen can change.
It now decides on two axes: newest version wins, an equal version goes to the immutable one.

**Highlights:**

1. Reproduced before the fix: the same `src` path returned different content across the tree move while the run still reported version 1.0.5.
2. Immutability is read off the path — a candidate is immutable when its own basename is the version it carries — so a bound checkout is correctly called mutable.
3. New `src_immutable` and per-candidate `immutable` fields; the newest-wins rule is untouched on the version axis.

## 2. Motivation

The failure is silent and self-concealing: the run keeps using the path it resolved, so a
reverted tree means every later script comes from a different build than the report names.
Measured 2026-08-12T22:24Z — a tick resolved the checkout at 1.0.172, then reached a
surveyable state by checking out a container image's stale baked `main`; the source reverted
200 commits to a `sync-main.sh` answering `diverged`, which the caller reads as `pending`.

`plugin-src.sh` is itself the answer to the previous instance of this class. Its header
justified the checkout tie-break as "the tip by construction after the run's own freshen" —
true only *after* the freshen, and the resolver runs before it.

## 3. Changes

### 3-1. Pin the plugin source across the freshen step ([41c9d51e](https://github.com/qmu/workaholic/commit/41c9d51e))

Added stability as the second tie-break axis in `plugin-src.sh`, emitted `src_immutable` and
`candidates[].immutable` so callers read the property instead of re-deriving it, and stated
the ordering rule once in `check-deps/SKILL.md` with `drive/SKILL.md` §1, `rules/general.md`
and `CLAUDE.md` pointing at it.

## 4. Outcome

An unattended run that resolves its source at step 0 now keeps executing that same code
through the freshen and every step after it, and can prove it from one field. Five hermetic
gates hold both axes.

## 5. Concerns

### The complementary re-resolve is documented, not implemented

- **Severity:** low
- **Description:** The tie-break protects a caller that resolves once at the top of a run; a caller that resolves a mutable source and holds it across a later tree move is still exposed, and only the prose rule stops it (see [41c9d51e](https://github.com/qmu/workaholic/commit/41c9d51e) in `plugins/workaholic/skills/check-deps/SKILL.md`)
- **How to Fix:** Have `/drive` §1 re-resolve after `sync-main.sh` when the first resolution reported `src_immutable: false`, so the ordering rule is enforced by code rather than by reading.

### The ticket cites a policy file that does not exist

- **Severity:** low
- **Description:** The ticket's `## Policies` names `workaholic:operation` / `policies/observability.md`; the operation pillar ships `ai-production-investigation.md`, `ci-cd.md` and `no-customer-support-in-repo.md` (see [41c9d51e](https://github.com/qmu/workaholic/commit/41c9d51e) in `.workaholic/tickets/archive/work-20260812-223743/20260812223046-pin-the-plugin-source-across-the-freshen-step.md`)

## 6. Successful Development Patterns

- Reproducing the defect in a throwaway repo *before* editing paid for itself twice: it proved the tie-break was the cause rather than the ordering alone, and the same probe re-run after the change was the acceptance evidence.
- Deriving immutability from the path shape rather than the source name caught a case a source-kind rule gets wrong — a developer who binds `${CLAUDE_PLUGIN_ROOT}` to a working tree.
