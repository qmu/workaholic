## 1. Overview

`/fullfill` becomes `/prepare-release`, and the repository routine that runs it hourly becomes
`[Prepare Release]`, posting `📦 Prepare release`. Behaviour did not move — the command is still
a pure reader — but the routine record moved this time, so the rename ships with the one-time
cutover instruction an operator must perform by hand.

**Highlights:**

1. Both surfaces renamed: the routine record **and** the notification heading the ask described.
2. The reason the heading was held back on 2026-08-17 turned out to be false, and both canonical
   files now say so rather than carrying a corrected claim silently.
3. `renamed_from:` carries the cutover into the setup sheet and the convergence report
   mechanically, and is designed to be deleted once the fleet has cut over.

## 2. Motivation

Issue #485 asks for a name that says what the command does — preparing a release — rather than
one optimized for a single word, and for the routine heading to follow it. That is an explicit
reversal of the naming preference that produced `/fullfill` a day earlier, and the ticket was
written as a reversal rather than a fresh idea.

The previous rename (2026-08-17, PR #484) deliberately left the routine record named
`[Release Status]`, recording the mechanical cost as its Open Decision 2: convergence matches an
account's routines by name, so renaming the record creates a duplicate rather than renaming the
operator's. That cost has not gone away — the ask overrides the decision, not the mechanics — so
this change had to carry the cutover instruction with it instead of instead of it.

## 3. Changes

### 3-1. Rename fullfill to prepare-release ([57b6d742](https://github.com/qmu/workaholic/commit/57b6d742))

Renamed the command file, the routine template (`id`, `name`, filename), and every prose
reference across skills, runbooks, `CLAUDE.md` and `README.md`; renamed the post root to
`📦 Prepare release`; and added the `renamed_from:` field that carries the duplicate-routine
cutover into `/setup-repo-routines`' report and its rendered setup sheet.

## 4. Outcome

`/prepare-release` is the command's only name and no `fullfill` hit survives outside
`.workaholic/`. The routine is `[Prepare Release] {repo_name}` with `id: prepare-release`, still
`scope: repository`, still `45 * * * *`, still carrying no `Write`/`Edit`. Two new assertions
pin the cutover on both the sheet and the report path, and both assert nothing once the field is
deleted.

## 5. Concerns

### check-version-bump reads a stale local main

- **Severity:** moderate
- **Description:** `check-version-bump.sh` runs `git log main..HEAD`, reading the **local** `main`
  ref; in this claim worktree local `main` stood 200+ commits behind `origin/main`, so it returned
  `already_bumped: true` on a branch carrying no bump (see [52f03590](https://github.com/qmu/workaholic/commit/52f03590) in `plugins/workaholic/skills/branching/scripts/check-version-bump.sh`)
- **How to Fix:** Ticket `20260818065258-check-version-bump-reads-a-stale-local-main` is queued —
  resolve the base as `origin/main` and report an unresolvable base by name rather than answering
  `already_bumped: true`

### The cutover cannot be verified from here

- **Severity:** moderate
- **Description:** A routine is an account-level record no other account can list, so nothing in
  the plugin can tell whether an operator renamed `[Release Status]` or let convergence create a
  second one firing hourly beside it (see [57b6d742](https://github.com/qmu/workaholic/commit/57b6d742) in `plugins/workaholic/skills/workaholify/routines/prepare-release.md`)
- **How to Fix:** No product fix exists; the instruction is stated on both paths. Delete
  `renamed_from:` from the template once the fleet has cut over

### Second rename of the same command in two days

- **Severity:** low
- **Description:** `/release-status` → `/fullfill` → `/prepare-release`, and the cost of each is
  paid by every operator with the routine configured (see [57b6d742](https://github.com/qmu/workaholic/commit/57b6d742) in `plugins/workaholic/commands/prepare-release.md`)
- **How to Fix:** Nothing to fix in code; recorded as a fact rather than smoothed over, and the
  one-word convention that drove the first rename is now retired outright

## 6. Successful Development Patterns

- Re-deriving a recorded cost before honouring it caught one that was simply untrue — the
  "renaming the heading posts a duplicate" claim lived in a routine template while both canonical
  files named a different dedup key, and a cost recorded in the wrong file survives review by
  looking like a measurement.
- Carrying a migration instruction in a template field (`renamed_from:`) rather than in prose
  makes its deletion the same act as retiring the migration — the sheet note, the report line and
  the tests all disappear with the field.
