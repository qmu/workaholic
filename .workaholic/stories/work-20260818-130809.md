## 1. Overview

A draft release note's `## Key Changes` rendered `no branch story on the base` as a whole line for any merge without a story — and proposal merges, the commonest kind here, structurally never have one. The line now falls back to the merge commit's body, which is that pull request's own title.

**Highlights:**

1. The fallback is the merge **body**, not the subject the reporter proposed — the subject only restates what the placeholder already said.
2. The title is local git data, so no network read and `--enrich` stays off by default.
3. The Open Decision resolved as fallback-only: no reordering, no cap, no merge dropped.

## 2. Motivation

The section is a release note's one summary of what is shipping, so a line saying only "there is no summary here" spends a reader's attention and returns nothing. It was not a rare fallback: a `/propose` pull request is published through the publish tree and auto-merges without ever running `/report`, so it can never have a story, and those are the most frequent merges in this repository.

The reporter's causal account was checked before being built on, as the ticket required, and was wrong in a way that mattered: there is no cap and no selection: the renderer emits one line per merge in the whole range. So the defect was the placeholder's content, and the fix had nowhere else to hide.

## 3. Changes

### 3-1. Key Changes renders story-less merges as dead lines ([38f92422](https://github.com/qmu/workaholic/commit/38f92422))

The story-less arm now emits the merge commit body's first line — GitHub writes the pull request's title there — clamped to the same 160 characters the story sentence uses, with the number appended. A merge carrying neither a story nor a body still names itself rather than vanishing.

## 4. Outcome

Rendered over `v1.0.179..HEAD` before and after: 8 lines both times, placeholders down from 3 to 0, and every story-bearing line byte-identical. The renderer stays clock-free and idempotent, proved by comparing two renders of an unchanged base.

## 5. Concerns

### The story-bearing path truncates at a period inside backticks

- **Severity:** moderate
- **Description:** The Overview sentence split cuts at the first `.`, so a story opening with a backticked filename renders as `` - `check-version-bump. `` — an unclosed backtick that corrupts the markdown after it (see [38f92422](https://github.com/qmu/workaholic/commit/38f92422) in `plugins/workaholic/skills/ship/scripts/draft-release-note.sh`).
- **How to Fix:** Ticket `20260818131500-key-changes-cuts-a-story-sentence-at-a-period-inside-backticks` is queued; it proposes requiring whitespace after the period before reaching for backtick-aware parsing.

### The 160-character clamp is now written twice

- **Description:** The story path clamps through a `sed`/`awk` pipeline and the new fallback clamps inside its record-splitting `awk`, so one rule lives in two places and could drift (see [38f92422](https://github.com/qmu/workaholic/commit/38f92422) in `plugins/workaholic/skills/ship/scripts/draft-release-note.sh`).
- **Severity:** low
- **How to Fix:** Fold both into one clamp when the backtick ticket above rewrites the sentence split, which touches the same pipeline.

## 6. Successful Development Patterns

- Checking the reporter's proposed fix against real data before adopting it turned out to be the whole ticket: the proposal and the defect were one `git log` apart, and adopting it unchecked would have shipped the same defect in new words.
