## 1. Overview

The hourly `[Prepare Release]` tick derived its unreleased-commit count from whatever git refs its
container happened to arrive with, and never fetched — so one unchanged repository could report
three different numbers under three different dedup keys. The reader now freshens those refs, names
the freshness when it cannot, and withholds a count it does not trust.

**Highlights:**

1. The reader freshens the base branch and tags before reading them, and reports `refs: fresh|stale|skipped`.
2. A collapsed boundary is reported `doubtful`, redacted out of the digest, and rendered without its count.
3. The Slack heading moved to `📦 Release Preparation`, and its shape pin now actually exists.

## 2. Motivation

PR #499 fixed the *writing* half of this by giving CI a defined checkout, and recorded the *reading*
half as a stated open limit. Measured on a clone shaped like the live container — no tags,
`origin/main` five days stale — one unchanged repository reported **2721** commits
(`full_history`), then **2950**, then the true **4** (`latest_tag:v1.0.185`) as refs were fetched.
The wrong number was the visible defect; the worse one was that the `deploy:<digest>` moved with it,
so the silence rule that keeps an unchanged repository quiet could post repeatedly instead.

The heading rename is a smaller ask landing in the same files: seeing the previous day's wording in
a live post, the developer ruled the heading should name the report, not repeat the command's verb.

## 3. Changes

### 3-1. Freshen or distrust the deploy status reader's refs ([c5dfedcd](https://github.com/qmu/workaholic/commit/c5dfedcd))

`report-deploy-status.sh` — the one entry the hourly tick reaches — now attempts one bounded
`git fetch --tags origin` before deriving the boundary, in the shape `workaholic:catch`'s window
scan already established here, and reports `refs`/`refs_reason`/`doubtful` so a degraded read is
never rendered as a healthy one. `read-deploy-state.sh` gained no network I/O.

### 3-2. Rename the tick's post heading to Release Preparation ([e9627ad4](https://github.com/qmu/workaholic/commit/e9627ad4))

The heading is now `📦 Release Preparation` in both places carrying the shape and the three
documents citing it, with the naming history extended rather than overwritten. The routine name,
the command, the `deploy:<digest>` token and both posting gates are untouched.

## 4. Outcome

The tick's number no longer depends on what its clone happened to fetch, and when it cannot know,
it says so rather than publishing a figure it has flagged. Two drill rows and a hermetic
multi-clone suite pin behaviour the existing single-container checks were unable to see.

## 5. Concerns

### The live routine prompts still carry the old post heading

- **Severity:** moderate
- **Description:** A routine is an account-level record no plugin change reaches, so each account keeps posting `📦 Prepare release` until its prompt is hand-edited (see [e9627ad4](https://github.com/qmu/workaholic/commit/e9627ad4) in `plugins/workaholic/skills/workaholify/routines/prepare-release.md`)
- **How to Fix:** Each account edits the heading line of its prompt's post block; harmless until then, since the dedup is on the token.

### A doubtful read still reports a count in its JSON while the post withholds it

- **Severity:** low
- **Description:** `unreleased_count` and `since` stay in the per-target JSON under `doubtful: true`; only the digest redacts them and only the line withholds them (see [c5dfedcd](https://github.com/qmu/workaholic/commit/c5dfedcd) in `plugins/workaholic/skills/ship/scripts/report-deploy-status.sh`)
- **How to Fix:** Deliberate — a machine consumer may want the untrusted figure beside its flag; revisit if a second consumer renders it without checking `doubtful`.

## 6. Successful Development Patterns

- Reproducing the defect on a purpose-built clone before changing anything gave the fix its
  acceptance test for free: the three ref states became the assertion that they converge.
- Asking what the digest is a hash *of*, rather than which fields moved, resolved the old base-sha
  exclusion and the new redaction from one principle — it hashes what the post claims.

## 8. Notes

The rename's acceptance (no file may contain the retired string) and its own step 4 (extend the
naming history) pulled opposite ways. The assertion was written against the post *shapes*, not the
files: a rename erasing its own record would be a documentation defect by this repo's own rule.
