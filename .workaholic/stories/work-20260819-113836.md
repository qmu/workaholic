## 1. Overview

`/workaholify` §5 now **converges** the account's routines instead of describing them, over every scope, and every convergence seam reports each routine's enabled state. The mission's third ticket — ruling on whether convergence can rename a live routine in place — is **not** in this branch: its gate requires a measurement against a live routine record, and this session class carries no transport that can reach one.

**Highlights:**

1. `/workaholify` is a fourth caller of the one convergence flow, and the only one that passes no scope filter — because it answers *is this repository prepared*, not *how many copies should exist*.
2. The converged field set is now stated in exactly one place; four command bodies defer to it instead of each carrying a copy.
3. A routine's enabled state is **reported and never converged** — an explicitly resolved Open Decision, not a silent choice.

## 2. Motivation

The 2026-08-14 ruling (issue #445) made `/workaholify` the preparation command rather than an audit, and three of its four subjects converge: §3 applies the `CLAUDE.md` gateway reference, §3a converges the `.workaholic/` layout, §4 applies the web bootstrap. §5 alone rendered setup sheets and stopped.

That gap had a measured cost. On 2026-08-19 an interactive run reported this repository prepared while **2 routines existed against 6 templates**, both disabled since 2026-08-12 and both carrying prompts from 2026-08-07 — with a `RemoteTrigger`-family tool exposed to that very session the whole time. The command was not blocked from converging; it simply never tried.

The second defect compounded it: no template declares an `enabled` field and convergence diffs six fields that do not include it, so a routine switched off is converged in every other field and left silently off. Both of this account's live routines were in exactly that state, and no report anywhere said so. A convergence reporting "no changes" about a dead routine is the same class of untrue-but-plausible report as the first defect.

## 3. Changes

### 3-1. Converge the routines from workaholify ([1838f87c](https://github.com/qmu/workaholic/commit/1838f87c))

`workaholic:workaholify` §5's convergence flow gains a fifth numbered step naming `/workaholify` as a fourth caller, running the four existing steps verbatim over `list-routine-templates.sh` with **no argument**. The scope omission is stated as a choice with its reason, not left to be inferred: the three setup commands answer a per-scope counting question, `/workaholify` answers a question about the repository that is not answerable about a subset. `commands/workaholify.md` §5 now attempts the configuration and renders the sheets only under the named `no_transport: RemoteTrigger-family tool` refusal. `CLAUDE.md`, `README.md` and `reference/routines.md` follow in the same commit.

Step 1 of the ticket confirmed the precondition before anything moved: `list-routine-templates.sh` with no argument returns all six templates across all three scopes, so no script signature had to change.

### 3-2. Report each routine's enabled state ([b6bc5ddd](https://github.com/qmu/workaholic/commit/b6bc5ddd))

SKILL.md §5 step 2 now carries the converged field set as a two-row table — *diffed and converged* (`name`, prompt, `model`, `cron_expression`, `autofix_on_pr_create`, `mcp`/connectors) versus *reported, never converged* (the enabled state) — and all four command bodies defer to it rather than restating the list. Adding a seventh field is now one edit instead of five, which is the drift the ticket's step 4 asked to close.

## 4. Outcome

A `/workaholify` run now leaves a repository prepared in all four respects, and report-only is reachable solely through a named refusal. A routine that is switched off reads as *converged but off* at every seam, so the state that made a dead fleet look healthy is legible. The `AskUserQuestion` count is unchanged at two: converging a routine to its own already-declared template fails the Recommended-label test, so §5 adds no confirmation.

The overlap the change creates is reported rather than designed away — a developer who runs `/workaholify` and then `/setup-dev-routines` converges the developer templates twice (idempotent), and a scope-agnostic run touches `user`-scoped records that are not this repository's.

## 5. Concerns

This run confirmed by probe that no `RemoteTrigger`-family tool is exposed (`CronCreate`/`CronList`/`CronDelete` are the session-only in-memory scheduler and cannot touch an account routine), so it verified the prose, the scripts and the `no_transport` path — never the convergence. - **How to Fix:** An interactive session carrying the tool runs `/workaholify` on this repository and confirms it lists, diffs and converges the account's routines, reporting each by name with its enabled state.

### The enabled field's real name and shape are not confirmed

- **Severity:** medium
- **Description:** Ticket `20260819103851`'s step 1 required establishing where `enabled` actually lives on a routine record before writing prose about it, confirmed by reading a live record back rather than by the absence of a 400 — the API silently drops unknown fields. That read needs the same absent transport. The shipped prose therefore instructs the read-back rather than naming a field this run could not see, which is the honest shape but leaves the field name unpinned.
- **How to Fix:** Read one live routine record through the transport, record the field's real name and shape, and pin it in SKILL.md §5 step 2's table.

## 6. Successful Development Patterns

- Confirming the ticket's stated precondition first (`list-routine-templates.sh` with no argument) meant the change was six prose edits and no script change — the ticket had already reasoned that all three scripts take an optional scope, and checking it turned that reasoning into a fact before any edit depended on it.
- Resolving the Open Decision by asking *which caller has the power to do damage* rather than *which answer is more consistent* made it decidable without the operator: the risk surface is `[Workaholic]`, an hourly unattended account-wide tick, and an unbounded invisible failure loses to a bounded legible one.
- Separating "no transport" from "a negative result" kept ticket 3 out of this branch. Its gate asks for a measurement against a live record; absence of transport is not a measurement that failed, and shipping either branch of its ruling would have asserted an answer nobody has.

## 7. Handoff

**Why this PR stays open:** every member ticket of this mission declared `verification_handoff:` at creation, so the unit takes the handoff route whatever its merge policy says. The declared reason:

> A `RemoteTrigger`-family tool over account routines — absent from the routine-fired session class, present interactively (the ask measured both).

**The measurement the first run made** (reproducing the record in `CLAUDE.md`): `ToolSearch` over that session's full tool surface returned no `RemoteTrigger`-family tool. `CronCreate`/`CronList`/`CronDelete` are the session-only, in-memory scheduler, unrelated to account routines.

**What a second, attended run added on 2026-08-20 — the transport was present, and half of ticket `20260819103855`'s step 1 is now answered against live records:**

- `ToolSearch` returned `RemoteTrigger` in an interactive session, confirming the "present interactively" half of the declared reason. The routine-fired half is unchanged.
- `RemoteTrigger list` read the account's five live routines. **Every one carries a stable `id` (`trig_…`) distinct from its rendered `name`** — so the premise's own blocker ("name-matching cannot identify a routine whose name is what changed") has an answer available to convergence: address the record by id, not by name.
- The API's own shape separates the two operations: `update` is `POST /v1/code/triggers/{trigger_id}` (partial, addressed by id), while `create` is `POST /v1/code/triggers` with no id. A POST to an existing record's id cannot mint a second record.
- **Unrelated but measured and worth recording**: the account holds no routine for this repository at all — all five name `osbrjp/coop-csnet`, and `[Workaholic]` renders with no repository, as its template intends. That is the "a repository the account never created a routine on is invisible" limit, observed live.

**What is still not answered, and why:** the empirical read-back — set `name` on a live record through `update` and confirm the rename landed with no duplicate. The attempt was made and **refused by this session's permission classifier**, not by absent transport:

> `RemoteTrigger update trig_019R3g1g2L2fcgRvpez2RvVv {"name": "[Workaholic] rename-probe"}` → `Permission for this action was denied by the Claude Code auto mode classifier. Reason: Blocked by classifier.`

The denial was not worked around. This is a **different blocker from the one this PR was opened with**: transport is present, write permission is not.
