# Close a mission the run can prove is finished

## Motivation

`archive.sh` already reached into the mission on every archived ticket — appending the
`ticket archived` changelog line and ticking the acceptance item that ticket satisfies. It was the
one place in the run that knew a mission had just moved, and it stopped one step short of knowing
it was finished. A fully-accepted mission with an empty queue then sat `active` until a human ran
`/mission-close`, and the survey went on listing it.

**Eleven such missions had accumulated and nobody was told.** They were found only because the
mission lens printed all of them on every prompt and the list had grown long enough to read as
wrong.

## Outcome

**The gate closes the one outcome that is arithmetic.** After ticking the item, `archive.sh`
computes a proof from readers that already exist — `progress.sh` for `checked == total` and
`unlinked == 0`, `queue-size.sh` for `todo == 0` — and calls `close.sh <slug> achieved` when it
holds. No partial credit; an unreadable reader is not a proof and leaves the mission alone; the
close and any refusal are reported by name, so a mission that could not be closed never reads as
one that was.

**The single-writer rule does not move.** The run calls `close.sh`, never a status, and only ever
passes `achieved` — `abandoned` and `carried` assert something about *intent*, and a run that just
merged its own work is a poor judge of which applies.

**The residue is reported.** `/moderate` gained step 12, `closable-missions`: every active mission
at full acceptance with an empty queue, named with its `checked/total`. It **never closes one** —
two writers of an end state is what the single-writer rule exists to prevent.

The change proved itself on the way out: archiving this mission's own last ticket closed this
mission, `status: achieved`.

## Journey

**The measured objection had to be answered, not stepped around.** `plan-units.sh` carried the
note that of four missions closed by hand on 2026-08-04, one turned out not to be achieved at all,
so an automated close would have recorded it wrongly. That objection is about **judgment**, and
this proof makes none: it does not ask whether the work was good, only whether every acceptance
item is ticked, none is unlinked, and nothing is queued. The 2026-08-04 mission would have failed
it. That comment was rewritten in the same commit rather than left overstating a rule it now
shares.

**The report's composition changed mid-drive because its own test refused the first one.** Reading
the survey's `queue_drained` exclusion was the obvious move and is exactly the candidate set — but
the test caught the report leaving a modified mission in the index: `plan-units.sh` runs the living
migrations and stages what they change. A step whose contract is *writes nothing* may not reach it
through something that writes, so the set is composed from three pure readers instead.

**Two existing tests failed and were corrected, not suppressed.** Both fixtures were
single-acceptance missions that the archive completes, so closing them was the new behaviour
working. Each gained a second, unmet item to stay mid-mission, because each test is about something
else and a fixture that closed would stop testing it.

## Concerns

**One exception to "writes nothing" survives and is stated on the step itself**: on a
non-conformant tree — a mission outside `active/`/`archive/`, or one carrying a legacy `status:` —
the mission readers' living migration converges it and stages the change, as any other
mission-script touch does. That is the migration's contract rather than this step's behaviour, and
on a converged repository the index is left byte-identical. It is named because a reader that
silently enlarged a caller's commit is a defect this project has measured once already.

**The gate only fires when a run archives a ticket.** A mission finished any other way is caught by
the report, not the gate — that split is deliberate and is why both tickets shipped together, but it
means the report is load-bearing rather than a nicety.

## Successful Development Patterns

- **Separate the arithmetic from the judgment.** "Nothing may close a mission" was one rule
  covering three outcomes; only two of them needed it.
- **Answer the note that argues against you, in the file that carries it.** The 2026-08-04 comment
  was right about what it was about, and leaving it unedited would have left the repository holding
  two contradictory rules.
- **Let the test refuse the design.** The first composition was reasonable and wrong, and nothing
  but the "writes nothing" assertion would have caught it.
