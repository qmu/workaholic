# Say what happened, not what the tick counted

## Motivation

Each `🔎 Moderation` root line was a step's own **log** summary, rendered verbatim. Those summaries
were written for the tick log — the audit trail a maintainer reads when diagnosing the tick — and
they read like one:

```
inbound-sweep: GitHub read since <ts>: 1 updated, 0 already captured, 1 to judge; slack/gmail/drive left for the agent to probe
doc-drift: no new documentation drift since <sha> (0 finding(s) already filed by an earlier tick)
```

Of that, the repository events are "one new ask arrived" and **nothing at all**. `1 to judge`,
`0 already captured`, `0 finding(s) already filed by an earlier tick` are counters that exist only
inside the tick — and the second line reports that nothing happened while the change diff renders
it as a change.

The audit trail is not the wrong artifact. It is the wrong audience.

## Outcome

Each step now supplies **`event`** beside `summary`: the post-facing phrase, naming what happened
to the repository. `run.sh` carries it through, `render-tick-post.sh` renders it, and the log's
summaries are untouched.

**A step with no event renders no line and is not counted** — the independent guard, so a
nothing-happened step cannot reach the root even if a regression in the diff calls it changed.
Counting without rendering would have been its own defect: a header reading `2 change(s)` above one
line.

Measured on this repository's own tick after the change: four lines, each a repository fact
(`1 new inbound ask(s) arrived on GitHub`, `5 claimed unit(s) have not moved for a day or more`,
`2 mission(s) are finished and still open`, `1 direction(s) will not arrive by their date at this
pace`), and six steps rendering nothing because nothing happened in them.

## Journey

**The field went on the step, not on the renderer**, which is the preference the ticket states and
the reason it gives: the step knows what its finding means. A projection in the renderer would have
to re-derive each step's meaning from its prose — the free-text dependency this skill has already
been bitten by twice (the already-asked gate matching a summary, the change diff comparing an
embedded timestamp).

**The diff still reads `summary`.** That is what tells this hour from the last one and it is the
richer signal; diffing the event would hide a real change behind a phrase that happens to be worded
the same.

**Five existing tests failed and were corrected rather than suppressed** — their fixtures carried
only `summary`, so under the new rule they rendered nothing, which is the change working. The
fixture builder now supplies both, and a new case pins the empty-event guard directly.

## Concerns

**A step added later, with no event, is silent on the root.** That is the safe failure — it cannot
put a counter in front of a person — but it is silent, not loud, so a new step's author has to know
to write one. The suite pins the thirteen steps that exist; it cannot pin the fourteenth.

**The events are prose and will drift from what the step actually measures.** They live beside the
summary in the same emitter, which is the closest the two can be kept, but nothing checks that they
agree.

**Only the two "something happened" emitters of the four inline steps gained an event.** The calm
and degraded branches of every step deliberately have none — correct today, and it means a
degradation is visible only in the log, which is the same trade the mission's second ticket already
made for changes with no question attached.

## Successful Development Patterns

- **Separate the audiences instead of rewriting for the louder one.** Shortening the log summaries
  would have cost the audit trail that was the only place the truth lived.
- **Guard the property twice when one guard is a derivation.** The diff decides what changed; the
  empty event decides what is worth saying — a regression in either cannot resurrect the defect.
- **Let the failing fixtures tell you the change landed.** Five tests broke in exactly the way the
  new rule predicts, which was the cheapest confirmation available.
