## 1. Overview

Both inbound readers resolved the unset `WORKAHOLIC_INBOUND_SLACK_CHANNEL` to `<repo_name>` —
`workaholic` — a channel this workspace does not have, so the inbound path was dark and quiet
by construction. This aims both at the channel that exists and makes the next such divergence
visible.

**Highlights:**

1. The variable is set to `dev-workaholic` here; the default derivation is untouched.
2. *Could not read the channel* is its own named outcome, never a claim of absence.
3. It reaches a person through the tick's existing keyed question, quiet when unchanged.

## 2. Motivation

A private-inclusive channel search returns exactly one channel for this repository — the
private `#dev-workaholic` — and no `#workaholic`. So the writer found its thread by exact
string and succeeded, while the `:40` sweep and the tick's `unanswered-asks` step were aimed
at nothing. Both reported their reason honestly *inside* the tick, but neither fact reached a
person, so from outside a dark inbound path and a calm hour were indistinguishable — which is
why this ran for a day before a tick happened to name it.

## 3. Changes

### 3-1. Name the channel the routines post to ([e1cf3acc](https://github.com/qmu/workaholic/commit/e1cf3acc))

Sets `WORKAHOLIC_INBOUND_SLACK_CHANNEL` to `dev-workaholic` in this repository's own
`.claude/settings.json` `env` block and reconciles every document that states the default, so
the unchanged default and this repository's setting are readable together.

### 3-2. Tell an unresolvable channel from an empty one ([dc33b0cc](https://github.com/qmu/workaholic/commit/dc33b0cc))

Names three outcomes apart in `unanswered-asks`' contract — `asks_found`, `window_empty`,
`channel_unreadable` — routes the last through `ask-question.sh` on
`inbound-channel-unreadable:<channel>`, and puts the resolved channel name in the report.

## 4. Outcome

A question written in this repository's channel now reaches a reader that is pointed at it,
and the *next* divergence is visible rather than silent: the resolved channel rides both
readers' reports, and a channel that could not be read asks a person once instead of
rendering as a quiet hour.

## 5. Concerns

### The templates still do not name the channel, and the API's environment shape is unestablished

- **Severity:** moderate
- **Description:** The first ticket asked for the setting to live in the two routine templates; a prompt may not carry a repository name (P7) and the routines API silently drops unknown fields, so a frontmatter field could not be verified from a clock-fired container (see [e1cf3acc](https://github.com/qmu/workaholic/commit/e1cf3acc) in `plugins/workaholic/skills/workaholify/routines/`)
- **How to Fix:** `20260829093500-say-where-a-routines-environment-lives.md` was minted for it and is queued on this mission; it needs an interactive session holding a `RemoteTrigger`-family tool to write and read back.

### An unreadable channel is asked about once per channel, ever

- **Severity:** low
- **Description:** The escalation key names the channel, so a channel that breaks, is fixed and breaks again is not re-asked (see [dc33b0cc](https://github.com/qmu/workaholic/commit/dc33b0cc) in `plugins/workaholic/skills/moderate/scripts/step-unanswered-asks.sh`)
- **How to Fix:** Accepted — it is the property `base-red:<commit>` and `stalled-unit:<unit>` already carry, and it is what makes the route quiet by construction rather than by a suppression list. Widen the key only with a measured repeat.

## 6. Successful Development Patterns

- Checking a mechanism with `printenv` before relying on it turned "settings `env` probably
  reaches the scripts" into a measured fact — and revealed that it is read at **session
  start**, so a mid-session edit takes effect from the next container.
- Refusing to write an unverifiable frontmatter field, and minting a ticket for the
  measurement instead, kept a template from reading as configured over a routine that is not.
