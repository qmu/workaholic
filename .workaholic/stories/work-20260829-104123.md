## 1. Overview

A ticket minted mid-run three hours earlier asked where a per-repository value such as `WORKAHOLIC_INBOUND_SLACK_CHANNEL` may be declared, because two invariants collided and nothing stated the resolution. The answer turns out to be checkable without the transport the ticket assumed it needed: **a routine declares no environment variables at all — it selects a cloud environment, and the variables live on that record.**

**Highlights:**

1. The rule is stated once, in `workaholify/SKILL.md`, with the documentation that establishes it and an explicit limit on what it does not establish.
2. The ticket's own premise — that the sibling ticket about `job_config.ccr.environment_id` asks a *different* question — is disproved and recorded: that pointer is exactly where the variables live.
3. Four hermetic tests were failing before this branch, because the home this rule endorses leaks into the suite. Fixed at the suite level: 5024 passed / 4 failed → 5028 passed / 0 failed.

## 2. Motivation

`20260829062827` set the channel variable in this repository's own `.claude/settings.json` `env` block, because neither routine template has an environment block and no rule said where one would go. That left a documented refusal resting on an unknown: the routine-template frontmatter was ruled out because "the routines API silently drops unknown fields, so only a write-and-read-back proves an environment shape" — and no clock-fired container holds a `RemoteTrigger`-family tool to perform one. `CLAUDE.md` recorded establishing that shape as a separate queued ticket. This is that ticket, driven in exactly the container the refusal says cannot answer it.

## 3. Changes

### 3-1. Say where a routine's environment lives ([ae33d639](https://github.com/qmu/workaholic/commit/ae33d639))

The transport really is absent — a `ToolSearch` for `RemoteTrigger*` returns the session-only `CronCreate`/`CronList`/`CronDelete` family and nothing else. Rather than stop there, the question went to the product's own documentation, which the ticket's step 1 allowed for ("record the measured shape, **or** record the measured absence"). `routines`, *Select an environment*, lists what a routine is configured with — prompt, repositories, environment, connectors, triggers — and *Environments and network access* states it outright: "Each routine uses a cloud environment that controls network access, environment variables, and setup scripts." `cloud-environments` puts the variables on the environment as `.env` lines each session copies once at startup.

So there is **no per-routine field to read back**, which is why an absence was the only thing a read-back could ever have established here. The rule and its evidence live in `workaholify/SKILL.md`, *Where a routine's environment variables live*; `render-routine.sh` gained a pointer rather than a restatement; `CLAUDE.md`'s now-stale "separate queued ticket" clause is reconciled.

The decisive argument for the repository's own configuration is not preference but arithmetic: an environment is an **account-level** record shared by every routine that selects it, so a per-repository value set there would be set for every repository at once. P7 needs no exception — no prompt gains a repository name and no template gains a field.

### 3-2. The suite stops inheriting the home the rule endorses (same commit)

Every test spreads `process.env` into its throwaway repositories, so `WORKAHOLIC_INBOUND_SLACK_CHANNEL=dev-workaholic` silently overrode the default four assertions in `step-unanswered-asks.sh` exist to pin — they read `dev-workaholic` where the fixture's own remote says `source-repo`. Ambient `WORKAHOLIC_*` variables are now stripped once at suite startup, so every test controls its own, which is what the override assertions sitting beside the failures already did.

## 5. Concerns

### A queued ticket is scoped on the premise this branch disproves

- **Severity:** moderate
- **Description:** `20260821150359-state-the-environment-rule-and-its-named-refusal` was kept separate because the driving ticket held it to be "a different question — it is about `job_config.ccr.environment_id`, the runtime environment record, not about environment variables". They are the same question one indirection apart: that pointer names the record the variables live on. The ticket is owned by another identity and was not touched here.
- **How to Fix:** Re-scope or close it against `workaholify/SKILL.md`, *Where a routine's environment variables live* — what remains genuinely open there is the environment **id**'s own handling, not where variables live.

### The rule rests on documentation, not on a live record read-back

- **Severity:** low
- **Description:** This establishes the documented model. It does not establish the wire shape of a routine record, and the ticket's Gate ("no speculative field on an unverified shape") is satisfied by adding no field at all. The limit is stated inside the rule so it can be argued with rather than discovered.
- **How to Fix:** Nothing unless a per-routine environment key turns up in a live record; the standing read-back requirement then applies unchanged.

### Stripping ambient `WORKAHOLIC_*` could hide a test that meant to inherit one

- **Severity:** low
- **Description:** The strip is unconditional at startup. No current test relies on inheriting such a variable — the suite is 5028/0 — but a future test that set one in its parent process rather than on its own `run` would now see it disappear.
- **How to Fix:** Nothing; that is the intended direction. A test needing a value sets it on its own `run`, as the override assertions already do.

## 6. Successful Development Patterns

- "The transport is unreachable" and "the field does not exist" are different absences, and only the second answers a question about a field. Stopping at the first would have blocked a ticket whose answer was freely available; asserting the second *from* the first would have been the pre-declaration the ticket's own Considerations warned against.
- When a ticket names an instrument (`a write-and-read-back through a RemoteTrigger tool`), it is naming a means to an end. Reading the end — "record the measured shape, or record the measured absence" — is what let a container the ticket expected to fail answer it instead.
- A suite that spreads `process.env` is hermetic only until someone uses the configuration home the project itself recommends. Stripping the class once at startup beats a per-call-site exclusion every future test must remember.
