## 1. Overview

`/implement` mints a ticket when it meets a mid-run problem, and that ticket was written naming nothing at all — no `feedback:`, no `mission:`. The unit that later drove it therefore resolved `count: 0`, which leaves the notify lookup with no stem to search and no record to link, so a merge the loop performed on its own was announced to nobody. The mint now carries the minting unit's own resolved refs.

**Highlights:**

1. The carried field is `feedback:`, decided against `mission:` on the case that was actually measured: a mint from a **missionless batch**, which no mission hop can rescue.
2. The refs are emitted by `feedback/scripts/ask-feedback-line.sh` — that relation's one writer — and the test asserts the writer's exact output, so a hand-rolled line fails rather than drifting.
3. Carried **only** when the run can say the mint is about the same item. An unattributable mint carries nothing and its line stays unposted, because a wrong thread is worse than none.

## 2. Motivation

Measured twice within one hour, both times end to end. `batch-20260829093639` (PR #714) hit a resolver gap and minted `20260829102500-…`; that ticket became `batch-20260829102127` (PR #716), merged, and `unit-feedback-stems.sh` answered `count: 0` for it, so its finish line went unposted. The run that drove this ticket then reproduced it live: PR #718's unit was itself a ticket minted with no relation, and its finish line was unpostable for the same reason.

This is the other half of the gap #716 closed, not a repeat of it. #716 taught the resolver the `mission:` hop, so a ticket that *names* a mission reaches that mission's refs. A minted ticket names nothing, so no hop can help it — the refs must be written at minting time or they do not exist.

## 3. Changes

### 3-1. Carry the minting unit's refs onto a mint ([1fdf8514](https://github.com/qmu/workaholic/commit/1fdf8514))

The rule is stated where the mint is governed — the mint bullet in `drive/SKILL.md`'s failure contract, and the *An unqueued problem becomes a ticket* section of `drive/reference/failure-contract.md` — carrying the measurement, the field argument, and the attribution bound.

**Why `feedback:` and not `mission:` alone.** The mission hop already rescues a mint made while driving a mission unit. A batch with no mission has no hop to make, and that is the shape both measurements produced. `feedback:` is correct for both unit kinds and is the field `/specificate` already writes for this purpose; the existing `mission:` inheritance is untouched, so a mint with both carries both. The refs cost no new lookup — the minting unit resolved its own stems to post its own finish line, so they are in hand when the ticket is written.

**Where the enforcement comes from.** The mint is performed by the agent, not by a script, so nothing can mechanically compel the carry. Three checkable things stand in for that: the rule is written where the mint happens, the test pins that the contract text still names the field and its writer, and the resolver behaviour a correct mint depends on is asserted from a **missionless** fixture — which it had to be, or the assertion would have passed through #716's hop and proved nothing.

The rejected alternative is named as the ticket asked: teaching case 4 a record-less root shape is worse, because the routine prompt is the ceiling on what may be posted and a root that links nothing is the post the developer ruled unusable on 2026-08-22.

## 4. Outcome

A unit driving a minted ticket resolves a non-empty stem set and its merge lands in the thread its own item is already living in. `count: 0` stays a designed answer, exit 0, for an artifact that genuinely names nothing — including a mint the run could not attribute, which is the side this change deliberately took.

## 5. Concerns

### The carry is a prose contract, so a mint that drops it fails no gate

- **Severity:** moderate
- **Description:** Nothing executes at minting time, so a run that writes a mint without the refs produces a ticket that passes `validate-ticket.sh` and is silently unannounceable when driven. The change makes that visibly non-conformant and pins the rule text against deletion, but it cannot make it fail.
- **How to Fix:** If it recurs, the mechanical form is a floor at the write seam — `validate-ticket.sh` cannot ask "was this minted", so it would need the mint to go through a script that stamps the refs, which is a larger change than this ticket scoped.

### Two tickets in this run were themselves minted without refs

- **Severity:** low
- **Description:** `20260829110500` and this one were both minted before the rule existed, so both were driven as units with `count: 0` and neither merge was announced in a thread. The rule applies from here; nothing backfills them.
- **How to Fix:** Nothing. `/moderate`'s `thread-reconcile` step exists for threads whose last word is stale, and an item with no feedback record has no thread to reconcile — which is precisely the state this change stops creating.

## 6. Successful Development Patterns

- A fixture that can pass through an adjacent, already-working path proves nothing about the case at hand. Making the minted fixture missionless was the difference between asserting the repair and asserting #716 again.
- Where a contract has no script seam, the checkable substitutes are: state the rule where the act happens, pin the rule's own text in the suite, and assert the downstream behaviour a correct act depends on. That is weaker than a gate and much stronger than prose alone.
