## 1. Overview

A unit whose first ticket runs longer than the resume window lost its own claim by construction: `archive.sh` refreshes the branch tip for free, but only at the **end** of a ticket, so a unit that is one long ticket ran its whole implementation on the claim commit's own timestamp. The beat is now step 0 of every ticket rather than a ten-minute cadence an agent has to track while its attention is on the implementation.

**Highlights:**

1. The window that bit is the 30-minute `WORKAHOLIC_CLAIM_HEARTBEAT_STALE_MINUTES` resume gate, not the 24-hour reported staleness — measured, and neither default moved.
2. Both alternatives are refused with their reasons in the document itself, and a background timer is refused outright.
3. The prose is pinned: the suite proves the beat is what changes the answer, and that the workflow still opens with it.

## 2. Motivation

Measured on `batch-20260831141002`, a unit of exactly one ticket: claimed at 14:10:27, implementation and its hermetic rows finished around 14:55, and the push was rejected non-fast-forward because a second `[Implement]` tick had already resumed the claim at 14:43:13 — 33 minutes in, against a 30-minute window.

**No mechanism was broken, and that is the point.** `claim.sh resume` is correct, the window is correct, and the driving run was the non-conformant part. The losing run stood down rather than force-pushing over a branch another run was actively driving, so a complete, validated, locally-committed implementation was thrown away and the same ticket was re-driven from the top. What the failure exposed is that the one seam beating for free fires only when the work is already over.

## 3. Changes

### 3-1. Beat the heartbeat as step 0 of a ticket ([c0b66372](https://github.com/qmu/workaholic/commit/c0b66372))

The per-ticket workflow gains a step 0 that runs `heartbeat.sh <unit-id>` before the ticket is read, and `drive/SKILL.md` §4's *"roughly every ten minutes or once per ticket"* is replaced by that fixed point. A cadence is something an agent must track while working; a step is discharged where the workflow already stops. A beat inside an existing per-ticket seam is refused (the only one that runs early is a pure reader shared with other callers), making the loss visible instead is refused (a reading after the fact returns none of the work), and a background timer is refused outright as a second liveness authority beside the branch tip. No store, no cursor, no field on any artifact.

## 4. Outcome

A long ticket keeps its own claim, and the instruction sits where the workflow already pauses rather than in an agent's memory. The suite carries the behaviour — a claim aged past the window is resumable, and after one beat it is not, the beat being the only thing that changed between the two reads — plus a pin that the workflow still opens with the step and that the retired cadence has not survived.

## 5. Concerns

### A losing run still has no hand-over path

- **Severity:** moderate
- **Description:** when a run does lose its claim, its finished work is discarded — the rule forbidding a force-push over an actively-driven branch is right, and what it exposes is that the loser can only throw the work away (see [c0b66372](https://github.com/qmu/workaholic/commit/c0b66372) in `plugins/workaholic/skills/drive/reference/ticket-workflow.md`)
- **How to Fix:** its own ticket. This change makes the loss much rarer and does not make it recoverable; the two are different asks, and the ticket said so rather than folding a hand-over design into a mission about the beat

## 6. Successful Development Patterns

- The fix was applied to the run applying it: this ticket's own unit is one long ticket, so the run had to beat by hand before it could work — the strongest available evidence that step 0 belongs where it was put.
- Pinning prose by its **behaviour** as well as its text: the row proves a claim aged past the window becomes non-resumable after one beat, so a future refactor that keeps the words and loses the effect still fails.
