## 1. Overview

> **This branch must not be merged as it stands.** While it was being driven, a second run
> shipped the same mission's ask to `main` as **PR #789** (`5b642765`, *Take the moderation
> tick's log off `main`*). That implementation is complete, tested and landed. This branch is
> an independent implementation of the same eight tickets, and merging it would replace a
> landed design with a competing one — a decision no unattended run may make.
>
> It is opened, unmerged, so the work is visible, the claim is parked rather than left
> resumable, and a person can rule on the residue named in §5.

All eight tickets of `take-the-moderation-tick-s-log-off-main` were driven, gated and
archived: the tick log moves off `main` onto a dedicated ref, every reader resolves the log's
location through one script, the feedback records stay on the base, the persist count is
re-justified against its own objection, and two hermetic drills guard both halves.

**Highlights:**

1. The namespace was **measured, not inherited**: `refs/moderations/*`, `refs/claims/*` and
   `refs/notes/*` each answered `RPC failed; HTTP 403` on create in this container, so
   `refs/heads/` is the only namespace this can use — and the response is quoted in the ruling.
2. Dropping the publish tree from the log half made the byte-identical caller checkout a
   **structural** property: the commit is built with `GIT_INDEX_FILE` plumbing, touching no
   working tree, HEAD or index, so there is no `.publish/` an interrupted run can leave dirty.
3. Two drills shipped, and repairing a third: **`verify-blocked-tick`'s breaker had been
   passing for an unrelated reason since it shipped**, and `--only open-log` stops the steps
   rather than the run, so its first row was satisfied whether or not the mechanism under
   test existed. Both are fixed here.

## 2. Motivation

`main` is the development target's history and this log was its largest single author.
Measured over one calendar day on a consuming repository: 275 commits, 138 touching only
`.workaholic/`, 25 empty, 44 merge commits, and **five** touching the product. The log's
content was never in question — it is the tick's only memory across discarded containers —
only its home.

## 3. Changes

### 3-1. Rule which ref the tick log lives on

`workaholic:moderate` gains *Where the log lives, and why it is not `main`* as the
mechanism's one home: the ref (`refs/heads/workaholic/moderation-log`, an orphan history),
the measured 403 that forces its namespace, who creates it (the first tick that needs it, with
the `/workaholify` alternative refused on its failure mode), the exact bounded fetch a fresh
container runs, and what each of the two ref-walking mechanisms must say about it.

`guard-git-branch.sh` is deliberately **not** widened: it matches local branch-creation
surfaces, and the log ref is created by a push, which is not one. The suite pins that the
publisher reaches for no local-branch form instead.

### 3-2. Publish the tick log to its own ref

`persist-log.sh` publishes the day files to the ref and makes no commit to the base for the
log. The `(tick, step)` union, the bounded retry against a freshly fetched target and the
closed `status`/`reason` vocabulary are unchanged, with `log_ref_unreachable` added as its
own reason rather than folded into an existing one. Carrying **every** day file rather than
only the tick's own closes a day-boundary hole that was in the old behaviour.

### 3-3. Keep the tick's feedback records on the base

The seam splits. A feedback record is knowledge whose `feedback:` relation resolves it **by
its path on the base**, so it did not follow the log; the two halves report independently,
and a tick with no records opens no publish tree and commits nothing to the base at all.

### 3-4. Read the tick log through one reader

`log-read.sh` is the one resolver of the log's location. It unions the ref's copy with the
checkout's, **the checkout winning** per `(tick, step)`, and a ref it could not fetch answers
`log_ref_unreachable` with a **null** count — never an empty entry list, which would make
every dedup in the tick re-fire. Five direct walkers now compose it.

### 3-5. Rule on the history left on `main`

**This branch rules that the existing day files stay on `main`, read-only, and the area stays
registered** — settled by a mechanical fact rather than taste: `step-open-log.sh` refuses
`area_unregistered` without the allowlist entry, and `log-append.sh` still writes the checkout
copy, so de-listing would stop the tick logging at all. **PR #789 ruled the other way and
removed the history.** This is the clearest single point on which the two implementations
differ and is the first thing a person should look at.

### 3-6. Justify each persist the tick makes

All three persists are kept, each with a paragraph naming what it buys. Measured: ~120 ms per
carrying persist, ~62 ms for a no-op, two remote round-trips each, and **3 commits on the log
ref, 0 on `main`**. The objection was never three publishes; it was three commits a tick on
`main`, which the move answers rather than a drop.

### 3-7 / 3-8. Two drills

`verify-log-ref` (7 load-bearing rows) proves the log arrives where it should;
`verify-log-off-main` (5 rows) runs a **whole tick** and asserts from git that no commit it
added to the base touches the log area, while keeping the one legitimate base write — a
feedback record — passing. Both are `hermetic` **measured** rather than asserted: run twice
with `gh` shimmed to exit 127, no proxy and no API key, with identical row counts. Both carry
a breaker that was run and observed to fail its drill.

## 4. Concerns

- **The collision is the headline.** Two runs drove the same mission's ask concurrently. The
  ticket queue could not prevent it: PR #789 archived **no** ticket and touched **no** mission,
  so the claim protocol never saw a competing claim on this unit and `plan-units.sh` went on
  offering it. This is the documented claim-race shape one level up — at the level of the
  *ask* rather than the *unit* — and no mechanism in the loop currently reads it.
- **The two implementations differ on real decisions**, not only on wording: the ref's name
  (`workaholic/moderation-log` vs `workaholic-log`), how the ref's copy reaches a reader (a
  cache under the git directory, read by `log-read.sh`, vs hydration into the checkout by
  `step-open-log.sh`), and whether the historical day files stay on `main`. PR #789 also ships
  a migration this branch does not.
- **This branch conflicts with `main`** in seven files. The conflict is `content`, not
  mechanical, and resolving it means choosing between two designs — a person's call.

## 5. Residue a person must rule on

**The eight tickets are still queued on `main`.** PR #789 satisfied their ask without
archiving them, so `.workaholic/tickets/todo/20260831182058-*` (8 files) remain in the queue
on the base, and the mission stays `active` there. The next `/implement` tick will offer them
again and drive work that is already done. This run did not abandon or icebox them: the
failure contract forbids an unattended run from doing either.

The available resolutions, for the person ruling:

1. Close this pull request and archive or abandon the eight tickets against `main` directly,

2. Take specific pieces from this branch that PR #789 does not carry — most plausibly the

   independent of which log design wins.

## 6. Successful Development Patterns

- **Reproducing a constraint before designing against it.** The 403 probe took one command and
  removed a whole class of unimplementable design; citing `claims.md` alone would not have
  extended the finding to `refs/moderations/*` and `refs/notes/*`.
- **A breaker that stops breaking is a finding.** Repointing the log at a ref removed a
  relative-path dependency in the `verify-blocked-tick` fixture, and the breaker immediately
  stopped failing — exposing that it had never been testing what it claimed. The register's
  own premise, landing on a live row.
