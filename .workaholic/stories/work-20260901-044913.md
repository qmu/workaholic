## 1. Overview

`/specificate`'s inbound discovery excluded an issue only when a feedback record naming it was on the base, so an ask already captured on an **unmerged** branch was handed back every hour and re-captured. The walk that answers *is this on a branch* was extracted into `lib/unmerged-branches.sh` and is now shared by both readers.

**Highlights:**

1. `captured_on_branch` is its own reason word — `already_captured` keeps meaning *settled on the base*.
2. The branch walk is **extracted, not copied**: `list-proposed-refs.sh` and `list-inbound-issues.sh` differ only in the pathspec they hand it.
3. Reported by a run that died before opening this pull request; resumed, re-validated and reported here.

## 2. Motivation

`list-inbound-issues.sh` subtracted issues a feedback record already named, and read only the base to decide it. `/specificate` writes that record into a publish tree behind a pull request, so between the capture and its merge the record exists on a branch and nowhere the reader looked — and the issue came back on the next tick, and the one after. The sibling reader `list-proposed-refs.sh` already walked unmerged branches for exactly this reason, so the fix was to share that walk rather than to teach a second script the same trick.

## 3. Changes

### 3-1. Exclude an ask whose capture waits on a branch ([e6c6a73f](https://github.com/qmu/workaholic/commit/e6c6a73f))

Extracts the base resolution, the shallow warning and the added-paths walk into `specificate/scripts/lib/unmerged-branches.sh`; both readers source it. An issue whose only record lives on an unmerged branch now lands in `excluded[]` under the new reason `captured_on_branch`, distinct from `already_captured`.

## 4. Outcome

An ask captured on an open branch is no longer re-offered while its pull request waits. The two exclusion words send a reader to different places — one to the record, one to the pull request — and nothing keys on either: the only consumers are the run report and the drill runbook's blame table.
