## 1. Overview

Publications read `clean` from `git merge-tree` and `dirty` from GitHub, so the loop attempted a
merge the remote refused every hour. The cause was this repository's `.gitattributes`:
`merge=union` on the generated indexes, which git applies and GitHub does not.

**Highlights:**

1. Lazy `mergeable` computation and branch protection were both ruled out with readings.
2. The reader computes from an empty directory with `GIT_DIR` set; its class now matches the API
   on all six open publications.
3. A new hermetic row goes red when the fix is reverted.

## 2. Motivation

The mission that gave the `clean` class an owner shipped an hour earlier and delivered nothing:
the first publication it settled came back `merge_refused: merge_not_allowed`. The ticket it
minted asked what the loop should do about a publication the remote declines, and required the
diagnosis before any repair, because lazy computation, a stale ref and branch protection have
different answers and only one of them is code.

It was a fourth cause. Issue #780 had added `merge=union` for the generated indexes so that
concurrent branches stop conflicting on a file nobody authored — which works for every local
merge and for none of GitHub's. The side effect was that these branches stopped reading
`mechanical`, so the one act that would have made them mergeable never ran on them.

## 3. Changes

### 3-1. Predict the remote's merge, not this checkout's ([9e334729](https://github.com/qmu/workaholic/commit/9e334729))

`claim-mergeability.sh` computes its `merge-tree` from an empty directory with `GIT_DIR` set, so
the working tree's `.gitattributes` is out of reach; a branch whose only collision is a generated
index reads `mechanical` again, which is the class the existing catch-up settles. The union
driver, the writer, the shared classification rule and every refusal word are untouched.

## 4. Outcome

The reader agrees with GitHub on all six open publications — 813/688/625 `mechanical`, 799/635
`clean`, 622 `content` — so the loop's own catch-up can bring the stranded ones back onto the base
and deliver them. No question, key, cap, addressee or gate moved.

## 5. Concerns

### A local-resolution repair can hide the condition from the machinery built to fix it

- **Severity:** moderate
- **Description:** `merge=union` (issue #780) and the mergeability reader were each correct and
  wrong together for six days: the driver removed the conflict from every local merge, taking the
  branches out of the `mechanical` class whose act makes them mergeable (see
  [9e334729](https://github.com/qmu/workaholic/commit/9e334729) in
  `drive/scripts/claim-mergeability.sh`).
- **How to Fix:** Ask of any future local-resolution repair which readings it silences. Nothing
  mechanical checks this; the new row pins the measured instance.

## 6. Successful Development Patterns

- Reading the same six pull requests three ways — local class, API `mergeable`, and the merge run
  without `.gitattributes` — ruled out two candidate causes before any code changed.
- Every first API read answered `unknown` and a second resolved it: worth knowing before treating
  `mergeable` as a fact.
