## 1. Overview

The operator's correction was that the implementation is entirely contrary to intent: the tick "only spews reports and shows no sign of resolving anything", and a conflict announced as belonging to a claim holder belongs to nobody, because a claim holder never comes. Parked pull requests read as progress to the loop and as stagnation to its operator.

This branch moves conflict work from reporting to acting. The loop now **attempts** every conflict class it can, **merges** what it settles, and reaches a person only with the residue the merge itself could not resolve.

**Highlights:**

1. `content` was never a finding — it is a **prediction** made by a reader that computes with the repository's own `.gitattributes` out of reach. The acts now test it instead of refusing on it.
2. Resolving without delivering was the stagnation itself, so a repaired `queue_drained` claim is now merged by the act that repaired it, behind the release-safety scan.
3. An uncomputed mergeable state leaves the pass entirely — it says nothing about the pull request and names no act anybody can take.
4. Three of this mission's five tickets carried a premise the tree contradicted; each correction is recorded rather than quietly implemented around.

## 2. Motivation

Two readers of one conflict disagree here **on purpose**, and nobody had noticed what that implied. `claim-mergeability.sh` runs `git merge-tree` from an empty directory with `GIT_DIR` set so the repository's `.gitattributes` is unreachable — because its job is to predict **GitHub**, which applies no merge driver when it computes `mergeable`. The writer, `catchup-main.sh`, merges in a real checkout where `merge=union` on the generated OKF indexes is in force. The tree already recorded the measurement: same git, same two commits, the checkout merge exits 0 while the attribute-less computation exits 1.

So the reader is **pessimistic by construction** against the writer — and both acting scripts were refusing on the reader's guess, before anything was checked out. Every branch in that gap was declined by a machine and handed to a person who never came. `content` is by construction everything the mechanical and append-only *proofs* could not accept, so "resolve a content conflict" could never mean giving a machine a new judgement; what it means is that the loop finds out by trying.

## 3. Journey

### 3-2. Attempt a content conflict instead of deferring ([ef49c6f](https://github.com/qmu/workaholic/commit/ef49c6f0))

`catch-up-claim.sh` and `settle-stranded-publication.sh` accept a `content` prediction as a candidate, attach the worktree and perform the merge; the refusal moved to the **writer's own residue** — still `content_conflict`, still nothing pushed, still the branch byte-identical. `list-catchable-claims.sh` offers the class so the act is reachable, and carries it through rather than re-spelling the literal `mechanical`. The strategy per class is written down in `claims.md` before it was written in code, as the ticket required.

### 3-3. Deliver the pull request the catch-up repaired ([43d3a14](https://github.com/qmu/workaholic/commit/43d3a148))

Resolving and stopping leaves the pull request open, which is the stagnation itself. A `queue_drained` claim the catch-up repairs is now merged by it, after the scan and only on `pass` or `override_only`. The outcome rides its own `delivery` field: a branch can be genuinely repaired while its merge is held, and collapsing those two facts would report an open pull request as delivered.

### 3-4. Drop the uncomputed mergeable state from the pass ([a9de3ee](https://github.com/qmu/workaholic/commit/a9de3ee7))

`blocked_by: unknown` means GitHub has not finished computing `mergeable`. The only act it ever named was *re-read before acting*, which is nobody's. It leaves the question candidates **and** the `ask_key` digest — filtered at candidate selection, because `ask-question.sh` records a key as asked when the question is composed, so a post-time filter would leave the key spent while reaching nobody. The uncomputed note also leaves `merge-conflicts`' root `event`. Both counts survive on their steps' own `uncomputed` fields.

### 3-5. Stop telling a person a conflict is theirs ([ef7077c](https://github.com/qmu/workaholic/commit/ef7077c4))

The first part of the retirement ticket: every sentence the four changes above made false. The conflict rows in both steps, the `catchup-blocked` question body and heading, and the two "does not rebase" bounds now say the loop attempts the conflict and that only an unsettleable hunk reaches a person. The rebase bounds themselves are **unchanged and still true** — the repair is a *merge*, on this identity's own claim, so neither half of the race those bounds refuse arises.

### 3-6. Retire the step that defers a conflict ([b9bd50c](https://github.com/qmu/workaholic/commit/b9bd50ca))

`catchup-blocked` is retired outright — script, registry row, spec, question key, both step

## 4. Outcome

The loop attempts every conflict class it can reach, merges what it settles, and delivers a repaired claim rather than parking it. What the merge itself could not settle is **reported by the act that met it** and asked about by nobody — the mission's last acceptance item, and it closed `achieved`.

Nothing in the safety story moved: `conflict-class.sh` is untouched and no path was reclassified; there is still exactly one merge engine; `unanswerable` is still never acted on, being the absence of a reading; the release-safety scan runs before every merge and `secret`/`leak` still stop it; the repository's fast checks still gate every push; a colleague's claim is still untouchable and a live claim still left alone.

Verified: `node scripts/test-workflow-scripts.mjs` — 6041 passed, 0 failed; `sh scripts/e2e/loop-drill.sh verify-all` — 43 drills, 0 failed, 33 proved (up one, from a new breaker row); `build.mjs` / `verify.mjs` / `validate-metadata.mjs` clean; `layout-doctor.sh` `conforming: true`.

**Three existing checks went red first and each was right to.** A publication test expected `not_mechanical:content` and got `content_conflict` — the refusal moving from before the attempt to after it. `verify-catch-up` asserted a `content` claim was never offered; that row was **split in two**, one for the widening and one for the identity bound that did not move, because collapsing them is how a colleague's claim would quietly become offerable next time. And `verify-tick-thread`'s breaker stopped matching a `sed` anchor on a printf line that gained an argument, reporting `noisy=no` — *the rows above prove nothing* — which is exactly a breaker doing its job; it was re-anchored, not relaxed.

## 6. Successful Development Patterns

- **A safety property must be asserted as an order, not a presence.** The scan-before-merge row compares the two offsets in the source; a test that only checks both are present passes the one arrangement that gates nothing.
- **Reproduce before designing.** The offline `content` conflict was built first, as ticket 2's step 1 required, and it is what showed that the honest widening is *attempt the prediction*, not *give a machine a new judgement* — a design the described version of the problem would not have reached.
- **A breaker that stops matching is a breaker working.** When an anchor drifts, the drill reports that the rows above prove nothing. Re-anchor it; a loose pattern is a breaker that has stopped noticing.
- **Check the premise against the tree before implementing a ticket.** Three of five here were wrong, in ways that would each have produced a silent no-op or a false bound.
- **When a ticket's step blocks, re-read which object it names before accepting the block.** The retirement blocked for a day on the reading that it meant `stuck-prs`; step 1 names *the composer of the "belongs to the claim holder" line*, which is a different step whose one reading is already named elsewhere — so the Considerations' test was satisfied rather than violated, and nothing had to be decided without evidence.
