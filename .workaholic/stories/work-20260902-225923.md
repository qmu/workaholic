## 1. Overview

`check-version-bump.sh` answered *did this branch make a bump commit*. That is true of the
branch and says nothing about **which number it landed on**, so concurrent branches each bumped
`N → N+1` correctly and every later merge landed its work on a spent number.

**Highlights:**

1. Measured on `main`: five consecutive merges, two version numbers between them.
2. The reader gains a second question, `version_ahead`, three-valued and compared field-wise.
3. `/drive` re-reads immediately before the merge and **re-bumps** — a repair, never a gate.

## 2. Motivation

`.claude-plugin/marketplace.json` is what a consumer installs from and CI publishes a Release
per version, so a published `1.0.285` and a `main` carrying two further merges are different
trees under one number. Nothing was broken; what was lost is the ability to say which code a
version is. And since `/spawn-loops` runs three loops beside the developer's own sessions,
concurrent branches from one base are the normal state — so this is what the rule produces,
not a slip in one run.

## 3. Changes

### 3-1. Ask whether a bumped version is still free ([a98a50a](https://github.com/qmu/workaholic/commit/a98a50a8))

`version_ahead` joins `already_bumped`, comparing the branch's manifest to the base's
field-wise (`1.0.9 < 1.0.10`) and answering `null` for an unreadable manifest rather than
`false`. `/story` Phase 0 bumps unless both hold; `/drive` §6 re-reads before the merge and
re-bumps when the base has overtaken the branch, reporting `version_rebumped` /
`version_already_ahead` / `version_rebump_failed` and merging either way.

## 4. Outcome

Two branches from one base now leave `main` at two distinct versions, and the reproduction that
shows the old shape is a hermetic row. This branch was its own first case: it read
`version_ahead: false` at `1.0.285` against a base at `1.0.285` and was bumped to `1.0.286`.

## 5. Concerns

### The window between the freshen and the merge is still open

- **Severity:** low
- **Description:** The re-check happens immediately before the `PUT .../merge`, so two runs merging inside that interval — seconds — can still land on one number (see [a98a50a](https://github.com/qmu/workaholic/commit/a98a50a8) in `plugins/workaholic/skills/drive/SKILL.md`)
- **How to Fix:** Stated rather than designed away. Closing it would mean arbitrating a shared counter at the remote, which is a bigger mechanism than the fact is worth; the collision it would prevent is bookkeeping, not a defect in the work.

### `1.0.284` and `1.0.285` each name more than one tree

- **Severity:** low
- **Description:** The versions already collided are not repaired (see [a98a50a](https://github.com/qmu/workaholic/commit/a98a50a8) in `CLAUDE.md`)
- **How to Fix:** Ruled deliberately: recorded and left. Re-cutting published releases to tidy history is a worse act than the one it would cure, and the next bump names the current `main`.

## 6. Successful Development Patterns

- The old reader was **incomplete rather than wrong**, and noticing that decided the design: repairing its question was smaller than replacing it or moving the bump to a post-merge seam on `main`. A true answer to the wrong question is worth looking for in every predicate this loop keys a decision on.
- A fixture of two branches from one base needs each branch to carry **its own work** — identical trees and messages from one parent produce the same commit object, and the row then passes or fails for a reason unrelated to what it tests.
