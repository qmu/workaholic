## 1. Overview

A denied Slack post is not an accident. Measured 2026-09-02, two `/implement` runs minutes apart in
one session: one had every connector call refused and lost three lines; the other posted three of
the same shape. With `SLACK_BOT_TOKEN` unset the transport model's **middle** branch does not
exist, so a *refused* call fell to the branch written for a session that never had a surface — and
the run said the post does not exist and stopped. The three that did land were `🟡 Handoff` lines
carrying no mention token, the unit's assignee being the posting identity. Six directed lines:
three lost, three paging nobody.

**Highlights:**

1. **`post_refused` is the fourth branch of the transport model**, distinct from
   `no_slack_transport` by one sentence carried byte-identically across four surfaces: a refusal is
   per call, an absence is per session.
2. **A refused line is carried on the unit's own story and sent once by a later tick** — one
   idempotent section, one writer, one reader, one candidate list, one clear. No timer, no queue,
   no cursor, no second liveness authority beside the branch tip.
3. **A directed post carrying no mention token says so in its own line**, so an unanswered thread
   is never read as silence from the person it was addressed to.

## 2. Motivation

Each ticket's step 1 was *reproduce and localize first*, and each was answered before anything was
designed for it.

The transport model in `workaholic:notify` reads as three branches — connector primary, tokened
script as the fallback for a caller with **no** connector, neither available means the post does
not exist. There is no branch for a connector call the harness **declined**, so a per-call denial
was classified as the third, whose whole meaning is *this session cannot post at all*. The two are
not the same fact and do not have the same repair: an absence cannot be fixed inside the run, and a
refusal leaves a line that is still sendable.

The per-unit outcome vocabulary was `no_surface` / `no_token` / `slack_<error>`
(`drive/SKILL.md` §7, `drive/reference/routing.md`), and nothing anywhere carried a lost line
forward — the run report is the only surface and it dies with the container.

On the directed side, the model's answer for *the mention target is the posting identity* is that
the shape takes the **bot** identity so the mention becomes real. With no bot token there is no bot
identity, so `Never mention the identity you are posting as` drops the token and the line reaches
the channel addressed to nobody, with nothing saying so.

## 3. Changes

### 3-1. `post_refused`, and the wording that keeps it one rule

`workaholic:notify`'s transport section gains a fourth branch and one paragraph defining both words
against each other. That paragraph is carried **byte-identically** into
`notify/reference/notifications.md` and into the two routine-fired command ceilings
(`commands/implement.md`, `commands/moderate.md`), and `scripts/test-workflow-scripts.mjs` pins all
four copies — the discipline the wire formats already carry, for the reason the ceiling rule states:
a paraphrase in any one surface is a third version of the rule.

`drive/SKILL.md` §7 and `drive/reference/routing.md` name `post_refused` beside
`no_slack_transport` in the per-unit notification outcome, and `CLAUDE.md` states it in the same
change.

### 3-2. The carry — four scripts, each with one job

- `story/scripts/record-unposted-line.sh` writes the shape, the reason and the text into a
  `## Unposted Line` section on the unit's branch story. Idempotent: an identical re-run reports
  `changed: false` and rewrites nothing; a different line **replaces** the section rather than
  stacking a second one, because the question is *what is still unsent* and two answers in one file
  is the ambiguity the record exists to remove. `--clear` removes it.
- `story/scripts/read-unposted-line.sh` is its one reader, taking either a path (a run standing in
  the worktree it just wrote) or `--ref/--branch` (a run reading another claim's tip with no
  worktree at all). A section present but not in the writer's shape reads `section_malformed`
  rather than yielding a half-read line to post.
- `drive/scripts/list-unposted-lines.sh` names this identity's standing claims carrying one,
  composing `list-claims.sh` — one walk of the refs, no second oracle, no re-derived verdict. A
  degraded read yields no candidates, its reason and a **null** count; an unreadable story is named
  in `unreadable[]` rather than dropped, while a branch with no story at all is skipped, because
  *not reported yet* is not a degradation.
- `drive/scripts/clear-unposted-line.sh` removes the record after a landed re-send, with the same
  worktree-free plumbing `retry-undelivered.sh` uses to record a merge outcome: no checkout, no
  worktree, the caller's index untouched. It is this identity's own claim only — `foreign_identity`
  and `identity_unresolved` are refused by name.

The story is the home because it already **is** the branch's own record, already committed at the
tip, and already the blob the claim oracle fetches — the ground `record-merge-outcome.sh` stands on.
No new artifact, no field on any artifact, no store.

### 3-3. The directed line that paged nobody

One wording, byte-identical across the model, the catalog and both ceilings: a directed post
carrying no mention token appends `(メンション先未解決: 誰にも通知していません)`, and the
deployment's single-transport reality — with no `SLACK_BOT_TOKEN` the two-transport model is one
transport — is written where the transport model is stated.

It changes the post's **text** and nothing else. `/moderate`'s `already_asked` keys on the step id
`lib/question-id.sh` derives from the key, never on the text, so no question is re-asked by it, and
that is asserted in both the model and the `/moderate` ceiling rather than left to a reader.

## 4. Outcome

`post_refused` and `no_slack_transport` are now different words with different repairs, on every
surface that reports a notification outcome. A line the transport declined is left where the next
tick will find it and sent once; a line that landed is cleared and never sent again. A directed
line that reached the channel without paging anyone says so on its face.

## 5. Concerns

- **The carry does not reach a merged unit, and that limit is stated rather than worked around.**
  The merge releases the claim and deletes the branch, so there is no branch to record onto and
  none to read back from; carrying it would mean writing to the base outside a merge, which no run
  may do. Such a line is reported unposted by the run that lost it and carried by nobody. The
  measured case — three `🟡 Handoff` lines — is fully covered, because a handoff unit's claim stands
  by design.
- **Nothing mechanical checks what a run actually emits.** The four-surface pin is on the
  documents, which is what the repository's existing ceiling pins buy and no more.
- **The ask's other fork on the directed shape is recorded, not taken**: *a deployment emitting
  directed shapes must provision the token* is a provisioning act rather than one a run can
  deliver, and it is written into `notify/SKILL.md` as the alternative.

## 6. Successful Development Patterns

- **Localize before adopting the reporter's mechanism.** Each ticket's step 1 named the current
  classification verbatim before the proposed word was written; the three-branch model and the
  `no_surface` vocabulary are quoted in the tickets' Final Reports rather than assumed.
- **A named degradation with no act behind it is half a repair.** `post_refused` alone would have
  left the measured failure exactly where it was — the carry is what makes the distinction worth
  anything, which is why the suite asserts the ceiling names the write, the read, the send *and*
  the clear.
- **A duplicate post is the loud failure and a lost one the quiet failure.** The record is precise
  enough to tell a landed line from an unsent one because the tree is the only store: writing it is
  a commit and clearing it is a commit, and both are idempotent.
