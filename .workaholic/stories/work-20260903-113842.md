## 1. Overview

Squash-merging (2026-09-01) was supposed to keep the loop's own bookkeeping off `main`. It kept it
out of the *commit list* and put it straight into the *commit body*: a squash whose API call carries
no `commit_message` gets the forge's default, which is the concatenation of every commit message on
the branch. So the claim stamp, the heartbeats and the index refreshes reached the trunk anyway,
one layer down where nothing was looking.

**Highlights:**

1. **One new derivation, `gather/scripts/merge-commit-body.sh`**, the sibling of `merge-method.sh`.
   It answers a merge's `commit_title` and `commit_message`, preferring the branch story's own
   `description:` line, and it is read by **every** merge the loop makes.
2. **Housekeeping is dropped by a marker, never by a title.** `commit.sh --housekeeping <kind>`
   emits a `Workaholic-Housekeeping:` trailer over a closed kind set, and the composer filters on
   that. `Refresh heartbeat` is one wording of one writer; the next housekeeping commit will carry
   another.
3. **Seven call sites, and the suite can now see an omission.** The five REST merges read the
   composer, the two agent-level merges are instructed to, and a new suite row **enumerates the
   merge call sites from the tree** and fails one that reads no composer — the assertion a
   literal-text check cannot make.

## 2. Motivation

The measurements were taken before anything was built for them, as the first ticket required.

On this repository's `main`: **48** commits whose message body carries the text `Refresh heartbeat`,
and **48 of 48** have a subject that is not `Refresh heartbeat` — every one is a squash body rather
than a heartbeat commit. The longest is **11,515 lines** (`499a7435`). On the other side, all five
REST merge call sites passed `merge_method` and nothing else: the strings `commit_title` and
`commit_message` appeared **nowhere** in the repository.

That is the whole defect. `merge-method.sh`'s header argues that *a commit is a change to the
development target* and that a squash carries the unit's tree and one subject instead of the loop's
memory. The premise was right and the implementation was half-done: the subject was composed by the
pull request's title, and the body by nobody.

## 3. What changed

**The derivation.** `merge-commit-body.sh <number>` or `--branch <branch> [--number <n>]` emits
`{ok, title, body, source, reason}` on stdout and nothing else. `source` is three-valued and each
value is named: `story` (the branch story resolved), `fallback` (no story — a publication's ordinary
answer, not a failure), and `unreadable:<reason>`. **An `unreadable` read still yields the fallback
body**, because a composer that fails must never hand the forge its default back by omission, and a
merge is never held on a body. It writes no file, touches no ref, and its one network read is the
pull-request lookup that `--branch` skips.

**The marker.** `commit.sh` gained `--housekeeping <kind>` with a closed set —
`heartbeat | claim | index | hours` — refusing an unlisted kind `bad_housekeeping_kind` **before the
staging section**, so nothing is committed. `heartbeat.sh` and `claim.sh` (both its stamps) pass it.
The index and hours seams pass **nothing**, and that is conformance rather than an omission: neither
commits through `commit.sh` on its own — both ride `archive.sh`'s commit, and that commit moves the
ticket, which is a unit's actual work.

**The call sites.** `merge-pr.sh`, `publish-tree-pr.sh`, `retry-undelivered.sh`, `catch-up-claim.sh`
and `settle-stranded-publication.sh` each read the composer and report its word as a new
`body_source` field. Every refusal at every one of them is byte-identical and still runs **before**
the composer, so no body is composed for a merge that will not be attempted. The two agent-level
merges — the `review` route and the connector retry — are instructed in `workaholic:drive` and in
`commands/implement.md`.

## 4. Concerns

**Nothing mechanical can check an agent's merge call.** It is composed at run time and appears in no
file. The suite proves only that the instruction sits in the ceiling the session will read, and the
assertion's own comment says so rather than implying a stronger guarantee.

**The instruction reached one ceiling, not the two the ticket named.** `/specificate` performs no
merge — its publication is merged by `publish-tree-pr.sh`, a script, which this branch patched — so
inlining a merge instruction there would put a rule into a ceiling whose command never executes it.
The suite asserts its absence positively, so a later contributor adding one is making a visible
decision rather than a silent one.

**A commit already on the trunk carries no marker and is not rewritten.** The composer therefore
reads an unmarked commit as ordinary work. That is the safe direction — it over-includes on history
and under-includes on nothing — and it is visible on this very branch: six heartbeats written by the
base's own script survive in the composed body, while the one written by this branch's patched script
is correctly dropped.

## 5. Successful development patterns

**The obvious record format was wrong, and cheap to find out.** A single `git log --format='%s%x00%b'`
walk is the natural shape for "subject plus body per commit", and it cannot work in shell: a command
substitution **drops NUL bytes**, so every body ran into the next subject and the first version
emitted one mangled entry. The shipped shape is two walks — subjects, and
`git log --grep='^Workaholic-Housekeeping:'` for the marked set — which loses no separator and leaves
the marker test as git's own.

**A row that cannot see an omission needs a second row.** The existing `merge_method=` row protects
against *drift* — a call site spelling the answer. This defect was the opposite: a call site
spelling nothing at all, which has no text to match. The second row enumerates the merge call sites
**from the tree** and asserts each reads the composer, so a sixth call site added tomorrow is covered
the day it lands with no hand-kept list.

**Proving a gate goes red is worth a small tool.** The ticket asked for the rows to be proved by
reverting a call site. Doing that meant three full 6410-row suite runs. A four-line single-row filter
(`node scripts/test-workflow-scripts.mjs "<substring>"`) made the proof cheap: the row went red on
`merge-pr.sh` **by name**, then green once restored. CI passes no argument, so an unfiltered run is
byte-for-byte what it always was.

**Doing the documentation last found a second defect.** `drive/reference/routing.md` still described
the `review` merge as `merge_method: merge` — stale since 2026-09-01. Nothing was looking for it; it
surfaced only because the last ticket's job was to read every document that describes the merge.
