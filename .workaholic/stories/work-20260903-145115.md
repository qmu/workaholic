## 1. Overview

The operator's intent is that a subagent is discarded when its work finishes, so every run starts on
a fresh context window. The tick specified the **opposite**: an idle agent was the loop's clock, so
it had to be kept alive until the next spawn.

**Highlights:**

1. **The clock moved off the agent** onto a `loop-finish-<name>` line written by the tick that
   first observes a run idle, through the log writer that already exists.
2. **Every idle subagent is stopped at the head of the tick, unconditionally** — an idle agent is a
   **resumable session holding its whole transcript**, not a corpse.
3. **An `/implement` run takes one PR-unit and ends**, so no context spans two missions.

## 2. Motivation

Three measurements, and the ordering of the tickets follows from them. A send woke an idle agent
**inside its prior context**, twice in one session — so an idle agent is not free and reaping is the
only act that returns the window. The cadence read `started N ago`, which is the previous run's
start **plus its whole duration**, so the fifteen-minute `propose` loop respawned at 21, 31 and 45
minutes. And nothing bounded a run: one `implement` agent lived ninety minutes, landed an
eight-ticket mission, then claimed a **second, unrelated** one and planned it inside a context still
carrying the whole of the first.

## 3. What changed

`ListAgents` answers exactly one question — is this loop still running. The finish is recorded
before the stop; the cadence reads it back with `--latest-tick`, the one-line reader the sibling
mission `pay-only-the-operative-cost-on-every-tick` added hours earlier. `/implement`'s ceiling
and `workaholic:drive` both carry the one-unit bound, and the tick's report names every reaping and
the cadence's own source.

## 4. Concerns

**The three tickets are ordered and the order is not arbitrary.** Reaping at the head **before** the
clock moved would have destroyed every cadence. A later reader undoing one of the three in isolation
re-creates the defect the other two exist to prevent.

**One unit per run costs throughput, and the ticket says so.** A full queue now drains over more
ticks. That is the trade the ask makes: a plan formed inside a context carrying an unrelated mission
is worse than one formed an hour later on a clean context.

**None of this is a script, and the suite says so.** All three rules are prose in ceilings a session
reads; what is checkable is that each rule is present where the run will read it, and each assertion
names that bound rather than implying a stronger one.

**This run is itself the measured defect, once more.** The `/implement` run that implemented this
mission drove **six** units before reaching the ticket that forbids it, under an explicit instruction
to drain the offer. The rule lands with this merge and did not exist while the run was driving, so it
is not a violation — but it is the behaviour, observed again, and the next tick's run is the first
bounded one.

## 5. Successful development patterns

**Move the dependency before removing the thing it depends on.** The idle agent could not be reaped
promptly while it was the clock. Recording a finish first, reading the cadence from it second, and
only then reaping unconditionally is three tickets where one would have been a rewrite — and each
step is independently correct.

**A new reader paid for itself the same day.** `log-read.sh --latest-tick`, written hours earlier
for a different mission's cadence gate, is exactly the read this one needed. Neither mission planned
for the other; the shape was general because it answered *one value from a log* rather than *the
moderate gate's question*.

**Name the absence's meaning where the absence is read.** *No recorded finish* has three ordinary
causes and all three must mean **due**. Writing that down — including the case that cannot occur —
is what stops a later reader treating the empty answer as *not yet*.
