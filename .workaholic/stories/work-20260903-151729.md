## 1. Overview

A `/ship` run drafted a Deployment Plan whose target heading came out as
`### リポジトリ... (<slug>)`, and a person decoded it by hand before the note
could be committed. The Release Note is written to be read, so a heading made of escape sequences
is unreadable for every project that does not name its targets in English.

**Highlights:**

1. **The escape is introduced at one place and repaired there** — `escape_json()` in
   `read-deployments.sh`, whose `python3` branch ASCII-escapes by default. Neither the `sed`
   extraction downstream nor the Markdown writer introduces it.
2. **The three interpreter fallbacks disagreed three ways**, which is worse than the report
   suspected: one of them was silently corrupting data. All three now agree byte for byte.
3. **A hermetic case pins the pipeline, not the escaper**, so it exercises whichever interpreter
   branch the test machine happens to have.

## 2. Motivation

The ticket asked for diagnosis before repair, and recorded the reporter's hypothesis — that the
escaping survives from `read-deployments.sh`'s JSON into the Markdown writer — as a hypothesis
rather than as the design, naming three points at which the escape could have been introduced or
decoded.

The reproduction ran all three stages against a throwaway repository holding one deployment record
titled `リポジトリ文書サイト`. The escape sequences appear at **stage 1**. `read-deploy-state.sh`
lifts the title out of that JSON with `sed` and never decodes it; `draft-deploy-plan.sh` writes
what it is given. Both carry the string forward faithfully, and neither is the defect.

So the hypothesis is confirmed about the *path* and wrong about the *repair*: the escaping does
survive into the Markdown writer, and the writer is not the place to decode it.

## 3. Changes

**`escape_json()` keeps non-ASCII as raw UTF-8.** `python3` now runs with `ensure_ascii=False`
over binary I/O; `perl` decodes its input before `encode_json` re-encodes it; `node` was already
correct and is the answer the other two are pinned to. The output is still valid JSON — raw UTF-8
in a string always was — so every consumer that parses it is untouched. What changes is that the
one consumer which lifts a value back out **as text** now gets text.

**The same repair in all three copies.** The identical block is copied into
`read-release-notes.sh`, and appears as `escape_file_json` in `draft-release-note.sh`, which
carries a whole rendered note. Both were repaired the same way — this is the ticket's step 4
sweep, and it is what keeps the release-note render from reproducing the heading defect one
document over.

**The other two readers needed nothing.** `report-deploy-status.sh` and `read-deploy-state.sh`
carry `sed`-based escapers that already pass non-ASCII through raw; they were checked and left
alone rather than changed on symmetry.

**Four hermetic assertions.** The new case builds a repository with a Japanese-titled target and
asserts both halves together: the heading renders as characters, no `\uXXXX` survives anywhere in
the note, and `read-deployments.sh`'s stdout still parses as JSON with the title intact. The
second half is the point — raw UTF-8 in the heading is only the right repair if the JSON is still
parseable for every other consumer.

## 4. Concerns

The two remaining JSON-string escapers in the repository carry the same defect and were
deliberately left outside this ticket's sweep, which named deployment record fields and the
release-note render:

- `gather/scripts/merge-commit-body.sh` composes the squash title and body every `/implement`
  merge passes to GitHub, so a Japanese story title lands on the trunk's permanent record as
  `\uXXXX` — the same hand-decoding, one artifact over.
- `drive/scripts/run-verification-probe.sh` carries a probe's captured output into `## Handoff`
  and the `🟡 Handoff` post, both read by a person.

Both are worse than the escapers repaired here, because their `sed` fallbacks do not escape
non-ASCII at all — the two paths of one function disagree, and which answer a caller gets depends
on whether `python3` is installed. Ticket
`20260903064753-agree-the-two-remaining-json-string-escapers-on-raw-utf-8.md` is minted for them
and is queued on this branch.

## 5. Successful Development Patterns

**A three-way interpreter fallback with no shared test is three implementations.** The `perl`
branch had been emitting mojibake — re-encoding bytes it had never decoded — since it was written,
and nothing caught it because that branch only runs on a machine with neither `python3` nor
`node`. The ticket flagged that the fallbacks "may not behave identically" as something worth
confirming; confirming it was the highest-value ten seconds of the work. Where a script carries
interpreter fallbacks, one input through all of them is the test.

**`\uXXXX` was never invalid JSON, and saying so in the comment matters.** The defect is invisible
to every consumer that actually parses the JSON; it surfaces only where a value is lifted back out
as text. A future reviewer looking at `ensure_ascii=False` would otherwise reasonably read it as a
correctness fix to a serialiser that was fine.
