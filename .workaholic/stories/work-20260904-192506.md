# Document the shared development loop

## 1. Overview

The README and operator runbook now describe `/work` as the orchestration boundary, while preserving `/drive` and `/implement` as the single executor. The command map, platform clocks, relay states, sequential allocation, prompt refusals, and recovery paths now match the executable contracts.

**Highlights:**

1. Makes one `/work` invocation and its platform-specific clock discoverable from the README.
2. Updates the full command graph from its stale fourteen-command model to all 22 entry files.
3. Gives operators exact status and refusal words for connector relay and recovery.

## 2. Motivation

The executable loop had gained a shared tick orchestrator and a Codex clock/relay boundary, but the durable documentation still centered the retired routine-first and direct-cron model. That mismatch could lead operators to start competing clocks or interpret emitted Slack intent as delivery.

## 3. Changes

### 3-1. Document the work command ([83b007db8](https://github.com/qmu/workaholic/commit/83b007db8))

Added the development-loop overview and completed the Mermaid command graph with the explicit orchestration edges. The text keeps `/work` out of the executor role and links detailed behavior to the work skill.

### 3-2. Update loop operator guidance ([8a9876dbc](https://github.com/qmu/workaholic/commit/8a9876dbc))

Reframed the runbook around one tick and its external clock, and documented relay status, allocation, permission refusal, and claim/publication recovery using the owning scripts' vocabulary.

## 4. Outcome

A reader can now choose the correct clock for their agent, understand what one tick runs, and diagnose pending or refused work without relying on stale routine assumptions.
