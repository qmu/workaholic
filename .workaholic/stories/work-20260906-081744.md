## 1. Overview

The 2026-09-02 repair for issue #865 moved an unattended run's plugin reads off `sed`/`grep`/`cat`/`head` and onto the Read tool — and the `[Propose]` tick went on parking hourly anyway. This branch names why: the shell readers are allowed by **prefix with no path term**, while the Read tool is allowed **only under `Read(//home/**)`**, so the reach was moved onto a rule that covers it *less*. The repair separates the two reaches by their permission class.

- `bash` keeps `<src>`; a **Read** takes the checkout's own path, inside the workspace.
- `rules/general.md`, which authorized the old shape, is corrected rather than left to contradict the new rule.
- The allow entry was refused a second time, with all four of its costs recorded.

## 2. Motivation

The mission's diagnosis ticket had already done the hard part and named two candidates it could not separate, with the sharp observation that issue #865's repair "walked into this." Its evidence stood up: the repository's allowlist carries nine Bash prefixes and exactly one Read entry, `Read(//home/**)`, and `plugin-src.sh` in the routine's own container answered `src: /root/.claude/plugins/cache/workaholic/workaholic/1.0.278`, `source: registry`. The checkout was present at an **equal** version, so the immutable candidate won the tie exactly as designed — and every routine prompt and all four command ceilings then pointed a Read at a path that is both outside `/home/**` and inside a `.claude/` directory.

## 3. Changes

Verified Candidate B (a Slack write in the `/propose` path) was already removed at its source by the 2026-09-03 Slack move, and closed Candidate C by naming the write directory.

## 4. Outcome

No routine prompt and no command ceiling now points a Read at `<src>`, and every prompt still runs its scripts from `<src>` — both pinned by the suite, in both directions. The newest-tree resolution is untouched: the code that executes is still the newest on the machine. What changed is which path a *read* names.

## 5. Concerns

### The restructure does not reach a consuming repository that does not vendor the plugin

- **Severity:** moderate
- **Description:** A repository that installs the plugin without a `plugins/workaholic/` in its workspace has no checkout copy of the command body, so `<src>` is the only tree carrying it and the Read of it cannot be moved (see [36805ff](https://github.com/qmu/workaholic/commit/36805ff1c) in `plugins/workaholic/rules/shell.md`). Such a repository can still park on this prompt.
- **How to Fix:** Its operator rules on an allow entry naming the cache path and nothing wider, in its own `.claude/settings.json` — the lever `workaholify/SKILL.md` already chose, applied to the one case the restructure cannot reach. This repository deliberately adds none.

### The derived handoff fires on a conditional `## Key Files` entry

- **Severity:** low
- **Description:** `verification-handoff.sh` routed this unit to handoff on a `## Key Files` line reading ``` `.claude/settings.json` — `permissions.allow`, if the ruled repair is an allow entry ```. The ruled repair was the restructure, so no `.claude/` path was edited (see [36805ff](https://github.com/qmu/workaholic/commit/36805ff1c) in `plugins/workaholic/skills/drive/scripts/verification-handoff.sh`). The reader's own header says the test is syntactic and narrow on purpose, so this is the derivation being conservative rather than wrong.
- **How to Fix:** Nothing here — widening the test to read the conditional would make it the prose-reading guess the field exists to avoid. Recorded so the next reader of a handoff quoting a reason the diff does not meet knows why.

### One suite failure was observed and not reproduced
