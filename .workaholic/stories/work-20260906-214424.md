## 1. Overview

`codex-loop.sh --dispatch` returns *at once* by design, and the role's lock was taken by the
**detached child** — so the claim did not exist yet when the run that made it returned, and a
second dispatch inside that window read `idle` and legitimately started a second worker.

**Highlights:**

1. The window was on the **parent's** side: in 5 of 6 rounds the lock file did not exist at the
   moment the dispatch returned, and two concurrent dispatches started two workers.
2. `dispatch_claim_role` takes the claim before the fork; the child inherits the open file
   description and is told `--claimed` so it does not retake it and refuse itself.
3. The `flock`-less fallback was the same window one layer down and is now an atomic
   `set -C` create — 4 of 4 concurrent pairs had started two workers there.

## 2. Motivation

The suite's `already_running` assertion failed twice on 2026-09-06, both times on a loaded
machine, and passed cleanly on the same tree in between. The ticket's own diagnosis-first
instruction was to establish which side the window was on before changing either — because the
two have different repairs and only one is a real defect in the loop. It was the loop: the
assertion was reporting a genuine gap that a sequential pair usually hid behind the first
dispatch's own return latency. This suite is a merge gate — `branch-checks.sh` refuses on
`checks_red` — so a race here parks a green unit for a tick at a time and, worse, trains a
reader to discount a red suite.

## 3. Changes

### 3-1. Claim a dispatched role before the fork ([e67286148](https://github.com/qmu/workaholic/commit/e67286148))

`dispatch_claim_role` is the one seam. With `flock`, the parent opens fd 8 and locks it before
forking; the child inherits that open file description, so the lock is held continuously from
before the parent returns until the worker exits. Without `flock`, the pid file is claimed with
an atomic `set -C` (`O_EXCL`) create, a dead pid cleared once and the create retried once. The
suite and `verify-codex-clock` now issue the pair **concurrently** — the shape that exposes the
window — and the drill's second breaker neuters the claim and requires the drill to notice.

## 4. Outcome

Two dispatches of one role start one worker and refuse the other: 8/8 rounds with `flock`, 6/6
without, 5/5 in the suite, and the drill's own row. No sleep and no retry stands in for the
exclusion — neutering `dispatch_claim_role` fails 10 of 10 new assertions deterministically.
`--status` is unchanged: it starts nothing, writes nothing, creates no state directory and takes
no lock.

## 5. Successful Development Patterns

- **Probing in-process, with no fork between the act and the read**, is what located the window:
  a second `sh` invocation was slow enough that the child had already taken the lock, which is
  exactly why the sequential assertion passed most of the time.
- **A parent that returns at once cannot delegate its own exclusion to the child it starts** —
  the claim has to be taken on the side that returns.

## 6. Notes

The `flock`-less path was racy before this change too and is not a regression introduced by it;
it was repaired because the ticket's acceptance criterion is stated unconditionally and the
fallback is a supported path (`verify-codex-clock` exercises it).
