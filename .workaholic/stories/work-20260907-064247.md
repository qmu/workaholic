## 1. Overview

`log-read.sh` now derives a **section owner** from the step id every tick-log line already carries and answers **moderation by default**, so the three producers writing into one day file stop shadowing each other. Two consumers that were silently wrong are repaired without being edited, and every future reader inherits the repair instead of the trap.

**Highlights:**

1. `--owner <moderate|loop|propose|all>` is derived per entry over a closed named table — no new field, no second store, no migration.
2. The change baseline and `blocked-tick` are fixed by the default alone; the loop's own three cadence reads and the propose arm opt in by name.
3. `condition-age.sh`'s `ticks` reading, inflated roughly fourfold by coordinator sections, is corrected by the same default.

## 2. Motivation

`/moderate` writes its steps into `.workaholic/moderations/<UTC-day>.md`, but `/infinite-development` records a `loop-finish-<name>` under the **coordinator's** tick id every five minutes and `/propose` writes `propose-open`/`propose-close` — three producers, one file, each opening `## <tick-id>` sections the others do not recognise. Measured on `2026-09-06.md`: 110 distinct sections, 29 moderate and 79 the coordinator's, with two holding exactly one `loop-finish-*` line and nothing else. A coordinator-only section is therefore the *ordinary* previous section, not an edge case.

The ask was to repair the cause rather than each reader, and the cause is that the log's one reader had no way to say which producer a caller meant.

## 3. Changes

### 3-1. Scope the tick log's one reader so the loop's finish lines stop shadowing moderation ([4e1c58a56](https://github.com/qmu/workaholic/commit/4e1c58a56))

`log-read.sh` gained `--owner`, defaulting to `moderate`, classified per entry from the step id (`loop-finish-*`/`loop-attempt-*` → `loop`, `propose-*` → `propose`, everything else → `moderate`) and composing with every existing filter including `--latest-tick`; an owner outside the closed set is refused `bad_owner`. `render-tick-post.sh` needed no change to its baseline selection — it names no owner and inherits the default. `step-blocked-tick.sh` now takes two reads, one per owner, so its propose arm keeps seeing its own lines while the moderate arm stops reading coordinator sections. The three cadence reads and `codex-loop.sh` name `--owner loop` explicitly.

## 4. Outcome

Both reported failures were reproduced on a hermetic fixture before the change and confirmed after: the change baseline no longer counts an unchanged summary as changed (`change_count` 1 → 0, `previous_tick` now the moderate tick), and `blocked-tick` no longer reports a coordinator-only section as a moderate tick that opened and closed. `log-append.sh` is byte-identical, no line was pruned and no file under `.workaholic/moderations/` was touched.

## 5. Concerns

### `scripts/e2e/loop-drill.sh` is past the per-file size ceiling and still growing

- **Severity:** moderate
- **Description:** The file is 723,798 bytes against a 524,288 ceiling, so the branch-safety scan raises an `override`-tier `large-file` finding on every branch that touches it (see [fe4202141](https://github.com/qmu/workaholic/commit/fe4202141) in `scripts/e2e/loop-drill.sh`). This branch added 56 lines to it; each new drill adds more, so the tax recurs and the override becomes routine — which is how an override stops being read.
- **How to Fix:** Split the dispatcher from the per-drill bodies, so each `verify-*` lives in its own file under `scripts/e2e/` and `loop-drill.sh` keeps only the `case` arms and the shared helpers.

## 6. Successful Development Patterns

- Changing a shared reader's **default** means auditing its callers in the same commit, not just its own tests: the sibling ticket `20260907031134` had landed a `--step-prefix loop-finish-moderate` read hours earlier, which the new default would have silently emptied — the failure would have been a cadence gate that spawned every tick, with nothing reporting it.
- Reproducing a reported defect **before** changing anything paid twice here: it confirmed the two real failures and falsified the ask's own causal account (`no_rows` is emitted from the run JSON before the baseline is selected), so the ticket's scope stayed honest instead of chasing a symptom that could not come from this cause.
