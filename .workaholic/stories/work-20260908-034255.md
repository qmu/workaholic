# Share loop snapshots and atomic state

## 1. Overview

The loop now builds one evidence snapshot for planners, executors, and reporters,
while local runtime state is written through revision and generation checks.

- Claims and mission data are observed once and projected through legacy facades.
- Dirty content invalidates snapshots even when Git HEAD is unchanged.
- Unknown remote or recovery reads remain distinct from an empty queue.

## 2. Motivation

Several consumers repeated the same broad Git and queue surveys, so one turn could
pay for the same evidence more than once or derive conflicting answers. The redesign
needed a shared boundary before transport and dispatch could safely rely on durable
state, while retaining every established plan field and refusal direction.

## 3. Changes

### 3-1. Share loop snapshots and atomic state ([03f3270](https://github.com/qmu/workaholic/commit/03f327007))

The runtime adds typed configuration, capability, state, planning, and context
contracts. A shared claims observation and mission corpus feed the existing readers,
and the generated portable bundles carry the full dependency closure at 1.0.333
([0ee6706](https://github.com/qmu/workaholic/commit/0ee6706cd)).

## 4. Outcome

Three consumer views can now reuse one claims scan. State creation is atomic,
updates detect stale revisions and generations, takeover requires evidence beyond
TTL, and compatibility projections remain byte-identical on repository data.

## 5. Release Preparation

- The safety scan reports one override-tier size finding because the dependency
  closure adds 154 source and generated files; it reports no secret or leak finding.
- Provider transport, worker dispatch, and delivery remain in their dependency-linked
  P3, P4, and P8 units.

## 6. Successful Development Patterns

- Comparing the precomputed and direct plan JSON byte-for-byte caught facade drift
  before the shared observation path was enabled.
