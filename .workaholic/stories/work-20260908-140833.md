# Make Slack acknowledgements useful without adding noise

## Summary

Slack の受領通知を、定型文の繰り返しではなく、人が内容と実際の進行状態をその場で判断できる会話へ変えます。3枚のチケットを一つのミッションとして完了し、次を同じ PR・story・version 境界にまとめました。

1. subject、Issue、実際の workflow state、source message を prose から分離し、機械検証できる acknowledgement contract を追加しました。
2. 同じ観測ページ内で明確に目的を共有する依頼だけを一つの返信にまとめ、各 source message の durable reaction は個別に残します。
3. 自然な文面を snapshot 固定せず、grouping、deduplication、ordering、identity、delivery facts をテストします。

## Motivation

Issue #1090 では、連続する feedback に同じ受領文が一件ずつ返り、Issue 番号以外から依頼内容を識別できませんでした。これは単なる文面の問題ではなく、Slack を人と汎用エージェントの共同作業空間として扱うための情報設計の問題です。一方で、自由な言い回しだけを許すと、まだ記録しただけの依頼を「実装準備済み」と誤って約束したり、個々の message の処理状態を失ったりします。

このミッションは、人向けの自然な表現と、workflow が保証すべき事実を分離することで、その両方を守ります。

## Changes

### Facts before prose

`acknowledgement-contract.sh` が batch、source coordinate、recognizable subject、GitHub Issue、実際の closed state を検証し、返信先、reaction 対象、次の段階を正規化します。可視文面は同じ contract の上で人の言語と register に合わせて生成し、固定テンプレートや完了の約束を要求しません。

### Burst grouping without lost state

既存の observation page を batching boundary とし、明確に同じ intended outcome を持つ依頼だけを observation order でまとめます。任意の timer や件数 threshold、新しい global buffer は導入しません。grouped receipt は最初の thread に一度だけ投稿しますが、全 subject を対応する Issue に写し、全 source coordinate に durable reaction を残します。関連性が不確かな依頼は singleton のままです。

### Semantic tests

日本語・英語の subject、captured/deferred/proposed の truthful state、関連2件と非関連1件の分離、first-source threading、全 source reaction、重複 source と不正 state の拒否を独立した fixture で検証します。loop 全体のテストも同じ facts-first、page-bounded contract を pin します。

## Outcome

- 受領通知を開かなくても、何を受け取り、どの Issue に記録し、次に何が起きるかを識別できます。
- 関連する burst は compact な一返信になりつつ、各 message の durable handled state は失われません。
- 3 acknowledgement contract tests と workflow suite 6834 tests が成功しました。
- plugin build、bundle verification、metadata validation、shell syntax が成功しました。
- ミッションは 3/3 accepted、queue empty で `achieved` となり、v1.0.339 を一度だけ準備しました。

## Concerns

### Relatedness remains a semantic judgement

- **Severity:** low
- **Description:** どの依頼が同じ intended outcome を共有するかは conversation context に依存し、validator 単独では決められません。
- **Mitigation:** 明確な関係だけを group 化し、不確かなものは singleton に保つ契約とテストにしています。timer や件数だけで強制的にまとめません。

## Successful Development Patterns

- 自然言語を固定せず、その下にある workflow facts を小さな JSON 境界にすることで、会話品質と機械検証を独立して改善できました。
- 既存の observation page を burst boundary に再利用したため、mutable timer state を増やさず overlap replay と合成できます。
- mission acceptance を3枚の archive で順に roll し、3/3 と queue empty の後だけ version を進めました。
