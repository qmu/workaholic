## 1. Overview

Merge delivery now selects its check gate from the pull request's base branch role, keeping development `main` on local proof while release promotion requires remote CI. Moderation also distinguishes deliberately held handoff pull requests from repairable conflicts through one claim-derived verdict.

**Highlights:**

1. Development and release branches have explicit, machine-selected gates.
2. Unknown branch roles keep the stricter remote-check requirement.
3. Held handoff pull requests remain visible without producing conflict questions.

## 2. Motivation

One remote-CI rule was serving two different quality windows, and handoff pull requests waiting for a person looked identical to broken branches. Explicit role and held-state readers prevent those states from being inferred independently at each caller.

## 3. Changes

### 3-1. Select merge gates from branch role ([f707a935b](https://github.com/qmu/workaholic/commit/f707a935b))

The pre-merge seam resolves development `main`, release branches, and unknown roles through one policy reader. Remote CI becomes post-merge detection for locally proved development units while release and unknown roles remain strict.

### 3-2. Classify deliberately held pull requests without filing conflict findings ([d2f231eb3](https://github.com/qmu/workaholic/commit/d2f231eb3))

The moderation tick caches one claim snapshot and projects `awaiting_verification` branches into both conflict consumers. Those branches are reported as held, ask no repair question, and unreadable evidence excludes nothing.

## 4. Outcome

Merge gates now match the repository's development/release split, and expected human waits no longer masquerade as repairable pull-request failures.

## 5. Successful Development Patterns

- A tick-owned snapshot preserved hermetic standalone behavior while keeping both moderation consumers on one answer.
