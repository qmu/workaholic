## 1. Overview

Four readings the loop was making optimistically now state what they could not see. The Slack
observation drains its delta inside one call, remembers every root and mention it discovers, and
refuses to report a partly-read channel as quiet. A unit waiting on somebody else's merge is a
per-unit wait that no longer ends the parent turn. And an accepted request answered by several
pull requests has one delivery state instead of whichever one a caller happened to pick.

**Highlights:**

1. `has_more: true` is drained rather than deferred, and what the delta discovers survives the tick.
2. A mention on a root outside the read window is found and tracked on the tick that finds it.
3. `observation_settled` is the one answer to whether a read may be called quiet — the word moves, the cadence does not.
4. A blocked merge holds one unit, not the loop.
5. A request is delivered only when every part of it merged, deployed and was publicly verified.

## 2. Motivation

Each of the four was a reading that answered optimistically where it could not see. A tick read one
page of the channel delta and called the rest *later*, which makes a coverage claim false for as
long as the channel is busy. A mention could only be seen where the delta had already looked, so a
mention on an older root — or in a reply, which Slack channel history never carries — was invisible
until somebody pasted a link, and nothing registered the thread either, so the next tick looked past
it too. A green pull request whose merge is another authority's act was classified `review_required`,
because the criterion says *a refusal that stops the work is review-required* and a refused merge
reads exactly like one; the parent then persisted `hold`, asked its one question and ended with
independent work queued behind it. And `feedback-outcome.sh` reads one `implementation_pr`, so a
request answered by three pull requests had no reading at all: whichever one a caller picked, the two
it dropped were invisible, and a request with one merged part and two open ones read exactly like a
finished one.

## 3. Changes

### 3-1. Drain the Slack delta and say when unread ([ec81d0971](https://github.com/qmu/workaholic/commit/ec81d0971))

`read_channel_delta` is paged until `has_more` is false or `WORKAHOLIC_CHANNEL_PAGES` (default 5) is
spent, each page captured before the next is asked for — so page N+1's lower bound is page N's own
advanced cursor with no overlap, and the boundary message is dropped by the existing provider-id
dedup. `window_since` rides the first page only, because the capture is the one writer of the
unproved mark. Every root and explicit Slack permalink the delta names joins a durable, bounded watch
set (`watch_threads` on the binding record, newest `WORKAHOLIC_WATCH_SET_MAX`, default 50), and that
set is what the thread-discovery fallback reads when `list_thread_changes` refuses — newest first,
through the same one classifier. A fallback read is evidence, never coverage: the status stays
`partial` with the discovery's own reason and `source: watch_set_fallback`, the fallback's own
failure riding `fallback_reason` beside it. `observation_settled` is false while
`channel_delta_incomplete`, `thread_coverage_partial`, `thread_fanout_truncated` or
`sender_identity_unverified` stands, each named in `unsettled[]`; `plan-poll.sh` then answers
`observation_incomplete` in place of `quiet`.

### 3-2. Discover Slack mentions outside the window ([39874074c](https://github.com/qmu/workaholic/commit/39874074c))

One bounded `search_exact` per tick for the declared sender's mention token joins every coordinate it
finds to the watch set and reads it immediately (`WORKAHOLIC_MENTION_FANOUT`, default 3) — a mention
is the one discovery that means a person is waiting. One thread is read at most once per tick
whichever arm named it. The search captures nothing, deliberately: capture is per surface, and
capturing there makes the thread read see its own message as a duplicate, so the classifier — which
emits only new ids — drops the very reply the arm exists to route. `coverage.mentions` reports
`searched`, `discovered`, `tracked` and `exhaustive: false`. A human reply discovered in a thread now
counts as activity, which `new_input_ids` could never say.

### 3-3. Keep the loop running on a blocked merge ([28f49eefb](https://github.com/qmu/workaholic/commit/28f49eefb))

`final-response-contract.sh` takes a `blocked_on` fact from a closed set of three per-unit blockers —
`merge_authority`, `pull_request_review`, `verification_handoff` — and refuses
`unit_wait_is_not_global_hold` for `review_required` beside any of them, echoing `blocked_on` and
`unit` onto the `task_wait` answer so the receipt records which unit waits and on what. The
`task_wait` path also gained the `interruptible_parent` derivation the routine path already read: it
answered `next_action: null` unconditionally, which ended a paused-goal parent for want of a
derivation the same file already held. The reader still reads no sentence and classifies nothing by
content.

### 3-4. Read one request across all its pull requests ([75e826307](https://github.com/qmu/workaholic/commit/75e826307))

`work/scripts/delivery-ledger.sh` composes `feedback-outcome.sh` over a request's whole pull-request
set — that reader stays the one derivation of `state` / `notification` / `deployment` — and adds only
what it cannot see: the fold with `every` rather than `any`; the first absent stage (`merge`,
`deployment`, `public_verification`); a per-row `delivered` conjoining the two readings so no call
site has to; a bounded dependency-ordered `next[]` refusing `order_unresolved` and
`depends_on_outside_item` rather than guessing; one `blockers[]` entry per gate naming every request
and pull request it holds; and `independent[]`, the open work no gate holds. Both reconciliation
seams read it.

### 3-5. Bump version to v1.0.360 ([065404f89](https://github.com/qmu/workaholic/commit/065404f89))

The base reached 1.0.359 while this branch was cut at 1.0.358, so the branch's own number would have
landed on a spent one and contributed no version diff.

## 4. Outcome

A tick can no longer say the channel was quiet when it read part of it, can find a mention nobody
pointed it at, does not stop the whole loop because one unit's merge belongs to somebody else, and
cannot report a request as delivered while two of its three pull requests are open or its deployment
failed. Every new reading is evidence: nothing here clears a gate, merges, deploys or verifies
anything.

## 5. Concerns

- **A route that can never carry `list_thread_changes` reports `observation_incomplete` on every
  tick** rather than `observed_quiet`. That is the honest reading — such a loop cannot prove it saw
  every reply — and it costs nothing, because the word was deliberately separated from the cadence:
  the interval is byte-identical. The alternative, shortening the interval on a standing limitation,
  is a spin rather than a repair.
- **A search is not an index.** Zero rows from the mention search certify nothing, so the reading
  stays `exhaustive: false`. The non-native QFS adapter spells `search_exact` as whole-text equality,
  so only the pipe-SQL route can answer a containment query; `search_exact` is deliberately *not*
  added to a binding's declared `operations`, because a declared operation is a required one and
  declaring it would fail the whole observation on a route that cannot search.
- **`blocked_on` is a judgement the run writes out**, like `interruption_kind`. The reader classifies
  nothing by content, so a run that mislabels its own wait is caught only where the two facts
  contradict each other.
- **One `size` / `too-large-commit` finding** (override tier): commit `ec81d0971`, 630 added lines of
  implementation against a 500 ceiling. A granularity nudge, not a hard block.
- **The local hermetic suite could not complete on this host.** `node scripts/test-workflow-scripts.mjs`
  reached **1586 assertions with zero failures** — including `every shipped shell script parses` and
  `every embedded jq program compiles`, the two rows that catch the defect classes this branch
  introduced — and was then killed (exit 144) while the box was carrying a `rustc` build, two dev
  servers and another session on a single core. CI's own run is the gate and was not overridden.

## 6. Successful Development Patterns

- **Four defects of two families, all in first drafts, all silent.** jq's `//` treats `false` as
  empty, so `X // true` answers `true` for a key explicitly set to `false` — every absent-means-true
  boolean I wrote (`settled`, `observation_settled`, `public_verification`) read the wrong way, and
  the direction of the error is always the dangerous one: *not verified* becomes *nobody looked*,
  *partly read* becomes *quiet*. And `<array> | index(.)` tests the array against itself, because the
  pipe rebinds `.`. Both are now **rules** in `plugins/workaholic/rules/shell.md` — the first stated
  as the generalisation of the convention the degradation readings already carry (*the test is
  `readable == false`, never `readable // true`*) — rather than comments at four call sites. Neither
  is machine-checkable: both programs compile and answer.
- **Capture placement decides whether a discovered message can be routed at all.** Capturing the
  mention search's rows before reading their thread made the thread read see its own message as a
  duplicate, so the classifier dropped it. Capture belongs to whichever surface reads the message.
- **Exit zero is not a passing JSON gate, twice over.** A `>` redirect refused under `noclobber` and
  left a stale file, and `gate-decision.sh` reads stdin rather than `--input`, so passing a flag fed
  it empty stdin — both answered a confident `decision: pass` over a gate that actually said
  `block` / `override_only`. The real gate came from `scan-branch-safety.sh | gate-decision.sh`.
- **A `pgrep`-based waiter greps its own command line** and can never exit; a file-based waiter on
  the job's own exit line cannot match itself.
