## 1. Overview

`/moderate`'s question reconciliation retired a check-in question that was never asked and whose
premise still held, structurally and every tick. It now retires only on a positive reading — the
owning step's own statement that it resolved the key — and reinstates the rows the old rule wrote.

**Highlights:**

1. `question-liveness.sh` answers an additive `resolution` (`proved | unwitnessed | unknown`); the three `liveness` words and both existing consumers are byte-identical.
2. The retirement's evidence is a new word, `owning_step_reported_resolution`, so the old one is never written again.
3. One bounded `reinstate` event returns an extinguished row to `candidate` — never to `asked`.

## 2. Motivation

`reconcile-questions.sh` read `question-liveness.sh`'s `settled` — *the owning step ran and did
not name this key* — as proof the premise had resolved, hard-coding `evidence: {proved: true}`
out of it: an absence presented as a proof, the one shape `drive/reference/claims.md` forbids.
The measured victim was the only route by which *this channel cannot be read* reaches a person.
`inbound-channel-unreadable:<channel>` is composed by the **agent** after `unanswered-asks` runs,
so the step can never name it and it carries only as a substring of the escalation sentence.
Confirmed here: `question-state.sh` answered `state: retired` with `asked_tick: ""` for
`inbound-channel-unreadable:dev-workaholic` while the channel was measurably unreadable in the
same tick — and `register`/`asked` are both no-ops over a retired row, so it was permanent.

## 3. Changes

### 3-1. Retire a question only on a positive reading ([5959c00f](https://github.com/qmu/workaholic/commit/5959c00ff))

`question-liveness.sh` gained `resolution`, read off a step row's own `resolved_keys` with the same
exact-string match `needs_agent` already uses; `reconcile-questions.sh` retires only on `proved`,
reports every untouched row as `not_retired` with its reason, and reinstates the old rule's residue
first. `question-registry.sh`'s `retire` guard is untouched.

## 4. Outcome

The reconciliation can no longer extinguish a question out of silence, and the one live question
this repository held is askable again. No step emits `resolved_keys` yet, so it retires nothing.

## 5. Concerns

### The retirement is unreachable until a step emits `resolved_keys`

- **Severity:** low
- **Description:** No step names resolved keys, so every key reads `unwitnessed` and nothing is retired (see [5959c00f](https://github.com/qmu/workaholic/commit/5959c00ff) in `plugins/workaholic/skills/moderate/scripts/reconcile-questions.sh`). The ticket's chosen trade, stated in the prose rather than left to be inferred.
- **How to Fix:** Have a step that genuinely settles its own subjects emit `resolved_keys` beside `needs_agent`; nothing else changes.

## 6. Successful Development Patterns

- Reproducing the defect against both a throwaway fixture and the live registry before touching code made the legacy-row requirement concrete rather than theoretical — the fixture was then written from the row the checkout actually held.
- Adding a field beside an existing reading, rather than narrowing the reading itself, kept two unrelated consumers byte-identical; narrowing the match would have moved the defect to the next agent-composed key.

## 8. Notes

The registry is per-clone runtime state under `.git/workaholic/runtime/v1/instances/`, so no pull
request can carry a migration to it — every checkout repairs its own copy inside the tick's own
seam, which is why the reinstatement lives in `reconcile-questions.sh`.
