## 1. Overview

The native coordinator's durable record stopped being writable — and then stopped being readable at all — once it grew past a single argument's length limit, and every one of the three failures was silent in a different way. Unbounded values now travel by file rather than through `argv`, what the coordinator stores per worker is bounded, and each refusal answers by its own name.

**Highlights:**

1. `state.sh` passes every record, data block, owner and evidence payload through `--slurpfile`, so no size of record reaches `argv`.
2. Three refusal words — `state_too_large`, `state_write_failed`, `state_unreadable` — replace an empty stdout and a misleading `state_invalid`.
3. The stored `result.report` is bounded and re-bounded on every write, which is the upgrade path for records the old code already wrote.

## 2. Motivation

The record is rewritten in full on every event, so `state.sh` composed the new value from the old one and passed both through `argv` — which Linux caps at `MAX_ARG_STRLEN` (`32 × PAGE_SIZE`: 131,072 bytes here, not the far larger `ARG_MAX`). Measured on a live instance, 24 workers at 2.7–5.4 KB of prose each took `.data` to 129,906 bytes, a `finish` event failed, the receipt stayed `running`, and the record had to be pruned by hand before the loop could resume.

Each of the three sites then failed differently and quietly. The composition left the value empty and the shape assertion answered `state_invalid` — the wrong cause, with nothing written. The success render failed *after* the record had landed on disk, exiting 2 with empty stdout while the revision had advanced, so a caller read failure, retried, and collided with its own successful write. And the read render failed the same way, so `coordinator.sh` read an empty file and every coordinator event — a plain read included — answered with total silence carrying no reason word.

## 3. Changes

### 3-1. Keep the coordinator record writable past the argument cap ([11d177d6c](https://github.com/qmu/workaholic/commit/11d177d6c))

Every unbounded value in `state.sh` now travels by file out of one trap-cleaned scratch directory, and `lib/result.sh` gained `runtime_json_result_file` beside the existing function rather than changing its signature. The success result is rendered *before* the record lands, so every refusal reachable at the write seam leaves the record byte-identical; `lib/coordinator.jq` bounds each stored `result.report` to 1200 characters while the finishing tick still relays that worker's full report.

## 4. Outcome

A record far larger than the argument cap is created, updated and read back correctly, and the ~100-byte window where the old code wrote and then reported failure is closed by ordering rather than by size. `coordinator.sh` answers `state_unreadable` with the stage instead of exiting silently, and the store no longer grows with the loop's own history.

## 5. Concerns

### The relay is lossless only for the tick that records the finish

- **Severity:** low
- **Description:** `completed[]` carries the finishing worker's untruncated report by substituting the incoming result, but a worker completed on an earlier tick and reported later is read from the bounded store (see [11d177d6c](https://github.com/qmu/workaholic/commit/11d177d6c) in `plugins/workaholic/skills/runtime/scripts/lib/coordinator.jq`)
- **How to Fix:** If a later reader ever needs the full prose, carry it where the finish log already goes rather than widening the durable record, which is the growth this change exists to bound

### The base is red for an unrelated reason and this branch cannot merge over it

- **Severity:** moderate
- **Description:** `validate` fails on `4b6b2e444` because a 34th `/moderate` step was added while three `33` constants stayed pinned — `delivery-report.test.mjs:73`, `:74` and `polling-cost.test.mjs:86` — attributed to [#1224](https://github.com/qmu/workaholic/pull/1224); proved failing on the untouched base
- **How to Fix:** Raise those three constants to the registry's own length, or derive them from `moderate/scripts/steps.json` so the next added step cannot reproduce it

## 6. Successful Development Patterns

- Reproducing both failure modes against the pre-change code first made the ordering fix visible: the dangerous half was the write that *succeeded* and reported failure, not the one that refused.
- A `--slurpfile` guard tests the array's **length**, not the value's type — testing the type folds the caller's malformed input into our own staging failure and silently retires the one path that still reaches `state_invalid`.
