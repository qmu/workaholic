## 1. Overview

`main` was red: the `validate` check failed because `plugins/workaholic/skills/moderate/scripts/steps.json` holds 34 steps while three assertions still pinned the literal `33`. The branch replaces those literals with a named, ordered pin in one file and a derivation in the other, so a registry change now fails with the step id that moved rather than with `34 !== 33`.

**Highlights:**

1. Pin the moderation registry by name, clearing `main`'s red `validate` check
2. Replace the duplicate-count check with a number-free invariant that keeps working at step 35
3. Record a latent planner defect the probes exposed as its own ticket rather than fixing it here

## 2. Motivation

The three literals all arrived in `0ef45bad5` (#1080) and were never touched again, so they went stale on the **first** step addition after it — `worktree-sweep`, added by PR #1224. That is what a bare integer guarantees. `main` does not gate merges on remote CI, so this red blocked no unit, but it is the ground every unit lands on, and a base left red over a stale constant trains everyone to ignore the colour.

The repository had already learned this lesson twice against this same registry, from both sides. `scripts/e2e/loop-drill.sh:1326` derives its expected count from `steps.json` and carries a 2026-08-26 comment recording that the literal "went stale every single time a step was added"; `scripts/test-workflow-scripts.mjs`'s `moderateSteps()` helper and all fourteen of its consumers assert membership and ordinal position **by name**. The two `node --test` files were the last place in the repository still counting.

## 3. Changes

### 3-1. Pin the moderation registry by name, not by a count that goes stale ([72683bce0](https://github.com/qmu/workaholic/commit/72683bce0))

`delivery-report.test.mjs` now compares the registry's ids against a declared, ordered `EXPECTED_STEPS` list with `deepEqual`, and its duplicate check became `new Set(ids).size === ids.length` — an invariant carrying no number at all. `polling-cost.test.mjs` hoists the `steps.json` read it already performed one line below and derives its cold-tick expectation from `registry.steps.length`.

## 4. Outcome

`node --test scripts/tests/agentic-loop/*.test.mjs` is green at 147/147 on the 34-step tree, which is the check that was red on `main`. The two numbers were deliberately **not** collapsed into one constant: `delivery-report.test.mjs` asserts the registry's own contents, while `polling-cost.test.mjs` asserts that `plan-steps.sh` selects all of them on a cold tick. One is a fact about a data file, the other a fact about a script under test, and a shared constant would let one edit silently satisfy both.

The `open-log` / `human-checkin` bookends and the per-row shape loop were kept beside the `deepEqual` although it subsumes them, so a violated bookend still fails with its own message rather than inside a 34-element diff. `loop-drill.sh:1326` and `test-workflow-scripts.mjs`'s `moderateSteps()` were read and confirmed to pin no literal count; neither was touched.

**Probe results**, run against a scratch copy of the registry and restored after each — each fails `delivery-report.test.mjs` naming the exact id:

| Probe | Failure |
| --- | --- |
| Add `fabricated-probe` | `AssertionError … Expected values to be strictly deep-equal: + 'fabricated-probe'` |
| Remove `retire-claims` | `… - 'retire-claims',` |
| Swap `doc-drift` / `release-status` | `… + 'release-status', - 'release-status',` — a case the literal count could not catch at all |

**The derived `polling-cost.test.mjs` assertion passes all three probes, and that asymmetry is correct rather than a hole.** It asserts that the planner selects everything on a cold tick, which stays true at any registry size; the registry's own contents are what `delivery-report.test.mjs` pins.

## 5. Concerns

### The moderation planner stops answering at the 35th step

- **Severity:** moderate
- **Description:** Under the add probe, `polling-cost.test.mjs`'s row still fails — not at the derived assertion, which passed with `35 === 35`, but at the pre-existing second-tick assertion (line 97). Measured directly: with a 35th step, `plan-steps.sh` emits empty stdout and `jq: error … Cannot index string with string "seconds"`, while the same sequence is green at the tree's real 34 steps. Both scripts involved (`runtime-plan.sh`, `plan-steps.sh`) are untouched by this branch (see [72683bce0](https://github.com/qmu/workaholic/commit/72683bce0)), so this is a latent property the next step addition will expose, not a regression here.
- **How to Fix:** Ticket `20260919141500` records the reproduction and both observed signals — a 1024-byte cut in one run and a shape error in another — without asserting a cause, and requires the repair's story to name which one it was.

## 6. Successful Development Patterns

- Probing a pin by mutating the fixture it guards — add, remove **and** swap — is what showed the named set to be strictly stronger than the literal: the swap passes a count-based assertion and fails a name-based one, which no amount of reading the code would have demonstrated.
- Restoring the mutated fixture by `cp` from a scratchpad backup rather than by `git restore` kept the probe inside the failure contract's safety floor while leaving the tree verifiably byte-identical between probes.
