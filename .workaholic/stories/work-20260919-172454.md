## 1. Overview

A batch a person reviewed as one pass now arrives as one mission, one claim, one pull request and
one report. Two seams moved — the ingest judgement gained a named case, the driver's grouping bar
a second grounds — and a third act carries an operator's granularity correction onto work already
split.

**Highlights:**

1. Rule 2 names the review-batch case: one review surface, one feedback thread, one coherent acceptance walk.
2. A shared `feedback:` ref is grounds for one PR-unit, beside `depends_on`; `plan-units.sh` groups nothing.
3. `mission/scripts/regroup-tickets.sh` carries an announced regroup, all-or-nothing and idempotent.

## 2. Motivation

One continuation thread was published as nine loose tickets on one proposal pull request and
driven through four implementation pull requests. Two rules produced that shape and neither was
wrong alone: the 2026-09-03 ingest term wants a mid-term plan before it will hold a mission, and
`/drive` §2 named `depends_on` as the only grounds for grouping. Together they maximised
atomicity against the one unit that actually matters — the developer's single review pass.

The 2026-09-03 term was itself measured (eight asks, seven missions, forty-eight tickets in
twenty-one minutes) and this branch reopens none of it: the two rules answer different questions,
and saying which is which is most of the work.

## 3. Changes

### 3-1. Name the review-batch case in the mission rule ([5e3363ce1](https://github.com/qmu/workaholic/commit/5e3363ce1))

Rule 2 in `rules/workaholic.md` gained one named case — a batch sharing one review surface, one
feedback thread and one coherent acceptance walk is a mid-term container — with all three terms
required and release, dependency, ownership or risk evidence separating it. Both `/specificate`
surfaces cite it in one byte-identical wording, and the run reports `mission_held_by:review_batch`
so a mission held by a review unit never reads like an ordinary one.

### 3-2. Name a shared feedback ref as grounds to group ([bca7de52d](https://github.com/qmu/workaholic/commit/bca7de52d))

`/drive` §2 and `reference/routing.md` name a shared `feedback:` ref as the second grounds, read
through the relation's one reader. `plan-units.sh` gained the `feedback_refs` annotation and
**no grouping**: its offer, every exclusion reason and the header's own no-heuristic claim are
unchanged, so the judgement stays with the executor.

### 3-3. Regroup queued tickets on an announced ruling ([f87bd225e](https://github.com/qmu/workaholic/commit/f87bd225e))

`mission/scripts/regroup-tickets.sh` writes the `mission:` relation onto an explicitly named set
of queued tickets and appends one changelog line. It copies `carry-attribution.sh` property for
property — explicit announcement, all-or-nothing, idempotent, every bound refused by its own word
with the tree byte-identical — and lands at `/specificate` step 9f.

## 4. Outcome

The batch grain is stated where each seam reads it, and an operator catching the fragmentation
mid-flight has an act rather than a hand edit. Nothing was loosened — the two-ticket floor, the
ceiling and the mid-term-plan term refuse as before, `check-floor.sh` and `size.sh` byte-identical.

## 5. Concerns

### The review-batch case could return mission proliferation

- **Severity:** moderate
- **Description:** rule 2 was measured against one mission per inbound ask, and a case that reads *this batch is one review pass* is the kind of judgement that widens under pressure (see [5e3363ce1](https://github.com/qmu/workaholic/commit/5e3363ce1) in `plugins/workaholic/rules/workaholic.md`)
- **How to Fix:** the bound is that **all three** shared terms must hold; re-measure the mission size distribution if two- and three-ticket missions reappear, and tighten the case rather than the floor

### The regroup's non-auto-merge is the caller's rule, not the seam's

- **Severity:** moderate
- **Description:** `publish-tree-pr.sh`'s `ruling_touching` test fires on a mission whose diff moves its `feedback:` line, and a regroup moves a ticket's `mission:` line, so the seam cannot derive the refusal (see [f87bd225e](https://github.com/qmu/workaholic/commit/f87bd225e) in `plugins/workaholic/skills/specificate/reference/workflow.md`)
- **How to Fix:** it is stated plainly at step 9f and pinned by a test over that step's own text, the same weaker guarantee step 9e records; widening the seam's test to the ticket relation would settle it mechanically

### A regrouped batch may breach the mission ceiling

- **Severity:** low
- **Description:** the act writes the relation for every ticket the operator named, and the mission's `## Acceptance` ceiling is normative rather than checked here (see [f87bd225e](https://github.com/qmu/workaholic/commit/f87bd225e) in `plugins/workaholic/skills/mission/scripts/regroup-tickets.sh`)
- **How to Fix:** report the breach and let the operator decide — silently trimming their own ruling is the worse act; a `size.sh` reading beside the regroup's output would make it visible

## 6. Successful Development Patterns

- Copying an existing writer property-for-property (`carry-attribution.sh`) made the new act's admissibility argument short: the four bounds are cited, not re-argued.
- Reading a floor's own header before claiming it covers something caught a traceability claim that was about to be implied rather than stated.
