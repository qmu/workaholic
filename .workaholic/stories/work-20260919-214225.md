## 1. Overview

`delivery-report.test.mjs`'s `P8 maintenance registry` row held a literal copy of `steps.json`'s
step order. A copy of a derived list goes stale on the first change that is not made in the same
pull request, and this one did — twice in two days, both times turning `main` red for every runner
building on it. The row now derives both halves of its own name from sources that are not the
list: **complete** against the `step-*.sh` files that ship, in both directions, and **ordered**
from the adjacencies `reference/workflow.md` states.

**Highlights:**

1. `EXPECTED_STEPS` is gone. Adding a step is one edit — the registry, plus its script — and no
   second list anywhere needs the same edit.
2. The completeness check is **stronger** than the list it replaces: the literal list never
   checked that a registered step's script existed at all.
3. Five registry mutations were run against the new row and each fails with its own named
   message, so the row is not passing vacuously.

## 2. Motivation

The row has now been written three ways and the first two were the same defect.

A bare `length` pin failed `34 !== 33` when `worktree-sweep` landed (PR #1224), naming nothing.
PR #1231 replaced it with the ids **by name**, which fixed the message and kept the mechanism: a
literal copy of `steps.json` living in a test file. The same day, PR #1239 added
`unattributed-asks` and `propose-yield` to the registry. Both branches were green against their
own base; `main` went red on merge and stayed red, which is what this ticket was written against
and what `read-base-checks.sh` reported as `state: red`, `validate` failing.

By the time this unit was claimed the **symptom** had already been patched on the base by PR #1246,
which appended the two names to the list — implementation step 2 of the ticket, and precisely the
repair its own Considerations forbid: *leave the two lists derived from one source or pinned in one
place, rather than adding a third copy of the order.* The suite was green on claim (163/163) and
the work taken here is the other half. Without it the next concurrent step addition reproduces the
same red.

Two things were established before changing anything. `run.sh` derives its step list from the
registry (`jq -r '.steps[].id' steps.json`), so there was never a second *runtime* ordering to
reconcile — the two lists that disagreed were the registry and the test's literal. And
`reference/workflow.md` says in its own words that its section numbering is authoring order rather
than run order, and that the registry is the contract; so copying the registry into a test proves
nothing about a contract that lives in the registry.

The repository had already reached the right shape twice and said so.
`polling-cost.test.mjs` compares `plan-steps.sh`'s selected count to the registry **because the
planner is the subject**, with a comment naming the distinction — *rather than restating
`steps.json` to itself* — and stays green at any registry size. `loop-drill.sh:1326` derives its
own count, recorded 2026-08-26.

## 3. Changes

### 3-1. Derive the P8 registry contract from the step set ([835bf0ac6](https://github.com/qmu/workaholic/commit/835bf0ac6))

**Complete**, against the tree in both directions: the registry's `script` values compared to the
`step-*.sh` files in `moderate/scripts/`, plus `script == "step-<id>.sh"` per row so the two lists
compare on a name that carries the id. A shipped-but-unregistered step never runs; a row whose
script is missing reports `degraded`/`step_missing` every hour. Neither was checked before, and
neither needs an edit when a step is added.

**Ordered**, from the reference and nowhere else, each assertion carrying its own message:
`open-log` first (nothing may log before the log is open), `human-checkin` last (it asks with every
finding in hand), `file-findings` after the steps whose reports it files (§25: *reordering the run
to close that window would put the filing before its own inputs*), `direction-health` immediately
after `strategy-pace` (§15), `date-will-not-hold` immediately after `direction-health` (§15a). The
rest of the sequence is a registry authoring decision the reference explicitly declines to fix, so
pinning it would be pinning a non-contract.

Per-step identity stays pinned where each step's own change lives: `test-workflow-scripts.mjs`
already carries a `moderateSteps().includes('<id>')` row for both steps PR #1239 added, so a
registry change is still **stated by the pull request that makes it** — which is what PR #1231's
comment said the row was for — rather than absorbed.

Two stale absolute positions in `reference/workflow.md` were repaired in the same change, being the
same defect in prose: *tenth in `run.sh`'s `STEPS`* and *fifteenth*, the second also asserting an
adjacency (`unanswered-asks` immediately before `human-checkin`) that `file-findings` now sits
inside. Both were rewritten to the relation that is load-bearing, and the adjacencies the
reference states are now exactly the ones the row asserts, so the two cannot drift apart silently.
`moderate/SKILL.md` records that nothing copies the registry and what the row derives instead.

The base had reached `1.0.379` under this branch; the three hand-maintained manifests were raised

## 4. Outcome

Adding a moderation step is one edit again. The registry is the single source of its own order,
the test asserts properties rather than a copy, and the completeness check covers a failure the
copy never could. `main`'s `validate` check was already green when this branch was cut — PR #1246
had patched the symptom — and this change removes the mechanism that produced it.

Five mutations were run against the new row, the registry restored after each: a registered row
whose script does not ship; a shipped script dropped from the registry; `direction-health` moved to
the end; `strategy-pace`/`direction-health` swapped; `file-findings` swapped with the step before
it. All five fail, each with its own named message.

## 5. Concerns

### The deferred-concern judge was not run on this branch

- **Severity:** moderate
- **Description:** `/story` Phase 1 judges the open concern set. The set on this repository is in
  the hundreds and judging it was outside this unit's budget, so no verdict was applied and no
  superseding record was written.
- **How to Fix:** run the judge seam on a branch with budget for it, or bound the open set.

### The mid-list order is no longer pinned anywhere

- **Severity:** low
- **Description:** a step moved between two positions that neither bookend nor a stated adjacency
  covers now changes the run order with nothing failing. This is deliberate — the reference calls
  that order an authoring decision rather than a contract, and pinning it is what produced the red
  base twice — but it is a real reduction in what the row catches, and it is stated rather than
  implied.
- **How to Fix:** if an ordering there turns out to be load-bearing, state it in
  `reference/workflow.md` beside the three that already are, and add the assertion that reads it.
  The rule is that the reference states the invariant and the row asserts it, never the reverse.

## 6. Successful Development Patterns

- **Pattern:** a test that restates its subject proves nothing and goes stale; a test whose
  assertion has a source other than the subject proves a property and survives.
  **Context:** the distinguishing question is *where does the expected value come from*. Here the
  registry's completeness comes from the filesystem and its ordering from the reference document,
  so neither expected value is the registry itself. `polling-cost.test.mjs` had already drawn the
  same line in its own comment, and this row now matches it.
- **Pattern:** mutate the artifact and confirm the new assertion fails, before trusting a green
  run on a change that removes assertions.
  **Context:** replacing a `deepEqual` over 36 elements with five narrow assertions is exactly the
  shape that can pass vacuously. Each mutation was run against a restored registry and checked for
  its own message, not merely for a non-zero exit.
