# Refuse a killed check, and declare the outcome token a finish line carries

## Summary

- A required check in the local proof set could be **killed part-way and still report `ok: true`**, so a `main`-bound merge stood on a check that proved nothing. It now refuses.
- `/moderate`'s `propose-yield` step could not read the log it was built to read and answered `degraded` on **every** run, while two composite outcomes carrying originated tokens were silently classified as *nothing*. The vocabulary is now declared once and read as a field.

## Overview

Two measured defects from issue #1248, each a reading that answered confidently and wrongly.

**The killed check.** `local-proof.sh` classified exit `137` — `128 + SIGKILL` — into the `124` timeout arm. A check the kernel ended part-way therefore reported `ran: false`, `reason: "timeout:0s"` on a row declaring *no* timeout, landed in `not_run` rather than `failed`, and left `ok: true`. Both consumers refuse on `ok: false` alone, so the push went through. Reproduced exactly: a throwaway repository whose `scripts/build-plugins/verify.mjs` is `process.kill(process.pid, "SIGKILL")`, run as `--only verify.mjs`, answered `{"ok": true, "complete": false, "not_run": ["verify.mjs: timeout:0s"], "failed": []}`, while the same command run directly exits **137**.

**The unread outcome.** `step-propose-yield.sh` enumerated its token set on the reader's side — its own header conceded that could only ever be a guess about what writers produce — and the guess was wrong on ordinary traffic. Measured over this checkout's newest two day files, `completed`, `published_and_merged` and `published` all fell outside it, so the step answered `degraded` and never once reached its finding. Worse and silently, its `if` chain tested the **whole summary line** and took the first arm that matched, so two composite rows carrying `proposed_6` and `proposed_mission` — each an originated token in that reader's own set — were classified `nothing`.

## Changes

### Changed — a killed required check refuses, and is not a timeout

`branching/scripts/local-proof.sh` splits `137` out of the `124` arm **on whether a timeout was applied**, never on the status alone: GNU `timeout` exits `137` when its own `--kill-after` escalation had to SIGKILL the child, so a row that *declares* a timeout keeps `124` and `137` as one byte-identical reading — the measured `agentic-loop.test.mjs` case the declaration comment already records. A row declaring `timeout 0` reads `ran: true, ok: false, reason: "killed:SIGKILL"`, joins `failed`, and refuses through the **existing** `validation_failed:<check>` word. No consumer's vocabulary moved and no `case` arm was edited.

The ticket's `## Open Decisions` was settled here, by reading both sources it named. `local-proof.sh`'s own header and `drive/scripts/catch-up-claim.sh:393-396` state the same split and give the **same one reason** for it: *a consuming repository that carries none of these files must keep pushing exactly as it did*. That reason is about `check_absent`. A kill is not that — the check is present, it started, and something ended it — so the rationale for `complete: false` never refusing does not reach this case. Option (B), a third refusing term in `not_run`, was refused because it makes two consumers grow an arm they can forget to read, which is the defect this ticket is about. Option (A)'s stated cost — that `ran: true` for a process with no verdict is inaccurate — is avoidable: `ran: false` is reserved in this script for a check that was never **launched**, and the reason string carries the signal.

### Changed — the proof set runs under a TMPDIR it owns, outside every repository

A per-run directory under `${XDG_CACHE_HOME:-$HOME/.cache}/workaholic/`, exported around each check and removed on every exit path by an `EXIT` trap. `test-workflow-scripts.mjs`, all 16 files under `scripts/tests/agentic-loop/` and `loop-drill.sh` create fixtures under the OS temp directory and nothing declared one; on this machine `/tmp` is a 3.8 G **tmpfs** holding 2.1 G of 7.7 G of RAM with **no swap**, 89,959 top-level entries, under up to 7 concurrent copies of the same suite.

**It reduces pressure and does not remove it** — the abort that produced the ticket was measured with `TMPDIR` already on local disk — so it is mitigation and the repair above is the fix.

### Changed — one declaration of what a finish line's outcome says about yield

`runtime/scripts/outcome-classify.sh` is the one declaration and the one reading: it parses each summary as JSON, reads **`.outcome` and never `.reason`**, splits a composite on ` / `, and applies a stated precedence — **any originated segment wins**. Four classes, and the last two are deliberately not one: `unmeasured` is a *recognised* terminal word carrying no yield (`worker-result.schema.json`'s own `ok | pending | blocked | failed`, plus `not_executed`, `unreadable`, `completed`) — the **writer** could not say — while `unclassified` is a token outside every set or a summary that is not JSON — the **reader** could not read it. `step-propose-yield.sh` composes it and spells no token; `outcome_unclassified` keeps its name and `outcome_unmeasured` joins it.

### Changed — both finish writers emit one shape

`work/scripts/codex-loop.sh`'s two `loop-finish-<role>` calls wrote prose while `runtime/scripts/coordinator.sh` wrote structured JSON into the same day files, so no reader could take `.outcome` as a field — measured on this checkout, **75** such lines, **54** JSON and **21** prose, some Japanese. Both now write `{executed, outcome, reason}`. The success arm says `ok`, which is what it honestly measured: no token was invented for a yield that path never measures.

### Changed — an originated tick settles the step before unread entries are consulted

The step tested `unclassified` **before** `originated`, so one unreadable entry suppressed a conclusion it cannot weaken. The rule the file has always stated is narrower than the code was — an unread entry makes *every tick originated nothing* a claim it has not established — so `originated > 0` now answers `ok` first, and the unread entries are consulted exactly where that claim is about to be made. This is what lets the step answer `ok` against the live log instead of `degraded`.

## Concerns

**[moderate] The `TMPDIR` mitigation cannot be verified by counting `/tmp` entries on a shared machine.**
The ticket's acceptance criterion asked for the absence of `workaholic-*` / `wh-*` prefixes directly under `/tmp` before and after. On this machine 106 such directories already exist from other agents' concurrent runs, so no count is attributable to one run. It was proved the stronger way instead — a check printing `os.tmpdir()` saw exactly the path the runner reported — but the count-based criterion as written is not measurable here.

**[moderate] Two concurrent runs of the proof set against one repository share their log paths.**
`${LOG_DIR}/.local-proof-<name>.log` is keyed on the check name and not on the run, so overlapping runs clobber each other's logs and neither's output is attributable. Observed directly while verifying this branch: it led to two wrong readings of an abort that had not happened. Not repaired here — it is outside both tickets — but a run-unique log name would fix it.

**[low] A repository driven only through the Codex path will now read `outcome_unmeasured` rather than ever reaching the yield finding.**
That is honest — `worker_outcome()` normalises to a terminal token that carries no yield for any role — but it means the step's finding is reachable only where the native coordinator writes the richer outcome. The remedy is for that path to report what it originated, which is a separate ask.

## Successful Development Patterns

- **The proof set caught a regression in the change that added it.** Ticket 1 step 5 prescribed `${LOG_DIR}/tmp.$$` — inside `.git/` — and `scripts/tests/agentic-loop/legacy-contracts.test.mjs` asserts the *outside-repo refusal* of four publication scripts, so a `TMPDIR` under `.git/` makes git resolve the enclosing gitdir and answer `fatal: this operation must be run in a work tree` (status 128) where the test expects `{"error": "not inside a git repository"}` (status 1). Measured both ways on that one file: exit 0 on plain local disk, exit 1 under `.git/`. The runner now **proves** its scratch directory is outside every repository before using it rather than documenting the constraint.
- **Reading the two sources an Open Decision named settled it in one step.** Both gave the same single rationale, and that rationale was about a different case — which is a stronger answer than weighing the two options' costs against each other.
- **A degraded arm placed above an ok arm suppresses conclusions that unreadability cannot weaken.** Worth checking wherever else that ordering appears: an existential claim survives missing data, a universal one does not.
