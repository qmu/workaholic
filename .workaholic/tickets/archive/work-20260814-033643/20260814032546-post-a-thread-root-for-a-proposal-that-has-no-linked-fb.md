# Post a thread root for a proposal that has no linked FB

## Overview

PROPOSED. When a `[Propose]` tick finishes and `workaholic:notify`'s stateless lookup
finds no existing thread (case 4), the `🔵 Proposed` finish line is itself posted as the
new top-level root. The reporter asks for a different arrangement in that case: Claude
first posts a short description together with the FB's URL — **carrying no `@Claude`
mention** — and then posts `🔵 Proposed` as a threaded reply to that message, so the
item's Slack thread opens with something a human can read and reply to rather than with a
status line. The report's title asks additionally that a short FB issue be auto-filed for
a proposal that has no linked FB, so the root has a URL to point at; whether that half is
adopted, and what the root links when it is not, is left as an Open Decision below rather
than resolved unattended.

The change is a notification-model change, so it is not finished when the propose run
posts differently: `workaholic:notify` states the model once, its `reference/notifications.md`
is the shape catalog, and *The prompt is the ceiling — no self-authorized shapes* means the
`[Propose]` routine template must name the new post before any session may emit it. All of
that lands in one change; splitting it would ship a documented-but-unauthorized shape.

## Open Decisions

- **Whether a short FB issue is auto-filed at all, and what the root links when it is not.** Options: (A) the run opens a short `[FB]` issue on this repository through `feedback/scripts/open-issue.sh` and the root links it, as the report's title asks; (B) no issue is filed and the root links the feedback record's file URL on `main`, as the report's body ("the FB's URL") also reads. Neither is clearly recommendable: (A) creates a class of unattended write the crossing rules currently reserve for *other* repositories, and it interacts with clock-fired discovery — an issue filed **assigned** would be re-discovered as an inbound ask on the next tick and cannot be excluded, because the record naming it was already written and records are immutable; an **unassigned** issue is never discovered, which makes it safe and also makes it a page nobody is asked to act on. (B) writes nothing outside the repository and gives the human no GitHub thread to reply in, which is the affordance the report is asking for.
- **What "a proposal that has no linked FB" selects.** Options: the lookup's case 4 (no thread was found, whatever the ask carried) versus "the ask carried no originating `[FB]` issue" (which can be false while a thread still exists, and true while one does). Case 4 is the only branch where no root exists to reply into, so it is the reading this ticket's steps assume — but it is not what the report's words literally say, and picking it silently would answer a question the reporter may have meant differently.

## Considerations

- The ceiling rule means the template edit is load-bearing, not documentation: a session may emit only the shapes its own routine prompt names (`plugins/workaholic/skills/notify/SKILL.md`, *The prompt is the ceiling*). Shipping the model change without the template edit ships a shape nobody may post; shipping the template edit without re-syncing the account routine leaves the live prompt behind (`/setup-routines` commonly reports `no_transport`, so this is an operator step, not a code step).
- Two messages per proposal raises the channel's volume against the bright line "an event earns its post" (`plugins/workaholic/skills/notify/SKILL.md`) — the root is not a new event, it is the same event split into a readable header and a status line. Say so where the shape is written, so a later reader does not mistake it for a second announcement.
- The root must carry `` `fb:<stem>` `` or the whole stateless lookup regresses: case 2 searches for that key, and moving it onto a message the finish line replies to is fine only as long as the root itself carries it (`plugins/workaholic/skills/notify/SKILL.md`, case 2).
- The case-3 query defect in Related History is still open and unproposed; if it lands first, fewer runs reach case 4 at all. Neither change blocks the other, but a run measured under the defect will over-report how often the root is needed (`plugins/workaholic/skills/notify/SKILL.md`, case 3).
- Whatever the root's link target, it must not be a Slack thread coordinate written into a public artifact — that reintroduces the exposure the P9 withdrawal refused (`plugins/workaholic/skills/notify/reference/notifications.md`, *The carried-target disclosure*).

### Open Decision 1 — no issue is auto-filed; the root links the feedback record (option B)

Option A (file a short `[FB]` issue and link it) is refused on two grounds that are
measurable rather than stylistic. An **assigned** issue is re-discovered as an inbound ask
by `list-inbound-issues.sh` on the next tick and **cannot be excluded** — the exclusion set
is "issues a feedback record already names", and the record naming it was written before it
and is immutable — so it would propose itself in a loop with no clean exit. An **unassigned**
issue is never discovered, which makes it safe and simultaneously makes it a page nobody is
asked to act on. Independently, opening an issue on this repository unattended is a new
class of write: the confinement rule reserves issue-opening for `/fb`'s cross-repository
mode behind a verbatim human confirmation, and a routine may not grant itself that.

Option B answers the ask as stated — the reporter asked for "a short FB and its URL", and
the feedback record *is* the FB in this project's vocabulary. Accepted cost, stated rather
than hidden: the `main` blob URL 404s until the proposal's pull request merges. It
auto-merges on opening, so the window is seconds; when a scan finding holds the PR open the
run reports the link as pending instead of claiming it resolves. Precedent for the link
form already exists in the channel (the `📝 FB registered` post of 2026-08-10).

### Open Decision 2 — "no linked FB" selects the lookup's case 4

Case 4 is the only branch where no root exists to reply into, so it is the only branch where
one must be created; the alternative reading ("the ask carried no originating `[FB]` issue")
would post a root into a thread that already has one — two roots with one key, the exact
defect the not-found branch is written to avoid. The reporter's stated goal is also only
unsatisfied in case 4: when a thread exists, its root is already the human's own message.
Mechanics and intent agree, so case 4 it is.

### Scope ruling the ticket did not ask for, recorded because it changes what shipped

Case 4 is shared by `/propose` **and** `/implement`. The description root is scoped to
`/propose` alone: extending it to `/implement` would emit a shape the `[Implement]` routine
prompt does not name, which *The prompt is the ceiling* forbids however well documented the
shape is. `/implement`'s case-4 finish line stays its own keyed root, and both the skill and
the catalog say so by name.

### Discovered Insights

- **Insight**: The channel evidence shows two distinct failure modes wearing one symptom —
  a legitimate case 4 (no thread was ever created) and the case-3 query-form defect (a
  findable thread was missed). They need opposite fixes, and only the first is what this
  root is for.
  **Context**: FB `20260813121647` is still open and unproposed. When it lands, fewer runs
  reach case 4 at all, so any future measurement of "how often the root is needed" taken
  before that fix will over-count — as the ticket's own Considerations predicted.
- **Insight**: `/propose`'s clock-fired discovery makes a self-filed assigned issue
  structurally un-excludable, because the exclusion set is keyed on records that are written
  before the issue exists and are immutable afterwards.
  **Context**: This turns "should a routine file its own issue?" from a taste question into
  a mechanical one, and the same argument applies to any future proposal to have an
  unattended run open issues on its own repository.
- **Insight**: The `[Propose]` template and the shape catalog use different placeholder
  vocabularies (`{repo}` vs `<repo-url>`), so "byte-identical" was only achievable for the
  new block by copying the catalog's placeholders and saying so in the template's prose.
  **Context**: The new test compares the fenced blocks verbatim; a future edit that
  "normalizes" the root's placeholders to `{repo}` will fail that assertion, which is the
  intended behavior, not a bug in the test.
