# Rename /fullfill to /prepare-release

## Overview

<!-- PROPOSED. Merging the pull request this was published on is what turns it from a
     proposal into queued work. -->

Rename the `/fullfill` command to `/prepare-release`, and rename the routine record
`[Release Status]` to `[Prepare Release]` so the routine's heading matches the command it
runs. Issue #485 asks for both halves in one breath.

**This deliberately reverses two decisions made a day earlier** (2026-08-17, PR #484,
ticket `20260817113323-rename-release-status-to-fullfill`), and the ticket is written that
way rather than as a fresh idea:

1. `/release-status` became `/fullfill` **for a one-word command naming convention**. The
   new ask states its own reason for reversing that: the name should describe what the
   command does (preparing a release) rather than optimize for a single word. Behaviour is
   unchanged by either rename — the command is still a pure reader.
2. The routine record was left named `[Release Status]` as that ticket's recorded **Open
   Decision 2**, with a stated cost: `/setup-repo-routines` converges an account's routines
   **by name**, so renaming the template's `name:` does not rename an operator's existing
   routine — the next convergence creates a *second* one, and a routine is an account-level
   record no other account can list or delete, so the old `[Release Status]` keeps firing
   hourly beside it until its owner removes it by hand.

That cost has not gone away; the ask overrides the decision, not the mechanics. The rename
therefore has to ship **with** the one-time cutover instruction, not instead of it.

   `grep -rn "Release Status\|Release status" plugins/ scripts/ docs/ CLAUDE.md README.md`.
   Record the hit list; every hit must end up either changed or explicitly accounted for, the

   Confirm `list-routine-templates.sh` and `render-setup-sheet.sh` read the id from the file
   rather than a hardcoded list — if any list is hardcoded, it is part of this step.
4. Ship the cutover instruction with the rename: `/setup-repo-routines`' report and the
   rendered setup sheet must say, once, that an account already running
   `[Release Status] <repo>` should **rename that routine** rather than create a second, and
   that nothing in the plugin can detect or remove a duplicate on another account (the
   account-level-record limit `/setup-repo-routines` already states).
5. Update every prose reference from step 1's hit list: skills, references, runbooks,

6. Update the literal-string assertions in `scripts/test-workflow-scripts.mjs` and the
   `verify-status` text in `scripts/e2e/loop-drill.sh`.
7. Resolve Open Decision 1 below **explicitly in the Final Report** before touching (or
   deliberately not touching) the `📦 Release status` post shape.
8. Regenerate and verify: `node scripts/build-plugins/build.mjs`, `verify.mjs`,
   `validate-metadata.mjs`, `node scripts/test-workflow-scripts.mjs`,

1. **Is the Slack post root `📦 Release status` in scope?** The ask says "update the
   routine's notification heading from `[Release Status]` to `[Prepare Release]`". It names
   the **routine record's name** literally, but "notification heading" also describes the

   the 2026-08-17 ticket left the post shape alone on a stated reason: it names the **event**,
   not the command, and its prefix is the notify lookup's own exact-string dedup key, so
   changing it posts one duplicate line at the cutover. Renaming the record only is the
   literal reading of the ask; renaming both is the consistent one. Neither is recommendable
   over the other without the reporter, and the run must state which it took.

  hand-edited; the `Outputs Freshness` CI fails on any drift.
