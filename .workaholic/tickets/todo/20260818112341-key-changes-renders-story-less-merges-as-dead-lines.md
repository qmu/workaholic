# Key Changes renders story-less merges as dead lines

## Overview

<!-- PROPOSED. What this ticket would implement and why, from the feedback and
     repository state the proposal grew from. Merging the pull request this was
     published on is what turns it from a proposal into queued work. -->

Issue #496 reports that the `marketplace` draft release note's `## Key Changes` section
rendered entries whose entire content was `no branch story on the base`. The section is the
note's one summary of what is shipping, and a line that says only "there is no summary here"
carries nothing for a reader.

`ship/scripts/draft-release-note.sh` builds the section by walking every merge subject in the
range, extracting the `work-*` branch name, and preferring `.workaholic/stories/<branch>.md`'s
Overview first sentence. When no story file exists it emits the placeholder line above. A
`/propose` pull request is published through the publish tree and auto-merges without ever
running `/report`, so it structurally never has a story — and proposal merges are the most
frequent merge kind in this repository, which is why the placeholder is not a rare fallback but
a routine one.

The reporter's causal account should be checked before it is built on: it says the renderer
"takes the most recent merges regardless of kind", implying a selection or cap. Reading the
script at `plugins/workaholic/skills/ship/scripts/draft-release-note.sh:168-214` shows no
selection and no cap — it emits one line per merge in the whole range. Rendering the current
base confirms the shape: story lines and placeholder lines interleave across a long section
rather than three placeholders being *chosen* over available stories. So the defect to fix is
the **placeholder's content**, and whether "prefer" implies any selection at all is an open
decision below.

## Implementation Steps

<!-- The ordered steps. A proposal is judged on these, so they are the point. -->

1. **Reproduce.** Render the current base's note and capture the section verbatim:
   `bash plugins/workaholic/skills/ship/scripts/draft-release-note.sh` and read each target's
   `body` at `## Key Changes`. Record how many lines are placeholders and how many carry a
   story — the before-measurement the fix is judged against.
2. **Localize.** Confirm in `draft-release-note.sh` where the placeholder is emitted (the
   `elif [ -n "$prnum" ]` arm of the merge loop) and confirm there is no cap or selection step
   ahead of it, so the change is scoped to what that arm writes rather than to which merges are
   walked. Note whether the merge subject is already available in the loop (`$msubject`) — it is,
   which decides how cheap the fallback is.
3. **Decide what the fallback line says**, and write the decision into the script's header
   comment beside the existing "THE STORY IS PREFERRED OVER THE COMMIT LIST" paragraph. The
   reporter's proposal — fall back to the merge's own commit subject — is the leading
   hypothesis; check what a real proposal merge subject actually reads like on this base before
   committing to it (`Merge pull request #NNN from qmu/work-…` carries no title of its own,
   whereas an auto-merged proposal's merge subject may carry the `[Proposal] …` title). The
   fallback must produce a line a reader learns something from, or it is the same defect with
   new words.
4. **Implement the fallback** in that one arm, keeping the renderer's stated properties intact:
   clock-free, byte-identical output for the same base state, no network (the `--enrich` path
   stays off by default).
5. **Resolve the Open Decision below explicitly** and record the resolution in the Final Report.
6. **Test.** Add a hermetic case to `scripts/test-workflow-scripts.mjs` covering a merge with a
   story and a merge without one, asserting the rendered lines. Run
   `node scripts/test-workflow-scripts.mjs`.
7. **Regenerate and verify.** `node scripts/build-plugins/build.mjs`, then
   `node scripts/build-plugins/verify.mjs`.
8. **Re-render and compare** against step 1's capture: no line's only content is the absence of
   a story.
9. **Update the docs in the same change** — `workaholic:ship` §7 wherever it states the Key
   Changes rule, and `CLAUDE.md` if the stated behaviour moves.

## Open Decisions

<!-- Recorded verbatim rather than resolved: the proposing session could not
     recommend one side, and the driving session resolves it explicitly. -->

1. **Does "prefer merges that have a story" introduce any selection, or does the fallback alone
   answer the report?** The ask asks for both preference and fallback, but the renderer performs
   no selection today — it lists every merge in the range — so "prefer" has nothing to act on
   unless a cap or a reordering is added. Three readings, and this session cannot recommend one:
   (a) fallback only, order stays chronological — smallest change, and it makes every line
   informative, which is what the report actually complains about; (b) reorder so story-bearing
   lines come first — changes the section from a timeline into a ranking, which a reader may not
   expect; (c) introduce a cap and fill it with story-bearing merges first — bounded output for a
   base carrying 166 unreleased commits, but it silently drops merges, which is the failure mode
   the current placeholder was written to avoid ("a silently shortened list reads as 'nothing else
   happened'"). Resolve this before step 4 and record which reading was taken and why.

- `node scripts/build-plugins/build.mjs && node scripts/build-plugins/verify.mjs`.

**Gate** — what must pass before approval:

- The before/after render shows zero content-free lines and no story line regressed.

## Considerations

<!-- Risks and open questions the proposal already sees. -->

- **The reporter's fix is a hypothesis, not the design.** "Fall back to the merge's own commit
  subject" is recorded here as the leading candidate precisely because it came from the reporter;
  step 3 checks what those subjects actually read like before it is adopted. A merge subject of
  the form `Merge pull request #441 from qmu/work-20260813-124452` restates what the placeholder
  already said, so the fallback may need the pull request title rather than the raw subject —
  and fetching a title is a network read the renderer deliberately keeps behind `--enrich`.
- **An adjacent defect is visible in the same section and is deliberately not in scope.** The
  current render's first line reads `- \`check-version-bump.` — the story's first "sentence" was
  cut at a period inside a backticked filename by the `sed 's/\([^.]*\.\).*/\1/'` sentence split
  at line 198. It is a separate truncation bug in the story-bearing path; this ticket is about
  the story-less path. Raise it separately rather than widening this unit.
- **Proposal merges will always lack stories** — that is structural (`/propose` never runs
  `/report`), so whatever the fallback says will be the common case in this repository, not the
  rare one. Judge the wording on that basis.
