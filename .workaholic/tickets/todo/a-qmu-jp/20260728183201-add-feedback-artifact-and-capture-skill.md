# Add the feedback artifact and capture skill

## Overview

Introduce **feedback** as a first-class knowledge artifact: the inbound record of a human clue about this repository — a design discussion's conclusion, an instruction given over chat, a meeting's takeaway — technical or not. The feedback corpus is the raw material the later proposal batch (decision record `docs/loop-engineering-workflow.md`, phase 2) reads to propose missions; this ticket builds the artifact, its capture path, and its write-time floor only.

Decided shape (decision record A1–A3, H2): **one feedback = one file**, immutable once written; consumers track "new" by commit cursor, never by mutating feedback frontmatter. Feedback is the **single unified stream** of project-context information (decision H2): `concerns/` will merge into it as `kind: concern` in a later ticket — this ticket does **not** perform that merger, but the schema carries the `kind` axis from day one so the merger changes no file shape.

```
.workaholic/feedbacks/<YYYYMMDDHHMMSS>-<slug>.md   # flat area — no active/archive split; records never move
.workaholic/feedbacks/index.md                     # regenerated by okf/refresh-index.sh
```

Schema (frontmatter): `type: Feedback`, `title`, `kind` (the nature of the entry — H2's axis; finalize the enum in this ticket, starting from `insight | instruction | concern | material | answer`), `source: meeting | slack | discussion` (the channel it arrived through), `created_at` (ISO 8601), `author` (email), and an optional `supersedes` (filename of an earlier feedback this entry moots/resolves — the immutable alternative to a status flip). No `status` field — immutability is the design, and adding lifecycle state here would recreate the mutation channel A3 rules out; resolution is a new superseding entry, never an edit. Body: free prose — the transcript excerpt, the instruction, or the conclusion, in the contributor's own words; no mandated sections beyond a leading `# <title>`.

## Considerations

- Do not add lifecycle state (`status`, `processed`, checkboxes) to feedback files — the proposal batch's cursor (phase 2) is the only "new vs seen" mechanism, and mutation would break the immutable-record design (`docs/loop-engineering-workflow.md` A3).
- The relation direction is mission→feedback (a later `feedback:` reference on proposed missions, phase 2); nothing is stored on the feedback side, so the corpus never dangles.
- `metadata.internal: true` is mandatory — the skill is script-bearing (CLAUDE.md Cross-Agent Skill Exposure); the loop components are Claude-Code-only by decision F3.
- Keep the `/feedback` command honest about voice: it records what the human said/concluded, in summary or verbatim — it must not editorialize the content it captures.
