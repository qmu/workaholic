# Workaholic

Private, cross-agent distribution of structured development workflows and engineering standards. It is richest on **Claude Code**, where it installs as a plugin marketplace (slash commands, hooks, the always-on policy and mission lenses); the portable skills also ship to **Codex** (via `.agents/plugins/marketplace.json` → `outputs/workflows`) and to **OpenCode** plus 40+ other agents via the Agent Skills standard / `skills` CLI. Authored source lives under `plugins/`; cross-agent artifacts are generated into `outputs/`.

## Important

Edit `plugins/` not `.claude/`. This repo develops plugins - changes go to `plugins/`, never `.claude/` unless explicitly requested.

**Update the docs in the same change.** When a change alters behavior, structure, commands, skills, or conventions, update every affected document — `README.md`, `.workaholic/README.md`, `CLAUDE.md`, `plugins/workaholic/rules/*.md` — in the same commit as the change. Outdated documentation is a defect: before requesting approval for any change, check whether the docs that describe the touched area still tell the truth (`/report` runs `doc-drift.sh` as a backstop, but the fix belongs at change time, not report time).

## Architecture Policy

### Component Nesting Rules

| Caller                         | Can invoke                                   | Cannot invoke              |
| ------------------------------ | -------------------------------------------- | -------------------------- |
| Command                        | Skill, `general-purpose` subagent            | —                          |
| Skill                          | Skill; (when loaded by a command/main agent) may direct it to spawn `general-purpose` subagents | Command                    |
| `general-purpose` subagent     | Skill (via preload)                          | Command, Task (no nesting) |

There is exactly **one** kind of subagent in this repo, and the table above governs it. **`general-purpose` subagents** are the built-in Claude Code subagent type. They have **no `.md` agent file** — a command (or a skill running in the command's main-agent context) spawns them with a `Task` call whose prompt says "preload `workaholic:<skill>`, run `<section>` with these inputs, return `<schema>`." This is how `/report`, `/drive`, and `/ticket` fan out. Skills cannot issue `Task` calls themselves; the prohibition on Skill→Subagent that previously appeared here is lifted **only** in the sense that a skill's prose may instruct its loading agent (a command/main agent) to spawn `general-purpose` leaves.

The plugin ships **no named agent files at all**. It once carried three Agent Teams members (`planner`, `architect`, `constructor`) that only the retired `/trip` command launched, exempt from the nesting table; the whole `plugins/workaholic/agents/` directory went with that command (decision I1, 2026-07-28). Nothing in the plugin is Agent-Teams-based any more.

Everything converges on the **ticket** as the unit of work. The model is **sources × one executor**: the ticket is the spine, *sources* fill the `tickets/todo/` queue and the executor drains it to `tickets/archive/`.

- **Sources** (write to `todo/`): `/ticket` (human-directed, with discovery) and `/mission`'s Creation Interrogation, which emits a mission's whole ordered ticket set in one pass. A mission is deliberately **small**: `## Scope` was dropped from the template (2026-08-01 — nothing read it), `## Acceptance` is normatively **three items or fewer** (the minimum conditions for calling the work done, not a coverage list), and the whole `mission.md` is held to ~60 lines / 2 KB — a **norm** measured by `mission/scripts/size.sh` for a human author, **enforced** on `/propose`'s unattended drafts. That is a ceiling; the write-time floor (`## Experience`, ≥1 acceptance item — ownership dropped, 2026-07-31) is unchanged in substance. Both write through a publish tree and **publish onto a `work-*` branch behind a pull request** (decision J4, superseding J1's direct-to-`main` half); the artifact reaches `main`, and therefore `/drive`'s survey, when that pull request merges. `/propose` feeds them upstream by proposing missions **with their ticket sets** from the feedback stream and the repository's own state.
- **The executor is `/drive`, and there is one of it** (decision G1, 2026-07-28). One command drains `todo/ → archive/`, identically whether a developer typed it or the 5-minute routine invoked it (`docs/drive-loop-runbook.md`), and **with no drive-time confirmation of any kind** — it issues no `AskUserQuestion` anywhere in the run. Its shape is the **Unified Run** (`skills/drive/SKILL.md`): *freshen* the checkout (`sync-main.sh` — artifacts live on `main`, so a runner behind `origin/main` would survey a stale queue and report it confidently; decision J3) → *survey* what is claimable (`plan-units.sh` — the active missions on `main` this runner may take, **filtered by ownership through `mission-owners.sh`** so a colleague's mission is dropped as `owned_by_other` and an unowned one stays claimable, plus the unclaimed backlog, with in-flight claims subtracted through the shared claim reader — and any claim of this runner's **own** whose heartbeat lapsed offered back as `resumable[]` rather than stranded — every drop reported with its reason, and the survey's own trustworthiness reported as `current` plus `backlog_error`/`user_slug` — an *unreadable* queue, such as a runner with no `git config user.email`, never renders as an *empty* one) → *partition* the remainder into **PR-units**, one unit being "what deserves one merge" (a mission is one unit; related backlog tickets batch into one, conservatively — the partition is **reported, never asked**) → *claim* each unit on a pushed branch (`claim.sh`, born with its `.worktrees/<unit-id>/`) → *drive* its tickets there under the closed four-outcome failure contract (implemented / failed / blocked / `deferred`-as-a-minted-ticket) → *report* via `/report`'s own story + PR seam → *route* by the unit's **effective merge policy** (`effective-policy.sh` per decision G5: the mission's recorded policy for a mission unit, unanimity across members for a batch, **absent means review**) — `auto` ships through the full evidence-gated `/ship` doctrine and then tears the claim down (I6), `review` stops at the PR and posts its URL to Slack — → *account* (`record-run-hours.sh` per mission unit, I7) and close with the **honest terminal token**: an `N units: X shipped, Y PR'd, Z blocked` reconciliation and then `ok` **only** when nothing claimable remains undone, else `pending` (the `/goal /drive ok` caller contract, I4). **An unattended run never overrides a gate**: a `secret` finding hard-stops, and a `size`/`leak` block or a missing deployment-confirmation method **demotes the unit to the PR path** — `auto` means "no *approval* needed", never "no *gate* applies". The per-ticket approval prompt is **retired, not loosened**: approval moved to artifact creation (`merge_policy`, on a mission and a ticket alike) and to **merging the artifact's pull request** (decision K1, 2026-07-31 — the mission `approve.sh` flip that briefly held that role is gone), and the non-delegable looking-through relocated to the PR.

The executors that preceded it are gone, and their ideas are recorded where they landed (decisions I1/I3/I5, 2026-07-28). `/monitor`'s parallel per-worktree execution, honest terminal token, PR auto-creation, agent-hour accounting, and front-loading doctrine are all in the Unified Run above; its interactive pre-flight is superseded by creation-time `merge_policy` plus the claim protocol. `/trip`'s design discussion is the feedback stream, its decomposition is `/mission` and `/propose`, its execution is `/drive`. `/carry`'s hand-off is unnecessary because in-flight state lives on the pushed claim branch, which the next run re-claims and resumes (`claim.sh resume`, gated on same-identity plus a lapsed heartbeat). `.workaholic/trips/` stays on disk and in the layout allowlist as **legacy, read-only history** with no writer — knowledge is never deleted — so `trips/` still holds the *why* behind the tickets those sessions produced.

### No Per-Workflow Agent Files

Workflow orchestration does **not** get dedicated agent `.md` files. A command spawns `subagent_type: "general-purpose"` subagents whose prompts instruct them to preload the relevant `workaholic` skill and run a named section. The knowledge lives in the skill; the subagent is a throwaway leaf. There are **no** agent `.md` files in the repo at all — the three that existed served only the retired `/trip`.

When adding a new fan-out step, do not create an agent file — write the knowledge as a section in a `workaholic` skill and have the command spawn a `general-purpose` subagent that preloads it.

### One-Level Fan-Out

A subagent **cannot** nest `Task` calls and **cannot** call `AskUserQuestion`. Therefore:

- All fan-out happens at the command/main-agent level. No subagent-that-spawns-subagents.
- All user interaction (`AskUserQuestion`) happens at the command/main-agent level.
- Leaf `general-purpose` subagents do non-interactive work only and return JSON for the command to act on.

When a workflow needs both parallel work and a user decision, the command spawns the leaves, collects their JSON, then issues the `AskUserQuestion` itself.

### Plugin Dependencies

There is **one** plugin (`workaholic`) with `dependencies: []` — everything that was previously split across `core`, `standards`, and `work` now lives in it. All skill references are same-plugin: `${CLAUDE_PLUGIN_ROOT}/skills/<name>/...` (no cross-plugin `../<name>/` paths) and `workaholic:<skill>` namespaces. The `workflows` plugin in the marketplace is the **generated** `outputs/workflows` bundle, not an authored plugin.

### Cross-Agent Skill Exposure

The `workaholic` plugin's skills are installable by non-Claude agents (Cursor, OpenCode, Codex, Pi, 50+) via `npx skills add qmu/workaholic`. The `skills` CLI (`vercel-labs/skills`) reads `.claude-plugin/marketplace.json`: the `skills` array on the `workaholic` plugin entry labels its cross-agent discovery group (the `design`/`implementation`/`operation` policy skills). Three rules keep the exposed set honest:

- **Script-bearing skills carry `metadata.internal: true`** in their SKILL.md frontmatter. Claude Code ignores this field (the skills still load normally); the `skills` CLI hides them from cross-agent discovery. This is required because the CLI always scans the plugin's `skills/` dir — `metadata.internal` is the only per-skill exclusion. Any new skill that invokes a bundled script MUST include it.
- **The pure-prose skills are intentionally exposed** (no `metadata.internal`): the three policy skills (`design`/`implementation`/`operation`) plus `write-release-note` and `review-sections`. They have no bundled script, no `${CLAUDE_PLUGIN_ROOT}`, no namespaced preload — so they resolve on every agent via the `skills` CLI. The script-bearing workflow skills also reach non-Claude agents, but only through the generated `outputs/workflows` bundle (see below), never the source.
- **Why script-bearing skills stay internal** (verified 2026-05-26): every agent (Claude Code, OpenCode, Codex, Pi) runs a skill's shell in the *project* CWD and only injects the skill's base directory as text for the *model* to prepend — none `cd`s into the skill dir. Claude Code additionally expands `${CLAUDE_PLUGIN_ROOT}`/`${CLAUDE_SKILL_DIR}` deterministically at load time. Rewriting a script call to the spec-relative `scripts/X.sh` form would drop that determinism and rely on non-deterministic model-prepend — unacceptable for skills workaholic runs in its own Claude-Code `/drive`/`/ship` critical path. So script-bearing skills keep the token and stay internal.

The plugin's `commands/`, `agents/`, `hooks/`, and `rules/` are Claude-Code-only: the `skills` CLI reads only the `skills/` dir, so those directories are not exposed through that path. Codex still installs the raw plugin directory from `.agents/plugins/marketplace.json` and parses `hooks/hooks.json`; that file must keep `hooks` as its only top-level key because Codex rejects Claude-only sibling keys such as `description`. Hook documentation lives here and in `.claude-plugin/plugin.json`, not in `hooks/hooks.json`.

To preview what the CLI would install, run `npx skills add . --list` (add `INSTALL_INTERNAL_SKILLS=1` to include internal skills).

#### Cross-agent distribution (workflow skills, built)

The workflow skills (ticket/drive/report/ship/catch/mission) depend on shared scripts elsewhere in the plugin (via `${CLAUDE_PLUGIN_ROOT}`) and so are **not** self-contained in source. They ship to non-Claude agents as a **generated, self-contained, committed plugin** at `outputs/workflows/`, produced by `scripts/build-plugins` from the DRY `plugins/workaholic` source. **One neutral generated dir serves every non-Claude agent** through two manifests that point at it:

- **Codex** reads `.agents/plugins/marketplace.json` (repo root); its `workflows` plugin `source.path` is `./outputs/workflows`, and Codex consumes the co-located `outputs/workflows/.codex-plugin/plugin.json`.
- **OpenCode, Cursor, Pi, 40+** get it via the `skills` CLI, which reads the `workflows` plugin entry in `.claude-plugin/marketplace.json` (`source: ./outputs/workflows`) and its `skills/` (the `design`/`implementation`/`operation` policy skills are exposed the same way). The `skills` CLI ignores the co-located `.codex-plugin/` dir, so the same folder serves both systems. `write-release-note` and `review-sections` ship inside this plugin too.

Source-vs-artifact rule: the `plugins/workaholic` workflow skills keep `metadata.internal: true` and `${CLAUDE_PLUGIN_ROOT}` (so the `skills` CLI never offers the broken source); the **committed `outputs/workflows/` artifacts** are the public versions — self-contained, `${CLAUDE_PLUGIN_ROOT}` rewritten to relative paths, and `metadata.internal` / `user-invocable` / the `skills:` preload block stripped with namespace prefixes flattened by `publicizeSkillMd`. **Regenerate with the argument-less `node scripts/build-plugins/build.mjs` whenever a `workaholic` workflow skill or its script closure changes** (a *targeted* build only writes a throwaway scratch dir and does not touch `outputs/`). `outputs/` is **committed, not gitignored** — Codex and the `skills` CLI install by reading repo paths, so the artifacts must be present. The `Outputs Freshness` CI workflow (`.github/workflows/outputs-freshness.yml`) rebuilds and fails on any `outputs/` diff, keeping artifact and source in lockstep.

**A skill may relocate detail into a companion `reference/` directory**, and the build carries it. When a `SKILL.md` grows past the ~50-150 line guideline, the reference-only material — per-script contracts, per-field schema detail — moves to `skills/<name>/reference/<topic>.md` and the `SKILL.md` keeps an index that links to it. `build.mjs` copies that directory into the bundle, rewrites its script references with an extra `../` (a reference file sits one level below the skill root the `SKILL.md` form is relative to), and runs `publicizeSkillMd` over it, because a reference file carries the same namespace prefixes and ships to the same non-Claude agents. `computeClosure` reads it too, so a cross-skill reference appearing only in a reference file still pulls that skill's `scripts/` into the bundle. `verify.mjs` asserts every intra-bundle markdown link resolves — deliberately narrowed to links into or out of a `reference/` dir, because a skill's prose is full of relative-looking paths that are *not* bundle files (runtime artifact paths in the consuming project, `<placeholder>` templates), and a containment check that cries wolf gets deleted. `skills/mission/` is the first user of this (562 → 380 lines).

Claude Code reads `plugins/` directly and consumes nothing from `outputs/`. The `workflows` entry in `.claude-plugin/marketplace.json` is read by Claude Code too, so it is **opt-in** — its description points Claude users to the `workaholic` plugin to avoid installing duplicate workflow skills.

That entry carries **`"strict": false`**, and must keep it. Claude Code's marketplace sync otherwise requires the plugin's `source` directory to hold a `.claude-plugin/plugin.json` (or a top-level `SKILL.md`) and **skips the plugin with an error** when it finds neither — which is exactly the generated bundle's shape, since `outputs/workflows/` deliberately carries only `.codex-plugin/plugin.json` for Codex. `strict: false` tells the sync to use the **inline** manifest already present in the marketplace entry (name, version, author, `skills`), so the bundle stays Codex/`skills`-CLI-shaped and Claude Code stops erroring on it. Do **not** "fix" this by generating a `.claude-plugin/plugin.json` into `outputs/workflows/`: that would add a fifth version file to the lockstep set and make the duplicate-skills install the description warns against easier, not harder.

#### OKF knowledge bundle (generated)

`outputs/okf/` is an [Open Knowledge Format](https://github.com/GoogleCloudPlatform/knowledge-catalog/tree/main/okf) (OKF v0.1) bundle of the four pillars' policy hard copies, generated by `scripts/build-plugins/okf.mjs` (wired into the same argument-less `build.mjs` full build): one concept document per `plugins/workaholic/skills/<pillar>/policies/*.md` with OKF frontmatter (`type`/`title`/`description`/`resource`/`tags`; no `timestamp` — commit-date-derived values would break the rebuild-and-diff freshness guard), bundle-absolute intra-bundle links, and a bundle-root `index.md` declaring `okf_version`. Any OKF consumer reads it straight from the repo path — no marketplace manifest involved, so neither Claude Code nor the `skills` CLI/Codex ever installs it as a plugin. `verify.mjs` asserts freshness plus OKF conformance (parseable frontmatter, non-empty `type`, reserved filenames, in-bundle link resolution); the `Outputs Freshness` CI diff over `outputs/` covers it like every other generated artifact. The adoption record (reason/assessment/monitoring/exit) is `docs/dependencies/okf.md`; OKF vocabulary stays inside `okf.mjs` — the translation boundary — and never shapes the source conventions.

#### `.workaholic/` as an OKF bundle (runtime)

Separately from the generated policy bundle, the `.workaholic/` tree of any project using the plugin is itself kept OKF-compatible **as the workflows generate documents**: every written artifact carries frontmatter with a non-empty `type` (tickets `enhancement|bugfix|refactoring|housekeeping`, stories `Story`, missions `Mission`, feedbacks `Feedback`, release notes `Release Note`, release records `Release`, and — in the legacy `trips/` tree, which has no writer since 2026-07-28 — trip artifacts `Direction|Model|Design|Review|Rollback|Trip Plan|Event Log`), and the internal `okf` skill's `refresh-index.sh` deterministically regenerates the bundle hierarchy — `.workaholic/index.md` (bundle root, declares `okf_version`) plus per-area `index.md` files — before each knowledge commit (called by `drive`'s `archive.sh`, `ship`'s `commit-release-note.sh`/`extract-deferred-concerns.sh`, and the `report` story flow). `stories/index.md` stays report-maintained; `tickets/` internals are never index-managed (the queue scripts and structure guards own that tree). `README.md` and `index.md` are the two files allowed at the `.workaholic/` root. Those same commit seams also **roll any related mission** (`missions/active/<slug>/mission.md`; ended missions live under `missions/archive/<slug>/`, moved there by the mission skill's `close.sh` — the only sanctioned way to end a mission — with a living migration relocating any legacy flat `missions/<slug>/` dir by its `status` on the next mission-script touch): when an archived ticket, shipped story, or extracted/resolved concern carries a `mission:` relation, the seam appends a `## Changelog` line and reconciles the mission's `## Acceptance` checklist through the `mission` skill's shared, idempotent mutators (`append-changelog.sh` / `tick-acceptance.sh`), so a mission's progress (`checked ÷ total`, computed — never stored) and history stay current without hand-editing. **What makes an item tickable at all is its `(#<filename>)` link, and the link is stamped by the seam that *emits* the ticket set** — the Creation Interrogation, a replan, or `/propose` — through `link-acceptance.sh`, the only writer of a link and one that takes the pairing from its caller rather than inferring it (2026-08-03; `skills/mission/reference/schema.md`, *The link contract*). An acceptance item is legitimately written **before** its ticket exists, so nothing demands the link at authoring time; what is demanded is that the emitting seam close the loop. When it does not, the board is *unaddressable* rather than merely unfinished, and both the ticker (`unlinked_items`, distinct from `no_unchecked_match`) and `progress.sh` (an `unlinked` count beside `checked`/`total`) say so rather than letting `0/N` read as stalled work — the state six missions were in when this was measured, 37 unlinked items to zero linked. The relation is **many-valued** — an artifact records every mission it advances (`mission: [alpha, beta]`; a bare `mission: alpha` still reads as one) and each seam rolls all of them, reading the field through the mission skill's single reader (`read-relation.sh`) rather than parsing frontmatter itself. Data is plural, **placement stays singular**: `.worktrees/<slug>` remains keyed 1:1 to a mission, and a ticket is still driven in exactly one worktree. `/drive` holds a ticket to the quality gate of **every** mission it names — naming a mission is a commitment, not a label. **The strategy layer is retired** (2026-07-28 — `docs/loop-engineering-workflow.md` B3): long-lived direction accretes in the **feedbacks stream** instead of a second direction artifact, a mission is an **optional, epic-equivalent grouping** — never a required parent of any ticket (B5) — and a lingering `.workaholic/strategies/` tree is folded by the living migration (`mission/scripts/migrate-strategies.sh`, run from every mission script's `lib/resolve.sh` seam: each strategy document survives verbatim as a feedback record, its `assignees` fold down into linked active missions, then the directory is removed; legacy `strategy:` keys on missions are tolerated and ignored). **Mission ownership is carried on the mission itself** (B4): a mission's own plural `assignees` (creator-seeded by `create.sh` — the creator is the default owner; empty = team-owned/claimable) is the primary source, resolved through `mission/scripts/mission-owners.sh` with a **legacy fallback** to the mission's singular `assignee`, so nothing predating the field is orphaned. Every ownership consumer — the mission lens, `/drive`'s survey, `summary.sh`, `list.sh`'s `relation`, and `ship`'s concern-lane owner — reads through `mission-owners.sh`; `validate-mission.sh` stopped being one when ownership ceased to be a floor (K2). **The mission lifecycle is one axis with one in-flight state** (I2, 2026-07-28; K1, 2026-07-31): `status: active | achieved | abandoned | carried`. `drive_authorized` was retired into `status: approved` by I2, and **`draft` and `approved` were then retired into `active` by K1** — since J4 every mission arrives behind a pull request, so **merging that pull request is the approval**, and a status-word gate only re-asked the question the PR had already answered (the observable cost was six active missions on `main`, none claimable, `/drive` reporting `pending` every tick). `active` lives in `active/`, the three end states in `archive/`; **`close.sh` is the only status flip that remains**, and `mission/scripts/approve.sh` plus the `/mission approve` subcommand are **gone**. **Drivability is no longer a status word**: a mission is claimable when it is in the active area, has a plan (`no_plan`) and has a queued ticket naming it (`no_tickets`) — `plan-units.sh` stops reading `status` for the offer, and `not_approved` left its reason vocabulary. Retired `status: draft`/`status: approved` files fold to `active` on the next mission-script touch (`lib/resolve.sh`, dropping the long-retired `drive_authorized` key line), and every reader keeps a legacy-tolerance branch for the transition window. **Merge policy is a separate, orthogonal axis** (G5, amended by K2): `merge_policy: auto | review` is recorded **at creation** on a mission and a ticket alike — **absent means `review`**, the conservative default, validated by `validate-ticket.sh` only when present. **Deferred concerns live in the feedback stream** (`docs/loop-engineering-workflow.md` H2/H3, 2026-07-28): a branch story records every concern in its **Concerns** section (the immutable record — the story *file* carries every severity; the PR *body* is a rendering of it with the `low` blocks dropped for the reviewer, `report/scripts/filter-low-concerns.sh`), and `ship`'s `extract-deferred-concerns.sh` persists each one as a `kind: concern` feedback record — every severity, append-only, keyed on `concern_id` so a known id is never re-emitted. The **open set is computed, never stored**: a concern is open until a later record names it in `supersedes` — which is exactly what `/report`'s judge seam writes (`apply-deferred-concern-verdicts.sh`) for each concern a branch resolved. The former `concerns/` corpus and its lifecycle machinery (promotion floor, triage, merge/re-grade/demote) are retired — curation is the reader's judgment over the stream — and a lingering `concerns/` tree is folded by the living migration (`feedback/scripts/migrate-concerns.sh`, run from the extraction and report seams; archived files become `closed:`-stamped records so history never resurfaces as open).

### Claim protocol (the repository is the coordination medium)

**Implemented** (`docs/loop-engineering-workflow.md` G3/I6; the model is stated once in `plugins/workaholic/skills/drive/SKILL.md`'s **Claims** section, which the scripts implement and never extend silently). Before driving a unit a runner *claims* it on a **pushed branch**, and every runner reads the claims in flight from the **unmerged remote branches** — so a 5-minute tick, or a runner on another machine, never double-picks work. Run-locks are gone entirely: there is no lock file and no server, so nothing leaks when a runner dies mid-run.

- **PR-unit** — one approved **mission** (unit id = the slug) or one **batch** of backlog tickets (`batch-<YYYYMMDDHHMMSS>`, minted at claim time). One unit ↔ one branch ↔ one worktree ↔ one PR.
- **Claim** — `drive/scripts/claim.sh mission <slug>` / `claim.sh batch <ticket-file>...`: a `Claim <unit-id>` commit on a fresh `work-*` branch cut from `origin/main` by the standard creator, stamping `claim: <branch>` into the claimed artifacts' frontmatter **in the worktree checkout**, pushed immediately. The stamp is written **only in the worktree**, so the runner's main checkout stays clean between ticks (which the `/propose` batch depends on). **A stamp that reaches the base is history, not a claim** (decision M1, 2026-08-04): a `handoff` or `blocked` unit merges its PR with tickets still in `todo/`, so a base-side stamp on a live queue item is expected — the unmerged-branch scan (`list-claims.sh`) is the only claim oracle, and it already reports a merged branch's claim as released. Never prompts.
- **Reader** — `drive/scripts/list-claims.sh`: pure read, emits `{fetched, stale_hours, heartbeat_stale_minutes, base, claims: [{unit, branch, artifacts, last_commit_at, stale, author, resumable, resume_reason}]}`. Claims come from git refs, but a survey's **artifacts** come from the working tree — so `/drive` fast-forwards before surveying and `plan-units.sh` reports `current` either way (J3). A driven ticket is *renamed* by `archive.sh`, so each stamp is read at the file's **current** path via a tree-to-tree rename map — **and, when git reports no rename, by an exact lookup on the ticket's filename**, which is unique in the tree by construction. That second path is load-bearing rather than belt-and-braces: `--find-renames` pairs a delete with an add only above 50% similarity, and `archive.sh` also appends the Final Report, so a short ticket with a long report is reported as add + delete. The resulting **empty artifact list is two visible failures at once** (measured 2026-08-04): `plan-units.sh` subtracts a claim *by its artifacts*, so it offered an already-driven ticket as fresh backlog with no `excluded[]` row; and `claims_has_work`'s conservative "no artifacts means unknown" branch called a drained unit `resumable`, inviting a takeover of a branch under review. The fallback is scoped to `.workaholic/tickets/` and to an unambiguous single match — every mission's artifact is named `mission.md`, so an unscoped lookup could cross one mission's claim onto another's file. `claim.sh` no longer tolerates a mission absent from the claiming checkout: it refuses `mission_missing`, because after J1 absence means a wrong slug or a stale checkout, not an artifact hiding on an unmerged branch.
- **Release** — a **merge** releases by definition (the commits reach the base, so the claim leaves the unmerged set with no bookkeeping); **discarding** an unfinished unit is the explicit `drive/scripts/release-claim.sh <unit-id>`, which tears the worktree down *before* deleting the remote branch so a refused teardown never publishes "this unit is free" over unpushed work. It deletes the branch, so it is **not** the recovery path for an interrupted unit — resumption is.
- **Resumption** — a claim whose run stopped is **taken over**, not stranded (2026-08-01, closing decision I5, which the code had contradicted: every claimed unit was dropped as `claimed` and refused as `already_claimed`, so no survey ever offered it again — fatal for a cloud runner whose worktree dies with its sandbox, leaving the pushed branch as the sole surviving copy with nothing routing anyone to it). The verdict is computed in the one shared scan and carried on every row (`resumable`, `resume_reason`), because a writer free to decide it independently could take over a unit the reader still calls active. Two conditions, identity first: the claim commit's **author must be this runner's `git config user.email`** (a colleague's claim is `foreign_identity`, untouchable at any age — *a pushed claim is the loop's work*, but only your own loop's), and its **heartbeat must have lapsed** (`WORKAHOLIC_CLAIM_HEARTBEAT_STALE_MINUTES`, default 30). `claim.sh resume <unit-id>` re-creates the worktree **at the pushed branch tip** (`create-mission-worktree.sh --branch`) so archived tickets are not re-driven, then publishes an empty `Resume <unit-id>` commit whose push **is** the race arbiter — two runners racing resolve non-fast-forward exactly as `branch_collision` resolves two fresh claims, never by comparing clocks.
- **The heartbeat is the branch tip** — `drive/scripts/heartbeat.sh <unit-id>` pushes an empty commit, and every ordinary work commit refreshes the same signal. No lock file, no heartbeat file, no server: all three leak when a runner dies, which is the failure the claim protocol exists to avoid. An empty commit changes no file, so it never reaches the PR diff, and the merge or release that cleans up the claim cleans it up too. `commit.sh --allow-empty` is the one seam these coordination markers use, so they still get the subject gate and the trailers — and there **`--allow-empty` means empty**, not "empty is tolerated": git's own flag merely permits a changeless commit and still commits whatever the index holds, so a beat fired mid-ticket over a staged `git rm` produced a `Refresh heartbeat` commit carrying three real deletions (measured 2026-08-04), a commit whose content was right and whose message was wrong. The commit is now built against a scratch index seeded from `HEAD`, so its tree equals `HEAD`'s by construction and the caller's index is left byte-identical. Refusing to beat over a dirty index was rejected: mid-ticket is exactly when the index is dirty and exactly when a missed beat makes a working unit look abandoned.
- **Staleness is reported, never auto-broken, and is a different axis from resumability** — past `WORKAHOLIC_CLAIM_STALE_HOURS` (default 24) a claim is marked `stale: true` and **nothing acts on it**, because reclaiming a colleague's work on a local verdict can silently duplicate it. Resumption acts, and is narrower by exactly that margin: your own claim, heartbeat lapsed, measured in minutes — a routine that recovers its own dropped unit only after a day is not a recovery path.
- **Claiming announces** — `claim.sh` posts one Slack line (unit, branch, member count) after its push succeeds, reporting `announced`/`announce_reason` in its JSON. It is the operator's first signal that a run started; before it, the first human-visible artifact was the PR opened after every ticket was driven, and a working fleet was indistinguishable from a dead one for tens of minutes. **Never load-bearing**: a missing token, an unreachable Slack, or a broken notifier leaves the claim intact, and a refused claim announces nothing.
- **Worktree lifecycle (I6)** — worktrees are **claim-born and ship-torn**. `claim.sh` creates `.worktrees/<unit-id>/`; ship or `release-claim.sh` removes it. **Every one of those teardowns needs a run to reach its end**, so a sweep backs them up: `branching/scripts/survey-worktrees.sh` reports each worktree's size, `ahead`, `dirty` and `reclaimable` state, `reap-worktrees.sh` (dry run by default, `--apply` to act) removes only those both **merged and clean** and names every skip with its reason, and `prune-worktree-artifacts.sh` reclaims build output from a worktree worth keeping (git-ignored **and** a named build directory — ignored-ness alone would take `.env`). Creation now reports `size_bytes`. **`.worktrees/` sits inside the repository root**, so it enters any build context, archive, or index rooted there — add it and `.publish/` to `.dockerignore` and to any archiver's ignore list; `.git/info/exclude` covers git and nothing else. **`/mission close` keeps only the archive move** — a lingering worktree is an in-flight or stale *claim*, which the reader surfaces and a human decides about, so a bookkeeping action no longer doubles as a destructive one. `cleanup-mission-worktree.sh` is unchanged and still the sanctioned cleaner.
- **The claim is the only creator of a *worktree*, and the only creator of a branch a runner may drive** (decision J1, 2026-07-30, amended by J4, 2026-08-01). J1's rule was "artifact creation publishes to `main` and cuts no ref", motivated by immediate visibility to every runner and fresh clone. **J4 keeps the isolation and changes the destination**: an artifact writer still writes into a **publish tree** — never the caller's checkout — but pushes onto a `work-*` branch and opens a pull request, because the project standard is that every artifact reaches `main` through a *merged* PR, and the merge is the event that can be announced. The cost is accepted knowingly: an artifact is **not** visible to a runner until its PR merges, so "published" and "queued" are now different states and every source reports which one it reached. A publication branch carries no `Claim <unit-id>` commit, and the claim scan keys on that subject rather than on the branch name, so it is never mistaken for a claim. `create.sh` and `create-mission-worktree.sh` remain claim-side creators only.

**The publish tree** (`plugins/workaholic/skills/branching/SKILL.md`, decision J2) is a checkout of `origin/main` at the fixed, git-ignored `.publish/` on the fixed local branch `publish-main`, opened → written → published → closed by `open-publish-tree.sh` / `publish-tree-pr.sh` (the default — a `work-*` branch plus a pull request) or `publish-tree-commit.sh` (direct to the base, reserved for seams already downstream of a merge, such as ship-time concern extraction) / `close-publish-tree.sh`. It exists because publication must not depend on, or disturb, the caller's checkout: `/propose` can guard on "on `main`, clean tree, else abort" because it is a headless batch, but a developer types `/ticket` and `/mission` mid-work on a dirty branch. The caller's branch, staged set, untracked set, and file contents are left byte-identical; the commit goes through `commit.sh` (so it inherits the subject gate and the trailers, which is why the branch is named rather than detached). The **local** branch is always `publish-main`; only the remote ref differs — `publish-main:main` for a direct publish, `publish-main:refs/heads/work-YYYYMMDD-HHMMSS` for the PR path. The `work-*` name on the remote is safe because `claims_scan` keys on a `Claim <unit-id>` **commit subject**, not on the branch name, and a publication branch carries none. **A publish tree is not a claim worktree**: it holds no unit, is never pushed as a branch, and is disposable at any moment; and neither `open` nor `close` will destroy recoverable state (both refuse a dirty publish tree, and `close` also refuses a clean one whose `publish-main` still carries unpushed commits — the state a `diverged` publish leaves behind). Publishing to `main` is necessary but not sufficient: a runner whose local `main` trails `origin/main` would still survey a stale queue, so `/drive` fast-forwards first through `sync-main.sh` (decision J3).

Two design points worth not re-litigating. **The reader degrades offline, the writer fails loudly**: `list-claims.sh` reports `fetched: false` and answers from the last-known remote-tracking refs, while `claim.sh` refuses outright — a stale reader over-reports claims (a runner waits), but a claim nobody else can see is not a claim, and false "unclaimed" is the error that double-picks work. And **one scan serves both**: `drive/scripts/lib/claims.sh` holds the scan, `list-claims.sh` merely renders it as JSON and `claim.sh` verifies through it, because a writer carrying its own scan would be free to disagree with the reader. The optional `claim:` key on a ticket is **tolerated and never validated** by `hooks/validate-ticket.sh` — its truth lives in git (does an unmerged remote branch of that name still carry the artifact?), which a hook reading one file cannot answer.

### The release tier (`release/*`)

**One extra branch form, and nothing else** (decisions L1-L3, 2026-08-03). No `develop`, no `hotfix/*`; `main` stays the default and production branch, and **the per-unit claim/branch/worktree/PR mechanics above are untouched** — there is still exactly one merge target for a unit, which is why "what does a claim mean against a second base" and "what does `merge_policy` mean under two merge targets" do not arise. Full Git Flow was rejected for creating that second base; a `develop`-only tier was rejected because a continuous integration branch has no bounded identity to attach a durable record to, and the record was half the ask.

- **A `release/*` branch is the QA window between *merged onto `main`* and *released to production*.** It is cut from `main` by `branching/scripts/cut-release-branch.sh`, which mints `release/YYYYMMDD-HHMMSS` (the second literal pattern `guard-git-branch.sh` permits), pushes it, and **never checks it out**. Cutting one is **batch-level and explicitly invoked** — `/drive` neither cuts nor confirms one, and a unit landing on `main` is unchanged by the tier. If it were a step of the per-unit ship, every `auto` unit would open a release window.
- **The branch carries no commits of its own.** It is exactly a pointer at a `main` commit, which is what keeps "which commits did this release carry" answerable by `git log <previous>..<tip>` forever. It is invisible to the claim protocol for the same reason the publication branches are: `claims_scan` keys on a `Claim a PR-unit` subject / `Unit:` trailer, and a release branch carries no commit at all.
- **The durable ship record is `.workaholic/releases/<release-branch>.md`**, written by `ship/scripts/record-release-cut.sh` at the cut and `confirm-release.sh` at each confirmation attempt, both on `main` and both derived from git — never hand-authored. It is **additive**: `.workaholic/release-notes/<branch>.md` and the story's `## Deployment Evidence` block keep exactly their shape. `since_reason` records how the carried range was chosen (`given` / `prior_release` / `latest_tag:<tag>` / `full_history`), because a range is only trustworthy if the reader can see how it was picked.
- **A promotion adds a second confirmation; it never weakens the first.** `/ship` §5's per-unit confirmation proves one branch before it lands; §6's proves a batch already on `main`. Inverting the evidence-before-merge rule is the one thing a promotion must not do. **A failed confirmation deletes nothing**: the release branch is the rollback boundary, `main` is unaffected because its units are already merged there, the failure is recorded rather than erased, and the next attempt cuts a *fresh* release branch — re-pointing or force-pushing one destroys the only account of what was tried.

### Design Principle

**Thin commands, comprehensive skills.**

- **Commands**: Orchestration only (~50-100 lines). Define workflow steps, spawn `general-purpose` subagents, handle all user interaction.
- **`general-purpose` subagent prompts**: Orchestration only. Name the `workaholic` skill to preload, the section to run, the inputs, and the return schema — no per-workflow `.md` file.
- **Skills**: Comprehensive knowledge (~50-150 lines). Contain templates, guidelines, rules, and bash scripts.

Skills are the knowledge layer. Commands (and the leaf subagents they spawn) are the orchestration layer.

### Common Operations

Commands, skills, and subagent prompts must use skills for common operations instead of inline shell commands:

| Operation | Skill | Usage |
| --------- | ----- | ----- |
| Git context (branch, base, URL) | gather | `bash ${CLAUDE_PLUGIN_ROOT}/skills/gather/scripts/git-context.sh` |
| Ticket metadata (date, author) | gather | `bash ${CLAUDE_PLUGIN_ROOT}/skills/gather/scripts/ticket-metadata.sh` |

Never write inline git commands like `git branch --show-current` or `git remote show origin` in command or agent markdown files. Preload the skill and gather context through it.

### Shell Script Principle

> **CRITICAL: Never use complex inline shell commands in subagent or command markdown files.**

This includes:
- **Conditionals**: `if`, `case`, `test`, `[ ]`, `[[ ]]`
- **Pipes and chains**: `|`, `&&`, `||`
- **Text processing**: `sed`, `awk`, `grep`, `cut`
- **Loops**: `for`, `while`
- **Variable expansion with logic**: `${var:-default}`, `${var:+alt}`

Extract ALL multi-step or conditional shell operations to bundled scripts in skills (`skills/<name>/scripts/<script>.sh`). This ensures consistency, testability, and permission-free execution.

**Wrong** (inline conditional):
```bash
current=$(git branch --show-current)
if [ "$current" = "main" ]; then echo "on_main"; fi
```

**Correct** (skill script):
```bash
bash ${CLAUDE_PLUGIN_ROOT}/skills/branching/scripts/check.sh
```

### Skill Script Path Rule

> **CRITICAL: All skill shell script references must use `${CLAUDE_PLUGIN_ROOT}`.**

Claude Code expands `${CLAUDE_PLUGIN_ROOT}` inline in all plugin content (skills, agents, commands) at load time. This resolves to the plugin's installed directory. Relative paths like `.claude/skills/` do NOT resolve at runtime and cause exit code 127 failures.

**Wrong** (relative path):
```bash
bash .claude/skills/gather/scripts/ticket-metadata.sh
```

**Correct** (same-plugin reference):
```bash
bash ${CLAUDE_PLUGIN_ROOT}/skills/gather/scripts/ticket-metadata.sh
```

**Correct** (cross-plugin reference — declared dependency):
```bash
bash ${CLAUDE_PLUGIN_ROOT}/../core/skills/branching/scripts/check-worktrees.sh
```

### Plugin Boundary Rule

> **CRITICAL: Reach skills only through `${CLAUDE_PLUGIN_ROOT}` and their loaded namespace. Never spelunk for skill content on disk.**

A command's skills are already loaded via its `skills:` frontmatter and resolved through `${CLAUDE_PLUGIN_ROOT}` at load time. Invoke them by their loaded namespace (`workaholic:`) and run their bundled scripts via `${CLAUDE_PLUGIN_ROOT}`. Do **not**:

- read or run anything under `~/.claude/plugins/marketplaces/` or any other global/marketplace install — those may be stale copies from older versions and will silently run obsolete logic;
- guess a plugin or skill namespace. `drivin`, `trippin`, `core`, `standards`, and `work` are **obsolete** plugin names — all merged into the single `workaholic` plugin, which is the only live plugin.

If a skill you expect is not in context, ask the user which plugins are loaded — do not search the filesystem for it. The five `workaholic` command `**Notice:**` headers carry a short echo of this rule.

### Closed `.workaholic/` layout (lockstep registration)

The `.workaholic/` tree is a **closed structure**: the set of permitted top-level artifact directories is fixed and defined in **two sources of truth that MUST stay in lockstep** — `hooks/workaholic-layout-allowlist.txt` (one directory per line) and the table in `plugins/workaholic/rules/workaholic.md`. Introducing a new top-level artifact directory (as `strategies/` was) is a **deliberate amendment**, not an ad-hoc `mkdir`, and it is subject to a verifiable rule an auditor can check:

- **Register in the same change.** A new artifact directory MUST be added to **both** `hooks/workaholic-layout-allowlist.txt` **and** the `rules/workaholic.md` table — plus any skill/docs that name the artifact — **in the same commit** that first writes to it. A new artifact type is not shipped until its directory is registered. (Concretely: `git show <commit>` for any commit that introduces `.workaholic/<newdir>/…` must also touch both sources of truth.)
- **The guards are load-bearing, not advisory.** The working-directory and `.workaholic/` layout guards **block by construction** whenever the plugin is installed — enforcement is built into the plugin code with **no env-var toggle** (see `hooks/guard-working-directory.sh` and `hooks/validate-ticket.sh`). So the layout source of truth is enforced, not decorative: a **stale allowlist becomes a correctness bug** — it hard-blocks a legitimate write into the unregistered directory — which is exactly why registration must ride in the same change.
- **Named anti-drift audit.** `hooks/layout-doctor.sh [path]` reports undesignated directories against the allowlist without mutating the tree (read-only). Run it when amending the structure; it is wired into the **`## Local Verification`** commands and the **`Validate Plugins`** CI workflow, which **fails the merge** on `conforming: false` — so a drifted allowlist is caught before merge rather than surfacing as a guard block later.

This policy exists because `strategies/` shipped live (its skill and `create.sh` writing `.workaholic/strategies/active/`) while both sources of truth stayed stale — the class of drift the lockstep rule and its gate now prevent.

Each problem is named separately (`hook_missing` / `hook_stale` / `not_registered` / `matcher` / `timeout` / `enabled_plugin` / `marketplace`) because each needs a different fix; the hook is POSIX `sh`, deliberately has **no `set -e`** (it must never block session start), and is idempotent (qmu/workaholic#126); its already-installed fast path is **version-gated against the checkout's `.claude-plugin/marketplace.json`** — a container image's baked-in stale install is refreshed with `plugin update`, never skipped on mere presence, which is the defect that dirtied the tree and aborted every hourly drive tick on 2026-08-02〜04. Routines are **Claude Code Web routines** (cloud sessions reached through `RemoteTrigger`), never cron: the plugin holds **one set of templates** (`skills/workaholify/routines/` — `fb`, `merged-pr`, `drive`) and applies them to whichever repository the command runs in, so **no per-repository routine file exists and `.workaholic/` gains nothing**. `compare-routines.sh` matches a live routine to a repo by its **source URL, never its name** (names are what drift), and reports drift **per field** — **across every repository that carries a workaholic routine**, not just this checkout, since one defect replicated seven times is still one defect. `this_repo` gets missing *and* drifted; `other_repos` gets drifted only, because proposing to create routines where nobody is working would invent policy from a survey. Two preconditions are reported before anything is scheduled: the account's Slack connector (discovered from a live routine, since a new body needs its uuid/url — a routine lacking it is drift) and the `dev-<repo>` channel via `check-slack-channel.sh`, which reports **`checked: false` rather than `exists: false`** when it cannot reach Slack — a locked store returns the same error as a missing channel, and conflating them sends a developer to create a channel that already exists. `unknown` entries are deliberate one-offs, never deletion proposals — the API has no delete. Creating or refreshing a routine is confirmed **verbatim, one at a time**, because a routine is a standing outward-facing process |
| `/setup-routines [repository name]` | Answer what a repository could not answer about itself: **what runs against it** — each scheduled Claude Code Web routine with its trigger, schedule, target repository, `enabled` state and whether it still matches the shipped template (reported **per drifted field**), plus the templates it has no routine for, the untemplated one-offs, and a summary of drift elsewhere in the fleet. Decided 2026-08-03: the repository declares **nothing** — the templates live in the plugin, the live routines in the account, and every per-repository fact (`{repo}`, `{repo_slug}`, `{repo_name}`) derives from the git remote — so the command asks the account and reports, and no `.workaholic/` area was introduced. Reading is unattended-safe, and an unreachable or unrecognised response reports `checked: false` with **no `routines` key at all**, never an empty list: "I could not look" and "nothing runs here" are different answers, and the audience is a developer who cannot tell a wrong one from a right one. It also **adds, refreshes and removes** one routine at a time, and the verbatim-confirmation bar is enforced in code rather than described: `plan-routine-change.sh` stamps the exact content with a `confirm_digest` and `authorize-routine-change.sh` refuses `plan_tampered` (the plan no longer hashes to its own digest) and `digest_mismatch` (one confirmation carries exactly one routine), so substitution and batching are both closed — it cannot prove a human was present, and is not sold as doing so. A noop carries no digest and cannot be forced through (`no_drift` on an undrifted refresh, `disabled_routine` rather than silently re-enabling something switched off), and **"remove" means disable** because the API has no delete, with permanent deletion named as a human act |

## Development Workflow

1. **Create specs**: Use `/ticket` to write implementation specs — published onto a `work-*` branch behind a pull request, from whatever branch you are on; merging the PR is what queues them
2. **Implement specs**: Use `/drive` to implement and commit each spec
3. **Create PR**: Use `/report` to generate story and create PR
4. **Ship**: Use `/ship` to merge PR, deploy, and verify

### Commit-subject and branch-name enforcement

The commit-subject rule (present-tense, ≤50 chars, no `feat:`/`[bracket]` prefix — see `skills/commit/SKILL.md`) and the branch-name rule (`work-YYYYMMDD-HHMMSS` named only by `create.sh`, plus the release tier's `release/YYYYMMDD-HHMMSS` named only by `cut-release-branch.sh` — two literal patterns, nothing else) are enforced as gates, not just prose, in **two layers**:

- **Agent/harness surface (always on, zero opt-in):** `hooks/guard-git-commit.sh` and `hooks/guard-git-branch.sh` are blocking `PreToolUse(Bash)` hooks (shipped active in `hooks.json`). The commit gate blocks a direct `git commit` only when its `-m` subject is off-policy (it does **not** block `Co-Authored-By` trailers, conformant subjects, or script-wrapped commits like `commit.sh`/`archive.sh`, which never expose a top-level `git commit`). The branch gate blocks off-pattern/variable branch creation. Both route the caller to the sanctioned script.
- **Human-terminal surface (opt-in):** `hooks/git/commit-msg` is a git-native hook that enforces the **same subject rule** on every commit (including a developer's own terminal `git commit`), since `PreToolUse(Bash)` cannot see those. It is subject-only (never rewrites the message). Install it deliberately per-repo:

  ```bash
  sh ${CLAUDE_PLUGIN_ROOT}/hooks/install-git-hooks.sh   # sets core.hooksPath; refuses to clobber an existing one / classic .git/hooks without --force
  ```

  Bypass a single commit with `git commit --no-verify`; undo with `git config --unset core.hooksPath`. All layers share one rule source — the canonical validator is `skills/commit/scripts/check-subject.sh` (it pins `LC_ALL` to a UTF-8 locale so a multibyte subject measures identically on every host), which `commit.sh` runs itself before staging anything (closing the script-wrapped path the `PreToolUse` gate deliberately does not inspect) and which both hooks reach through the stable `hooks/lib/check-subject.sh` delegator — so the layers cannot drift. Because the validator lives in the commit skill's `scripts/`, the generated `outputs/workflows` bundle carries the gate too (rebuild on change); the hooks themselves remain Claude-Code-only / git-native with no `outputs/` footprint. `commit-msg` is exempt from `posix-lint` only because git requires that exact extensionless name; it is POSIX `#!/bin/sh -eu` by construction.

### AskUserQuestion project-label enforcement

The `[<project label>]` prompt-prefix convention (each `AskUserQuestion` question body opens with the owning repo's label, from `skills/gather/scripts/project-label.sh`, so a developer with many parallel sessions sees which repo is asking) is enforced as a gate, not just prose. `hooks/guard-askuserquestion-label.sh` is a blocking `PreToolUse(AskUserQuestion)` hook (shipped active in `hooks.json`): it reads `tool_input.questions[].question` and exits 2 (re-issue) when any body lacks a leading `[…]` label. It fires on every `AskUserQuestion` by design — labeling any prompt with its repo is a net good, so the over-fire onto ad-hoc questions is intentional. Claude-Code-only, POSIX `#!/bin/sh -eu`, **no `outputs/` footprint**. The rule itself stays where it was — the per-skill "User interaction" prose — this hook only makes it machine-checked.

**Whether a prompt should fire at all** — a separate question from its label — is governed by `rules/interaction.md` (always-loaded): ask only for genuine decisions, else **act and report** and let the developer correct. Its sharpened form is the **Recommended-label test** — if you could honestly mark an option "(Recommended)", do not ask; decide it, record the decision and its reason where the work is written, and let the developer veto. This stays deliberately **not** hooked, and the sharpening does not change that: necessity — and *a fortiori* whether an option was recommendable — is a judgement a `PreToolUse(AskUserQuestion)` hook cannot read (it sees only the prompt text), the same reason `/request`'s masking is a judgement, not a matcher. The label hook checks a prompt's shape; the rule governs its necessity. The interrogation surfaces (`/ticket` §4b, `/mission` Creation Interrogation and replan) all reference the one canonical statement in `rules/interaction.md` rather than restating it.

A companion `hooks/guard-working-directory.sh` (`PreToolUse(Bash)`, shipped active) **denies** a top-level cwd-moving `cd` via `permissionDecision: "deny"` naming the offending command and the sanctioned alternatives — **unconditionally, with no env-var toggle**: enforcement is built into the plugin code, so "plugin installed = guard active", identical on every machine and fresh clone (an injectable opt-in switch fails open exactly when it is not set, which is when the guard is needed, and an advisory reminder is text an agent ignores). The match set is unchanged (a `( cd … )` subshell, an absolute path, and a `--prefix`-style command always pass silently). It is the machine-enforced half of the `workaholify` working-directory ground rules (`skills/workaholify/`); like the other guards it is Claude-Code-only, POSIX `#!/bin/sh -eu`, with no `outputs/` footprint.

### Repository confinement

Every write lands inside the current repository or one of its own worktrees. Crossing to another repository is done **only** through `/request`, which masks this project's customer context before submitting. Two layers, and the order matters:

- **The rule is primary.** It lives in `rules/general.md` ("Never modify another repository", plus "Never carry one repository's context into another's artifacts"), which is `paths: '**/*'` — always loaded, and shipped to every repo that installs the plugin. This is deliberately where the weight sits: the rule is what an agent reads before it acts.
- **The hook is a syntactic backstop.** `hooks/guard-repo-confinement.sh` is a blocking `PreToolUse(Write|Edit)` hook (shipped active) that resolves `tool_input.file_path` against `git rev-parse --show-toplevel` plus every entry of `git worktree list`, and exits 2 when the target is outside all of them. It runs PreToolUse because `validate-ticket.sh` is PostToolUse — refusing *after* the file exists in the foreign repo is not confinement. It accepts worktrees in both directions, because missions run in `.worktrees/<slug>/` and a toplevel-only test would break the mission model. It also exempts the agent's per-project memory store (`~/.claude/projects/<slug>/memory/`): that is the harness's own store — not another repository — the harness itself directs the agent to write there, and a stale memory's only correction path is a write (blocking it once left a memory contradicting the current design firing every session with no way to repair it). It fails open outside a git repo. Claude-Code-only, POSIX `#!/bin/sh -eu`, no `outputs/` footprint.

**Do not grow the hook toward content matching.** A path is syntax and a matcher handles it well; a customer's vocabulary is semantic and a matcher cannot recognise it — the terms that leak are usually not enumerable until the moment they leak. That judgement belongs to `/request`, where a person confirms it.

`/request` (`commands/request.md` + `skills/request/`) is the outlet the confinement needs: `resolve-target.sh` resolves the target and reports its **visibility** (public vs private is a different decision, and the developer must see which they are making), and `submit-request.sh` is the only sanctioned writer of a cross-repo artifact. Between them sits the step that actually does the work — **the developer confirms the destination and the exact body, verbatim, in one confirmation that cannot be skipped** (the destination is folded in, but the verbatim body is the surviving gate). `submit-request.sh`'s checks are mechanics (empty body, malformed filename, and this repo's own name, `owner/name` remote form, clone URL or absolute path); they are not assurance. The bare-name check matches an **identifier, not a substring** — it was a plain case-insensitive substring until 2026-08-02, which made a repository whose basename is an ordinary English word unable to submit any request whose body listed paths embedding that word (including directories belonging to the *target* repo), refusing it **after** the developer had confirmed the body verbatim and instructing them to "mask" something that could not be removed. This backstop is the one place a legitimate request is refused past the human gate, so its false-positive rate is a usability property, not only a safety one; every refusal now cites the matched text and its line. The test suite asserts this directly: the four real leaked sentences from the incident pass through the script *without complaint*, because none of them names this repo. That is not a bug to fix — it is the measured reason the human gate exists, and `request/SKILL.md` §1 explains why no matcher can replace it.

The guard watches the Write/Edit tools; a shell redirect from Bash is not seen (which is how `submit-request.sh` writes), and neither is a write performed by an MCP server (which is how `/explain`'s browser prints its PDF to the developer's Desktop). The threat model is an agent doing the natural thing, not one evading a gate.

**It cannot exempt a caller, and that shapes `/explain`.** A `PreToolUse` hook receives only `tool_input.file_path` — never which skill is asking — so an `.html` bound for Home is indistinguishable from any other write there and there is no narrow carve-out to write. `/explain` therefore stages its HTML **in-repo** at a git-ignored `.explain/<slug>.html` and lets the **browser** write the PDF to `chosen_dir` over MCP. The export is unchanged; only the staging file moved. `skills/explain/SKILL.md` §2-4 carries the rationale, and `test-workflow-scripts.mjs` pins the constraint ("confine blocks a non-repo path outside the repo (export dir)") so the dead `<chosen_dir>/<slug>.html` path cannot be reintroduced silently.

**The rule only reaches a repo that installs the plugin.** This is the failure that produced the incident: rules, hooks, and the scan are all inert in a repo where `workaholic@workaholic` is not in `enabledPlugins` — no matter what is written here. Enable it at the user level (`~/.claude/settings.json`) so every repo is covered, not per-project.

### Always-on policy lens

`hooks/policy-lens.sh` is a non-blocking `UserPromptSubmit` hook that injects the engineering-policy lens for the workflow commands that carry the `workaholic:policy-lens` sentinel marker (`/ticket`, `/request`, `/report`, `/ship`, `/drive`, `/catch`, `/explain`). The sentinel rides in the expanded command body, so the lens fires once per workflow invocation and stays in accumulated context. Two layers, by design:

- **Refer for bodies**: the hook points at the four pillar policy skills (`workaholic:planning`/`design`/`implementation`/`operation`); the full Goal/Responsibility/Practices live in `skills/<pillar>/policies/<slug>.md` and are read **on demand** when a change touches that policy.
- **Embed the index only**: the hook appends `hooks/policy-index.md` — a **generated** table of contents (per-policy heading + one-line summary across all four pillars), produced by `scripts/build-plugins/policy-index.mjs` from the four `SKILL.md` `## Policies` sections. This is the single bounded exception to "refer, never embed": headings are an index, not policy rules. The `## Policies` sections stay the single source of the heading list (kept fresh from qmu.co.jp by the `workaholic-standards-sync` controller). **Regenerate with `build.mjs` after editing any pillar's `## Policies` list.** Freshness is enforced in CI the same way `outputs/` is: the `Outputs Freshness` workflow rebuilds and fails on any diff to the committed `hooks/policy-index.md` (not by `verify.mjs`, which only flags a stale *working-tree* index when run before a build — after a build it is vacuously fresh).

### Always-on mission lens

`hooks/mission-lens.sh` keeps the agent — and the developer — oriented to the roadmap. It is registered on two events and is **non-forcing** on both (it never blocks a stop): on every `UserPromptSubmit` it injects a **model-visible** `additionalContext` line, and on every `Stop` a **user-visible** `systemMessage`. Each names the **active** missions (`.workaholic/missions/active/<slug>/mission.md`) that pass all **three** gates, with derived `checked/total` and the next unchecked acceptance item: **ownership** (the mission is *not somebody else's* — the current `git config user.email` is among its **derived** owners via `mission-owners.sh`, or it is **unowned**, in which case it is surfaced to everyone as claimable, after the developer's own; only a mission owned solely by others stays silent), **location** (the worktree-focus rule below), and **signal** (at least one acceptance criterion). The signal gate exists because the line is printed unasked, directly above the agent's answer: a mission whose `## Acceptance` is empty renders as `0/0` with no next step — a technical condition with nothing to act on — so it says nothing instead. It is a silent no-op when nothing passes all three, so it usually costs only a few greps per turn (with many missions the per-mission `progress.sh` subshells are not free; if that ever bites, the fix is a batch reader in `skills/mission/scripts/`, not parsing inlined into the hook).

**Summarize on change.** The roster rarely changes within a session, yet a long `/goal` Stop condition re-fires this hook on essentially every turn — and re-injecting the whole block each time buries the developer's own message under redundant context (worse the larger the roster). So the **full** block is emitted only when the roster **changed** since the last turn of this session (or on the first turn, or when `session_id` is absent — a case that cannot be deduped and stays full, keeping the bare-harness/test path backward-compatible). An **unchanged** turn collapses to a compact one-liner — the count plus the single next action plus a bare `/mission` pointer — so the active goal and next step stay visible without the volume. The change-detector is keyed per session **and** per event (`UserPromptSubmit` and `Stop` dedupe independently), cksum-compared under `${TMPDIR:-/tmp}/workaholic-mission-lens/`, and fails open to the full roster; it never blocks a stop, so `/goal`'s gating is untouched. (`/goal` itself is a Claude Code harness feature, not a workaholic command — the only lever this repo owns over that per-turn volume is this hook's roster injection.)

The bare `/mission` view's **full tier** deliberately keeps the **lower** bar — ownership alone (`list.sh`'s `relation`: `mine`/`unassigned`) — so an unfilled `0/0` mission is still visible on demand. An always-on nudge and a view you asked for should not share a threshold; the divergence is intentional, not drift. (The old `/mission summary` mode carried this bar before it was folded into the bare view, 2026-07-22; `summary.sh` remains as the gate's canonical statement.) The **ownership** gate itself is shared through `mission-owners.sh`: both read "not somebody else's", so an unowned mission surfaces in each (the lens and the bare view mark it unclaimed). Ownership is carried on the mission's own plural `assignees` (2026-07-28), with a legacy fallback to the singular `assignee`; "mine" means the caller is among the owners, since a mission can be co-owned.

The **worktree-focus** rule (missions run in their own `.worktrees/<slug>` worktree) has three cases, each decided rather than left to fall through: inside a mission's worktree it surfaces **only that mission** (you are already focused on it, so other worktrees' missions are noise); inside a worktree that owns **no** mission — a `/drive` worktree such as `.worktrees/work-20260714-005155` — it surfaces **nothing at all** (that session is focused on one ticket; the roadmap is not its business); and in the main tree it surfaces only missions that do **not** own a dedicated worktree (a worktree-owned mission stays silent everywhere but its own worktree). Basename-matching is sound here because `slug.sh` is the single source deriving both the mission directory name and the worktree name. This keeps each worktree's nudge scoped to its own work instead of listing every mission you own.

- **Why two events:** a `Stop` hook cannot inject model-visible context without `decision: block` (which would *force* the agent to keep working) — its only non-forcing channel is the user-facing `systemMessage`. So the model-facing half deliberately rides `UserPromptSubmit` (the same mechanism `policy-lens.sh` uses), which fires exactly when the agent decides "what to do next"; the `Stop` half is the developer-facing nudge. Together they honor "every time the agent stops or asks what next" without ever hijacking the turn.
- **Ownership is the gate:** a mission's owners are its own plural `assignees` (`mission-owners.sh` — mission `assignees` first, legacy `assignee` fallback; see the mission skill's *Ownership* section). Because each git worktree checks out its own `.workaholic/`, the lens that fires in a worktree reflects the missions owned by whoever is working that tree.
- **Reuse, not duplication:** the hook computes progress via `mission/scripts/progress.sh` and the next step via `mission/scripts/next-acceptance.sh`, so the Acceptance-scoping convention lives in one place. Claude-Code-only, POSIX `#!/bin/sh -eu`, **no `outputs/` footprint** (lives in `hooks/`, not built). The mission skill itself *is* built into `outputs/workflows`, so the `assignee`/`next-acceptance.sh` changes there require a `build.mjs` rebuild; the hook does not.

### Release-safety scan

The `release-scan` skill (`skills/release-scan/scan-branch-safety.sh`) is a **deterministic, script-only** branch-safety gate that `/report` (warn) and `/ship` (block, pre-merge) run over `git diff <base>..HEAD` to catch, before content reaches a public remote: **credentials** (`secret`, hard block — `release-scan/scripts/lib/secret-patterns.sh`, whose generic-assignment rule matches on the **value**, not the key name: a quoted-alphanumeric or line-ending bare run is a literal, and everything else — identifier, call, env read, template, annotation — is a reference that needs no rule of its own), **oversized/too-many files plus per-commit changed-lines** (`size`, overridable — `MAX_FILES`/`MAX_FILE_ADDED_LINES`/`MAX_FILE_BYTES` per file/branch, and `MAX_COMMIT_CHANGED_LINES` per commit via a `too-large-commit` rule that sums a commit's **non-generated** added+deleted lines, exempting binary rows, lockfiles, minified artifacts, `linguist-generated` paths — workaholic marks `outputs/**` so — and any file already over the per-file ceiling; it standardizes commit size so commit count is a comparable throughput unit), and **re-introduction of an already-known client/project term** (`leak`, confirm — the git-ignored, developer-maintained `.workaholic/leak-denylist`). It emits `{verdict, findings[]}` with each finding citing `file:line` + the matched rule (objective, so it can gate a merge); the consumers enforce the severity tiers. It is a script, not a subagent, on purpose — a merge gate must be reproducible, not a model judgment.

**Read the scope of the `leak` rule literally.** It matches listed terms in the branch diff, nothing more. It is blind to content already on `main`, and because the denylist is git-ignored it is a silent no-op in any repo where nobody created the file. It does **not** enforce "keep motivation generic, never name other repos/clients" — that rule is enforced by confining every workflow's writes to the current repo and by `/request`'s masking confirmation, which is a judgement a person makes when content crosses a repository boundary. A `pass` verdict means "no listed term was re-introduced", never "no client context here". An earlier version of this paragraph claimed the scan machine-enforced the convention; a structured internal-hostname pattern that backed that claim was removed after it was measured to detect none of five real leaks while misfiring on `metadata.internal`.

## Version Management

Version bumps are **manual** — there is no `/release` command. After bumping the files below and pushing to `main`, CI (`.github/workflows/release.yml`) publishes the GitHub Release automatically (it reads the version and the latest `.workaholic/release-notes/` note).

Version files (all must stay at the same semver):
- `.claude-plugin/marketplace.json` - root `version` AND every `plugins[].version` entry (workaholic, workflows)
- `plugins/workaholic/.claude-plugin/plugin.json`
- `plugins/workaholic/.codex-plugin/plugin.json` - hand-maintained Codex-facing manifest

Generated (do NOT hand-edit; rebuild with `node scripts/build-plugins/build.mjs`):
- `outputs/workflows/.codex-plugin/plugin.json` - version is read from `.claude-plugin/marketplace.json`'s `workflows` plugin entry at build time

`.claude-plugin/marketplace.json` is the single source of truth. When bumping version:
1. Read current version from `.claude-plugin/marketplace.json`
2. Increment PATCH by default (e.g., 1.0.0 → 1.0.1)
3. Update the root `version` and every `plugins[].version` in `.claude-plugin/marketplace.json`
4. Update `plugins/workaholic/.claude-plugin/plugin.json` and `plugins/workaholic/.codex-plugin/plugin.json` to match
5. Regenerate `outputs/workflows/` so its Codex manifest picks up the new version
6. Stage and commit: `Bump version to v{new_version}`
