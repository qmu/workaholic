# Workaholic

Private, cross-agent distribution of structured development workflows and engineering standards. **AI agents are the primary users** — routines invoking `/implement` and `/specificate`, and sessions running the workflow skills — while the **developer is the operator** who approves pull requests, configures routines, and rules on deferred decisions. Richest on **Claude Code** (plugin marketplace: commands, hooks, the always-on policy lens); portable skills also ship to **Codex** (`.agents/plugins/marketplace.json` → `outputs/workflows`) and to 40+ agents via the Agent Skills standard / `skills` CLI. Authored source lives under `plugins/`; cross-agent artifacts are generated into `outputs/`.

This file states **current behavior only**. Decision history and rationale live in `docs/loop-engineering-workflow.md`, `docs/proposal-loop-runbook.md`, `docs/drive-loop-runbook.md`, each skill's `reference/` directory, the feedback stream (`.workaholic/feedbacks/`), and this file's own git history.

## Important

- Edit `plugins/`, not `.claude/` — this repo develops plugins; changes go to `plugins/` unless explicitly requested otherwise.
- **Update the docs in the same change.** When a change alters behavior, structure, commands, skills, or conventions, update every affected document (`README.md`, `.workaholic/README.md`, `CLAUDE.md`, `plugins/workaholic/rules/*.md`) in the same commit. Outdated documentation is a defect; `/story` runs `doc-drift.sh` and `area-freshness.sh` only as backstops.
- **Write each surface in the language its audience reads.** Reasoning on the `#dev-workaholic` channel and in Claude Code Web routines is **Japanese** — the developer reads it there. GitHub artifacts (issues, pull requests, commit messages) and `.workaholic/` artifacts are **English** — they are the durable, shared record, read by tooling and by whoever arrives later. The rule covers those surfaces and no others: code, code comments and this repository's `docs/` tree are untouched by it.

### Hooks (all shipped active in hooks.json)

- `validate-ticket.sh` (PostToolUse Write|Edit) — ticket floor on the `todo/` queue only: frontmatter, location, mandatory `## Policies`/`## Quality Gate`, resolvable `mission:` relation.
- `validate-mission.sh` (PostToolUse) — Experience/≥1-acceptance floor on any mission under `missions/active/`; archive never retro-blocked.
- `validate-story.sh` / `validate-trip.sh` / `validate-feedback.sh` / `validate-strategy.sh` (PostToolUse) — OKF `type:` and schema floors on new writes; git-tracked history is grandfathered. `validate-strategy.sh` holds the revived strategy artifact to the three properties that distinguish it from the one retired in 2026-07-28: a `YYYY-MM-DD` `target_date`, a **non-empty** `assignees` (the one artifact where empty is a refusal, not team-owned), and non-empty `## Aim` / `## Schedule`.
- `guard-ticket-structure.sh` (PreToolUse Bash) — blocks non-canonical ticket moves.
- `guard-git-commit.sh` / `guard-git-branch.sh` (PreToolUse Bash) — commit-subject and branch-name gates (see below).
- `guard-askuserquestion-label.sh` (PreToolUse AskUserQuestion) — every question body must open with a `[<project label>]` prefix (`gather/scripts/project-label.sh`).
- `guard-working-directory.sh` (PreToolUse Bash) — denies a top-level cwd-moving `cd`; a `( cd … )` subshell, an absolute path, or a `--prefix` form always passes. No env-var toggle. **A leading `cd` that lands on a repository root passes** (2026-08-23) — the main checkout's root or a worktree's, resolved through `git rev-parse --show-toplevel`: that command restores the ground rule rather than breaking it, and refusing it was refusing the only repair. Measured: a session whose cwd had been moved into a worktree could not return, so every later command needed hand-wrapping and the scripts that read the cwd operated on the wrong tree — `branching/scripts/create.sh` switched a **claim** worktree off its claim branch. Only the leading form and only a root; a chained mid-command `cd` stays denied whatever its target, a target carrying shell syntax the hook cannot resolve without evaluating it is denied rather than guessed, and bare `cd` (to `$HOME`) is now denied too — it had matched nothing at all.
- `guard-repo-confinement.sh` (PreToolUse Write|Edit) — blocks writes outside this repository and its worktrees (the agent's per-project memory store is exempt). Syntactic backstop only; the primary rule lives in `rules/general.md`.
- `policy-lens.sh` (UserPromptSubmit) — injects the engineering-policy index for commands carrying the `workaholic:policy-lens` sentinel; bodies are read on demand from `skills/<pillar>/policies/`. Regenerate `hooks/policy-index.md` with `build.mjs` after editing a pillar's `## Policies` list (CI rebuilds and fails on drift).
- `layout-doctor.sh [path]` — read-only audit of `.workaholic/` against the layout allowlist.

## Architecture Policy

### Component Nesting Rules

| Caller                         | Can invoke                                   | Cannot invoke              |
| ------------------------------ | -------------------------------------------- | -------------------------- |
| Command                        | Skill, `general-purpose` subagent            | —                          |
| Skill                          | Skill; (when loaded by a command/main agent) may direct it to spawn `general-purpose` subagents | Command                    |
| `general-purpose` subagent     | Skill (via preload)                          | Command, Task (no nesting) |

- **No per-workflow agent files.** The repo ships no agent `.md` files at all. A command spawns `subagent_type: "general-purpose"` subagents whose prompts name the `workaholic` skill to preload, the section, the inputs, and the return schema.
- **One-level fan-out.** A subagent cannot nest `Task` and cannot call `AskUserQuestion`; all fan-out and all user interaction happen at the command/main-agent level. Leaves do non-interactive work and return JSON.
- **One plugin.** `workaholic` has `dependencies: []`. All skill references are same-plugin (`${CLAUDE_PLUGIN_ROOT}/skills/<name>/...`, `workaholic:<name>` namespaces). The `workflows` marketplace entry is the generated `outputs/workflows` bundle, not an authored plugin.

### The ticket spine

Everything converges on the **ticket** as the unit of work: *sources* fill `tickets/todo/`, one executor drains it to `tickets/archive/`.

- **Sources**: `/ticket` (human-directed, with discovery) and `/mission`'s Creation Interrogation (which emits a mission's whole ordered ticket set). `/specificate` feeds them from the feedback stream. All publish through a **publish tree** onto a `work-*` branch behind a pull request; the artifact reaches `main` — and the executor's survey — when that PR merges.
- **Mission floor and ceiling**: a mission is created with **two or more tickets** or it is not a mission (checked at the publish seam by `mission/scripts/check-floor.sh`; a ticketless direction is a feedback record, a one-ticket one is a plain ticket). The ceiling: `## Acceptance` normatively ≤3 items, whole `mission.md` ~60 lines / 2 KB — measured by `mission/scripts/size.sh`, enforced on `/specificate`'s unattended drafts. Write-time floor: `## Experience` + ≥1 acceptance item.
- **One executor, two commands**: `/drive` (attended — asks exactly one thing: which units to take when several are offered) and `/implement` (unattended — no prompt at any step). Same Unified Run either way: freshen (`sync-main.sh`) → survey (`plan-units.sh`) → partition into PR-units → claim → drive → report → route by effective merge policy → account. **A survey that excluded its whole backlog says so** (2026-08-26): `plan-units.sh` emits `backlog_all_excluded` — a derived reading over `backlog_size`, `backlog[]` and `excluded[]`, carrying a count per exclusion reason, because a queue emptied by claims is the protocol working while one emptied by `owned_by_other` is work nothing can drive. No new scan, no stored state, no field on any artifact, and no token moves. The full contract lives in `skills/drive/SKILL.md` and its `reference/`.
- **Merge policy** (`merge_policy: auto | review`, recorded at creation on missions and tickets; **absent means review**): `auto` ships through `/ship` — which drafts the plan and merges, never deploys — then tears the claim down; `review` merges its PR immediately after `/story` opens it — a `hard` (`secret`) or `confirm` (`leak`) scan finding is what leaves it open. **No gate is ever overridden** by either entry point: a `secret` finding hard-stops; a `size`/`leak` block or a missing confirmation method demotes an `auto` unit to the PR path.

**The `review` route reads the severity tier, never the binary verdict** (2026-08-21). It read `verdict == "pass"` until then, which held a merge open on the one tier `workaholic:release-scan` itself calls *a granularity nudge, not a hard block* — the same skill that has always said *the severity tells the consumer how hard to block, and both consumers key on it, never on the binary verdict alone*, and that *a branch whose only findings are `override`-tier stays releasable*. `/story` obeyed it; this route did not. **Measured** on a documentation repository consuming this plugin: a `review` unit of 42 documentation pages in two languages produced three `too-large-commit` findings (749 / 983 / 1119 added lines against a 500 ceiling) and nothing else — no mixed concerns, no secret, no leak; the line count *was* the shape of the work. The unit sat at an open pull request and the run reporting it went on to **ask a human whether to merge**, which `/implement` may never do — one cause, both symptoms. `gate-decision.sh` now computes **`override_only`** beside `overridable`, so the tier policy stays in one script rather than being re-counted by each of its three consumers, and the route merges on `pass` **or** `override_only`. An `override_only` merge still reports every finding, in the run report and in the pull-request body `/story` writes: the nudge is delivered where it is useful and nowhere that it stops the loop. `secret` still hard-stops, `leak` still holds the pull request open, and the `auto` route's demotion table is untouched — there the override is a real human ruling recorded in deployment evidence.
- **An Open Decision is a question to answer, not a ruling that the question is unanswerable** (2026-08-23): before a driving run may honour a written `## Open Decisions` item as a blocker it **reads the sources the item names**, plus the whole of any page it cites, and a `blocked` outcome reached that way **names those sources and what they said** — a block that cannot name a source it read is not a block (`drive/reference/ticket-workflow.md` §1, `reference/failure-contract.md`, the run report contract in `drive/SKILL.md`). The item had been **self-certifying**: `/specificate` declared a fork unresolvable and the driving run took the declaration as evidence rather than as a claim to check, which the failure contract's own words permitted because a session can name an authority without ever having looked. Measured: a tick honoured an item whose answer sat fifty lines further down the very page the ticket named; on a consuming repository the same shape ran eleven consecutive ticks for zero lines of implementation while the operator's own answer sat unread in the same tree. It is a **prose contract, not a script gate** — no mechanical check tells a real read from a claimed one; what it buys is that a blocked report naming no source is visibly non-conformant. This is the driver-side half of the 2026-08-23 `/specificate` fix above, which stopped the *writing* of unclearable gates. **The writing side gained the matching floor in the same change**: an `## Open Decisions` item now has three required parts — the question, **the sources consulted and what they said**, and the fork's sides — may name whose ruling would settle it, and may **not** declare the question unanswerable or instruct a later session not to decide (`create-ticket/reference/ticket-format.md`; `/specificate`'s discovery must have covered the item's own subject, and the **whole** of any page it cites, before the item may be written — the measured failure was a partial read of one table). A genuinely unrecommendable fork is still recordable: what is removed is the self-certification, not the section. `/ticket` is untouched — it resolves the same kind of fork by asking a human directly, so it never writes one.
- **The verification axis is read before merge policy** (2026-08-14, issue #452): a mission or ticket may declare `verification_handoff: <what cannot run here>` **at creation** — a credential, device or third-party account an unattended run does not have. `drive/scripts/verification-handoff.sh` reads it, any member declaring it carries the whole unit, and that unit takes the **`handoff`** route whatever `merge_policy` says: the PR opens and stays open, the non-droppable `## Handoff` quotes the reason, the claim stays standing, the finish line is `🟡 Handoff` and the token is `pending`. Written by `/ticket` and by `/specificate` (`scaffold-proposed-ticket.sh --verification-handoff`) **only when the ask itself states it**; a run never declares it for its own unit, which is what keeps `handoff` from becoming a soft landing. **One second writer since 2026-08-23** (issue #83): `/specificate` also declares it for an **unresolved operator-only fork** that survived the operator-record check — the axis is the same (what cannot be settled here) and the rule's intent is untouched, because the declarer is the *writer* ruling at creation about a unit it will not drive, never a driver excusing its own work. Such a fork must **never** be written as a `## Quality Gate` item instead: `/implement` may neither ask nor override, so a gate item is re-claimed and re-failed every tick forever, while a standing handoff claim is not re-surveyed and costs nothing per tick. Measured: nine consecutive resumes over nine hours, 1.6 recorded agent-hours, zero lines of implementation. **The claim behind such a unit is no longer re-offered either** (2026-08-27, mission `stop-re-resuming-a-declared-handoff-unit`): the sentence above — *a standing handoff claim is not re-surveyed and costs nothing per tick* — was the design and not the behaviour, because the route read the declaration and the **claim oracle never consulted it again**. So the moment `/story` committed the branch story the claim read `parked_with_pr`, `resumable: true`, and every survey offered a takeover that could drive nothing; measured on PR #647, routed at 02:14 UTC and taken over again at 06:43. The claim now answers **`awaiting_verification`** and the sentence is true as written.
- Retired predecessors (`/monitor`, `/trip`, `/carry`) and their landed ideas: `docs/loop-engineering-workflow.md` I1/I3/I5. `.workaholic/trips/` is read-only legacy history.

### `.workaholic/` runtime conventions

- **OKF floor**: every knowledge artifact carries a non-empty `type:` (`Story`, `Mission`, `Feedback`, `Strategy`, `Deployment`, `Term`, `Release Note`, `Release`); `okf/scripts/refresh-index.sh` regenerates the bundle indexes before each knowledge commit. **Two exceptions, both deliberate**: `tickets/` (no `type:`, internals never index-managed) and, since 2026-08-17 (issue #471), `moderations/` — the `/moderate` tick log, one file per UTC day, one `## <tick-id>` section per tick, one line per step. It is an operational log, not knowledge: 24 entries a day would rewrite the bundle indexes hourly, so entries carry no frontmatter, the area has no `index.md`, and the root index links the directory bare. `moderate/scripts/log-append.sh` is the only writer (append-only, idempotent per (tick, step), **never prunes** — deleting a day file is the operator's act) and `log-read.sh` the reader a step consults before re-filing what an earlier tick already filed. The tick **commits its own log to the base as its closing act** (`persist-log.sh`, after the last step) — a routine's container is discarded, so a log left in the checkout would blind every dedup and leave an hourly unattended process with no audit trail. The seam is the **publish tree directly**: the caller's checkout stays byte-identical, no branch is created, concurrent ticks **union by `(tick, step)`** so two containers on the same day both land — whole sections the base lacks, and, inside a section it already has, the entries it lacks, with a `(tick, step)` already on the base never rewritten — and a persist that missed the base is reported `degraded` by name with the log left in the checkout for the next tick. **It runs twice** (2026-08-18, PR #489): the agent acts on `needs_agent` only *after* `run.sh` returns, so it persists again once it has recorded what it filed, and without that second run — and without the line-wise half of the union, which is what makes it carry anything — every `<step>-filed` line died with the container and the dedups those lines feed read an empty memory forever. It is not the unattended-`main`-writer class `workaholic:ship` §7 refused — the append is not self-referential, touches no claimed branch, and merges nothing (`rules/workaholic.md`). **It carries the tick's feedback records too** (2026-08-23): `create.sh` stages a record and stops, so a finding the sweep or the triage wrote died with the container while the tick reported it filed. `persist-log.sh --record <path>` puts them on the same commit — named one by one, **never a sweep of whatever is staged**, and a record already on the base is left untouched because a feedback record is immutable, so concurrent ticks both land and nothing is rewritten; each is reported `carried` / `already_on_base` / `missing` / `unreadable`. **And a `<step>-filed` line no longer proves a filing**: `filed-records.sh` reads the paths the line names and asks the tree, so an `unlanded` record is treated as **not filed** and the next tick re-derives the finding — measured, the persist reported both records filed while the base carried the log section and not one record, and the next tick skipped both on the strength of those lines. `readable: false` is named rather than rendered as an empty set. `README.md` and `index.md` are the only files allowed at the `.workaholic/` root.
- **Mission rolling**: commit seams (archive, ship, report) append `## Changelog` lines and tick `## Acceptance` items via the mission skill's idempotent mutators (`append-changelog.sh` / `tick-acceptance.sh`). Progress (`checked ÷ total`) is computed, never stored. Acceptance items become tickable through their `(#<filename>)` link, stamped only by the emitting seam via `link-acceptance.sh`. The `mission:` relation is many-valued; read it only through `read-relation.sh`.
- **Strategy** (`.workaholic/strategies/<slug>.md`, revived 2026-08-13 — issue #436): the operator's **outbound, resolved direction** — an **Aim**, a **Schedule** (`target_date`), an **Assignee** (non-empty `assignees`) and, since 2026-08-29 (mission `make-a-direction-s-lifecycle-a-declared-stage`), a **Stage**: `stage:` from the closed set `進行中 | 改良中 | 観察中`, the operator's own vocabulary kept verbatim. It is **declared, never derived** — every other reading in this layer (`pace`, `overdue`, `expiring`, `dormant`, `quiescent`, and the one answer `direction-state.sh` composes) is evidence the loop computed, while no reading anywhere may compute, move or infer this one; a reading may **suggest** a transition and the operator's announcement performs it. A **sixth `direction-state.sh` value** is refused for the reason `overdue` was kept out of `pace` and `expiring` out of both, so the stage rides **beside** that answer and never enters its precedence. **Absent means 進行中**, the convention `merge_policy` (absent means review) and a ticket's `status:` (absent means queued) already use, which is what makes it a field addition with **no migration**: every committed strategy stays valid and byte-identical, and the default is resolved in exactly one place — `read.sh` — which `list.sh` composes rather than parsing the field a second time. `create.sh` takes `--stage` and refuses `bad_stage` with nothing written; `validate-strategy.sh` checks only the closed set, because **presence is never required**. An ASCII alias set is refused: one field with two spellings is the drift the closed set exists to prevent. **Stuckness is orthogonal to the stage** — a handoff, a block, a stale claim or a queue that will not drain occurs in any phase and is never read as one. Flat, one file, operator-authored through `workaholic:strategy`; no command, hook or routine puts one on `main` on its own and `/drive` never surveys it. **Which work belongs to a strategy is answered by one reader and adds no field** (2026-08-17, issue #473): `strategy/scripts/attributed-work.sh` walks the citation that already exists — `strategy.feedback[] ∩ artifact.feedback[]` (`direct`), plus the hop through a mission attributed that way (`via_mission:<slug>`, load-bearing because `/specificate` puts the refs on the mission and its tickets carry `mission:`) — reading each relation through that relation's existing single reader. The `strategy:` relation and its ownership hop stay retired, which is exactly what choosing a no-new-field rule preserves; the attribution is **transitive and lossy**, so every consumer reports what it could not attribute instead of implying the answer is exhaustive, and a quiet strategy returns a named empty reason (`no_feedback_refs` / `no_citing_artifacts` / `no_activity_in_window`) rather than an error or a guess. **`no_citing_artifacts` became a *provable* reading on 2026-08-26** (mission `prove-the-loop-s-closing-link`): it used to cover two situations a reader could not tell apart — a direction nothing has answered yet, and one whose answer was published with the carry-forward link dropped — and the second was invisible and self-perpetuating. The hole is closed at the writing end by `/specificate`'s read-report-floor chain, pinned by a hermetic test that walks ask → reader → scaffold → floor and fails when the ref is dropped, so the reading now means *nothing has answered this direction yet* and nothing else. **Its limits are stated rather than implied**: work a run never emitted, an ask that named no refs, a ref that did not resolve, and any artifact written by hand outside `/specificate` stay uncited for ordinary reasons — the attribution is no more exhaustive than it was, only unambiguous where the loop itself produced the work. **And since 2026-08-29 the reading rests on a walk that says when it could not look** (mission `keep-the-closing-link-readable-as-the-corpus-grows`): the prefilter both hops share discarded every candidate the earlier `xargs` batches had found whenever a later batch matched nothing, so the closing link went **silent** the moment the corpus outgrew one command buffer — measured on this repository, 1411 corpus paths / 132292 bytes against a 131072-byte buffer, 0 candidates where an appending walk found 26, and `no_citing_artifacts` for a direction with 26 citing artifacts. The walk now appends across batches and treats a no-match batch as a success while a `grep` exit of 2 or more stays a failure; a walk it could not **complete** answers `readable: false` with a named reason (`corpus_unreadable` / `patterns_unreadable`) and **null** counts, an empty artifact list and no `empty_reason` at all — never `no_citing_artifacts`, which means the opposite. **`readable` is absent on a completed walk and that is the contract** — *absent means the walk completed*, the convention `merge_policy` (absent means review) and a ticket's `status:` (absent means queued) already use — so every completed reading is byte-identical and a consumer not yet taught the term behaves exactly as it did; the test is `readable == false`, never `readable // true`, because jq treats `false` itself as empty. **Every reading composed on the walk carries the degradation rather than deriving a verdict from it**: a survey row is refused `attribution_unreadable` — the word this condition already had — with `pace: unknown`, `dormant: false`, `quiescent: false` and null `waiting_*`, and **`work_waiting` cannot stand open on it** (a gate that cannot be read is not a gate; measured, the pre-change survey put both directions in `eligible` with `dormant: true` and `waiting_count: 0` and selected them both); `direction-state.sh` answers `unreadable` through its existing precedence and carries the nulls; `mission-strategy.sh` names such a direction unreadable instead of answering *no strategy*, so `unattributed-work.sh` reports `readable: false` with null counts and names nothing — under **`strategy_unreadable`** when at least one active direction failed, since a mission attributed *only* to that direction is named as residue in exactly the same way; and `/standup`'s digest renders a degraded strategy by name with `degraded_count` beside the other counts, its honesty line null, and **`all_attribution_unreadable`** as its own named no-op rather than `no_activity`. The date terms never move — `overdue`, `expiring` and `days_to_target` come from the strategy's own `target_date`. Drilled offline by `verify-corpus-boundary`. **The inverse is readable too, and the link is visible where missions are read** (2026-08-26): `strategy/scripts/mission-strategy.sh` answers *which strategy does this mission belong to* by composing the same walk — no second walker, no relation of its own, no field on any artifact — and the bare `/mission` roadmap names each mission's strategy, rendering an explicit **no strategy** where nothing could be attributed so that *belongs to no direction* and *could not be attributed* never look alike; `exhaustive` is `false` by construction and a strategy whose own read failed is named rather than contributing silence. **And the direction's own lifecycle is readable in one place** (2026-08-26): `strategy/scripts/direction-state.sh` answers `live | arrived | overdue | expiring | dormant | unreadable` per `active` strategy plus the repository-level `none`, by **composing** `survey-strategies.sh` — no date arithmetic, no attribution walk, no second derivation of a reading, and no field on any artifact. **The operator's declared `stage` rides beside this answer and never enters it** (2026-08-29): `survey-strategies.sh` carries it on every row, eligible and refused alike, off `list.sh` (which resolves the absent default through `read.sh`, the one place it lives), and `direction-state.sh` projects it exactly as it projects `target_date` and `landed`. A **sixth `state` value** is refused for the reason `overdue` was kept out of `pace` and `expiring` out of both — one field answering two questions is how the two drift — so `state` stays *what the evidence says* and `stage` stays *what the operator declared*, with the precedence, every gate, the sort and `selected` byte-identical across all three stages (pinned by a hermetic diff over the refused rows as well as the eligible ones). A **degraded** row still carries its stage: the degradation belongs to the attribution walk and the stage is read off the artifact. The precedence is the only thing it owns and it is fixed (`unreadable` > `arrived` > `overdue` > `expiring` > `dormant` > `live`): a reading we could not make is never dressed as one we did, and a direction past its date is the operator's to re-date or close whatever else is true of it. **`arrived` is the fourth reading and it outranks `overdue`** (2026-08-27, mission `say-when-a-direction-has-arrived`): it is projected from the survey's **`quiescent`** — legible, `active`, `mine`, cited, **its work landed** and nothing waiting at either grain, with **no date term at all** — and it is the complement of `dormant` on exactly one term, `landed` empty versus non-empty. Every other reading answers *is this direction in trouble*; none answered *has it arrived*, so a direction whose work was all in looked exactly like one still running, and once its date passed the loop reported that **success** as an hourly `direction-overdue` question. It outranks `overdue` because the two ask a person for different acts — *re-date or close* against *your work is in, is this done?* — and a finished direction is very often a late one, so ranking lateness first would make the reading unreachable for the case it exists to serve. ### Claim protocol

The repository is the coordination medium; the model is stated once in `skills/drive/SKILL.md` (**Claims**) with full detail in `skills/drive/reference/claims.md`. Operational facts:

- **Two of the oracle's words are proofs; every other word is a judgement** (2026-08-27, mission `deliver-and-retire-what-the-loop-already-proved-finished`): a consumer may **act** on a proof and may only **report** or **ask about** a judgement. `superseded` (the unit's content reached the base) and `report_undelivered` (the driving run recorded the transport's refusal into its own branch story) are the only proofs — readings the tree or a merged pull request **established**, which cannot become false by looking again. `stale`, `queue_drained`, `report_incomplete`, `heartbeat_lapsed`, `parked_with_pr`, `claim_active`, `foreign_identity`, `identity_unresolved`, `shallow_history`, `ambiguous_claim` and the merged lookup's `unanswerable` stay judgements, and a judgement is still a person's or a takeover's business; the last three are judgements because each is the **absence** of a reading, and acting on an absence is the failure the three-valued lookup exists to avoid. The classification lives in **one** place — `skills/drive/reference/claims.md`, *Proofs and judgements* — keyed on the word `lib/claims.sh` already emits, with **no field on any artifact, no new script and no classifier function** (a function returning `proof`/`judgement` would be a second derivation of the same fact, which is exactly what the table exists to prevent). It is prose, so `scripts/test-workflow-scripts.mjs` pins it: the suite fails when the table and either of its two consumers — the delivery retry and the retirement writer — disagree about a word, or when a consumer acts on one classified `judgement`. **The base's own checks are a second vocabulary in that same home, and it holds no proof at all** (2026-08-27, mission `read-whether-the-base-survived-what-the-loop-merged`): `green`, `red`, `unattributable` and `unanswerable` are **every one a judgement**, because a check run is designed to be re-runnable and every reading here can therefore become false by looking again — the one property a proof must not have — with `unanswerable` besides that the **absence** of a reading. So no consumer may revert, re-run, block, gate, hold or merge on it: the driving run reports it and `/moderate`'s `base-health` step asks about it, and that is the whole licence. It is a **sub-table beside** the claim tables — one section, two keyed tables, because one column cannot classify two different questions and a second document would be the second home the split exists to prevent — and the same pin covers it, failing when a word either script emits is unclassified, when the sub-table classifies a word neither emits, when any row is called a `proof`, or when either **enumerated** consumer reaches an acting call site.

- **And whether a pull request the loop opened *for a person* was acted on is a fifth vocabulary in that same home, holding no proof either** (2026-08-29, mission `follow-the-pull-requests-the-loop-opens-for-a-person`): `merged`, `closed`, `open:<age>` and `unreadable` are **every one a judgement**, because a pull request is *designed* to change state — anybody can merge, close or reopen it between two reads — which is the one property a proof must not have, with `unreadable` besides that the **absence** of a reading. ### The release tier (`release/*`)

`main` is the continuously auto-merged development branch; **quality is gated at the `release/*` QA window**, not at merge time. A release branch is cut from `main` by `branching/scripts/cut-release-branch.sh` (`release/YYYYMMDD-HHMMSS`, batch-level, explicitly invoked — never a step of the per-unit ship), carries no commits of its own, and is invisible to the claim protocol. **Since 2026-08-13 the window's confirmation is *the* production evidence, not a second one**: `/ship` §5 no longer deploys or confirms pre-merge, so what a unit branch used to prove before landing is proved here, over the batch, or not at all. The durable ship record is `.workaholic/releases/<release-branch>.md`, written by `ship/scripts/record-release-cut.sh` and `confirm-release.sh`, both derived from git. A promotion's confirmation is never skipped; a failed confirmation deletes nothing — the next attempt cuts a fresh release branch. No `develop`, no `hotfix/*`; per-unit mechanics are untouched.

### Design principles

- **Thin commands, comprehensive skills.** Commands are a few lines naming the skill, section, and entry-point contract; knowledge (templates, rules, scripts) lives in skills (~50-150 lines; overflow goes to `reference/`).
- **Common operations go through skills**: git context via `gather/scripts/git-context.sh`, ticket metadata via `gather/scripts/ticket-metadata.sh` — never inline `git branch --show-current` etc. in command/agent markdown.
- **No complex inline shell** in command/subagent markdown (no conditionals, pipes, loops, text processing, defaulting expansions) — extract to a skill script.
- **`${CLAUDE_PLUGIN_ROOT}` for every skill script reference** — relative paths do not resolve at runtime.
- **Plugin boundary**: invoke skills by their loaded `workaholic:` namespace; never read global/marketplace installs on disk to *find* skill content, never guess a namespace (`drivin`, `trippin`, `core`, `standards`, `work` are obsolete). That derivation is what makes an hourly root admissible: `📦 Release Preparation` was retired for restating an unchanged answer ten hours running, and a diff cannot do that by construction. **One gate, and a question is it** (2026-08-22, issue #569): the tick posts when it has at least one question. `idle`, **`no_question`** (changes, but nothing to ask), `no_previous_tick` and `no_log` all post nothing, and `no_log` is named rather than rendered as quiet. It was two gates OR'd until then, and the changed-step half is retired — the root exists to carry questions, so `0 question(s)` made it the status line addressed to nobody that two keyed roots were already retired for (measured four consecutive hours on a consuming repository, every post reading `2 change(s), 0 question(s)`). **The diff is now taken over a stable form**: `inbound-sweep` embeds a timestamp and `doc-drift` a sha in their summaries, so a raw string compare made both "changed" on every tick by construction and the derivation's own claim did not hold; a timestamp, a bare hex object name and a clock time are normalized out of both sides before comparing, and only those. The stated cost: a real change with no question attached is visible only in the tick log. The cost is stated rather than hidden: a person following one item's own thread no longer sees the tick's question there, so every root line links its item. **It works business days as well as business hours** — `WORKAHOLIC_WORK_DAYS` (default `1-5`) holds the weekend, because a question posted at 10:00 on a Sunday reached nobody and the asked-once gate then guaranteed it was never posted again on a day somebody was reading; held is not dropped, so it waits for Monday. **The asking step is exempt from `--deadline-seconds`**: the deadline cuts steps in order and this one is last, so a slow tick used to read nine things and say nothing — the one step whose absence nobody can see was the first to go. The two status roots it used to emit, `🔧 Needs a decision` and the merged-in `📦 Release Preparation`, stay **retired** and the 2026-08-21 root does not reverse that: a status line addressed to nobody is noise whatever its dedup key (measured on `#dev-workaholic`, 2026-08-19: ten `📦` lines in ten consecutive hours for one unchanged request, none answered), whereas this root exists to carry the questions beneath it and cannot restate an unchanged answer. A finding it cannot turn into a question with a name on it stays in the tick log, and where it is work, becomes a ticket. `step-strategy-proposals.sh` — gated since it shipped and never once emitting anything — was **deleted** in the same change. A degraded read is reported **by name**, never as a step that ran and found nothing; a step not reached inside `--deadline-seconds` is reported as unreached. `run.sh` invokes every step and every step contributes a report line. **The already-asked gate is mechanical again** (ticket `20260819062058`): it matched the raw key against the log's free-text *summary*, which no writer was ever required to produce, so the same key was re-asked an hour later with the question still unanswered; it now matches the step id derived from the key, and that id carries a digest of the whole key because the 32-character slug it used was not injective. **And which announced items may still be called in flight is readable in one place** (2026-08-28, mission `reconcile-a-stale-thread-with-the-unit-s-real-state`): `moderate/scripts/reconcile-candidates.sh` is a **pure read** naming the recently merged or closed `work-*` pull requests the loop itself opened, each resolved to its feedback stems through `drive/scripts/unit-feedback-stems.sh` — still the one translation — with the pull request's coordinates and, for a merge, **by whom and when**. The candidate set is **repository-derived, never a channel scan**: `workaholic:notify` bounds every thread lookup at two exact-string searches with no full-channel read at any point, so a channel scan would break that bound outright and make the reader's cost grow with the channel rather than with the work. It resolves a branch's artifacts from three **local** sources — the branch's own merge commit diff, the branch-keyed ticket archive, and the story's `mission:` relation — so a `/specificate` proposal resolves through the refs its mission carries by the carry floor. A pull request **closed without merging** is the one case no local path can answer — no merge commit, no story on the base, nothing archived — so **only** for a candidate the tree could not resolve it asks for that pull request's own changed files, one call bounded like every other per-pull read, without which `⚫ Closed` would be a shape nothing could reach. It **decides nothing about staleness**, which needs the thread and therefore the session's connector; both bounds are configurable and both are reported (`truncated`/`beyond_bound`, and `list_capped` when the page bound rather than the repository ended the read); a candidate resolving to no stem is named `stems_unresolvable` and **never keyed on `unit:<id>` here**, because an item with no feedback record has no thread to reconcile; and an unreadable read is `ok: false` with its reason and **exit 0**, carrying no candidate list at all rather than an empty one. |

## Enforcement gates

- **Commit trailers** (`skills/commit/SKILL.md`, *The trailer block*): `commit.sh` is the one writer and callers stay trailer-agnostic — `Category:` when `--category` was passed, `Claude-Session: https://claude.ai/code/<id>` whenever the process environment carries `CLAUDE_CODE_REMOTE_SESSION_ID` (every cloud/routine-fired run), and `Co-Authored-By:` always. **The trailer says which *run*, never which *routine*** (2026-08-14, issue #453, measured in a live `[Implement]` container): nothing in the container's environment names the standing routine record, so a `Routine:` value could only be fed by a caller — and an env var does not survive between a session's separate shell invocations while a `--routine` flag would have to be remembered at every seam. The session id is in every invocation's environment, so one writer stamps it and `archive.sh`/`claim.sh`/the scratch-index heartbeat all inherit it; outside a cloud session it is omitted, never faked. The **author email is deliberately untouched** — `drive/scripts/lib/claims.sh` resolves claim ownership and resumption from it. **The author *name* moved on 2026-08-18** (issue #506, the second half of the same report): the web bootstrap's `user.name` line was guarded by `[ -z "$(git config user.name)" ]`, the **effective** scope, which in a container is the global `Claude` and never empty — so the line never once executed and GitHub, which renders the name rather than the email, showed every routine commit as authored by Claude. The guard now reads `git config --local user.name`, on the same seam and under the same conditions as the email, and the value prefers the account's real name (`gh api user --jq .name`) over the login. A developer's own repo-local name is still never overwritten, every failure path logs and continues, and the repair is **forward-only**: history already on `main` keeps `Claude`, and a session already running keeps the name it started with. The name stays cosmetic to every mechanism — ownership, claims and resumption all read `user.email`, which is what makes moving it safe.
- **A commit that would be half a rename is refused** (2026-08-23): with default staging, a **staged deletion co-existing with an untracked file** is what half a convergent migration looks like — additions written untracked, originals deleted — and `git add -u` takes only the deletions. `commit.sh` **warned** and the commit went through, because a warning's enforcement is a human reading it and an unattended run has no such human; measured, 50 concern records lost their content on `main` and a story body was dropped while its index entry merged. It now refuses, names both halves and the concrete repair, commits nothing, and leaves the working tree untouched — no `git reset`, which would discard whatever the caller had staged before calling. Untracked files alone never trigger it (they are routine; a refusal keyed on them would be disabled within a day) and it never fires when the caller already named `files...`. The refusal was chosen over unstaging the deletion half inside `migrate-concerns.sh`: that is one migration's fix every future migration must remember, and it edges against that script's measured *never touch the caller's index* contract. The procedural half rides beside it — **a caller that has just written a NEW file passes it in `files...`**, stated once in `workaholic:commit` and referenced by `/story` Phase 4 and `/drive` §5, the one seam of the eight that relied on default staging for a file it had just created.
- **Commit subject** (present-tense, ≤50 chars, no `feat:`/`[bracket]` prefix — `skills/commit/SKILL.md`): canonical validator `skills/commit/scripts/check-subject.sh`, run by `commit.sh` itself, by `drive/scripts/archive.sh` **before it moves the ticket** (so a refused subject leaves the tree byte-identical rather than half-archived), by the `PreToolUse` hook `guard-git-commit.sh`, and by the opt-in git-native `hooks/git/commit-msg` (install with `sh ${CLAUDE_PLUGIN_ROOT}/hooks/install-git-hooks.sh`; bypass one commit with `--no-verify`). One rule source; the layers cannot drift.
- **An embedded jq program that does not compile is our defect, never an empty answer** (2026-08-29, mission `make-a-direction-s-lifecycle-a-declared-stage`; `rules/shell.md`): these scripts carry their readings as jq programs inside single-quoted shell strings under `… | jq -c '…' 2>/dev/null || echo '[]'`, and that fallback is **right for a data problem and catastrophic for our own** — a program that does not *compile* discards identically, so the caller reads an empty answer and reports success. Measured while shipping the mission's own work: `step-direction-health.sh` reported `"status": "ok"`, `1 expiring … 1 to ask` with the expiring direction's own question **silently gone**, from one missing parenthesis; `sh -n` passes (the shell parses fine — it is the embedded jq that does not), so the `every shipped shell script parses` row added in the same mission provably cannot see it. The two cases are told apart by **jq's own exit status** — 3 is a compile error, 5 a runtime or input error — so nothing new is invented and every existing fallback keeps its data behaviour byte-for-byte. **Two halves, and the build-time one matters more.** At **run** time, `skills/moderate/scripts/lib/jq-guard.sh` — a shadowing `jq` function sourced by every script in that skill that embeds a program, calling `command jq`, capturing nothing, redirecting nothing, and **inert** when nothing is listening — *records* the fact, and `run.sh` is the **one** place that reads the record and reclassifies the step `degraded` with reason `jq_compile_error`, beside the `step_missing` / `step_error` / `no_output` / `bad_output` it already owns; a step consulting the record for itself would be a second derivation of the same fact. A shadowing function rather than 58 edited call sites, because **the defect is the shape, not the file** — the repair reaches every present and future call site at one `.` line per script — and `needs_agent` is deliberately **not** zeroed like `bad_output` does, since a step's other readings may have compiled fine and dropping a question a person is owed trades one silence for another. The `2>/dev/null` is **not** removed: the stderr of a legitimately degraded read is noise on an hourly unattended run, and the fix is to classify, not to shout. At **build** time, `node scripts/test-workflow-scripts.mjs`'s `every embedded jq program compiles` row finds every `jq` in **command position** across `plugins/workaholic/`, `scripts/` and `hooks/`, tokenizes its arguments as the shell would, redeclares each `--arg`/`--argjson` name (an undefined `$name` is itself a compile error), and compiles the program with `jq -n` against closed stdin — **491 programs on the tree that shipped it**, failing on exit 3 alone. **Its limits are named rather than skipped silently**: a program built by string interpolation cannot be extracted without evaluating the shell, so those are counted and the count rides the assertion's own name — visible on every run, never a number to keep current — and a `-f`/`--from-file` invocation has no inline program and is not a gap. Scripts **outside** `workaholic:moderate` are covered by the build-time row alone, deliberately: they report no step status for anything to reclassify.
- **Branch names**: exactly two literal patterns — `work-YYYYMMDD-HHMMSS` (named only by `branching/scripts/create.sh`) and `release/YYYYMMDD-HHMMSS` (named only by `cut-release-branch.sh`); `guard-git-branch.sh` blocks everything else.
- **One behaviour per command**: no command's behaviour depends on the first word of its argument (bare-versus-argument is a scope and is kept; `/fb`'s cross-repository mode routes on destination, not a first word). Retired forks: `/mission close` → `/mission-close`; `/mission summary|approve`, `/ticket summary` dropped; `/drive auto|night` → `/implement`.
- **AskUserQuestion**: label hook enforces the `[<label>]` prefix; *whether* to ask is governed by `rules/interaction.md` — the **Recommended-label test**: if an option could honestly be marked "(Recommended)", don't ask; decide, record, let the developer veto.
- **Repository confinement**: every write lands inside this repository or its worktrees; the only crossing is `/fb`'s issue-opening mode with its verbatim human confirmation. Do not grow the confinement hook toward content matching — vocabulary is a human judgment. The rule only reaches repos that install the plugin; enable it user-level (`~/.claude/settings.json`).
- **GitHub over REST only** (`rules/shell.md`): every workflow script reaches GitHub through the one transport `gather/scripts/gh-rest.sh` (`slug` / `api` / `available` — the last **probes `GET /rate_limit`**, which every token type can call including a workflow's installation token, since 2026-08-29; it probed `GET /user` until then, measuring identity and calling it reachability, so every script guarded by it refused `gh_unavailable` in CI whatever its own permissions were — measured on `claim-retirement.yml`, which holds `contents: write` and had deleted nothing since it shipped. A caller needing a **person** calls `gh api user` itself and answers `identity_unresolved`; `available`'s `login` is vestigial, always empty, kept only so the shape does not move) — never `gh issue …`, `gh pr …` or `gh repo …`, which are GraphQL-backed and which a Claude Code Web session may 403 mid-run (measured 2026-08-12, a `[Specificate]` tick that pushed its branch and then could not open the PR). A bound session is narrower still: `search/*` is refused too, so slug matching uses repository-scoped endpoints and filters locally. `gh release …` is REST-backed and stays. **One qualification, ruled 2026-08-23**: a REST merge answered `403 "Merging pull requests is not permitted for this session type"` gets its own `merge_reason: session_type_cannot_merge` (its own rung beside 405 and 409, keyed on the message with a generic `merge_forbidden` behind it, because 403 alone is also a missing permission), and **that one refusal may be retried through `mcp__github__merge_pull_request`** — a second attempt behind REST, never a replacement, for the one act a script cannot perform at all. Reads, writes and pull-request creation stay REST. The cost is stated: a script cannot call an MCP tool, so this moves one step into the calling agent, against this repository's own no-inline-shell grain; it is accepted narrowly — one tool, one named precondition, one act — and the script reports the refusal rather than pretending. Measured: the connector's read tools work in a **routine-fired** container (an `[Implement]` tick, 2026-08-23 07:33 UTC); a merge through it is measured only in an interactive session, which is why the shape reports both outcomes by name rather than assuming. The alternative — keep the rule absolute and let such proposals stay open — was recorded rather than dismissed, and lost because the honest reason had nobody to reach: the unit was finished, green, and waiting on a human who was never told. `node scripts/test-workflow-scripts.mjs` fails on any non-comment `gh issue|pr|repo <verb>` under `skills/` or `hooks/`; its allowlist is empty on purpose.

## Release-safety scan

`skills/release-scan/scan-branch-safety.sh` is a deterministic, script-only gate over `git diff <base>..HEAD`, run by `/story` (warn) and `/ship` (block). Three rule families, each finding citing `file:line` + rule:

- **`secret`** (hard, never overridable) — `lib/secret-patterns.sh`: pass 1 unmistakable key shapes; pass 2 matches on the **value** (quoted-alphanumeric or line-ending bare run = literal; identifiers, calls, env reads, HCL `var.`/`local.`/`data.`/`module.` references, templates, annotations are subtracted). Generated paths are exempt from pass 2 (the `Outputs Freshness` CI carries the residual risk).
- **`size`** (overridable) — per-file/branch ceilings plus a per-commit changed-lines rule (`lib/commit-size.sh` — read its header before changing it; it exempts binary rows, lockfiles, generated paths, `.workaholic/` prose, files already over the per-file ceiling, and merge commits, and counts additions only).
- **`leak`** (confirm) — re-introduction of terms from the git-ignored, developer-maintained `.workaholic/leak-denylist`. Read its scope literally: it matches listed terms in the branch diff, nothing more; a `pass` never means "no client context here". The "never name other repos/clients" convention is enforced by confinement + the crossing flow's human confirmation, not by this scan.

## Version Management

Version bumps are manual (no `/release` command). After bumping and pushing to `main`, CI (`.github/workflows/release.yml`) publishes the GitHub Release.

Version files (all at the same semver; `.claude-plugin/marketplace.json` is the source of truth):

1. `.claude-plugin/marketplace.json` — root `version` AND every `plugins[].version` (workaholic, workflows)
2. `plugins/workaholic/.claude-plugin/plugin.json`
3. `plugins/workaholic/.codex-plugin/plugin.json`
4. `outputs/workflows/.codex-plugin/plugin.json` — generated; rebuild with `build.mjs`, never hand-edit

Bump PATCH by default, update 1-3, regenerate 4, commit as `Bump version to v{new_version}`.
