# Workaholic

Private, cross-agent distribution of structured development workflows and engineering standards. **AI agents are the primary users** — routines invoking `/implement` and `/specificate`, and sessions running the workflow skills — while the **developer is the operator** who approves pull requests, configures routines, and rules on deferred decisions. Richest on **Claude Code** (plugin marketplace: commands, hooks, always-on lenses); portable skills also ship to **Codex** (`.agents/plugins/marketplace.json` → `outputs/workflows`) and to 40+ agents via the Agent Skills standard / `skills` CLI. Authored source lives under `plugins/`; cross-agent artifacts are generated into `outputs/`.

This file states **current behavior only**. Decision history and rationale live in `docs/loop-engineering-workflow.md`, `docs/proposal-loop-runbook.md`, `docs/drive-loop-runbook.md`, each skill's `reference/` directory, the feedback stream (`.workaholic/feedbacks/`), and this file's own git history.

## Important

- Edit `plugins/`, not `.claude/` — this repo develops plugins; changes go to `plugins/` unless explicitly requested otherwise.
- **Update the docs in the same change.** When a change alters behavior, structure, commands, skills, or conventions, update every affected document (`README.md`, `.workaholic/README.md`, `CLAUDE.md`, `plugins/workaholic/rules/*.md`) in the same commit. Outdated documentation is a defect; `/story` runs `doc-drift.sh` and `area-freshness.sh` only as backstops.

### Hooks (all shipped active in hooks.json)

- `validate-ticket.sh` (PostToolUse Write|Edit) — ticket floor on the `todo/` queue only: frontmatter, location, mandatory `## Policies`/`## Quality Gate`, resolvable `mission:` relation.
- `validate-mission.sh` (PostToolUse) — Experience/≥1-acceptance floor on any mission under `missions/active/`; archive never retro-blocked.
- `validate-story.sh` / `validate-trip.sh` / `validate-feedback.sh` / `validate-strategy.sh` (PostToolUse) — OKF `type:` and schema floors on new writes; git-tracked history is grandfathered. `validate-strategy.sh` holds the revived strategy artifact to the three properties that distinguish it from the one retired in 2026-07-28: a `YYYY-MM-DD` `target_date`, a **non-empty** `assignees` (the one artifact where empty is a refusal, not team-owned), and non-empty `## Aim` / `## Schedule`.
- `guard-ticket-structure.sh` (PreToolUse Bash) — blocks non-canonical ticket moves.
- `guard-git-commit.sh` / `guard-git-branch.sh` (PreToolUse Bash) — commit-subject and branch-name gates (see below).
- `guard-askuserquestion-label.sh` (PreToolUse AskUserQuestion) — every question body must open with a `[<project label>]` prefix (`gather/scripts/project-label.sh`).
- `guard-working-directory.sh` (PreToolUse Bash) — denies a top-level cwd-moving `cd`; a `( cd … )` subshell, an absolute path, or a `--prefix` form always passes. No env-var toggle. **A leading `cd` that lands on a repository root passes** (2026-08-23) — the main checkout's root or a worktree's, resolved through `git rev-parse --show-toplevel`: that command restores the ground rule rather than breaking it, and refusing it was refusing the only repair. Measured: a session whose cwd had been moved into a worktree could not return, so every later command needed hand-wrapping and the scripts that read the cwd operated on the wrong tree — `branching/scripts/create.sh` switched a **claim** worktree off its claim branch. Only the leading form and only a root; a chained mid-command `cd` stays denied whatever its target, a target carrying shell syntax the hook cannot resolve without evaluating it is denied rather than guessed, and bare `cd` (to `$HOME`) is now denied too — it had matched nothing at all.
- `guard-repo-confinement.sh` (PreToolUse Write|Edit) — blocks writes outside this repository and its worktrees (the agent's per-project memory store is exempt). Syntactic backstop only; the primary rule lives in `rules/general.md`.
- `policy-lens.sh` (UserPromptSubmit) — injects the engineering-policy index for commands carrying the `workaholic:policy-lens` sentinel; bodies are read on demand from `skills/<pillar>/policies/`. Regenerate `hooks/policy-index.md` with `build.mjs` after editing a pillar's `## Policies` list (CI rebuilds and fails on drift).
- `mission-lens.sh` (UserPromptSubmit + Stop, non-forcing) — surfaces the active missions that pass ownership/location/signal gates, full block on roster change and a one-liner otherwise. Reads through `mission/scripts/progress.sh` / `next-acceptance.sh` and `gather/scripts/owners.sh`.
- `layout-doctor.sh [path]` — read-only audit of `.workaholic/` against the layout allowlist.

## Architecture Policy

### Component Nesting Rules

| Caller                         | Can invoke                                   | Cannot invoke              |
| ------------------------------ | -------------------------------------------- | -------------------------- |
| Command                        | Skill, `general-purpose` subagent            | —                          |
| Skill                          | Skill; (when loaded by a command/main agent) may direct it to spawn `general-purpose` subagents | Command                    |
| `general-purpose` subagent     | Skill (via preload)                          | Command, Task (no nesting) |

- **No per-workflow agent files.** The repo ships no agent `.md` files at all. A command spawns `subagent_type: "general-purpose"` subagents whose prompts name the `workaholic` skill to preload, the section, the inputs, and the return schema.
- **One-level fan-out.** A subagent cannot nest `Task` and cannot call `AskUserQuestion`; all fan-out and all user interaction happen at the command/main-agent level. Leaves do non-interactive work and return JSON.
- **One plugin.** `workaholic` has `dependencies: []`. All skill references are same-plugin (`${CLAUDE_PLUGIN_ROOT}/skills/<name>/...`, `workaholic:<name>` namespaces). The `workflows` marketplace entry is the generated `outputs/workflows` bundle, not an authored plugin.

### The ticket spine

Everything converges on the **ticket** as the unit of work: *sources* fill `tickets/todo/`, one executor drains it to `tickets/archive/`.

- **Sources**: `/ticket` (human-directed, with discovery) and `/mission`'s Creation Interrogation (which emits a mission's whole ordered ticket set). `/specificate` feeds them from the feedback stream. All publish through a **publish tree** onto a `work-*` branch behind a pull request; the artifact reaches `main` — and the executor's survey — when that PR merges.
- **Mission floor and ceiling**: a mission is created with **two or more tickets** or it is not a mission (checked at the publish seam by `mission/scripts/check-floor.sh`; a ticketless direction is a feedback record, a one-ticket one is a plain ticket). The ceiling: `## Acceptance` normatively ≤3 items, whole `mission.md` ~60 lines / 2 KB — measured by `mission/scripts/size.sh`, enforced on `/specificate`'s unattended drafts. Write-time floor: `## Experience` + ≥1 acceptance item.
- **One executor, two commands**: `/drive` (attended — asks exactly one thing: which units to take when several are offered) and `/implement` (unattended — no prompt at any step). Same Unified Run either way: freshen (`sync-main.sh`) → survey (`plan-units.sh`) → partition into PR-units → claim → drive → report → route by effective merge policy → account. The full contract lives in `skills/drive/SKILL.md` and its `reference/`.
- **Merge policy** (`merge_policy: auto | review`, recorded at creation on missions and tickets; **absent means review**): `auto` ships through `/ship` — which drafts the plan and merges, never deploys — then tears the claim down; `review` merges its PR immediately after `/story` opens it — a `hard` (`secret`) or `confirm` (`leak`) scan finding is what leaves it open. **No gate is ever overridden** by either entry point: a `secret` finding hard-stops; a `size`/`leak` block or a missing confirmation method demotes an `auto` unit to the PR path.

**The `review` route reads the severity tier, never the binary verdict** (2026-08-21). It read `verdict == "pass"` until then, which held a merge open on the one tier `workaholic:release-scan` itself calls *a granularity nudge, not a hard block* — the same skill that has always said *the severity tells the consumer how hard to block, and both consumers key on it, never on the binary verdict alone*, and that *a branch whose only findings are `override`-tier stays releasable*. `/story` obeyed it; this route did not. **Measured** on a documentation repository consuming this plugin: a `review` unit of 42 documentation pages in two languages produced three `too-large-commit` findings (749 / 983 / 1119 added lines against a 500 ceiling) and nothing else — no mixed concerns, no secret, no leak; the line count *was* the shape of the work. The unit sat at an open pull request and the run reporting it went on to **ask a human whether to merge**, which `/implement` may never do — one cause, both symptoms. `gate-decision.sh` now computes **`override_only`** beside `overridable`, so the tier policy stays in one script rather than being re-counted by each of its three consumers, and the route merges on `pass` **or** `override_only`. An `override_only` merge still reports every finding, in the run report and in the pull-request body `/story` writes: the nudge is delivered where it is useful and nowhere that it stops the loop. `secret` still hard-stops, `leak` still holds the pull request open, and the `auto` route's demotion table is untouched — there the override is a real human ruling recorded in deployment evidence.
- **An Open Decision is a question to answer, not a ruling that the question is unanswerable** (2026-08-23): before a driving run may honour a written `## Open Decisions` item as a blocker it **reads the sources the item names**, plus the whole of any page it cites, and a `blocked` outcome reached that way **names those sources and what they said** — a block that cannot name a source it read is not a block (`drive/reference/ticket-workflow.md` §1, `reference/failure-contract.md`, the run report contract in `drive/SKILL.md`). The item had been **self-certifying**: `/specificate` declared a fork unresolvable and the driving run took the declaration as evidence rather than as a claim to check, which the failure contract's own words permitted because a session can name an authority without ever having looked. Measured: a tick honoured an item whose answer sat fifty lines further down the very page the ticket named; on a consuming repository the same shape ran eleven consecutive ticks for zero lines of implementation while the operator's own answer sat unread in the same tree. It is a **prose contract, not a script gate** — no mechanical check tells a real read from a claimed one; what it buys is that a blocked report naming no source is visibly non-conformant. This is the driver-side half of the 2026-08-23 `/specificate` fix above, which stopped the *writing* of unclearable gates. **The writing side gained the matching floor in the same change**: an `## Open Decisions` item now has three required parts — the question, **the sources consulted and what they said**, and the fork's sides — may name whose ruling would settle it, and may **not** declare the question unanswerable or instruct a later session not to decide (`create-ticket/reference/ticket-format.md`; `/specificate`'s discovery must have covered the item's own subject, and the **whole** of any page it cites, before the item may be written — the measured failure was a partial read of one table). A genuinely unrecommendable fork is still recordable: what is removed is the self-certification, not the section. `/ticket` is untouched — it resolves the same kind of fork by asking a human directly, so it never writes one.
- **The verification axis is read before merge policy** (2026-08-14, issue #452): a mission or ticket may declare `verification_handoff: <what cannot run here>` **at creation** — a credential, device or third-party account an unattended run does not have. `drive/scripts/verification-handoff.sh` reads it, any member declaring it carries the whole unit, and that unit takes the **`handoff`** route whatever `merge_policy` says: the PR opens and stays open, the non-droppable `## Handoff` quotes the reason, the claim stays standing, the finish line is `🟡 Handoff` and the token is `pending`. Written by `/ticket` and by `/specificate` (`scaffold-proposed-ticket.sh --verification-handoff`) **only when the ask itself states it**; a run never declares it for its own unit, which is what keeps `handoff` from becoming a soft landing. **One second writer since 2026-08-23** (issue #83): `/specificate` also declares it for an **unresolved operator-only fork** that survived the operator-record check — the axis is the same (what cannot be settled here) and the rule's intent is untouched, because the declarer is the *writer* ruling at creation about a unit it will not drive, never a driver excusing its own work. Such a fork must **never** be written as a `## Quality Gate` item instead: `/implement` may neither ask nor override, so a gate item is re-claimed and re-failed every tick forever, while a standing handoff claim is not re-surveyed and costs nothing per tick. Measured: nine consecutive resumes over nine hours, 1.6 recorded agent-hours, zero lines of implementation.
- Retired predecessors (`/monitor`, `/trip`, `/carry`) and their landed ideas: `docs/loop-engineering-workflow.md` I1/I3/I5. `.workaholic/trips/` is read-only legacy history.

### `.workaholic/` runtime conventions

- **OKF floor**: every knowledge artifact carries a non-empty `type:` (`Story`, `Mission`, `Feedback`, `Strategy`, `Deployment`, `Term`, `Release Note`, `Release`); `okf/scripts/refresh-index.sh` regenerates the bundle indexes before each knowledge commit. **Two exceptions, both deliberate**: `tickets/` (no `type:`, internals never index-managed) and, since 2026-08-17 (issue #471), `moderations/` — the `/moderate` tick log, one file per UTC day, one `## <tick-id>` section per tick, one line per step. It is an operational log, not knowledge: 24 entries a day would rewrite the bundle indexes hourly, so entries carry no frontmatter, the area has no `index.md`, and the root index links the directory bare. `moderate/scripts/log-append.sh` is the only writer (append-only, idempotent per (tick, step), **never prunes** — deleting a day file is the operator's act) and `log-read.sh` the reader a step consults before re-filing what an earlier tick already filed. The tick **commits its own log to the base as its closing act** (`persist-log.sh`, after the ninth step) — a routine's container is discarded, so a log left in the checkout would blind every dedup and leave an hourly unattended process with no audit trail. The seam is the **publish tree directly**: the caller's checkout stays byte-identical, no branch is created, concurrent ticks **union by `(tick, step)`** so two containers on the same day both land — whole sections the base lacks, and, inside a section it already has, the entries it lacks, with a `(tick, step)` already on the base never rewritten — and a persist that missed the base is reported `degraded` by name with the log left in the checkout for the next tick. **It runs twice** (2026-08-18, PR #489): the agent acts on `needs_agent` only *after* `run.sh` returns, so it persists again once it has recorded what it filed, and without that second run — and without the line-wise half of the union, which is what makes it carry anything — every `<step>-filed` line died with the container and the dedups those lines feed read an empty memory forever. It is not the unattended-`main`-writer class `workaholic:ship` §7 refused — the append is not self-referential, touches no claimed branch, and merges nothing (`rules/workaholic.md`). **It carries the tick's feedback records too** (2026-08-23): `create.sh` stages a record and stops, so a finding the sweep or the triage wrote died with the container while the tick reported it filed. `persist-log.sh --record <path>` puts them on the same commit — named one by one, **never a sweep of whatever is staged**, and a record already on the base is left untouched because a feedback record is immutable, so concurrent ticks both land and nothing is rewritten; each is reported `carried` / `already_on_base` / `missing` / `unreadable`. **And a `<step>-filed` line no longer proves a filing**: `filed-records.sh` reads the paths the line names and asks the tree, so an `unlanded` record is treated as **not filed** and the next tick re-derives the finding — measured, the persist reported both records filed while the base carried the log section and not one record, and the next tick skipped both on the strength of those lines. `readable: false` is named rather than rendered as an empty set. `README.md` and `index.md` are the only files allowed at the `.workaholic/` root.
- **Mission rolling**: commit seams (archive, ship, report) append `## Changelog` lines and tick `## Acceptance` items via the mission skill's idempotent mutators (`append-changelog.sh` / `tick-acceptance.sh`). Progress (`checked ÷ total`) is computed, never stored. Acceptance items become tickable through their `(#<filename>)` link, stamped only by the emitting seam via `link-acceptance.sh`. The `mission:` relation is many-valued; read it only through `read-relation.sh`.
- **Strategy** (`.workaholic/strategies/<slug>.md`, revived 2026-08-13 — issue #436): the operator's **outbound, resolved direction** — an **Aim**, a **Schedule** (`target_date`), an **Assignee** (non-empty `assignees`). Flat, one file, operator-authored through `workaholic:strategy`; no command, hook or routine puts one on `main` on its own and `/drive` never surveys it. **Which work belongs to a strategy is answered by one reader and adds no field** (2026-08-17, issue #473): `strategy/scripts/attributed-work.sh` walks the citation that already exists — `strategy.feedback[] ∩ artifact.feedback[]` (`direct`), plus the hop through a mission attributed that way (`via_mission:<slug>`, load-bearing because `/specificate` puts the refs on the mission and its tickets carry `mission:`) — reading each relation through that relation's existing single reader. The `strategy:` relation and its ownership hop stay retired, which is exactly what choosing a no-new-field rule preserves; the attribution is **transitive and lossy**, so every consumer reports what it could not attribute instead of implying the answer is exhaustive, and a quiet strategy returns a named empty reason (`no_feedback_refs` / `no_citing_artifacts` / `no_activity_in_window`) rather than an error or a guess. `/standup` is its first consumer and reads it, like everything else, without writing. **One drafting exemption** (2026-08-14): `/specificate`'s strategy form may draft one into a proposal PR, and a strategy-touching PR alone among proposals **does not auto-merge** — the operator's merge is the authorship, restoring the approval premise auto-merge removed on 2026-08-11. The same exemption covers a `close.sh` reached by an *ended* lifecycle announcement. There are exactly **two** writers and no third: `create.sh` creates, `close.sh` ends, and nothing edits a live strategy's Aim, Schedule or Assignee — an announced *change* is captured in the feedback record and applied by the operator. It carries **no ticket plan** — planning executable work stays a mission's job. It is the complement of the feedback stream, not a rival inbox: `feedbacks/` holds what someone *said* (inbound, immutable), a strategy holds what the operator *decided*, and the citation link runs **one way** (strategy → feedback). The 2026-07-28 retirement (B3) stands as history and its reasoning is answered rather than dismissed — the retired artifact was open-ended `## Direction` prose with no completion condition, the revived one is bounded, owned and closable. The `strategy:` mission relation and its ownership hop did **not** return. `mission/scripts/migrate-strategies.sh` and the `missions_migrate_strategies` seam that erased `strategies/` on every mission-script touch are **retired**; do not re-add them. Full record: `skills/mission/SKILL.md`, *The strategy layer: retired, then redefined*.
- **Ticket state is a field, the archive is a place** (2026-08-13, issue #436): `tickets/` is **two-state** — `todo/` and `archive/<branch>/`, nothing else. A ticket's state is its `status:` frontmatter field: **absent means queued**, `done` (stamped by `archive.sh` at the gate), `abandoned`, `icebox`. `icebox` survives as a state distinct from `abandoned` — deferred and promotable versus decided against — and `promote-icebox.sh` **clears** the field when it returns a ticket to the queue. A ticket that was never driven lands in the synthetic `archive/unbranched/` (the archive is keyed by the branch that drove a ticket; inventing one would assert a drive that never happened). The retired `icebox/` and `abandoned/` directories are still read by every reader and accepted by the write floor while `gather/scripts/migrate-ticket-states.sh` converges them at the write seams; `layout-doctor.sh` reports a survivor as `retired-ticket-state`.
- **Ownership**: plural `assignees` on every artifact; **empty means team-owned/claimable**. One oracle resolves it — `gather/scripts/owners.sh`, with `owns.sh` returning `mine`/`unowned`/`other`/`unresolved` (compared by slug). Claim authorship and resumption key on `git config user.email` separately. **A third, ticket-only tolerance tier** (2026-08-14, issue #454): a queued ticket still at `tickets/todo/<user-slug>/<file>.md` with neither field resolves to `<user-slug>` — the directory that *was* the ownership record. Without it the directory read as its absence, so `owns.sh` answered `unowned` and every runner was offered every colleague's legacy queue (measured overnight 2026-08-13→14: ~10 PR-units driven and merged out of other people's queues). It is a tolerance written to be deleted with the layout: only that path shape, only when both field tiers are silent, only tickets — a ticket directly in `todo/` still answers `unowned`, and `author:` stays out of ownership.
- **Mission lifecycle**: `status: active | achieved | abandoned | carried` — one in-flight state; `active/` vs `archive/` areas; `mission/scripts/close.sh` is the **only** writer of an end state. Merging the mission's PR is the approval; drivability is derived (active area + plan + queued tickets), never a status word. **The run closes the one outcome that is arithmetic** (2026-08-23): `archive.sh` calls `close.sh <slug> achieved` when archiving a ticket leaves the mission's acceptance fully checked (`progress.sh`: `checked == total`, `unlinked == 0`) and its queue empty (`queue-size.sh`: `todo == 0`) — every part from an existing reader, no second parser of the many-valued `mission:` relation. **Never `abandoned`, never `carried`**: those assert *intent*, and a run that just merged its own work is a poor judge of which applies. The measured objection is answered rather than dropped — of four missions closed by hand on 2026-08-04 one turned out not to be achieved at all, and this proof would have refused it, because it asks whether the acceptance is complete rather than whether the work was good. The single-writer rule does not move: the run calls `close.sh`, never a status. An unreadable reader is not a proof and leaves the mission alone; the close and any refusal are reported by name in the archive output and the run report, so a mission that could not be closed never reads as one that was. A mission finished by a path that archives no ticket is not caught here and is **reported** instead, by `/moderate`'s `closable-missions` step (step 12): it composes three **pure** readers — `summary.sh` for the active set, `progress.sh` for `unlinked`, `queue-size.sh` (the number `plan-units.sh` itself reads) for the queue — and names each entry's `checked/total`, and it **never closes one** — two writers of an end state is what the single-writer rule exists to prevent. Measured: eleven finished-and-open missions had accumulated with nobody told, found only because the mission lens printed all of them on every prompt. `plan-units.sh` was the obvious composition and is **refused**: its `queue_drained` exclusion is exactly this candidate set, but the survey runs the living migrations and **stages** what they change — measured by the step's own test, which caught the report leaving a modified mission in the index. A step whose contract is *writes nothing* may not reach it through something that writes.
- **Feedback subject** (2026-08-13, issue #436): every new record names **whose opinion it is** — `subject: <kind>[:<identity>]`, kind from the closed set `person | meeting | observer_ai | customer | team | other`, identity free text. Three axes that look alike and answer different questions: **subject** = who formed the opinion, **source** = the channel it arrived through, **author** = the git identity that ran the capture. `create.sh` takes it as the `--subject` **option** (the positional contract did not move) and **refuses** (`no_subject`) rather than default it — a routine writes most of the stream, so a default would record every opinion as the machine's. `/specificate` supplies the triggering issue's author; `ship`'s extractor supplies `observer_ai:<author>`; `validate-feedback.sh` floors new writes and grandfathers everything written before the axis.
- **The red-alert cool-down expires at the next working day** (2026-08-23): a failure signature is suppressed at channel level until the **earlier** of 24 hours after the first report and the start of the next working day — the first hour inside `WORKAHOLIC_WORK_DAYS` at the end of `WORKAHOLIC_QUIET_HOURS`, in `WORKAHOLIC_QUIET_TZ`, all three the check-in gate's own, composed rather than re-derived. Measuring only from the first report meant a failure beginning in the evening posted nothing at channel level for the whole of the next working day: measured 2026-08-22→23, a unit blocked at 21:38 JST produced eleven consecutive `blocked` ticks and 2.1 agent-hours whose every escalation was a `↳ still failing` reply inside the previous day's thread, and the developer found the stall by noticing the channel had not moved in ten hours. A root re-posted at expiry names **how long** it has been failing; a signature first reported during the working day is unaffected; the `↳ still failing` reply, the first-report rule and the unreadable-history rule are unchanged (`workaholic:notify`).
- **Deferred concerns** live in the feedback stream: the story's Concerns section is the durable record (PR body drops `low` blocks at render); `ship`'s `extract-deferred-concerns.sh` persists each as a `kind: concern` record keyed on `concern_id`; the open set is computed — a concern is open until a later record names it in `supersedes`.
- **The two hand-maintained areas** (`deployments/`, `terms/`): the ones that survived the 2026-08-13 reshape, each now carrying a **definition** (what it holds, what it never holds, who writes it, when it is refreshed — `rules/workaholic.md`) and an **upkeep seam**. The seam is `story/scripts/area-freshness.sh`, read by `/story` beside `doc-drift.sh`: it **reports, it never writes** — a deployment record describes a procedure a human authored, so a machine rewriting it from a run would record what happened rather than what should happen, and a glossary a machine maintained would define the words it already uses. Two mechanical facts per record: `retired_terms` (it still names a de-listed area or a retired namespace — wrong, not merely old) and `stale_days` (reported, thresholded by nobody, because the right interval differs per project). `/ship` stays the only live *reader* of a deployment record and gates on its `## Confirmation`. Records carry `type: Deployment` / `type: Term`; `terms/inconsistencies.md` is a term entry like any other with no special status.
- **Retired areas** (2026-08-13, issue #436): `.workaholic/policies/`, `guides/` and `specs/` are gone — the three areas with **no writer in the loop**. An area nothing writes goes stale and then lies: all 17 substantive files in them still described the retired three-plugin architecture and had not been touched since 2026-05-14. Reference documentation lives in the repository's own `docs/` tree, **outside** `.workaholic/`; the `"docs" → specs/` request mapping now points there. Content was deleted, not relocated — git history is the durable record and nothing in them was still true. A consuming repository whose plugin updates before its tree is told by name: `layout-doctor.sh` classifies those three as `retired-area`, and the content decision stays the owner's.
- **A rename is a row, not a sweep** (2026-08-20): `skills/gather/scripts/renames.tsv` declares every rename this plugin has made, read only through `list-renames.sh`. Two kinds and no third. An **`area`** row (a `.workaholic/` top-level directory) is **applied** — `migrate-renamed-areas.sh` `git mv`s it and fixes the generated root index, and `layout-doctor.sh` classifies a survivor `renamed-area` **before** consulting the allowlist, so a repository is told what the name became rather than that its directory is unrecognised. A **`name`** row (a token: a command name, a skill namespace, a path fragment) is **proposed, never applied** — `rename-conversions.sh` counts the survivors outside `.workaholic/` and prints the bulk conversion for the operator to run or decline. The line is the one `retired-area` already draws, on the other axis: a machine-owned path has exactly one correct destination; a name lives in prose a human wrote, in code comments, and in a consuming repository's own vocabulary, where a renamed token is routinely also an ordinary English word. The registry never uses a live token as its own example — a real rename's conversion sweeps the files documenting it. **A retirement is not a rename** and stays out of the table — `guides/`/`policies/`/`specs/` were deleted and have no destination, and a row with an empty `new` would give one kind two behaviours, so those three keep their own classification. The table is a **migration record, not history**: a row is deleted once the fleet has cut over (as `renamed_from:` leaves a routine template), and an empty `rename_conversions` for a row is the signal that it has. `WORKAHOLIC_RENAMES_TABLE` points the whole chain at another table — a data source, never a gate opt-out.
- **Closed layout**: the permitted top-level `.workaholic/` directories are fixed in **two lockstep sources** — `hooks/workaholic-layout-allowlist.txt` and the table in `plugins/workaholic/rules/workaholic.md`. A new artifact directory must be registered in both **in the same commit** that first writes to it; `layout-doctor.sh` audits, and the `Validate Plugins` CI workflow fails the merge on `conforming: false`.

### Claim protocol

The repository is the coordination medium; the model is stated once in `skills/drive/SKILL.md` (**Claims**) with full detail in `skills/drive/reference/claims.md`. Operational facts:

- A runner claims a PR-unit (mission slug or `batch-<ts>`) as a `Claim <unit-id>` commit on a pushed `work-*` branch; **unmerged remote branches are the only claim oracle** (`list-claims.sh`). One unit ↔ one branch ↔ one worktree (`.worktrees/<unit-id>/`) ↔ one PR.
- A merge releases a claim by definition. `release-claim.sh` explicitly discards an unfinished unit (never a recovery path). `claim.sh resume` takes over **your own** claim whose heartbeat lapsed; a colleague's is untouchable at any age. Staleness is reported, never acted on.
- The heartbeat is the branch tip (`heartbeat.sh`, empty commit built against a scratch index). `archive.sh` pushes the claim branch itself after each archive commit.
- Worktrees are **claim-born and ship-torn** (`cleanup-mission-worktree.sh` is the sanctioned cleaner; `survey-worktrees.sh` / `reap-worktrees.sh` back the teardowns up). `.worktrees/` and `.publish/` sit inside the repo root — add them to `.dockerignore` and any archiver's ignore list.
- The claim is the only creator of a branch a runner may drive. Artifact writers use the **publish tree** instead: a checkout of `origin/main` at git-ignored `.publish/` on local branch `publish-main` (`open-publish-tree.sh` → write → `publish-tree-pr.sh` (default, PR path) or `publish-tree-commit.sh` (direct, post-merge seams only) → `close-publish-tree.sh`). The caller's checkout is left byte-identical.
- The reader degrades offline; the writer fails loudly. Under `/implement`, each unit posts **one finish line per unit, never one per feedback stem** (2026-08-22) into the thread the stateless lookup found (`unit-feedback-stems.sh` + `workaholic:notify`); when several stems match, the first-sorting stem's thread wins, and when none does the run posts the **description root** and replies the finish line into it — the same root `/specificate` has posted since 2026-08-14, extended here because the shipped alternative opened with a status emoji and a pull request number and ended in a bare machine key. The per-stem rule announced an event as many times as the corpus held records of it, and a strategy's carried-forward `feedback:` refs — which `/specificate` puts on every mission it emits, because `attributed-work.sh` has no other link back to the direction — made that **deterministic** for every unit the loop produced on its own. It posts on the transport that skill selects — **connector primary, the tokened `notify-slack.sh` the machine fallback** (keyed root only, it cannot thread); an attended `/drive` run posts nothing to Slack.

### The release tier (`release/*`)

`main` is the continuously auto-merged development branch; **quality is gated at the `release/*` QA window**, not at merge time. A release branch is cut from `main` by `branching/scripts/cut-release-branch.sh` (`release/YYYYMMDD-HHMMSS`, batch-level, explicitly invoked — never a step of the per-unit ship), carries no commits of its own, and is invisible to the claim protocol. **Since 2026-08-13 the window's confirmation is *the* production evidence, not a second one**: `/ship` §5 no longer deploys or confirms pre-merge, so what a unit branch used to prove before landing is proved here, over the batch, or not at all. The durable ship record is `.workaholic/releases/<release-branch>.md`, written by `ship/scripts/record-release-cut.sh` and `confirm-release.sh`, both derived from git. A promotion's confirmation is never skipped; a failed confirmation deletes nothing — the next attempt cuts a fresh release branch. No `develop`, no `hotfix/*`; per-unit mechanics are untouched.

### Design principles

- **Thin commands, comprehensive skills.** Commands are a few lines naming the skill, section, and entry-point contract; knowledge (templates, rules, scripts) lives in skills (~50-150 lines; overflow goes to `reference/`).
- **Common operations go through skills**: git context via `gather/scripts/git-context.sh`, ticket metadata via `gather/scripts/ticket-metadata.sh` — never inline `git branch --show-current` etc. in command/agent markdown.
- **No complex inline shell** in command/subagent markdown (no conditionals, pipes, loops, text processing, defaulting expansions) — extract to a skill script.
- **`${CLAUDE_PLUGIN_ROOT}` for every skill script reference** — relative paths do not resolve at runtime.
- **Plugin boundary**: invoke skills by their loaded `workaholic:` namespace; never read global/marketplace installs on disk to *find* skill content, never guess a namespace (`drivin`, `trippin`, `core`, `standards`, `work` are obsolete). The one sanctioned crossing is `check-deps/scripts/plugin-src.sh`, which resolves the newest plugin tree on the machine (checkout, registry install path, clone, binding) so an unattended run whose binding is missing or superseded still executes the workflow instead of stopping — the harness binding is an input, never a precondition (`rules/general.md`; measured 2026-08-12, twelve `[Implement]` ticks lost to a project-scope pin the bootstrap never updated). It resolves on **two axes: newest version wins, and an equal version goes to the immutable candidate** — a version-addressed cache path cannot move under a run, whereas the checkout the freshen is about to touch can (measured 2026-08-12, a container's stale baked `main` reverted a resolved checkout 200 commits mid-run). Callers read `src_immutable` and either require it or re-resolve after a tree-moving step. If a skill is missing from context in an *attended* session, ask which plugins are loaded.

### Cross-agent exposure and generated outputs

- Script-bearing skills carry `metadata.internal: true` (hides them from the `skills` CLI; Claude Code ignores the field). Pure-prose skills (`design`/`implementation`/`operation`, `write-release-note`, `review-sections`) are intentionally exposed. Script-bearing skills keep `${CLAUDE_PLUGIN_ROOT}` and reach non-Claude agents only through the generated bundle.
- `outputs/workflows/` is the self-contained public bundle: `${CLAUDE_PLUGIN_ROOT}` rewritten relative, internal/preload metadata stripped (`publicizeSkillMd`), `reference/` directories carried with their paths rewritten. **Regenerate with argument-less `node scripts/build-plugins/build.mjs` whenever a workflow skill or its script closure changes.** `outputs/` is committed; the `Outputs Freshness` CI workflow rebuilds and fails on any diff.
- The `workflows` marketplace entry keeps **`"strict": false`** (the bundle deliberately has no `.claude-plugin/plugin.json`; do not add one). Codex reads `.agents/plugins/marketplace.json`; `hooks/hooks.json` must keep `hooks` as its only top-level key.
- `outputs/okf/` is the OKF v0.1 policy bundle generated by `okf.mjs`; consumers read it from the repo path, no manifest involved. Adoption record: `docs/dependencies/okf.md`.

It is admitted on exactly the terms the third one was — the **repository scope** keeps the per-developer setup burden at two, and the routine **reads and never writes** (`workaholic:standup`), so it adds no unattended-write class to a tree whose conflicts are resolved append-only. What it does add is a **second routine for the one designated account to create**, which `render-setup-sheet.sh` now states as a count in the repository sheet's own header rather than leaving the second to be discovered by scrolling. Its silence rule is stricter than an hourly tick's because a *daily* post is a standing claim on attention: no active strategy, or nothing moved with no `target_date` inside the horizon, posts nothing at all.

**"Do not reintroduce a third routine" is superseded, and its reasoning is answered rather than dropped** (2026-08-14, issue #451). It was written on 2026-08-06 when `[Consent]` retired, and restated on 2026-08-13 when the deployment-plan refresh was placed on `[Implement]`'s tick: a third routine "costs every consuming repository a setup step". That cost was real and is what the **repository scope** removes — one account configures `[Prepare Release]`, not every member, so the per-developer setup burden is unchanged at two. What the scope does **not** answer is the second objection from the same 2026-08-13 decision — that an hourly agent rewriting a document on `main` is a new class of unattended write for a tree whose conflicts are resolved append-only — so `[Prepare Release]` does not make that write: **it reads and reports, it never writes** (`workaholic:ship` §7). `[Consent]`'s retirement stands untouched: a human-merged pull request is still announced by nobody.

**The deployment-plan refresh still rides `[Implement]`'s tick** (2026-08-13, resolving the Open Decision ticket `20260813123903-keep-the-deploy-plan-draft-current-periodically` carried). Every `auto` unit `[Implement]` ships reaches `/ship`'s drafting phase, which refreshes that unit's plan inside the unit's own pull request; nothing commits to `main` outside a merge, the refresh is idempotent (`draft-deploy-plan.sh` → `changed: false`), and a degraded read is reported and skipped, never half-written. The stated limit stands: a repository whose units are all `review` sees that per-unit plan refreshed only when an `auto` unit ships.

**The per-target release notes are kept current by CI, not by any tick** (2026-08-14 → 2026-08-17 → corrected 2026-08-18). The 2026-08-17 heading read *"ARE now kept current by `[Prepare Release]`'s tick"*, and it was **never true in practice**: a routine's container cannot write a release by any transport — `gh release` is refused as GraphQL, and REST answers *"Creating, editing, or deleting releases is not permitted for this session type"* — so the write failed on every tick from the day it shipped. The **home** the 2026-08-17 decision chose (a GitHub draft release, outside git) stands and was right; only the **writer** moved, to the `Release Note Draft` workflow (`.github/workflows/release-note-draft.yml`), which holds `contents: write` in a repository whose releases CI already publishes. `run-note-cadence.sh` now requires `--write`, passed by that workflow and by nothing else, so the tick makes no `gh` call at all and `/prepare-release` is the pure reader its own contract always claimed. CI also defines its checkout (`fetch-depth: 0` + tags) rather than inheriting a container's refs — measured 2026-08-18, a container with **no tags** and a five-day-stale `origin/main` collapsed the boundary to `full_history` and reported 9, then 191, against a true 8. **The reading half was stated as an open limit here and closed the same day** (issue #503, reproduced at 2721 → 2950 → 4 on this repository): `report-deploy-status.sh` — the one entry the tick reaches — freshens the base branch and tags itself before reading them, bounded and never fatal, and reports `refs`/`refs_reason`/`doubtful` when it could not. The two fixes stay separate on purpose: CI **defines** its checkout because it can, a container cannot be defined from inside itself, so the tick **freshens and reports**. `read-deploy-state.sh` gained no network I/O and is still the pure local read its header claims. The rest of the 2026-08-17 record stands, restated for what is now true — the 2026-08-14 line "the release notes are **not** updated by any tick" turns out to have described the shipped behaviour all along, and it is kept as an accurate statement about *ticks* rather than reinstated as a refusal, because the notes **are** kept current, by CI. What the 2026-08-17 decision got right, and what survives it, is the **home**. Its own words follow. The "the release notes are **not** updated by any tick" is retired rather than quietly dropped — it was true, it is not any more, and leaving it would be a documentation defect by this file's own rule. What changed is not the refusal but the **home**. `workaholic:ship` §7's three writer designs were each measured; the first — refreshing a merged note on `main` is self-referential, because for a target declaring no `paths:` (0 of 1 here) the refresh's own commit increments the `unreleased_count` it reports — is answered by putting the draft where it is **not a commit**: a per-target **GitHub draft release**, invisible to consumers and free to rewrite. A draft that never enters git cannot count itself, so the arithmetic goes to zero instead of being compensated for. Rows 2 and 3 stand untouched: no open pull request's branch is written, and `/ship` is never run on a tick. Neither store is the source of truth — **the derivation is** (`draft-release-note.sh` over the base state), so the GitHub copy and the `.workaholic` copy are projections of one renderer and identical by construction; `sync-release-note.sh` writes the non-authoritative side as a projection, never a merge, reports every divergence per target and section before writing, and never overwrites a *published* release. `.workaholic/release-notes/` is still written only at ship and release time, never by a tick — that is what remains deliberately undelivered.

**The renderer derives the facts; an agent's plan arranges them** (2026-08-18, issue #512). `draft-release-note.sh` gained a `--plan <path|->` seam: with a plan it renders that plan's grouping, order, risk notes and held-back set **over** the facts it derives; with none its output is byte-identical to the pre-seam render, which is what the seam had to prove. The header's idempotency sentence is superseded in place — *the same base state **plus the same plan** renders byte-identical output* — because determinism was never the defect and a diff-free re-render is a property the ask never asked to lose. A plan is one JSON document (`plugins/workaholic/skills/ship/reference/release-plan.md`) that may never invent a change, drop a merge, or move a derived fact: an unnamed merge renders under *Not arranged by the plan*, a reference outside the range is named rather than fabricated, and a plan whose `base_sha` is not the rendered base is shown as **stale**, never silently refreshed. Its home is the caller's — no well-known path, never inside git (§7's measured self-counting refusal), never trusted for freshness. A plan that cannot be applied is not applied: the derived list renders and the reason rides the JSON. **A target's note carries the whole release life** (2026-08-18, issue #512's fourth gap). The draft renders `## Deployment Plan` → `## Releases` → `## Deployment Verification`: the plan it already derived, the windows under `.workaholic/releases/` (cut and confirmation), and the per-target attempts appended to `.workaholic/release-notes/<slug>.md`. It is a **derivation, not a copy** (`ship/scripts/read-release-history.sh`), so no third store is created and append-only survives untouched — the projection never writes, and `record-evidence.sh` / `confirm-release.sh` remain the single writers of what they own. Two blurs are refused by name: a release window is **repository-wide**, so a batch confirmation never reads as "this target was checked", and `fail` / `not_run` / `bypassed` render exactly as loudly as `pass`. An empty stage says so in words rather than by an absent section.

**The judgment runs in CI, beside the writer** (2026-08-18, issue #512 — the Open Decision on ticket `20260818202056-run-the-release-planning-judgment-and-reach-ci`). The `Release Note Draft` workflow already holds `contents: write` and a defined checkout, so `plan-release.sh` authors each due target's plan there and hands it to the same run's cadence (`--plan-dir`): the judgment and the write happen in one place and nothing crosses between them, which answers `workaholic:ship` §7's three refusals by name — nothing is committed to `main`, no open pull request's branch is written, `/ship` never runs. The two alternatives are refused in §7 with their reasons: planning on the `[Prepare Release]` tick and **committing** the plan is the hourly-`main`-writer class refused twice (and contradicts the command's write-nothing contract), and a per-unit plan is not continuous and has nowhere to live but a commit. **The cost is a credential and it is paid visibly**: the planner command is pluggable (`WORKAHOLIC_PLANNER_CMD`, default `claude -p`), the workflow's planner steps are skipped when `ANTHROPIC_API_KEY` is unset, every non-arrival is named (`no_planner` / `planner_failed` / `invalid_plan` / `empty_range` / `no_renderer`), and **the note says on its face** when a plan was expected and did not apply — so a broken planner is never mistaken for a deliberate list. It refreshes exactly when the cadence would write (at most once per `Asia/Tokyo` day, plus on a stage advance), and the workflow asks what is due before it spends anything, so an idle base spends no agent budget. `/prepare-release` is untouched: still no `gh` call, still writing nothing, anywhere. Provable on demand with no key and no network — `sh scripts/e2e/loop-drill.sh verify-planner`.

**A story-less merge keeps its substance** (2026-08-18, issue #512). `## Key Changes` prefers a branch story, falls back to the merge body's pull request title, and now adds what that merge **published** as sub-bullets on the same row (`ship/scripts/resolve-merge-substance.sh`): the feedback record (`Asked for: …`, labelled that way because a record states what somebody asked for, not what the merge did), the mission it planned, the tickets it queued. It matters because the fallback is the **majority** path — measured over `v1.0.170..main`, 38 of 68 merges (56%) carry no story, since a `/specificate` pull request auto-merges without ever running `/story`. Nothing is dropped, reordered or capped; a merge that published no artifact renders exactly as before; a story-bearing merge is never asked. Local git plus base-tree reads only, so `--enrich` stays off by default and the same base state renders the same detail, and neither the `feedback:` nor the `mission:` relation gains a second parser — the script discovers paths from the merge's diff and reads a `title:` field.

**One routine, one job, and it stays hourly.** This read *"One routine, both jobs"* until 2026-08-18; the generation was never a job the tick could do, and it now rides CI instead of a routine. The reasons that ruled out the alternatives are unchanged and still rule them out — folding it into `[Implement]` by the 2026-08-14 scope reasoning (issue #451 — N developers would each run a repository-scoped generator), and a second repository-scoped routine because it gains only a cron field while costing every consuming repository a second setup step. A workflow is neither, and costs a consuming repository no setup step at all. The tick reports hourly as before; only the **generation** is bounded — at most once per **`Asia/Tokyo`** day (a floor derived from the draft release's own `updatedAt`, never a stored cursor), plus immediately whenever the release stage advances (`draft` / `staging` / `confirmed`, derived from git and `.workaholic/releases/`). An idle tick writes nothing and posts nothing. The routine's `allowed_tools` still carries **no `Write`/`Edit`**, unchanged by this: the draft lives outside git, so the tick still needs no ability to write a file, and the 2026-08-13 objection that an hourly agent rewriting a document on `main` is a new class of unattended write never comes due. All three are verifiable on demand — `sh scripts/e2e/loop-drill.sh verify-plan`, `verify-status` and `verify-cadence` — rather than by waiting for a tick, and `verify-standup` proves the same three properties for the daily digest.

## Enforcement gates

- **Commit trailers** (`skills/commit/SKILL.md`, *The trailer block*): `commit.sh` is the one writer and callers stay trailer-agnostic — `Category:` when `--category` was passed, `Claude-Session: https://claude.ai/code/<id>` whenever the process environment carries `CLAUDE_CODE_REMOTE_SESSION_ID` (every cloud/routine-fired run), and `Co-Authored-By:` always. **The trailer says which *run*, never which *routine*** (2026-08-14, issue #453, measured in a live `[Implement]` container): nothing in the container's environment names the standing routine record, so a `Routine:` value could only be fed by a caller — and an env var does not survive between a session's separate shell invocations while a `--routine` flag would have to be remembered at every seam. The session id is in every invocation's environment, so one writer stamps it and `archive.sh`/`claim.sh`/the scratch-index heartbeat all inherit it; outside a cloud session it is omitted, never faked. The **author email is deliberately untouched** — `drive/scripts/lib/claims.sh` resolves claim ownership and resumption from it. **The author *name* moved on 2026-08-18** (issue #506, the second half of the same report): the web bootstrap's `user.name` line was guarded by `[ -z "$(git config user.name)" ]`, the **effective** scope, which in a container is the global `Claude` and never empty — so the line never once executed and GitHub, which renders the name rather than the email, showed every routine commit as authored by Claude. The guard now reads `git config --local user.name`, on the same seam and under the same conditions as the email, and the value prefers the account's real name (`gh api user --jq .name`) over the login. A developer's own repo-local name is still never overwritten, every failure path logs and continues, and the repair is **forward-only**: history already on `main` keeps `Claude`, and a session already running keeps the name it started with. The name stays cosmetic to every mechanism — ownership, claims and resumption all read `user.email`, which is what makes moving it safe.
- **A commit that would be half a rename is refused** (2026-08-23): with default staging, a **staged deletion co-existing with an untracked file** is what half a convergent migration looks like — additions written untracked, originals deleted — and `git add -u` takes only the deletions. `commit.sh` **warned** and the commit went through, because a warning's enforcement is a human reading it and an unattended run has no such human; measured, 50 concern records lost their content on `main` and a story body was dropped while its index entry merged. It now refuses, names both halves and the concrete repair, commits nothing, and leaves the working tree untouched — no `git reset`, which would discard whatever the caller had staged before calling. Untracked files alone never trigger it (they are routine; a refusal keyed on them would be disabled within a day) and it never fires when the caller already named `files...`. The refusal was chosen over unstaging the deletion half inside `migrate-concerns.sh`: that is one migration's fix every future migration must remember, and it edges against that script's measured *never touch the caller's index* contract. The procedural half rides beside it — **a caller that has just written a NEW file passes it in `files...`**, stated once in `workaholic:commit` and referenced by `/story` Phase 4 and `/drive` §5, the one seam of the eight that relied on default staging for a file it had just created.
- **Commit subject** (present-tense, ≤50 chars, no `feat:`/`[bracket]` prefix — `skills/commit/SKILL.md`): canonical validator `skills/commit/scripts/check-subject.sh`, run by `commit.sh` itself, by `drive/scripts/archive.sh` **before it moves the ticket** (so a refused subject leaves the tree byte-identical rather than half-archived), by the `PreToolUse` hook `guard-git-commit.sh`, and by the opt-in git-native `hooks/git/commit-msg` (install with `sh ${CLAUDE_PLUGIN_ROOT}/hooks/install-git-hooks.sh`; bypass one commit with `--no-verify`). One rule source; the layers cannot drift.
- **Branch names**: exactly two literal patterns — `work-YYYYMMDD-HHMMSS` (named only by `branching/scripts/create.sh`) and `release/YYYYMMDD-HHMMSS` (named only by `cut-release-branch.sh`); `guard-git-branch.sh` blocks everything else.
- **One behaviour per command**: no command's behaviour depends on the first word of its argument (bare-versus-argument is a scope and is kept; `/fb`'s cross-repository mode routes on destination, not a first word). Retired forks: `/mission close` → `/mission-close`; `/mission summary|approve`, `/ticket summary` dropped; `/drive auto|night` → `/implement`.
- **AskUserQuestion**: label hook enforces the `[<label>]` prefix; *whether* to ask is governed by `rules/interaction.md` — the **Recommended-label test**: if an option could honestly be marked "(Recommended)", don't ask; decide, record, let the developer veto.
- **Repository confinement**: every write lands inside this repository or its worktrees; the only crossing is `/fb`'s issue-opening mode with its verbatim human confirmation. Do not grow the confinement hook toward content matching — vocabulary is a human judgment. The rule only reaches repos that install the plugin; enable it user-level (`~/.claude/settings.json`).
- **GitHub over REST only** (`rules/shell.md`): every workflow script reaches GitHub through the one transport `gather/scripts/gh-rest.sh` (`slug` / `api` / `available`) — never `gh issue …`, `gh pr …` or `gh repo …`, which are GraphQL-backed and which a Claude Code Web session may 403 mid-run (measured 2026-08-12, a `[Specificate]` tick that pushed its branch and then could not open the PR). A bound session is narrower still: `search/*` is refused too, so slug matching uses repository-scoped endpoints and filters locally. `gh release …` is REST-backed and stays. **One qualification, ruled 2026-08-23**: a REST merge answered `403 "Merging pull requests is not permitted for this session type"` gets its own `merge_reason: session_type_cannot_merge` (its own rung beside 405 and 409, keyed on the message with a generic `merge_forbidden` behind it, because 403 alone is also a missing permission), and **that one refusal may be retried through `mcp__github__merge_pull_request`** — a second attempt behind REST, never a replacement, for the one act a script cannot perform at all. Reads, writes and pull-request creation stay REST. The cost is stated: a script cannot call an MCP tool, so this moves one step into the calling agent, against this repository's own no-inline-shell grain; it is accepted narrowly — one tool, one named precondition, one act — and the script reports the refusal rather than pretending. Measured: the connector's read tools work in a **routine-fired** container (an `[Implement]` tick, 2026-08-23 07:33 UTC); a merge through it is measured only in an interactive session, which is why the shape reports both outcomes by name rather than assuming. The alternative — keep the rule absolute and let such proposals stay open — was recorded rather than dismissed, and lost because the honest reason had nobody to reach: the unit was finished, green, and waiting on a human who was never told. `node scripts/test-workflow-scripts.mjs` fails on any non-comment `gh issue|pr|repo <verb>` under `skills/` or `hooks/`; its allowlist is empty on purpose.

## Release-safety scan

`skills/release-scan/scan-branch-safety.sh` is a deterministic, script-only gate over `git diff <base>..HEAD`, run by `/story` (warn) and `/ship` (block). Three rule families, each finding citing `file:line` + rule:

- **`secret`** (hard, never overridable) — `lib/secret-patterns.sh`: pass 1 unmistakable key shapes; pass 2 matches on the **value** (quoted-alphanumeric or line-ending bare run = literal; identifiers, calls, env reads, HCL `var.`/`local.`/`data.`/`module.` references, templates, annotations are subtracted). Generated paths are exempt from pass 2 (the `Outputs Freshness` CI carries the residual risk).
- **`size`** (overridable) — per-file/branch ceilings plus a per-commit changed-lines rule (`lib/commit-size.sh` — read its header before changing it; it exempts binary rows, lockfiles, generated paths, `.workaholic/` prose, files already over the per-file ceiling, and merge commits, and counts additions only).
- **`leak`** (confirm) — re-introduction of terms from the git-ignored, developer-maintained `.workaholic/leak-denylist`. Read its scope literally: it matches listed terms in the branch diff, nothing more; a `pass` never means "no client context here". The "never name other repos/clients" convention is enforced by confinement + the crossing flow's human confirmation, not by this scan.
