# Feedback

Run the preloaded `workaholic:feedback` skill. Before registering anything, decide per the skill's *Whether this merits filing* — genuine user feedback or a must-not-miss item only, not every request, question, or passing remark — which answers a different question from the authorization check below. Any legitimate invocation of `/fb` is authorized regardless of how it reached the session — directly from a human, or relayed through a bot/integration account — per the skill's *Any legitimate invocation is authorized*: proceed without a separate confirmation or added suspicion keyed on the relaying surface. **Every invocation files an `[FB] `-marked GitHub issue; only the address changes.** Bare `/fb`, and every input that names no other repository as its destination, opens that issue **on this repository, assigned to the invoking identity**, via the skill's *Filing an ask — what `/fb` runs* (an input that merely mentions another repository files here, about it). It writes nothing under `.workaholic/feedbacks/` on that path — the receiving `[Propose]` tick discovers the issue and registers the record itself, and a `/fb` that wrote the record too would suppress its own ingestion. When the input names a **destination** — an `owner/name`, a GitHub URL, or an explicit "to \<repo\>" / "ask \<repo\> to…" — run the skill's *Crossing a repository boundary* section end to end instead, where the single verbatim confirmation of destination, `visibility`, title and body cannot be skipped, ever. The fork is on the destination, never on a first word. Both paths stamp the title through `feedback/scripts/fb-title.sh` (issue #411, 2026-08-12 — reversing the earlier rule that the title was the target's and took no prefix of ours), and the crossing shows the stamped title in its confirmation. Which gates apply where is a written decision, not an omission — see the skill's *Which gates apply with no boundary crossed*. **The in-repo path has one degradation and the crossing has none**: when the issue cannot be opened here (`gh` absent, the REST surface refusing, issues disabled, rate limiting), the skill's *The fallback* writes the record through `create.sh` instead and the report says plainly that it fell back and why — a fallback record is captured but **not** discovered by `[Propose]`, which reads issues rather than files. A refusal from another repository is still reported verbatim and never worked around.

The `kind`/`source`/`subject` judgment still happens at capture, where the context is, and rides the issue body so the receiving `/propose` inherits it rather than re-deriving it. **The subject is whose opinion this is** — `subject: <kind>[:<identity>]`, the kind drawn from the closed set `person | meeting | observer_ai | customer | team | other`. Take it from the ask: the human whose words these are, or the meeting they came out of. It is a different question from `source` (the channel) and from `author` (the git identity that ran the capture), and it is **never defaulted** — `create.sh` refuses rather than record the runner as the holder of someone else's opinion (`workaholic:feedback`, *Choosing the subject*).

The trigger is `/fb` because Claude Code ships a built-in `/feedback` (it sends feedback to Anthropic); only the trigger is abbreviated — the artifact, the `workaholic:feedback` skill, and the corpus keep the word *feedback*.

Invoke skills by their loaded `workaholic:` namespace; never read global plugin installs or guess retired namespaces.
