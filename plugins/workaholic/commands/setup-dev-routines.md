# Setup Dev Routines

Run the preloaded `workaholic:workaholify` skill's §5 **Scheduled routines** flow, as its *What the commands do with all this* section states, over the **`developer`-scoped templates only** (`list-routine-templates.sh developer`). Those are the routines every member of the team needs their own copy of, and this is the command a developer joining the repository runs. **This command's job is to configure them** — one job with a failure mode, not two branches to choose between. Resolve the repository (`resolve-repo-url.sh "$ARGUMENT"` — `$ARGUMENT` is an optional repository name or URL, absent means this checkout), then **attempt the configuration**: find the transport that can reach an account routine (a `RemoteTrigger`-family tool — never the session-only, in-memory `CronCreate`/`CronList`/`CronDelete`), list the account's routines, diff each against its template over the **converged field set** `workaholic:workaholify` §5 step 2 states (stated there and nowhere else, so four command bodies cannot drift apart on it), apply create/update to converge, and report exactly what changed per routine — **each line naming that routine's enabled state**, which convergence reports and never writes, so a routine switched off is never reported as a healthy one. Configuring is what happened, not what happened to be possible — never report it as luck.

**A RECLAIMED name needs the opposite instruction, and `[Propose]` is one** (2026-08-21, issue #555). `[Propose] {repo_name}` was the maintenance tick's rendered name until 2026-08-19 and was vacated in that change; this scope's `propose` template now takes it. Convergence matches by rendered name, so an account still holding a **pre-cutover** `[Propose] <repo>` — a `repository`-scoped record firing `/moderate` at `:50` — would have it silently converged into this developer-scoped `/propose` at `:40`. Where a `renamed_from:` template says *rename your old routine, do not create a second*, a reclaimed name says **delete any routine still rendering it before converging**. State it once, by name, and state that the plugin can neither detect nor remove another account's routine. The fleet cut over on 2026-08-19, so this is expected to apply to nobody; it is said because convergence cannot tell the two records apart if it does.

**A template declaring `renamed_from:` is converged, not handed to a human — when this session has the transport.** Convergence matches an account's routines **by name**, so a renamed template cannot find the routine that should become it on the name alone; `renamed_from:` is the input that supplies the link. With a `RemoteTrigger`-family tool, match the live record by the old name and write the new one through `update`: it **renames in place** — same routine id, same `created_at`, no second record and nothing for the developer to delete (measured 2026-09-01 against a live routine; the account held 15 before and 15 after, and no routine remained under the old name). Report the rename by name, with both names. **The ordering survives automation**: `[Specificate]`'s old name is the name the repository-scoped maintenance tick now takes, and an in-place rename is one `update` per routine, so the old `[Moderate]` must be renamed **before** `/setup-repo-routines` converges the new one — between the two calls the account otherwise holds one rendered name twice and convergence cannot tell the records apart. **Only under `no_transport`** does the rename become the operator's own step, stated once by name and riding the rendered setup sheet as that refusal's recovery path.

**When no transport is reachable, the attempt fails and says so**: report `no_transport: RemoteTrigger-family tool` (naming what was looked for), then render the copy-paste setup sheets for this scope (`render-setup-sheet.sh --all <repo-url> developer`, prompts verbatim) **as the recovery path for that refusal**, with the two preconditions (`check-slack-channel.sh <repo-name>`, `check-bootstrap.sh`) and a plain statement of what cannot be verified from here. A sheet is a repair the developer performs by hand; it is never the ordinary outcome of this command.

**It never touches a `repository`-scoped routine.** The scope filter is the whole difference between this command and `/setup-repo-routines`, and it is read from each template's own `scope:` field, never from a list written into a command body. A repository routine converged by every team member would exist N times and fire N times an hour.

Either way it asks no `AskUserQuestion` — converging to the developer's own already-declared template needs no decision to ask about (`rules/interaction.md`'s *Recommended-label test*); a mutation the tool itself refuses is reported as a refusal, never asked and never silently downgraded to the sheet.

Invoke skills by their loaded `workaholic:` namespace; never read global plugin installs or guess retired namespaces.
