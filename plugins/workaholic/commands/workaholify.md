# Workaholify

Run the preloaded `workaholic:workaholify` gateway skill end to end, in its own order. **This is the preparation command, not an audit: it leaves the repository prepared.** Refer to the gateway as the doorway to the pillar `policies/` and the working-directory ground rules (§1–§2), **apply the `CLAUDE.md` gateway reference** (§3, `audit-claude-md.sh` then `apply-claude-md-reference.sh` — a reference to the gateway, never a copy of the rules), **converge the `.workaholic/` layout** (§3a, `converge-layout.sh` — applies the mechanical migrations, including every `area` row of the rename registry, reports every judgment it will not make (`decisions`) and every rename conversion it proposes but will not apply (`rename_conversions`, with its ready-to-run command per row), stages and never commits), **apply the web bootstrap** (§4, `check-bootstrap.sh` then `apply-bootstrap.sh`) **before** the routines, **apply the remote's branch hygiene** (§4a, `check-repo-settings.sh` then `apply-repo-settings.sh` — `delete_branch_on_merge`, the one GitHub setting the claim oracle reads; the accumulated merged-but-undeleted branches are reported with their deletion command, never deleted here), **converge the account's routines** (§5 — *Configuring the routines is the job* run over **every** scope, `list-routine-templates.sh` unfiltered: find the `RemoteTrigger`-family transport, list the account's routines, diff each against its rendered template, apply create/update, and report per routine what was created, what fields moved, and what already matched), probe the channel (`check-slack-channel.sh <repo-name>`), and confirm the working-directory guard is registered (§2). Report what was checked, what was applied, and what still needs fixing.

**The environment is resolved before any routine is created, and `no_environment` renders nothing.** Enumerate the account's environments; **exactly one** is used without asking, **more than one** is asked about once, and **none reachable or none at all** reports `no_environment` by name with what was enumerated. Unlike `no_transport` it has **no sheet fallback**: a session that reached the account and could not resolve an environment is not helped by paste-by-hand instructions (`workaholic:workaholify` §5, *Which environment a routine is created in*).

**Rendering a setup sheet is a refusal's recovery path, never the outcome.** Only when no transport can reach an account routine: report `no_transport: RemoteTrigger-family tool` by name, then `render-setup-sheet.sh --all <repo-url>`. A run that renders sheets while carrying the tool is the defect this contract fixes (measured 2026-08-19 on a second repository: five sheets rendered and "whether any of them currently exist" reported as unanswerable, in a session holding `RemoteTrigger` throughout). Two things stay unanswerable **and must be said**: whether a teammate already created the `repository`-scoped routines — no account can list another's, so running this where a colleague already wired the repository is how a duplicate is made — and, for a repository the account has never put a routine on, that it is invisible to the enumeration.

The three applies each take **one** confirmation before writing — state the findings and exactly what will change, then ask once, with the body prefixed by the project label (`bash ${CLAUDE_PLUGIN_ROOT}/skills/gather/scripts/project-label.sh`). They are the only questions this command asks. A decline, or a refusal the script names (`unwritable`, `settings_unparseable`, `hook_source_missing`, `not_admin`, `unanswerable:<reason>`), falls back to reporting what is missing — **named as that refusal, never as the ordinary outcome**.

Invoke skills by their loaded `workaholic:` namespace; never read global plugin installs or guess retired namespaces.
