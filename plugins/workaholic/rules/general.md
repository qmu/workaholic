# General Rules

- **Never modify another repository** - Every write, edit, move, and commit lands inside the current repository or one of its own worktrees (`git worktree list`). Never write into a sibling checkout, never `cd` to another project and work there, never target a path outside `git rev-parse --show-toplevel`. To raise work against a different repository, use `/fb <the ask> to <owner/name>` - it opens the ask as a GitHub **issue** on the target, writing into no checkout of it at all. That is the only sanctioned way, and it exists so that this rule never has to be broken. (`/request`, which wrote a ticket file into the target's tree, was retired 2026-08-05.)
- **Never carry one repository's context into another's artifacts** - When work here is motivated by something observed elsewhere, describe it generically: "a consumer repo", "a tree that has drifted". Do not name the other repository, quote its paths, list its components, reproduce its filenames, or copy its data - and do not ground an example in a real customer's file, label, hostname, or infrastructure name. This holds for tickets, stories, commit messages, PR bodies, code comments, and test fixtures alike; a fixture copied from a real system is the same disclosure as a document pasted into a ticket. Reach for a synthetic example instead: if a placeholder would carry the point, the concrete detail was never load-bearing.
  - **Why this is a rule and not a preference:** these artifacts are committed, and a repository's history is permanent and often public. A name written once survives every later correction - `git` keeps it, and a host keeps pull-request refs even after a force-push. There is no automated gate behind you here. The branch-safety scan matches credential shapes and terms someone already listed; it cannot recognise a customer's vocabulary, because that is semantic and does not exist as a term to list until the moment it leaks. You are the control.
- **Never commit without explicit user request** - Only create git commits when executing a command that has commit steps: `/commit`, the executor (`/drive` / `/implement`), `/story`, `/ship`, and the publish-tree writers (`/ticket`, `/mission`, `/mission-close`, `/specificate`), which commit inside `.publish/` rather than the caller's checkout. `/fb` commits nothing on either of its filing paths — both open a GitHub issue — and only its in-repo **fallback**, taken when that issue cannot be opened, writes and commits a feedback record. Commits go through the sanctioned scripts (`commit.sh`, `archive.sh`, the publish-tree seams), never a hand-rolled `git commit`
- **Never use `git -C`** - Run git commands from the working directory, not with `-C` flag
- **Link markdown files when referenced** - When mentioning `.md` files in documentation, use markdown links: `[filename.md](path/to/file.md)` not just backticks. Especially important for stable docs (specs, terms, stories).
- **Number headings in documentation** - Use numbered headings for h2 and h3 levels: `## 1. Section`, `### 1-1. Subsection`. For h4, number only when it helps identify topics. Applies to specs, terms, stories, and skills. Exceptions: READMEs and configuration docs.
- **A Bash call naming a plugin path writes the path out in full** - One command per call, the reader or interpreter (`bash`, `node`, `sh`) as the **first token**, and no `VAR=…;`, `export VAR=…;` or `env VAR=… <cmd>` prefix. A permission rule matches on the command, so an assignment-prefixed call is covered by nothing but a rule naming the assignment's own token — which then permits everything after it, leaving an operator to choose between a routine that stalls and an allowlist that permits anything. `${CLAUDE_PLUGIN_ROOT}` stays the correct notation **in markdown**; a session expands it (to `plugin-src.sh`'s `src`) when it composes the call it actually runs. The measured stall, the allowlist reasoning and the named exception for the few seams documented with a one-command `VAR=value` prefix live in `rules/shell.md`, *Composing the call: the path in full, the reader first, no assignment prefix* — this bullet is the ceiling, because a rule about how a **session** composes a command must not load only when a `.sh` file happens to be in its context.
- **The harness's plugin binding is an input, never a precondition** - Neither an unbound skill surface nor a *stale* one is a reason to stop. When the `Skill`/`Command` tool abstraction is unreachable (a `Skill(...)` call fails "Unknown skill", `ListSkills` returns empty), **or the bound build is behind the registry**, resolve the tree to run from with `check-deps/scripts/plugin-src.sh` — it returns the newest plugin tree on the machine (checkout, registry install path, clone, or binding) — then read the needed skill's `SKILL.md` and its scripts directly via `Read`/`Bash` from that `src` and carry out the documented workflow instead of stopping. Markdown skills and commands are ordinary files: a session that can read them can run the workflow, whatever the harness did or did not bind. The measured reason this is a rule and not an allowance (2026-08-12): a cloud image's project-scope pin held the binding twelve consecutive `[Implement]` ticks behind the registry while the bootstrap updated only the user scope, and every one of those ticks stopped with claimable work queued and a current checkout sitting right there. This is the general form of a pattern first stated for `/drive`'s survey step (`workaholic:drive`'s `unbound_in_claude_session` handling, ticket `20260810090005`) after a developer's live correction (FB `20260810070110`) showed a run stopping over a *harness* binding gap rather than a *repository* problem — the plugin's own scripts stay directly runnable via `bash` from the checkout regardless of whether the tool abstraction resolved, and the always-on PreToolUse safety hooks stay registered and active independent of it. **Two exceptions still fail safe**: a step that is genuinely `AskUserQuestion`-driven (there is no unattended substitute for a human decision), and logic too risky to hand-reconstruct correctly from source under time pressure. Every unattended entry point (`/implement`, `/specificate`, and any future one) applies this rule the same way; a command-specific write-up may keep its own concrete detail (script paths, which condition it is specifically about) but should point here for the general principle rather than restate it. **The resolved source must outlive the run's tree-moving steps**: the resolution happens before the freshen, so a mutable `src` (a checkout, a clone) can change — including backwards — under a run already executing from it, which is why `plugin-src.sh` breaks an equal-version tie toward the immutable, version-addressed candidate and reports `src_immutable`; a caller either requires `src_immutable: true` or re-resolves after the tree moves (measured 2026-08-12: a container's stale baked `main` reverted a resolved checkout 200 commits mid-run — `check-deps/SKILL.md`).
