# Drive

The project's execution knowledge: one run with **two entry points that share every step below §2** (decision P1). **`/drive [<unit>]`** is **attended** — it asks which units to take (§2) and nothing else at any step. **`/implement [<unit>]`** is **unattended** — no `AskUserQuestion` anywhere; it is what the `[Implement]` routine and every `/goal /implement ok` loop invoke. Attendance is a property of which command was invoked — never of a TTY, an environment variable, or a guess. The optional argument names one unit: a **scope**, not a mode. On an agent with no question mechanism, run `/implement`'s shape; drive claimed units sequentially by default (per-unit parallel subagents are a Claude Code option, not the contract — throughput comes from the claim protocol).

Relocated detail: [survey contracts](reference/survey.md) · [claim protocol](reference/claims.md) · [partition/routing/report](reference/routing.md) · [per-ticket workflow & archive](reference/ticket-workflow.md) · [failure contract](reference/failure-contract.md)

## The Unified Run

A unit of execution is **what deserves one merge**. The run turns the artifact stream into merge-sized units, takes each visibly, finishes it, and routes it by a policy the artifacts already carry: `survey → partition → claim → drive → report → route → account`.

### 1. Survey

**Resolve the plugin source before anything else**: `bash ${CLAUDE_PLUGIN_ROOT}/skills/check-deps/scripts/plugin-src.sh` — reachable on the checkout path (`plugins/workaholic/skills/...`) too, which is what a session with no usable binding uses. It returns `src`, the **newest plugin tree present on this machine** (checkout, registry installPath, clone, bound — newest version wins, and an **equal version goes to the immutable, version-addressed candidate**), and from here **every script path in this run is `<src>/skills/...`**, never `${CLAUDE_PLUGIN_ROOT}`. Its `ok: false` (`no_plugin_source`) is the only terminal stop this step still has: the run cannot read its own workflow. Record `source`, `version`, `src_immutable` and `degraded` in the run report. **This resolution is what the whole run executes, and the freshen below moves the working tree** — so a `src` reported `src_immutable: false` must be **re-resolved after `sync-main.sh`** before any later step reads it (the tie-break makes that the exception; the contract and its measured origin are `workaholic:check-deps`, *Resolving the source to run from*).

Treat `registry_unreadable: true` and the **absence** of the field the same way. The step runs identically through both entry points: one code path, and each `ok: false` is a reported decision, never a prompt — `no_origin`/`origin_unreachable` survey locally, say so, and forbid `ok`; `not_on_main`/`dirty_workspace`/`diverged` terminate `pending` (never merge or reset; see [reference/survey.md](reference/survey.md)). One shape that *looks* like `not_on_main` is not one: a checkout parked off the base but standing on its **exact tip** with a **clean tree** returns `ok: true` with `off_base: true` (§1a — the cloud harness hands the session its own branch and checks that out; measured twice on 2026-08-12, each tick contractually finished before it could survey with work queued). **A second, since 2026-08-18**: a **detached**, clean checkout that is a strict **ancestor** of the base tip is **fast-forwarded** onto it (§1b) and returns `ok: true` with `advanced: true`, `fast_forwarded: true` and `previous_sha`. Full field and reason vocabulary: [reference/survey.md](reference/survey.md).

- **A queue that holds work and offers none of it says so** (2026-08-26): `backlog_all_excluded` is a **derived** reading over `backlog_size`, `backlog[]` and `excluded[]` — the queue holds tickets, none are offered, and something was excluded — carrying a **count per exclusion reason**, because a queue emptied by claims is the protocol working while one emptied by `owned_by_other` is work nothing can drive. Name it in the run report: *the queue is empty* and *the queue is full and I can offer none of it* rendered alike until then, and the second reported `ok` every hour for five days over ten undrivable units. It **moves no token** — that table belongs to one mission at a time.
- **The survey states its freshness and does not repair it** — the repair is the caller's `sync-main.sh` above. Four conditions **forbid `ok`** (§7): `current: false`, `shallow: true`, non-empty `backlog_error`, and `owner_unresolved`. An unreadable queue never renders as an empty one.
- **`resumable[]` is a third offer with three tiers**: `heartbeat_lapsed` (a run died mid-drive — take it over before claiming fresh; left untaken it forbids `ok`), **`report_incomplete`** (a run died *after* archiving its last ticket and *before* opening a pull request — its queue is drained, its work is pushed, and nobody was told; equally mandatory, and left untaken it **forbids `ok`**), and `parked_with_pr` (at its PR, waiting on a human — reportable rather than mandatory, does not forbid `ok`). All three are takeovers via `claim.sh resume`. The first two enter at §4 and §5 respectively — **a `report_incomplete` unit has nothing left to drive, so its takeover re-drives no archived ticket and goes straight to the story, the scan and the pull request the dead run never opened** — and `parked_with_pr` enters at §4 for its follow-up tickets.
- **A *reported* claim is two states, and only one is a human's business** (2026-08-27, mission `close-the-units-the-loop-already-finished`): `queue_drained` means *waiting on a person* and was also covering the loop's own **undelivered** work — a unit whose merge the transport refused, excluded `claimed_reported` at every later survey, offered by nothing and told to nobody (measured: four green pull requests unmerged with `ok` reported over all of them). The split is **`report_undelivered`**, excluded `claimed_undelivered`, `resumable: false`, and it **forbids `ok`**. It is read off the branch story the run that attempted the merge already committed (`record-merge-outcome.sh` → `claims_merge_outcome`) — no network call, no second derivation, and an **absent** section keeps `queue_drained`, so the new reason is claimed only on positive evidence. `resumable: false` for its own reason: the next action is a **merge retry**, not a takeover, and resuming would push an empty `Resume` commit onto a branch whose pull request is open — the 2026-08-01 gate. `claim.sh resume` refuses it by its own name.
- **And `undelivered[]` is where that unit's one remaining action is offered** (2026-08-27, mission `deliver-and-retire-what-the-loop-already-proved-finished`): `[{unit, branch, merge_outcome}]`, one entry per `report_undelivered` claim, carrying the refusal the run that made the attempt recorded on its own branch. Naming the state was half the repair — the unit was excluded honestly and offered to nothing, so it was delivered by nobody until a person noticed the pull request. It is a **field, not a loosened exclusion**: `claimed_undelivered` stays in `excluded[]` unchanged, because loosening it would return the unit's **archived** tickets to `backlog[]` and a run would re-drive work already written and pushed. What is offered is a **merge attempt on an existing branch** and nothing else — no takeover, no worktree, no ticket. §6 acts on it.
- **A *reported* claim with work left is two states, and only one is a takeover** (2026-08-27, mission `stop-re-resuming-a-declared-handoff-unit`): `parked_with_pr`'s own contract says *taking it over is legitimate*, which is **false by declaration** for a unit whose remaining queued work carries `verification_handoff:`. §6 routed that unit to the **handoff** route precisely because nothing unattended can finish it — pull request open on purpose, claim standing on purpose — and the oracle offered the takeover anyway, on every tick (measured on PR #647: routed at 02:14 UTC, taken over again at 06:43 for nothing). Such a row now reads **`awaiting_verification`**, `resumable: false`, excluded `claimed_awaiting_verification`, and appears in **no** offer — not `resumable[]`, not `undelivered[]`, not `resurveyed[]`. It **does not forbid `ok`**, on the scan-held pull request's own reasoning (§7): a unit waiting on a declared human verification is the gate working. It is read through `verification-handoff.sh` — still the one reader of that field — off the branch tip, from the work still **queued**, so driving that ticket releases the reading with nothing stored anywhere. `claim.sh resume` refuses it by its own name. **And since 2026-08-27 the verdict reaches a person** (mission `ask-for-the-one-act-a-declared-handoff-is-waiting-on`): `/moderate`'s `handoff-units` step asks the **claim holder** one question naming the declared reason verbatim and the open pull request, keyed `handoff-unit:<unit>` so it is asked exactly once, and `stalled-units` no longer asks the wrong question about the same unit — it filters the verdict and counts it instead. That step is the verdict's one enumerated **reporting** consumer: it clears no handoff, retries no verification, merges and closes nothing, and touches no claim.
- **A claim whose content already reached the base is `superseded`** (2026-08-26): its tickets are archived on the base under another branch — or, at the **mission** grain, a merged pull request has that branch as its head (`claim-merged.sh`, the protocol's one network read; an `unanswerable` read leaves the row's verdict untouched and is named in `merged_lookup_unanswered`). Either way the branch is unmerged forever and holds no work. Excluded `claimed_superseded`, **reported and never acted on** (nothing deletes a branch or closes a pull request), and it **does not forbid `ok`** — a claim holding no work is the opposite of outstanding work. **Its work comes back to the offer**: the mission and the queued tickets behind such a claim are surveyed again as ordinary backlog and named in `resurveyed[]` with the dead claim branch, so a unit that came back is never mistaken for one that was never claimed — a fresh claim drives them, because the old branch cannot land — and since 2026-08-27 `claim.sh` lets that fresh claim through, skipping a `superseded` row in its refusal loop rather than answering `already_claimed`. Until then the survey offered a unit both claim paths refused, so its work was reachable by no path at all and it forbade `ok` on every later tick. It frees the **work, not the branch**: nothing deletes the old branch or closes its pull request, and every other refusal is unchanged, because only a claim already proved to hold nothing may be claimed over.
- Both lists empty with empty `backlog_error` → nothing claimable: report plainly, print the reconciliation and token (§7), stop. With a non-empty `backlog_error` the same emptiness means the opposite: terminate `pending`.

**Then read the base's health, once** (2026-08-27, mission `read-whether-the-base-survived-what-the-loop-merged`): `bash ${CLAUDE_PLUGIN_ROOT}/skills/drive/scripts/read-base-checks.sh $(git rev-parse origin/main)` — and, **only when that answers `red`**, `bash ${CLAUDE_PLUGIN_ROOT}/skills/drive/scripts/attribute-base-red.sh` to name the merge. ### 2. Partition into PR-units

A PR-unit is one merge: one unit ↔ one claim ↔ one branch ↔ one worktree ↔ one PR. Each claimable mission is exactly one unit (id = the slug); related backlog tickets group into one batch unit — conservatively, on a reason statable in one sentence; `depends_on` alone is grounds ([reference/routing.md](reference/routing.md)). Never mix merge policies to force a route. **Report the partition in full, always** — the composition is never asked through either entry point.

**The choice among units is the operator's, when one is present.** When a developer typed `/drive` and the partition offers **more than one** claimable or resumable target, ask once: one `AskUserQuestion` with `multiSelect: true`, at most once per run — one option per unit (id, kind, one-line summary), the body opening with the project label (`bash ${CLAUDE_PLUGIN_ROOT}/skills/gather/scripts/project-label.sh`), units in the order the run would have driven them, the total named if the list is narrowed. Drive the selected units in the order selected; report every unselected unit as `deferred_by_operator` (§7) — still claimable, so it **forbids `ok`**. Selecting nothing is legitimate: the run ends `pending`. **Ask nothing when there is nothing to choose** — a single target, an argument that names a unit, or `/implement` (`rules/interaction.md`).

### 3. Claim

Claim with `bash ${CLAUDE_PLUGIN_ROOT}/skills/drive/scripts/claim.sh mission <slug>` or `bash ${CLAUDE_PLUGIN_ROOT}/skills/drive/scripts/claim.sh batch <ticket-file>...`. Claim before driving, **one unit at a time** — claim, drive, report, route, then survey again; never claim several up front (an untaken claim sits invisible until its heartbeat lapses). No per-run limit in the other direction: keep going until nothing is claimable. Prefer a mission over backlog tickets. Read a refusal rather than working around it: `already_claimed` → drop the unit and continue (the protocol working); `origin_unreachable`/`no_origin` → end claiming (an unpublished claim is not a claim). All refusals: [reference/claims.md](reference/claims.md). The claim creates `.worktrees/<unit-id>/`; **all of the unit's work happens there**, every command `( cd <worktree_path> && … )` or absolute-pathed.

**Under `/implement` only, read whose work the unit is**: `bash ${CLAUDE_PLUGIN_ROOT}/skills/drive/scripts/unit-authors.sh <artifact>...` over the unit's members. `foreign` names the authors, `unresolved` says this runner has no identity to compare against, `mine` says nothing anywhere. It is **disclosure, never a claim decision** — `author:` stays outside ownership (`gather/scripts/owners.sh`), so the survey, the claim and the route are untouched by it; what changes is that a unit taken out of somebody else's queue says so where a human reads the outcome (2026-08-14, issue #454: an unattended runner took colleagues' work and merged it with nothing in the report or the finish line naming whose it was). It rides **§7's per-unit report only**: the appended finish-post line it also carried between 2026-08-14 and 2026-08-21 is retired (`workaholic:notify`, *the authorship line*) — it was noise on a deliberately short post, and in a container with no identity mapping it printed `noreply@anthropic.com` as an author, which is the one thing `unresolved` exists to prevent.

**Under `/implement` only, resolve the unit's feedback stems** for reuse at the finish post — `bash ${CLAUDE_PLUGIN_ROOT}/skills/drive/scripts/unit-feedback-stems.sh <artifact>...`, then find **one** thread by the **stateless lookup** in `workaholic:notify` (*One thread per feedback item*): exact-string searches only, at most two queries, the first-sorting stem's thread when several match, and a new **description root** when none does — resolved **once per run** and reused for the finish. **One finish line per unit, never one per stem** (2026-08-22): a strategy's carried-forward refs put two or more stems on every unit the loop produces, so the old per-stem rule announced each of them twice (the start post is retired; a unit posts its one finish line only). **An attended `/drive` run posts nothing to Slack, at any step** — the operator is present. Post rules: [reference/routing.md](reference/routing.md); `claim.sh`'s own one-line bot notice is a separate token-gated surface, never load-bearing.

### 4. Drive the unit

Inside the worktree, order the queue — dependency toposort → context grouping → implicit deps, reported, never asked ([reference/ticket-workflow.md](reference/ticket-workflow.md)); on Claude Code the ordering may be delegated to a `general-purpose` subagent. That subagent issues no `AskUserQuestion` — nothing in this run below §2 does. Then run each ticket through the **Workflow** below. **Beat the heartbeat as the first act of every ticket** — `bash ${CLAUDE_PLUGIN_ROOT}/skills/drive/scripts/heartbeat.sh <unit-id>`, step 0 of the per-ticket workflow ([reference/ticket-workflow.md](reference/ticket-workflow.md)), and again at any natural pause inside a long one. It was *"roughly every ten minutes or once per ticket"* until 2026-08-31, and those two coincide only for short tickets: `archive.sh` beats for free but only at the **end**, so a unit that is **one long ticket** runs its whole implementation on the claim commit's own timestamp and loses its own claim to the 30-minute resume window (`WORKAHOLIC_CLAIM_HEARTBEAT_STALE_MINUTES`) by construction. Measured on `batch-20260831141002`: resumed by a second tick at 33 minutes, and a complete, validated, locally-committed implementation was discarded rather than force-pushed over a branch another run was actively driving. A cadence is something an agent must track while its attention is elsewhere; a step is discharged where the workflow already stops. A failed beat is reported, never fatal. There is no per-ticket prompt and no gate-skipping decision: the authorization floor `drive-authorized.sh` states per ticket **moved up to the unit** — the survey applies it before offering ([reference/failure-contract.md](reference/failure-contract.md)).

### 5. Report

From inside the worktree, generate the story per `workaholic:story`'s Write Story flow, run the branch-safety scan (warn tier — findings fold into the PR body, never a prompt), then `bash ${CLAUDE_PLUGIN_ROOT}/skills/story/scripts/create-or-update.sh <branch> "<title>"`. The story file it writes is **new**, so whatever commits it names it in `commit.sh`'s `files...` — default staging cannot pick up a file that did not exist (`workaholic:commit`). **Compose `/story`; never fork or absorb it** — if context detection misreads, scope by branch, do not write a second story generator. A PR-creation failure (including `gh_unavailable`) is its own report item, never a change to the unit's outcome — though a unit that was going to ship demotes to the PR path ([reference/routing.md](reference/routing.md)).

### 6. Route by effective merge policy

**Read the verification axis first**: `bash ${CLAUDE_PLUGIN_ROOT}/skills/drive/scripts/verification-handoff.sh mission <slug>` or `… tickets <ticket-file>...`. A unit whose mission or any member ticket **declared** `verification_handoff: <what cannot run here>` at creation takes the **handoff** route whatever its merge policy says — its PR opens and stays open, `## Handoff` quotes the declared reason, the claim stays standing, the finish line is `🟡 Handoff`, and the token is `pending`. **And the claim is no longer re-offered, which is what "stays standing" always meant and could not deliver** (2026-08-27, mission `stop-re-resuming-a-declared-handoff-unit`): the oracle never consulted the declaration again, so the moment `/story` committed the branch story the claim read `parked_with_pr`, `resumable: true`, and every later survey offered a takeover that could drive nothing. It now reads `awaiting_verification` and is excluded `claimed_awaiting_verification` (§1) — the claim stands *and* costs no tick, so a **later** run reports `ok` over it while **this** run, which finished nothing, still ends `pending`. `auto` never outranks it: work nobody can verify here is not work this run may merge, the same shape as ship's §1-4 halt on a target that declares no confirmation method. The declaration is read off the artifact and is **never** made mid-drive ([reference/routing.md](reference/routing.md)).

Otherwise derive the route with `bash ${CLAUDE_PLUGIN_ROOT}/skills/drive/scripts/effective-policy.sh mission <slug>` or `bash ${CLAUDE_PLUGIN_ROOT}/skills/drive/scripts/effective-policy.sh tickets <ticket-file>...` — a script, not prose, because the answer decides whether machinery merges to `main` (G5):

| Unit | Policy source | Effective policy |
| ---- | ------------- | ---------------- |
| Mission unit | the mission's `merge_policy`, recorded at creation | `auto` iff the mission says `auto` |
| Batch unit | each member ticket's own `merge_policy` | `auto` iff **every** member says `auto` |
| Any member says `review`, or records nothing | — | `review` (any review member wins; **absent means review** — review costs a human one look, auto merges work nobody authorized) |

**`review` → merge the PR immediately** (mission `auto-merge-propose-and-implement-prs-under-a-dev-release-branch-split`, 2026-08-11, superseding the stop-at-the-PR route): once `/story` has opened the unit's pull request, read the scan through **`release-scan`'s `gate-decision.sh`** — never the raw `verdict` — and merge it when that reader says `decision: pass` **or** `override_only: true` (REST — `gh-rest.sh api repos/<slug>/pulls/<n>/merge --method PUT -f merge_method=merge`; never `gh pr merge`, which is GraphQL-backed, `rules/shell.md`) with no human confirmation, tearing the claim down exactly as `auto` does — quality is gated downstream at the `release/*` QA window, not at merge time. **A `hard` or `confirm` finding leaves the PR open instead** (there is no human here to override — the demotion doctrine unchanged), and that open PR is the unit's reported outcome.

**The merge attempt's result is reported per unit** (2026-08-27, mission `close-the-units-the-loop-already-finished`). This route reported which route it took and never whether the merge landed, so a run that was **refused** the merge produced the same report line as one that merged — measured 2026-08-27, four green units (#622, #625, #633, #635) open and undelivered while the run reported `ok`. Three outcomes, never collapsed: **`merged`**; **`merge_refused: <word>`**, the word being `merge-reason.sh`'s own (`merge_not_allowed` / `head_moved` / `session_type_cannot_merge` / `merge_forbidden` / `merge_failed`, unchanged in derivation and format); and **`merge_not_attempted: <hard|confirm>`** when a scan finding held the pull request and no merge was tried. The third is **not** a merge failure — a scan-held pull request is the gate working, a refused one is the loop stopping — the same distinction the `auto` route already draws between `shipped` and a demotion with the gate that caused it. `session_type_cannot_merge` is the one refusal with a sanctioned second attempt, and since 2026-08-27 that attempt is a **numbered, mandatory step of the route with its own reported outcome** — it was a sentence in `rules/shell.md` and nothing more, so the closing act was one a run could simply not take with nothing recording that it had not. Its bounds are `rules/shell.md`'s own and are not widened here: **precondition** `merge_reason == session_type_cannot_merge` and no other word (every other rung names a conflict, a race, a permission or an unclassified failure, none of which a different transport fixes); **one attempt, one tool** — `mcp__github__merge_pull_request`, at most once, with reads, writes and pull-request creation staying REST; **the retry's own outcome reported** — `merged`, or the pull request left open with **both** refusals named. **A run that reports `session_type_cannot_merge` and no retry outcome is non-conformant on its face**, which is the whole enforcement and is deliberate: no script may call an MCP tool, and a wrapper shelling out to one would be the same gap with more moving parts. A connector merge is measured only in an interactive session, so both outcomes are reported by name rather than the retry being assumed to succeed. **An outcome that is not `merged` is recorded on the branch, not only in the run report**: `bash ${CLAUDE_PLUGIN_ROOT}/skills/story/scripts/record-merge-outcome.sh `.workaholic/stories/<branch>.md` "<outcome>"` from inside the worktree, then commit and push. The run report dies with the container, and without a durable answer the claim oracle cannot tell this unit from one legitimately waiting on a person — both are drained, both reported, both at an open pull request. A merged unit records nothing, because the merge releases the claim. The oracle reads that one line back as `report_undelivered` (**Claims** below). Full step list: [reference/routing.md](reference/routing.md).

**A unit an earlier run finished and could not deliver gets one merge re-attempt** (2026-08-27, mission `deliver-and-retire-what-the-loop-already-proved-finished`). The in-session retry above covers the run that made the attempt; **no later run ever retried**, so a green, finished, undelivered unit was delivered by nobody until a human opened the pull request and pressed the button — measured 2026-08-26, four such pull requests still open a day later. For each entry the survey put in **`undelivered[]`** (§1), run `bash ${CLAUDE_PLUGIN_ROOT}/skills/drive/scripts/retry-undelivered.sh <unit-id>` **once**, before or after this run's own units, and report its outcome per §7. The script drives nothing, claims nothing, creates no branch and no worktree: the unit's queue is drained and every ticket is archived, so its single outward act is one `PUT .../merge` on a pull request the loop itself opened.

**And a unit the base has moved under is caught up first, in the same turn** (2026-08-29, mission `land-the-loop-s-own-work-when-the-base-moves-under-it`). The retry above re-attempts the *merge*, which is the right act for a refused transport and **no act at all for a moved base** — GitHub refuses the same merge every hour, forever. Nothing else looked either: `/moderate`'s `merge-conflicts` step reports a conflicted pull request and says in its own header that it never rebases. Measured 2026-08-29: 4 of 7 open pull requests conflicting with `main`, three of them units recorded `report_undelivered` two days earlier, with 4 active missions and 10 queued tickets behind them. So for each `undelivered[]` entry, **before** the retry:

1. `bash ${CLAUDE_PLUGIN_ROOT}/skills/drive/scripts/catch-up-claim.sh <unit-id>` — **once**, never a loop. It resolves the unit through the live-row rule, re-derives the verdict at the moment of its act, merges the base in (never a rebase, an amend or a force-push), regenerates, runs the repository's own fast checks and pushes. Its outcome is one of three words, reported per §7: **`caught_up`**, **`already_current`** (the branch already contains the base; no worktree, no merge, no ref touched), or **`catch_up_refused: <word>`**.
2. **A `caught_up` outcome, and only that, is followed by `retry-undelivered.sh <unit-id> --own-tip`.** A refused catch-up produces **no** retry — the refusal is the outcome. `already_current` means nothing moved, so the retry runs on its ordinary terms without the flag.

3. **After the retry, read whether the act took effect**: `bash ${CLAUDE_PLUGIN_ROOT}/skills/drive/scripts/act-effect.sh delivery <unit-id>` — one composed read, reported per §7 in its own four words (`taken` / `refused: <word>` / `pending` / `unreadable`). It answers *did what I did happen*, which is a different question from what the attempt returned, and it is the same reader that answers it for the retirement's Act 2. It gates nothing and moves no token.

**And every other reported claim this run can still catch up** (2026-08-30, mission `catch-a-reported-claim-up-before-its-conflict-hardens`). The loop above walks `undelivered[]`, which is a **delivery** verdict — so the catch-up, whose whole subject is whether the *base* still accepts a branch, ran only on units the *transport* had refused. A `queue_drained` claim is the other half of the same shape: finished, pushed, at an open pull request, waiting on a person, and its conflict hardens from `mechanical` to `content` while nothing looks. `/moderate`'s `catchup-blocked` step already **asks** about both verdicts; only the acting side was narrow. Measured live: one claim mechanical for four days, another content for twelve. So read `bash ${CLAUDE_PLUGIN_ROOT}/skills/drive/scripts/list-catchable-claims.sh` — this identity's **reported** claims (`report_undelivered` **or** `queue_drained`) whose `mergeability` is `mechanical`, composed off `list-claims.sh`, resolved through the live-row rule, with a degraded scan yielding no candidates, its reason and **null** counts — and run `catch-up-claim.sh <unit-id>` **once per candidate**, never batched and never retried inside the run. **A unit in both sets is caught up once**: the `undelivered[]` loop takes it, because that loop must catch up before its retry, and its outcome is reported there. **Both entry points walk it** — the act asks nothing, needs no ruling, and refuses the contested case — so an attended `/drive` behaves identically. The writer is **untouched**: it re-derives its own verdict at the moment of the act and applies its own bounds, which is exactly why widening the *caller* is safe, and the rule that makes it safe is written once in [reference/claims.md](reference/claims.md), *When a bounded act may read a judgement*. **No route, demotion, claim, merge, survey, refusal or sort reads this set**, and a run with no candidates behaves byte-identically to one before the widening existed. **One bound is new and belongs to the widening**: `catch-up-claim.sh` refuses **`pull_request_reviewed`** when a person has submitted a review, because an `undelivered` unit's pull request was refused by a transport and nobody is looking at it while a `queue_drained` unit's may be one a person is mid-review on, where a push resets an approval — and the lookup is three-valued, so `reviews_unreadable:<reason>` never reads as *nobody has reviewed*.

`--own-tip` exists because the catch-up's own push makes the tip fresh, so the very next verdict reads `claim_active` and the delivery the catch-up exists to unblock would be refused by the act that unblocked it. It relaxes **one term**, by re-asking the same oracle with the liveness window collapsed; identity, ancestry, supersession, the drained fork and the recorded refusal stay the oracle's own answers, and the scan-held refusal is untouched. Pass it only immediately after this run's own `caught_up`.

**The catch-up overrides no gate and resolves no judgement.** A `content` conflict is refused `content_conflict` with the branch byte-identical, and reaches its claim holder through `/moderate`'s `catchup-blocked:<unit>` question; a scan-held pull request is refused `scan_held:<tier>`; a colleague's claim is untouchable at any age. This **narrows** the standing rule that resolving a conflict on a claimed branch is nobody's job here — narrowed to the mechanical case on this identity's own claim, with the contested case still a person's ([reference/claims.md](reference/claims.md)).

**It acts on a proof and on nothing else.** `report_undelivered` is one of exactly two verdicts the claim protocol classifies as a **proof** ([reference/claims.md](reference/claims.md), *Proofs and judgements*) — the refusal is recorded on the branch by the run that made the attempt, never inferred here — and the script refuses every other verdict by name (`not_undelivered:<verdict>`). **No gate is overridden**: a `hard` (`secret`) or `confirm` (`leak`) finding holding a pull request open is the gate *working*, and such a unit cannot reach the verdict at all (its recorded outcome is `merge_not_attempted: <tier>`, which the chain routes to `queue_drained`) — the script refuses it a second time by name (`scan_held:<tier>`) regardless, because the cost of the redundant check is a string compare and the cost of its absence is an unattended merge past a secret finding. `queue_drained` is a judgement meaning *waiting on a person* and is never widened into this. The retry's outcome is §6's own vocabulary — `merged` or `merge_refused: <word>` — and a still-refused unit has the **new** word recorded back onto its branch (no worktree: the story blob is fetched, handed to `record-merge-outcome.sh`, and committed with plumbing against a scratch index), so the next survey and `/moderate`'s question read a current answer rather than a stale one. A `session_type_cannot_merge` from the retry takes the same numbered connector step below, on the same bounds.

**The route keys on the severity tier, never on the binary verdict** (2026-08-21). `workaholic:release-scan` has always said so in its own words — *the severity tells the consumer how hard to block, and both consumers key on it, never on the binary verdict alone* — and says of the `size` tier that it is *a granularity nudge, not a hard block (hence `override`)* and that *a branch whose only findings are `override`-tier stays releasable*. `/story` obeyed that; this route did not, and read `verdict == "pass"`. **Measured** on a documentation repository consuming this plugin: a `review` unit carrying 42 documentation pages in two languages produced three `too-large-commit` findings (749 / 983 / 1119 added lines against a 500 ceiling) and nothing else — no mixed concerns, no secret, no leak; the line count was the shape of the work. The unit sat at an open pull request, and the run reporting it went on to **ask a human whether to merge**, which `/implement` may never do. One cause, both symptoms: a tier read as a verdict. **An `override_only` merge still reports every finding** — in the run report and in the pull-request body `/story` already writes — so the nudge is delivered where it is useful and nowhere that it stops the loop. Nothing else moved: `secret` still hard-stops, `leak` still holds the pull request open, and the `auto` route's demotion table below is untouched, because there the override is a real human ruling recorded in deployment evidence. Under `/implement`, post the one `🟢 Implemented` finish line **on the transport `workaholic:notify` selects** (*The transport* — the connector where the session has one, the tokened script as the machine fallback; never load-bearing, and its outcome is reported per §7); under `/drive` report it in the session and post nothing. **`auto` → ship** through `workaholic:ship`'s full flow, no prompts and no shortcuts — which since 2026-08-13 **drafts the unit's deployment plan and merges; it deploys nothing** (`workaholic:ship`, *Standing rules*). `auto` therefore means "may merge unattended", never "may deploy unattended": a deployment needs the developer's instruction, and the production evidence for what has landed lives at the `release/*` window. A unit reported `shipped` means merged with a current plan drafted, not deployed. Then tear the claim down from the main checkout (claim-born and ship-torn): `bash ${CLAUDE_PLUGIN_ROOT}/skills/branching/scripts/cleanup-mission-worktree.sh <unit-id>` then delete the claim branch. **Under `/implement`, every route posts one finish line** (🟢/🚀/🟡/🔴) into the unit's resolved thread(s); an attended `/drive` run posts no finish line either ([reference/routing.md](reference/routing.md)).

**The run never overrides a gate — through either entry point.** `auto` means "no *approval* needed"; it never means "no *gate* applies", and a present developer recovers no override:

| Gate outcome on an `auto` unit | What the run does |
| ------------------------------ | ----------------- |
| `secret` finding (non-overridable) | **Hard stop.** Unit `blocked`, claim left in place — never laundered into the PR path. |
| `size`/`leak` finding (overridable interactively) | **Demote to the PR path.** The override is a human ruling an unattended caller does not have. |
| No confirmation method (ship §1-4) | **Demote to the PR path.** The accepted-risk bypass is a developer's conscious choice, and a plan whose verification reads "none declared" is the aspirational plan the gate exists to prevent. |
| A degraded plan read (ship §5 step 3) | **Report and skip the plan**, route the unit on the remaining gates. A half-written plan is worse than none. |
| A `content` conflict catching up with `main` (a `mechanical` one is routine) / a dirty claim worktree | **Demote to the PR path**, reported. Unchanged by the 2026-08-29 catch-up: this row is a unit on its way to shipping, and there the demotion *is* the repair. `catch-up-claim.sh` reads the same two words for a unit that has already reported and cannot be demoted anywhere — its pull request is open — so it refuses `content_conflict` and the question goes to a person ([reference/claims.md](reference/claims.md)). |

A demotion is reported as a demotion, with the gate that caused it. **The third route** — `bash ${CLAUDE_PLUGIN_ROOT}/skills/drive/scripts/land-unit.sh <unit-id> --developer-present [--override-scan]` — lands a `review` unit on a **present developer's instruction** so the next survey offers its leftover tickets. Neither entry point ever calls it; it refuses `headless_context` first and unoverridably, and the gates apply unchanged ([reference/routing.md](reference/routing.md)).

### 7. Account, reconcile, and the terminal token

**A mission the archive gate proved finished is already closed by the time this section runs** (2026-08-23): `archive.sh` calls `close.sh <slug> achieved` when the ticket it just archived left the acceptance fully checked and the queue empty. Only that one outcome, and only on the arithmetic — `abandoned` and `carried` assert intent and stay the operator's. The close, and any refusal from `close.sh`, appear in the run report by name ([reference/routing.md](reference/routing.md)); slug resolution searches `active/` then `archive/`, so every later lookup in this section survives the move.

Per **mission** unit, record wall-clock once via `bash ${CLAUDE_PLUGIN_ROOT}/skills/mission/scripts/record-run-hours.sh "<slug>" "<hours>" "<run-id>"` — one run-id per invocation, idempotent per run-id, the only writer of `actual_hours`.

**A unit may also end in `handoff`, by either of two entry paths.** **Half-driven**, when **all three** hold: its queue is **not drained**, the work that exists is pushed, and continuing it requires a person or another session. The second path cannot become one either, because the declaration is **on the artifact before the drive** and a run may never write it for itself. `handoff` is a property of the unit — **the four ticket outcomes stay four** and reconcile to the queue. A handoff unit writes the `## Handoff` section, opens/updates its PR with the work pushed, leaves any undriven tickets stamped in `todo/`, and (under `/implement`) its 🟡 is the unit's one finish post ([reference/routing.md](reference/routing.md)).

**A unit whose tickets are not the runner's says so in the run report** (2026-08-14, issue #454; narrowed to the report 2026-08-21). `unit-authors.sh` (§3) returns `foreign` / `unresolved` / `mine`; the first two name the authors in the unit's per-unit report entry below. `mine` adds nothing anywhere. **The report is the only surface** — the finish post carried the same line until 2026-08-21 and no longer does (`workaholic:notify`, *the authorship line*). This is disclosure of an existing, deliberate behaviour (empty `assignees:` means claimable by anyone), not a narrowing of what an unattended run may take.

**The run report opens with the base's reading** (2026-08-27, mission `read-whether-the-base-survived-what-the-loop-merged`) — once, before the per-unit outcomes, because it is context for everything that follows rather than an outcome of any one unit. One of the three words §1 read: **`green`**; **`red`**, naming the attributed merge (its commit, its pull request and its author) and the **failing checks**, or naming `unattributable` with its reason when the walk could not reach a green commit; or **`unanswerable`** with the reader's own reason. A degraded read is reported as degraded and **never as green** — that collapse is the whole defect the reading exists to close.

**And it names what is waiting on the operator, beside it** (2026-08-29, mission `follow-the-pull-requests-the-loop-opens-for-a-person`) — once per run, from §1's reading: each **un-acted** operator-facing pull request (`open:<age>`), with its number, its age and the **refusal word** that made it the operator's (`ruling_touching` / `strategy_touching`). A `merged` or `closed` reading is settled and is not named; an **`unreadable`** one is named **as unreadable, by its reason**, and never as *nothing waiting* — that collapse is the whole defect the reading exists to close, exactly as a degraded base read is never reported as green. A degraded **membership** read (`ok: false`) carries no pull list at all and is reported the same way.

**And it names how long each standing blocker has been standing** (2026-08-30, mission
`say-how-long-the-loop-has-been-stuck`) — once per run, from §1's reading: for each subject the
report already names, the age of the **question** about it (`age.ticks` ticks since
`age.first_seen`, *at least* that when `age.first_seen_is_floor`). A subject nobody has been
asked about yet reads `first_seen: null` and the report says nothing about its age — an ordinary
absence, the first time anybody is being asked. A **`readable: false`** reading is named **as
unreadable, by its reason**, and never as *nothing standing*: that collapse would render an

close.

**It moves no token and gates nothing, and that is stated here so a later reader does not "fix"
the omission.** §7's token table gains **no row** for it. The tempting error is to withhold `ok`
on the grounds that an old blocker is blocking the queue — it is, and `/implement` may not ask,
so a withheld token would report a failure hour after hour into a report nobody opens while the
person who can act is reached by `/moderate`'s own questions (`undrivable-unit`,
`retire-blocked`, `undelivered-unit`, `stalled-unit`). That is the reasoning

**It moves no token, and that is stated here so a later reader does not "fix" the omission.** A pull request waiting on a person is not a fact about the unit *this* run drove, and the run drove it cleanly: `ok` stays reachable over an un-acted ruling. The person who must act is reached by `/moderate`'s `operator-pull:<number>` question, not by this token. Same ground as `backlog_all_excluded` and the base's health.

**It moves no token, and that is stated here so a later reader does not "fix" the omission.** A red base is not a fact about the unit *this* run drove: a run that drove its unit cleanly onto a base somebody else broke reports `ok`, and names the red base while doing it. §7's table belongs to one mission at a time — the same reason `backlog_all_excluded` moves no token — and `ok` stays reachable on a red base. Nothing about the run's driving changes either: no gate, no skip, no stop (§1).

**An action this run REFUSED is named in the report** (2026-08-31, mission `stop-an-unattended-tick-from-waiting-on-a-person`). `rules/interaction.md`, *An unattended run never waits for a person*, admits two outcomes — proceed under a declared policy, or refuse the single action and carry on — and the second is only admissible if the record reaches somebody: without one a refusal is indistinguishable from an action that silently did nothing. **The run report is the deliverable** — always emitted. A unit the retry **delivered** reports `merged`; one still refused reports `merge_refused: <word>` with **both** words visible, the one it was retrying and the one it got, because *the same refusal again* and *a different refusal now* send a reader to different places. **And each of those entries names its catch-up outcome beside its delivery outcome** (2026-08-29, mission `land-the-loop-s-own-work-when-the-base-moves-under-it`), in **three words of its own**: **`caught_up`**, **`already_current`**, or **`catch_up_refused: <word>`** — the word being `catch-up-claim.sh`'s own (`content_conflict`, `not_my_claim`, `foreign_identity`, `claim_active`, `dirty_worktree`, `scan_held:<tier>`, `not_a_work_branch`, `mergeability_unanswerable:<reason>`, `validation_failed:<check>`, …). `read-back-whether-the-loop-s-own-act-took-effect`). The retry reports what the merge attempt

**It moves no token, and that is stated here so a later reader does not "fix" the omission.**

**And each `list-catchable-claims.sh` candidate names its catch-up outcome in the same three words** (2026-08-30, mission `catch-a-reported-claim-up-before-its-conflict-hardens`): one line per candidate — the unit and one of `caught_up` / `already_current` / `catch_up_refused: <word>`, the word **verbatim**, because a normalised word sends a reader to a string no script printed. **The same three words, never a second set**: the outcome of a catch-up on a `queue_drained` claim and on a `report_undelivered` one are the same kind of fact. **A run that names a candidate and reports no outcome for it is non-conformant on its face**, the retry row's enforcement for its reason. **No artifact gains a field**, and a run with no candidates reports nothing new.

**And a race this run MET is named as the run's own outcome, with both branches** (2026-08-30,
mission `stop-two-runs-from-claiming-and-driving-one-unit`). A run whose `archive.sh` refused

**Where the loss happens is stated rather than assumed.** The claim *push* does not arbitrate a
fresh claim — `create.sh` mints a clock-derived name, so two runners contend for nothing
([reference/claims.md](reference/claims.md), *What the claim contends for*) — and the
arbitration that would fix it is refused by this container's transport. So the loss is detected
one layer later, at `archive.sh`'s re-check, and the report names the refusal that exists rather
than one that does not.

**It moves no token, and that is stated here so a later reader does not "fix" the omission.**
The run wrote nothing — the refusal leaves the tree byte-identical — and the protocol worked, so
making it `pending` would report a failure on exactly the runs where the repair did its job.
It **gates nothing** either: no route, demotion, claim, merge, survey, refusal or sort reads it.
The claim holders who must decide which branch keeps going are reached by `/moderate`'s
`raced-unit:<unit>` question, not by this token. Same ground as `backlog_all_excluded`, the
base's health and the operator-facing pull requests.

**And each *reported* claim names its `mergeability`** (2026-08-30, the same mission) — one word off the row `list-claims.sh` already renders: `clean`, `mechanical`, `content`, or `unanswerable` **as unanswerable, by its reason**, never as `clean`, which is the reading that would make a decaying claim look healthy. A claim decaying from `mechanical` to `content` is the moment the loop's own work becomes a person's, and until this it was visible only after the decay, when `/moderate`'s question fired. **Nothing is derived and nothing is scanned twice** — the run already made that scan, so it costs no network call and no second walk — and it is bounded to **reported** claims, because naming the class for every claim on every tick turns the report into a claim table. **It moves no token and gates nothing**: no gate, sort, claim, route, demotion or survey reads it, the standing this repository gives `pace`, `overdue`, `expiring`, `arrived` and the base's own health.

**`catch_up_refused: content_conflict` moves no token, and the reasoning is written down rather than left to be re-derived.** The precedent is `claimed_awaiting_verification`: a unit waiting on a person's *judgement* is the gate working, and this is exactly that — the loop looked, classified the conflict, and declined to resolve what only a human can. Making it `pending` would put `ok` out of reach for as long as that person takes, on precisely the runs where the machinery did its job. The person is reached by `/moderate`'s `catchup-blocked:<unit>` question, not by this token. **Every other refusal moves no token by itself either**, for the same reason the survey rows do: what withholds `ok` is the unit's *delivery* outcome (`merge_refused: <word>`, the row further down), which a refused catch-up leaves exactly where it was. Then the survey's **`backlog_all_excluded`** reading when it fired — the queue's size and the count per exclusion reason — so a queue nothing could be offered from is never reported as an empty one. **Name `claimed_undelivered` for what it is** (2026-08-27): the other reasons say a human is on it, a colleague owns it, or the protocol is working; that one says the loop **finished a unit and could not deliver it**. **And `claimed_awaiting_verification` for what it is** (2026-08-27, mission `ask-for-the-one-act-a-declared-handoff-is-waiting-on`): a queue held by a **declared handoff** is a person's business, not the protocol working quietly — the unit is finished as far as anything unattended can take it, and the repair is the **declared verification** the artifact named at creation, run where the credentials exist. It **moves no token**, and that is the existing ruling recorded where the count is read rather than a change to it: a unit waiting on a declared human verification is the gate *working*, so `ok` stays reachable over a queue held only by declared handoffs, exactly as the row further down this section says. The counts are derived from whatever `excluded[]` carries, so a new reason rides the same derivation with no second vocabulary to keep in step. The reading still **moves no token** — that is the `merge_refused` row above, keyed on the units *this run* finished, and merging the two would turn an hourly survey reading into a completion gate. Then **Tickets minted mid-run**, deferred decisions (recorded, never asked), `deferred_by_operator` units, exclusions, stashes, predicted-vs-actual hours (full list: [reference/routing.md](reference/routing.md)). Then the reconciliation line, then the token, as the last two lines of the run — `N units: X shipped, Y PR'd, Z blocked` followed by `ok` or `pending`. The token is **derived, never self-asserted**:

**A withheld token names what withheld it.** A run that is not `ok` because a unit was refused its merge says which unit and which refusal, in the reconciliation's own line — the token is a signal a caller-side loop waits on, and one that cannot be traced to a unit is a signal nobody can act on. It is keyed on the **outcome the route already recorded** (§6's `merge_refused`), never re-derived: the run that made the attempt is the only thing that knows what happened to it. `merge_not_attempted` is not that outcome and never withholds the token, which is what keeps `ok` reachable on a run whose gates all worked.

**A retry names both refusals or it names nothing useful** (2026-08-27, mission `deliver-and-retire-what-the-loop-already-proved-finished`). Where a still-refused `undelivered[]` unit withholds the token, the line carries the unit, the refusal it was **retrying** and the refusal it **got** — the same refusal twice says the transport has not changed and a person must look at the pull request, while a different one says something moved and the new word is where to look. The extension is deliberately narrow and reopens nothing: `merge_refused` forbidding `ok` and `merge_not_attempted` never forbidding it are the 2026-08-27 rule unchanged, and the only new fact is that a unit the retry **delivered** stops forbidding it. Without that last part the loop could fix the problem and still report the token of a run that had not, which is the shape that makes a token stop being read.

"I stopped" is not "it's done": a blocked unit is `pending`, not `ok`. This table is verbatim the contract a caller-side loop such as `/goal /implement ok` waits on (decision I4); the reconciliation line always precedes the token so the outcome is graspable from outside.

## The failure contract

What an unattended unit may and may not do when a ticket goes wrong — every run, both entry points. Full statement: [reference/failure-contract.md](reference/failure-contract.md).

- **Attempt every ticket.** Size, complexity, and "needs a human" are not skip reasons; heavy, long, exclusive work is *preferred* unattended work. Only two buckets defer without an attempt: the safety floor (irreversible outward actions) and a genuinely external blocker, named concretely.
- **A closed set of four outcomes**, reconciling to the unit's queue: **implemented** (gate passed, archived) / **failed** (checks red — stash the partial work, leave the ticket in `todo`, record reason and stash) / **blocked** (a named external blocker with the attempted command and its raw output — a finding, not a forecast) / **`deferred`** (an unqueued problem became a ticket; the run continued).
- **Safety floor on any failure**: **NEVER** auto-icebox, auto-abandon, or run destructive git (`git restore .` / `git clean` / `git reset --hard` / `git stash drop` / `git checkout .`) — those need a human. "Missing credentials" is a checked claim (confirm `env_files_carried`, name the file). A backgrounded job's outcome is owed to the report either way.
- **An observation is not an obligation. Only a ticket is.** **Inside the current ticket's scope** → **implement it.** **Outside it** → **write a ticket, continue.** Do **not** fix it opportunistically ("unverified inferences pile up in the code" — the `overnight-ai` limit). **Blocks the current ticket** → write the ticket, then record the current one **`blocked`**, naming it. Mint only for an observed problem — speculative minting turns the queue into a diary. A minted ticket passes `validate-ticket.sh` like any other and inherits the provoking ticket's `mission:` relation **and the minting unit's own resolved `feedback:` refs** — written through `feedback/scripts/ask-feedback-line.sh`, that relation's one writer, never hand-formatted (2026-08-29, ticket `20260829111000`). A mint that carries neither is announceable by nothing: `unit-feedback-stems.sh` answers `count: 0` for it, so when that ticket is later driven as its own unit the notify lookup has no stem to search in case 2 **and** no record to link in case 4's root, and the merge is reported to nobody. Measured: `batch-20260829102127` (PR #716) merged with its finish line unposted for exactly this reason. **`feedback:` is the field to carry, not `mission:` alone** — the hop through a mission resolves a mission unit's mint but not a **batch**'s, which is the measured case, and `feedback:` is correct for both. The refs are in hand by construction: the minting unit resolved its own stems to post its own finish line. **Carry them only when the run can say the mint is about the same item**; a genuinely unrelated mint carries nothing and its line stays unposted, because a wrong thread is worse than none (`workaholic:notify`, *Fuzzy matching is prohibited*). Report every one. Do **not** append an acceptance item to the mission for it — promoting it into the definition of done is the developer's call.

### Where the per-ticket approval prompt went

The prompt is retired and **approval is relocated, not removed**: a mission unit was authorized when a human **merged the mission's pull request** (K1); a batch unit when **each ticket was created** (`merge_policy` at `/ticket` time). What is removed is the completeness check inside the drive loop — nothing else: the non-delegable looking-through relocates to the PR. The run does not relay evidence-resolvable decisions upward either — decide, record one line, proceed; a genuine developer-only ruling is deferred and recorded, never asked. Requirements elicitation at planning time is the opposite case and stays mandatory ([reference/failure-contract.md](reference/failure-contract.md)).

## Claims

**The repository is the coordination medium.** A runner claims a unit as a `Claim <unit-id>` commit on a pushed `work-*` branch; the unmerged remote branches are the only claim oracle (`bash ${CLAUDE_PLUGIN_ROOT}/skills/drive/scripts/list-claims.sh` — pure read). A merge releases by definition; `release-claim.sh` deliberately discards an unfinished unit (never a recovery path); `claim.sh resume <unit-id>` takes over **your own** claim whose heartbeat lapsed — a colleague's is `foreign_identity`, untouchable at any age, and races are settled by the push, never a clock. Staleness (`stale: true`, 24 h) is reported and never acted on. A stamp that reaches the base is history, not a claim (M1). The reader degrades offline; the writer refuses. **The archive commit pushes itself**: `archive.sh` pushes the claim branch immediately after making the archive commit, the same non-blocking convention `heartbeat.sh` uses for the branch tip — an archive commit is a progress signal that must always reach the remote, so this is no longer left to the driving session's discretion; a failed push is reported (never fatal) and the next heartbeat or commit carries it forward. Full protocol, script contracts, and refusal vocabularies: [reference/claims.md](reference/claims.md).

**Two of the oracle's words are proofs; every other word is a judgement** (2026-08-27, mission `deliver-and-retire-what-the-loop-already-proved-finished`). `superseded` (the content reached the base) and `report_undelivered` (the run recorded the transport's refusal) are readings the tree or a merged pull request **established**, and a consumer may **act** on them. Everything else — `stale`, `queue_drained`, `report_incomplete`, `heartbeat_lapsed`, `parked_with_pr`, `claim_active`, `foreign_identity`, `identity_unresolved`, `shallow_history`, `ambiguous_claim`, and the lookup's `unanswerable` — is a reading that says *look at this*, and a consumer may only **report** or **ask about** it. `unanswerable` is a judgement because it is the **absence** of a reading, and acting on an absence is the failure the three-valued lookup exists to avoid. The classification is written once, keyed on the word `lib/claims.sh` already emits, with no field on any artifact and no classifier script — the table and the rule are [reference/claims.md](reference/claims.md), *Proofs and judgements*, and every consumer reads it rather than restating it.

**The base's own checks are a second vocabulary in that same home, and it holds no proof at all** (2026-08-27, mission `read-whether-the-base-survived-what-the-loop-merged`). `green`, `red`, `unattributable` and `unanswerable` (§1) are **every one a judgement**: a check run is designed to be re-runnable, so each reading can become false by somebody looking again — the one property a proof must not have — and `unanswerable` is besides that the **absence** of a reading. So **no consumer may revert, re-run, block, gate, hold or merge on it**. This run reports it and gates nothing (§1, §7); `/moderate`'s `base-health` step asks the attributed author and does nothing else. The classification is a sub-table beside the claim tables — one section, two keyed tables, because one column cannot classify two different questions — and `scripts/test-workflow-scripts.mjs` pins it and enumerates both consumers, so a third must be registered rather than slipping in unclassified.

## Workflow

Implementing a single ticket, inside the unit's worktree — the full steps (read the ticket, its `## Policies`, its `## Quality Gate`, and the gate of **every** mission it names; apply patches; implement against the policy lens; return the JSON summary; append the Final Report; archive) live in [reference/ticket-workflow.md](reference/ticket-workflow.md), with the system-safety check (`bash ${CLAUDE_PLUGIN_ROOT}/skills/system-safety/scripts/detect.sh`) and the prohibited-git-operations table.

- **NEVER commit outside the sanctioned scripts** — `archive.sh` and `commit.sh` own the commit seam.
- **NEVER use AskUserQuestion while driving a ticket** — the run's only interaction point is the §2 selection.
- **NEVER archive tickets manually** — `bash ${CLAUDE_PLUGIN_ROOT}/skills/drive/scripts/archive.sh` is the only authorized method, and the ticket's `## Final Report` is appended first.
