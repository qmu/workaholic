# Notify

The notification model of the unattended loop, stated once. `workaholic:drive`'s claim and route steps, `workaholic:specificate`'s finish post, and the routine prompts ("the `workaholic:notify` lookup") defer here rather than restating rules; `workaholic:workaholify` owns the routine templates and their setup sheets and points here for the model the templates defer to. Relocated detail: [reference/notifications.md](reference/notifications.md) (post shapes, session URL, mention mechanics, red-alert history, the withdrawn disclosure, the lookup's history).

## One thread per feedback item — the notification model

The unit of a notification is the reader's item of interest, not the emitter's step: one Slack thread per feedback item, carrying its whole life. The `[Specificate]` routine posts the root; every later event of that item is an in-thread reply. The key is the feedback record's filename stem, embedded verbatim in the root as `` `fb:<stem>` `` — the identifier that lives in the repository (`feedback:` relations, `supersedes`, the publishing PR's diff), so a later session derives it from the artifact in hand; the issue number rides along as a human pointer only.

Finding the thread is **stateless** (Q1, 2026-08-07 — nothing carries a target between routines; the search is defined so it cannot guess). Ordered cases, take the first that applies — every search an **exact-string** Slack search, never a similarity or content match:

1. The session's own trigger message — reply there; that message is the item's thread. Not a search, and not reducible to one: a hand-off knows its target at write time, and a message written before the record existed can never carry the key.
2. Search `` <stem>.md `` — the record's own filename, which a thread root carries inside the URL it links, derived from the repository, never from Slack. (It was `` `fb:<stem>` `` on a line of its own until 2026-08-22; the line is gone from every rendered post and the URL answers the same query.) (`drive/scripts/unit-feedback-stems.sh` for `/implement`; the record `/specificate` just wrote for its finish post).
3. Search the **originating** Issue or pull-request URL — the one the ask arrived on, a string that existed *before this run began*, and **never a URL this run itself created** (the pull request it just opened, the branch it just pushed), because such a string cannot pre-exist the run that made it and the query is guaranteed to return nothing — or its `#<number>` reference when no URL is in hand, a substitute and never an extra query — which finds the originating human thread when somebody pasted the link into Slack.
4. No exact match → post a **new root** carrying `fb:<stem>` — never a keyless top-level line (two roots with one key is repairable; a keyless post is not attributable to anything). That root is a **description root**, and the finish line is a reply into it (*The description root*, below) — for `/specificate` and for `/implement` alike. Only a caller with no connector falls back to a keyed top-level finish line, because the tokened script cannot thread.

**Every search in cases 2 and 3 runs private-inclusive** (`slack_search_public_and_private`, `include_bots: true`), never the default `slack_search_public` (ticket `20260810163359`, measured root cause of issue #360's misses — [reference/notifications.md](reference/notifications.md)). `dev-<repo>` is a **private** channel, so the connector's default public-only search returns zero results for the record's filename by construction, however faithfully a root carries the key — not because the search is unreliable, but because it never looked. This is a **standing, one-time developer consent** to read the repository's own `dev-<repo>` channel, carried by this skill and by the routine templates that defer to it; a routine posting into that same channel needs no further, per-run consent to search it. Reading `include_bots: true` matters the same way: a routine's own prior posts are bots, and a search that silently excludes them can miss its own root.

**Fuzzy matching is prohibited by name**: never a similarity match, never "the most recent thread that looks related", never recency — it is what put a reply in the wrong place on 2026-08-05, and a guess in a notification path is a message that looks right and is unrelated to the event. The not-found branch is what makes the search safe: a lookup that cannot find the thread **says so** by starting one. **The bound is a written number**: **at most two search queries per lookup** (cases 2 and 3, one each), results capped to the top few matches, and **no full-channel read at any point** — search returns matches; channel history returns everything and is never the instrument. **Resolve once per run and reuse it**: a unit's start and finish go to the same thread — statelessness is between runs, never within one. (History and the withdrawn disclosure: [reference/notifications.md](reference/notifications.md).)

### The description root — what a run posts in case 4

Case 4 posts **two messages, not one**: the description root, then the run's finish line (`🔵 Proposed`, `🟢 Implemented`, `🚀`, `🟡`, `🔴`) as a threaded reply into it (developer's ask, 2026-08-14, issue #443 — a thread that opens with a status line gives a human nothing to read and nothing to answer). The pair is one event split into a readable header and a status line, never a second announcement: *The bright line* below is unmoved, and a found thread still gets exactly one message.

**Both callers, since 2026-08-22.** It was `/specificate` only until then, on the ground that extending it would emit a shape the `[Implement]` routine prompt does not name — *The prompt is the ceiling* — and that adopting it needed a template edit plus a developer's confirmation rather than an inference from this section. That is exactly what happened: shown the shipped `/implement` case-4 root twice, the developer ruled it unusable ("a message like this is of no use to anybody"), and the template moved in the same change. The reasoning that created the root for `/specificate` never distinguished the callers — a thread that opens with a status line gives a human nothing to read and nothing to answer, and `/implement`'s root was the worse of the two, opening with a status emoji and a pull request number and ending in a bare machine key.

- **The root carries the key in its LINK, not in a line of its own** (2026-08-22, the developer's instruction, repeated: *stop mixing strange ids into Slack*). The root already links the record at `<repo-url>/blob/main/.workaholic/feedbacks/<stem>.md`, and **Slack indexes link URLs** — measured by searching `` <stem>.md ``, a string that exists nowhere in the message but inside that URL, and getting the exact message back. So the separate `` `fb:<stem>` `` line was never load-bearing; it was the same identifier printed twice, once for the machine and once at a human.

  The standing objection — *a root without the key regresses the whole lookup* — is answered rather than overruled: **case 2 now searches `` <stem>.md ``**, which the root carries by construction because it links the record. Nothing is persisted, no `thread_ref` reaches the repository (the exposure the P9 withdrawal found irretractable), and the query stays a single exact string.
- **The root carries no Claude mention token** — no `<@U…>` resolving to the Claude app, no literal `@Claude` — because a mention re-triggers the Slack app on the routine's own post. Mentioning **another person** is untouched; since 2026-08-23 the finish reply carries no token at all, because the one it carried resolved to the account the post is made as (*Never mention the identity you are posting as*, below).
- **The root links the feedback record**, `<repo-url>/blob/main/.workaholic/feedbacks/<stem>.md`, and **no issue is filed to give it something to link** (the Open Decision, ruled 2026-08-14 — reasoning in [reference/notifications.md](reference/notifications.md)). The link resolves once the proposal's pull request merges, which it does on opening; a scan finding that holds the PR open leaves it pending, and the run says so.
- **The tokened fallback posts one message, not two.** `notify-slack.sh` cannot thread (*The transport* below), so it posts the keyed finish line alone exactly as before, and the run reports that it could not thread rather than reporting a root it never posted.
- Exact wording, and what a template must copy verbatim: [reference/notifications.md](reference/notifications.md).

### Which thread an `/implement` unit's posts land in

These posts are the unattended run's (`/implement` — the routine and any caller-side loop): they exist so an absent operator can tell a working fleet from a dead one. **An attended `/drive` session posts nothing to Slack** — the developer is watching the run, and its report is the session's.

A unit's start and finish are **per-unit, never per-run** ("a run started" names no item, so it has no thread to land in). `drive/scripts/unit-feedback-stems.sh` resolves the unit's artifacts to their deduped feedback stems. Rules:

- **One finish line per unit per channel — not one per stem** (2026-08-22). Several stems resolve to
  **one** post, into the thread the lookup found; the remaining stems get nothing. When more than one
  stem finds a thread, take the one whose stem sorts **first** — a rule, not a preference, so two runs
  of the same unit choose the same thread. No stem → key on `` `unit:<unit-id>` ``, never keyless.

  **Why it stopped being per-stem.** "Once per stem per event" reads as one announcement per audience,
  and is not: it announces an event as many times as the corpus happens to hold records of it. Measured
  twice. First, a unit whose two stems were two records of **one** request captured months apart — the
  identical finish line four seconds apart, one threaded, one a new root. Then, deterministically: a
  unit whose second stem was a **strategy's carried-forward `feedback:` ref**. That carry-forward is
  load-bearing — `/specificate` puts a strategy's refs on every mission it emits because
  `attributed-work.sh` has no other link back to the direction — so **every strategy-attributed unit**
  resolves to two or more stems, and the old rule turned each into two posts, the second always the
  naked root, because a strategy's stem has no description root to thread into. The duplicate was not a
  corpus accident a tidier stream would remove; it was guaranteed for every unit the loop produced on
  its own.
- **The start post is retired** (developer's order, 2026-08-11; mission `auto-merge-propose-and-implement-prs-under-a-dev-release-branch-split` — the `🟠 Implementing` / `📐 Proposing` beginning posts are gone from the live routine records and from the templates): a unit posts **exactly one finish line**, its shape following the outcome — `🟢 Implemented` for a merged unit, `🚀` ship, `🟡` handoff, `🔴` blocked. A handoff is the finish, never a second post.
- Never re-announce a merge the channel already carries (a resumed unit can reach the route step twice).

The bot notice `claim.sh` posts (bot token, no threading) is a different surface and is deliberately left alone; neither surface is load-bearing.

### The moderator's hourly thread — one root, its questions inside it

`/moderate` and its repository-scoped `[Moderate]` routine post a **root per tick** — `🔎 Moderation`, keyed on `` `tick:<tick-id>` `` — carrying what changed in the hour, and every question the tick has goes out as a **mentioned reply inside that root's thread**. Root = orientation, addressed to nobody; replies = directed questions, addressed by name. Two speech acts, one thread, told apart by position rather than by two routines (2026-08-21, the developer's design).

**Two gates, both required, or the tick posts nothing**: at least one question **or** at least one changed step. A change is a step whose summary differs from the same step's summary in the **previous tick** — derived from the log the tick already keeps, so nothing is stored and no step gained a field. An idle hour is silent, and so are `no_previous_tick` and `no_log`: a mechanism that could not read must never announce quiet. Exact shapes: [reference/notifications.md](reference/notifications.md).

**This does not reverse the 2026-08-19 retirement, and the difference is worth stating.** `🔧 Needs a decision` and `📦 Release Preparation` were retired — measured, ten `📦` lines in ten consecutive hours for one unchanged request, none answered — on the rule that *a status line addressed to nobody is noise whatever its dedup key*. This root is not that: it exists to carry the questions beneath it, and it cannot restate an unchanged answer, because the change test is a diff against the last tick rather than a content hash of the current one. **`/prepare-release` posts nothing at all** and nothing replaced it; the release reads it used to broadcast are steps 8 and 9 of this tick, and they report into the log.

**The cost is paid in the open**: a person following one item's own thread no longer sees the tick's question there, so every root line links the item it is about.

### The daily standup digest — the other post with no feedback item

`/standup` and its repository-scoped `[Standup]` routine post `📣 Standup` as a **top-level root** — never a reply, and carrying **no mention token of any kind**, for the same two reasons the moderator's root carries none: nobody *said* anything for this event, and the line names the repository's state rather than a person's work. A strategy's assignees appear *in* the digest as a fact; nobody is paged by it.

**What must be prevented is two posts for one morning** — exactly the failure the repository scope cannot prevent on its own, since nothing can detect N copies of a repository routine. A *daily* digest is expected to speak for today even when today resembles yesterday, so the check is a **date**, not a content hash.

**And the date is a search bound, not a printed key** (2026-08-22). Search `📣 Standup` once, private-inclusive with `include_bots: true`, bounded to today (`after` = the start of the local day): found ⇒ post nothing. The morning is expressed by the bound rather than by a `` `standup:<YYYY-MM-DD>` `` line, so nothing machine-shaped reaches the reader and the property the key protected is unchanged.

**The digest's own no-op is the other gate, and it is the reason a recurring post is allowed here at all**: `noop: true` posts nothing, whatever the date says — no active strategy (`no_strategies`), nothing moved and no `target_date` inside the horizon (`no_activity`), or an unreadable strategies area (`strategy_list_unreadable`, reported in the session and not posted, because a mechanism that could not read must not announce quiet). `workaholic:standup` owns those gates; this skill owns only the shape. Exact wording: [reference/notifications.md](reference/notifications.md).

## The transport — the connector is primary, the tokened script is the machine fallback

The model above says *which* thread a post lands in; this says *what carries it there*. Stated once here because a call site that names one transport as **the** way to post silently selects it for sessions that do not have it — measured 2026-08-12 (FB `20260812203825`, issue #406): the skills named the script, a routine session carries the connector and no token, and the finish line for four runs never existed.

1. **The connector is the primary surface wherever the session has one** — the account's Slack MCP tools, which every routine-fired session carries. It is the only transport that can run the lookup above at all (the exact-string searches of cases 2 and 3) and the only one that can reply *into* a thread (`thread_ts`), so a session holding it always posts through it. Choosing it needs nothing beyond the session: no token, no env file.
2. **The tokened script is the fallback for a caller with no connector** — a shell or CLI invocation: `bash ${CLAUDE_PLUGIN_ROOT}/skills/specificate/scripts/notify-slack.sh "<text>"` with `SLACK_BOT_TOKEN` + `WORKAHOLIC_SLACK_CHANNEL`.
3. **Neither surface available → the post does not exist, and the run says so** rather than proceeding as if it had been sent (`workaholic:drive` §7's per-unit notification outcome, `workaholic:specificate`'s `notified` flag).

**What the fallback cannot do, stated so no call site assumes otherwise** (measured 2026-08-12 by reading its payload construction): `notify-slack.sh` builds `{"channel", "text"}` and takes one text argument — there is **no `thread_ts` parameter and no search**, so it can post a **keyed root only**, never a reply into an existing thread. A run posting through it therefore carries the record's **URL** in the text (or, with no record to link, `` `unit:<unit-id>` ``), which is the lookup's own not-found branch reduced to what one message can do: two roots naming one record is repairable, an unattributable post is not. The URL rather than a bare key since 2026-08-22 — it is the same identifier in the one form a person can also use. Case 4's description root is a *connector* shape for the same reason — the fallback posts the keyed finish line alone and the run reports it could not thread, never a root it did not post. Teaching it to thread would require the exact-token search, hence a `search:read` scope the bot token does not have — an account-level provisioning change, not a plugin one, and not a thing to assume while writing a post.

**Never load-bearing, and never silent about it.** With no token the script records `{"notified": false, "reason": "no_token"}` and **exits 0**; a connector post can fail the same way. A run whose work landed is still a success — but the outcome is reported by the caller, because a notification that vanished and one that arrived must not read alike from outside the run.

## Post shapes, mentions, and the red-alert dedup

The exact shapes of the runner's posts (🔵 proposed / 🟢 implemented / 🔴 blocked / 🟡 handoff / 🚀 auto merge / ⚪ paused) are in [reference/notifications.md](reference/notifications.md); a template names its postable events and defers the shapes there. **The start shapes (`📐 Proposing`, `🟠 Implementing`) are retired** (2026-08-11, developer's order — a routine posts its finish only); `/specificate`'s and `/implement`'s finish lines carry issue #300's literal wording as the **sole** sanctioned format (P10, 2026-08-07, narrowed to the finish events), and the outcome-specific finish shapes (`🚀` merge, `🟡` handoff, `🔴` blocked) are unchanged, since each carries information the generic finish line would lose. The fourth outcome shape this line once listed, the purple-circle human-merge line, is erased (qmu/workaholic#317) — see *Which thread an `/implement` unit's posts land in* above and [reference/notifications.md](reference/notifications.md) for what stands in its place. Standing rules:

- 🔵 Proposed is the `[Specificate]` routine's finish line, and since 2026-08-14 it is a **reply** in every connector case — into the thread the lookup found, or into the description root case 4 posts (*The description root*, above). It is a keyed top-level line only on the tokened fallback, which cannot thread, and there its `` `fb:<stem>` `` line is never dropped. It announces only the pull request you just created in this session, exactly once — post nothing if you created none, and never announce another session's work.
- Every post carries its session URL when discoverable; a post missing it still posts. No thread URL rides a public Issue or pull-request body — the carried target is retired and its recorded disclosure withdrawn (Q1; [reference/notifications.md](reference/notifications.md)).
- Naming a person means mentioning them: resolve to a Slack user id and write `<@U…>` — plain `@name` pings nobody. Email is the reliable key (a GitHub login is not a Slack handle). The fallback is non-blocking: an unresolved id posts the plain name rather than not posting.
- **Never mention the identity you are posting as** (2026-08-23, the developer's instruction). Every routine post reaches Slack as the developer's own account, and Slack does not notify anyone of their own message — so a `<@U…>` resolving to the posting identity notifies nobody and is decoration, not a mention. Resolve both sides and emit no token when they match. Three shapes carried one and no longer do: `🔵 Proposed` and `🟢 Implemented` lose it from the `by the [routine](<session URL>) of <@U…>` attribution line (**the session URL stays** — it is what the developer opens to answer), and `🟡 Handoff` loses the runner it named. Mentioning **someone else** is untouched and is what a mention is for: `🙋 <@U…>`, the maintenance tick's question, keeps its token unconditionally — it addresses a named assignee, it is the one post whose whole purpose is to reach a person, and a loop whose blockers reach nobody is the defect issue #584 recorded. Shapes: [reference/notifications.md](reference/notifications.md), *A post never mentions the identity it is posted as*.
- **The precondition-stop class** is a named, closed list of pre-survey gate terminations: `no_plugin_source` (`workaholic:check-deps`, `workaholic:drive` §1). It held two more members until 2026-08-12 — `unbound_in_claude_session` and `loaded_version_behind_registry` — and both left it by ceasing to be stops at all: `plugin-src.sh` resolves the newest plugin tree on the machine and the run drives from it, so a missing or superseded binding is now a reported source-selection fact. A signature that no longer terminates a run posts nothing at all, calm or red. Extending the list is a deliberate edit to this skill, never a model judgment made at post time. A **first** report of a precondition-stop signature posts the calm shape `⚪ Paused - <signature>` (with the session URL, as every post carries) instead of a red alert — by the time the post is read the bootstrap has typically already repaired the environment and the next tick proceeds — keyed by the same failure signature and still landing as a top-level root, so persistence has something to thread onto.
- A red failure alert is deduped by its failure signature — the failed precondition or step plus its one-line reason class, stable across ticks: never a SHA, a timestamp, a file count or any varying detail. Before posting, read the channel's recent history (~50 messages) and suppress only the same signature until the cool-down expires; the rule suppresses repeats, never first reports. **The cool-down expires at the earlier of two moments** (2026-08-23): 24 hours after the first report, **or the start of the next working day** — the first hour of the next day inside `WORKAHOLIC_WORK_DAYS` (default `1-5`), at the end of the quiet window `WORKAHOLIC_QUIET_HOURS` (default `22-08`, so 08:00), in `WORKAHOLIC_QUIET_TZ` (default `Asia/Tokyo`). **No new constant and no second timezone**: those three are the check-in gate's own, composed rather than re-derived. The 24 hours were measured from the first report alone until then, and the defect was *where they were measured from*: a failure that begins in the evening posts nothing at channel level for the whole of the next working day. **Measured** 2026-08-22→23 — a unit blocked at 21:38 JST, eleven consecutive ticks reporting `blocked`, 2.1 agent-hours spent, and every one of those escalations a `↳ still failing` reply inside the previous day's thread; channel level showed nothing for ten hours and the developer asked why the channel had stopped updating. The cool-down was working correctly. A signature first reported *during* the working day is unaffected — the 24-hour term is still the earlier one, so nothing about that case moves. **A root re-posted at expiry says how long it has been failing** (`🔴 Blocked - <signature>, failing since <time>, <N> ticks`): the news at that point is the duration, and a root identical to yesterday's is the restatement this repository retires posts for. The cost is bounded and intended — at most one extra post per signature per working day, against ten hours of a stalled loop. A suppressed tick names the suppression in its terminal report (`alert suppressed as duplicate - <signature>`) and posts one line as a threaded reply on the existing alert (`↳ still failing - <signature>, first reported <time>, <N> ticks`) — the reply is not itself rate-limited, since only a fresh reply answers "is this still happening". The cool-down suppresses the **top-level** post and nothing else: a changed signature or a first report always posts a root, and an unreadable history posts the alert anyway, because silence must never be produced by a failure of the mechanism that decides to be silent. **A precondition-stop signature escalates to this red form exactly once**, when the same signature is found again in that same recent-history read (no new state) — a persisting, non-self-healing condition, such as a stale container image reproducing the same gate every tick. From the escalation onward the signature is an ordinary red alert: the existing cool-down and `↳ still failing` replies apply unchanged. Every genuine-failure shape — a `secret` hard stop, a `blocked` unit finish, and every other outcome shape — keeps its current severity untouched; this rule narrows only the precondition-stop class above.
- The orange/green/yellow/rocket posts announce events the session itself produced and are new every time; deduping those would hide real work.

## The prompt is the ceiling — no self-authorized shapes

A session may emit only the notification events and post shapes its own routine prompt or invoking command names. Nothing else authorizes one: not a shape documented in this skill or its [reference/notifications.md](reference/notifications.md) catalog, and not a post the session itself made or reasoned about earlier in the same run — this documentation describes the sanctioned wording for events a session was already instructed to post, it never grants permission to post. An event or shape not named by the prompt or command becomes standing behavior only after developer confirmation, and citing this skill's own text is not a substitute for that confirmation. Measured origin (FB `20260807082554`, issue #298): an `/implement` run posted a `🟣 Merged by` line its routine prompt never specified, justifying the addition from this skill's documentation and its own earlier in-session reasoning — exactly the move this rule forbids.

## The bright line — what earns a post

Slack is the only surface — the repository's `dev-<repo_name>` channel; no mobile or push notification. An event earns its post by being something a developer must act on or stay aware of: post a unit started, a proposal opened, a merge, a handoff, a blocked-on-precondition failure, a **changed** release status with something waiting; do not post an idle tick, a claim, a heartbeat, a ticket archived, a commit, a passing test, or a build — the tie goes to silence. The moderator's `🔎 Moderation` root is the one recurring post, and it survives this rule only because both of its gates make an idle tick silent: an hour with nothing changed and nothing to ask posts nothing, and a change is a diff against the previous tick rather than a restatement of the current state.
