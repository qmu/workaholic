# Web-bootstrap reference — mechanics and history

Companion to `SKILL.md` §4. The live rules are in the SKILL's Caveats list; this file carries the evidence and the decided limits.

## Why the fast path is version-gated (2026-08-04)

A cloud container image bakes a marketplace clone in, so "installed" can mean a version several releases behind the checkout, and skipping on mere presence made that permanent — the stale copy's retired mission migration dirtied the tree on every prompt and aborted every hourly drive tick on 2026-08-02〜04. The skip now requires the installed version to match the checkout's `.claude-plugin/marketplace.json`; anything else refreshes the marketplace and runs `plugin update` (or `install`).

Two limits of that gate are decided, not pending (2026-08-04): the hook runs at SessionStart and never refreshes a running session (swapping the plugin under already-loaded skills and always-on hooks mid-turn is worse than being one version behind, and there is no non-polling signal to hang a refresh on), and `WANTED` is read from a checkout that can itself be behind the base, so a stale clone and a stale baked-in install can agree and the fast path skips exactly when it should not. Both are answered by making the drift legible rather than adding a gate: `check-deps/scripts/check.sh` reports `checkout_version`/`version_drift` (and, on the second axis, `registry_version`/`registry_unreadable`/`loaded_version_behind_registry`), and `/drive` acts on them. The contract: *the bootstrap makes the install correct at session start; check-deps makes it honest afterwards.* The superseded-binding repair half was investigated and there is none inside the plugin — the binding, the cache layout and the registry are all the harness's; the evidence is recorded in `bootstrap/session-start.sh`'s header.

## The `gh` provisioning step (2026-08-06)

The web container ships no `gh`, and fourteen plugin scripts shell out to it — `publish-tree-pr.sh` pushed the branch and then reported `no_gh` instead of opening the pull request, and `merge-pr.sh` could not run at all, so every cloud `auto` unit was demoted to the PR path and every routine-published artifact waited for a human. The step is guarded on `command -v gh` (an already-provisioned container pays nothing), needs root, and is non-fatal in every branch — `gh` still absent afterwards is the status quo, not a regression, so the hook logs one legible line and session start still succeeds.

## The git-identity step (2026-08-07)

The web container's git identity is `noreply@anthropic.com`, and ticket/mission ownership is compared against `git config user.email` (`gather/scripts/owns.sh`) — measured live on the first full routine-chain day: a proposal's ticket carried the developer's own address in `assignees` (P6, correctly stamped from the Issue assignee) and the developer's own `[Implement]` routine ended 🔴 `ticket_owner_mismatch`, unable to claim the very ticket it existed to drive. The session pushes and merges *as* the developer's GitHub account, yet git did not know who it was — so every personally-assigned ticket was undrivable by the routine that exists to drive it.

The hook closes this at the provisioning seam: it resolves the session's GitHub login via `gh api user` and looks it up in the committed repo-root `.claude/git-identities` (`<login>=<canonical>[,<alias>...]`, one per line, `#` comments tolerated), setting the repo-local `git config user.email` and, when the **repo-local** `user.name` is unset, `user.name` from the account's real name (`gh api user --jq .name`, falling back to the login). Identity enters once, per developer, in a committed file; the emails are already public in git history, so the file discloses nothing new. Guards: it acts only when the current email is empty or an `@anthropic.com` default (a real local identity is never overwritten), every branch is non-fatal with one log line (absent mapping file, missing `gh`, failed API call are each the status quo, not a regression), and it runs before the version-gated fast path so a resume refire still repairs an unset identity — once set, later fires take the real-identity arm and cost one `git config` read.

**The name half shipped dead, and was repaired on 2026-08-18** (issue #506). The `user.name` line was there from the start, guarded by `[ -z "$(git config user.name)" ]` — the **effective** scope, which in a web container resolves the global `Claude` and is never empty — so it never executed once, and GitHub, which renders the author name rather than the email, showed every routine commit as authored by Claude. The guard reads `git config --local user.name` now: a container's global default no longer reads as "the developer already chose a name", while a developer's own repo-local name is still left alone. The value prefers `gh api user --jq .name` (the mapping file carries no display name, and the login call is already being made, so the success path costs no extra round trip) and falls back to the login when the account publishes none. The repair is **forward-only** — commits already on `main` keep `Claude`, and a session already running keeps the name it started with, because the hook fires at session start. `user.name` remains cosmetic to every mechanism (ownership, claims and resumption read `user.email`), which is what makes moving it safe; a consuming repository picks it up when `/workaholify` refreshes its bootstrap copy.

**A person may have more than one address, and the mapping says so in one field** (2026-08-26). The value after `=` is a comma-separated list whose **first** field is canonical; every field after it is another address of the same person. A line with no comma is exactly what the format was before, so every committed file stays valid and this hook's own parse is unchanged on it. The hook takes the canonical field (`cut -d, -f1`) and is the **one sanctioned second parser** of the format: it is copied to `.claude/hooks/` and runs at SessionStart, before the plugin is installed, so it cannot call `gather/scripts/identity.sh` — the mapping's one reader everywhere else, and the resolution `owns.sh`, `/specificate`'s assignee stamp, the recovery migration and `/moderate`'s undrivable-work question all go through. The exception is stated in both headers so the second parse reads as a decision rather than a bug.

**The mapping is audited beside the hook** (2026-08-26; a third problem 2026-09-02). `check-bootstrap.sh` carries three more named problems, all about `.claude/git-identities` and all emitted by `workaholify/scripts/audit-identity-coverage.sh`: `identity_map_missing` (absent — the identity step above is then a permanent no-op, which is exactly the state that reads as configured and does nothing), `identity_map_uncovered` (present, and naming no entry for an address the tree uses), and `identity_map_no_entry_for_account` (present, and naming no entry for the GitHub login **this session runs as** — the lookup step 0b actually performs, which the tree-facing question does not imply: a mapping covering every `assignees:` value can still leave a routine's own account unmapped, and the hook then keeps `noreply@anthropic.com`). That third check takes its login from `--account`, resolved by `check-bootstrap.sh` through `gh api user` — bounded and non-fatal, so the audit stays a pure local read — and is three-valued: with no login it reads `checked: false` with a named reason and raises nothing, because a check that could not run is neither a pass nor a finding. The audit walks every `assignees:` value under `tickets/`, `missions/` and `strategies/` through `gather/scripts/identity.sh` and names each uncovered address **with the line that would cover it**; `assignees: []` names nobody and is not an uncovered address. `apply-bootstrap.sh` scaffolds the file's header when it is missing and appends each proposed line as a **comment** — it proposes and never decides, because which account an address belongs to is a human's ruling, so `identity_map_uncovered` stays reported until a person completes the line. That is one named-problem set for one file, deliberately: two vocabularies for one file get one of them fixed and the other assumed. None of the three gates `ok`, and that is a decision rather than an omission: `identity_map_uncovered` can only be settled by a human — which GitHub account an address belongs to is a fact this plugin does not have — so gating a completion signal on it would make `ok` unreachable by any machine, and `/workaholify`'s report-only outcome is a named refusal's recovery path rather than the ordinary one. `identity_map_no_entry_for_account` is that argument in its strongest form: the missing line names an account, and only a person can say which address it commits as. **And `identity_map_missing` does not gate either** (ruled 2026-09-02 by the run that drove the ticket the 2026-08-26 note deferred it to): the case for gating is that its repair is machine-reachable, and that is what defeats it — the scaffold carries no entries, so a repository that applies it still logs `no entry for '<login>'` and still keeps `noreply@anthropic.com`, and the gate would go green on a file that leaves the hook exactly as dead. All three are carried in `check-bootstrap.sh`'s **`advisories`**, and `apply-bootstrap.sh` reads them from there.

Recorded in the hook's header: it fails open by design, status-checks each step rather than wrapping them in a `{ … } || echo FAILED` group that silently reported success on total failure, drops the invalid `marketplace add --scope user`, and is idempotent. `matches_canonical` compares the installed copy byte-for-byte against `bootstrap/session-start.sh`, so an older copy is reported as drift (`hook_stale`) rather than passing because a file exists at the path. The `[Implement]` prompt's own precondition is what fails without the bootstrap — *"the workaholic plugin must be loaded … if it is not, post the failure and stop"* — which is why a missing bootstrap reads as healthy from the routines list and leaves no trace in git.
