# Routine reference — trigger wiring, ownership, where configuration lives

Companion to `SKILL.md` §5. The standing rules live in the SKILL; this file carries the measurements, the retirement records, and the rejected alternatives.

**Reading the command name below.** Everything dated before 2026-08-14 says `/setup-routines`, and it is kept as written because it is what was decided and measured at the time. On 2026-08-14 (issue #451) that one command **split by routine scope** into `/setup-dev-routines` (the `developer`-scoped `[Specificate]`/`[Implement]`) and `/setup-repo-routines` (the `repository`-scoped `[Prepare Release]` — named `[Release Status]` until 2026-08-18 — and, since 2026-08-17, `[Standup]`, converged from one account). The flow, the `no_transport` refusal and the sheet-as-recovery-path are identical in both; only the template set differs, and every finding recorded here applies unchanged to each. The old name is removed rather than aliased (`SKILL.md` §5, *Two scopes, two commands*).

## The trigger surface, measured (2026-08-05/06)

The product's documentation ([Routines](https://code.claude.com/docs/en/routines), *Add a GitHub trigger*) states: "GitHub triggers are configured from the web UI only." Supported event categories are Pull request and Release, narrowable by AND-combined filters (author, title, body, base/head branch, labels, is-draft, is-merged); `matches regex` tests the whole value, so substring matching wants `contains`. An API trigger's token is likewise generated in the UI only and fires `POST /v1/claude_code/routines/<id>/fire` with an optional `text` payload.

Read back over the live account, a routine record's whole trigger surface is three fields — `cron_expression`, `run_once_at`, and `api_token_hint`/`api_token_created_at` (an external caller POSTing `/v1/code/triggers/<id>/run`). There is no event-subscription field of any kind, so the GitHub wiring is unreadable, unwritable and unverifiable from a session; `trigger: event` in the templates became `trigger: invoked` accordingly, and the `trigger_*` keys declare the *designed* wiring for the reader and the setup-sheet renderer.

`last_fired_at` is populated for a cron fire and absent for a GitHub-triggered one — `[Specificate] workaholic` turned issue #266 into PR #267 at 2026-08-06T03:23Z and its record still carries no such key. Two prior readings of the account failed the same way, by treating the record as able to answer a question it does not carry: an absent `last_fired_at` was read as "never fired", then the absent event field was read as "no event path exists". A reader who needs to know whether a routine ran looks at what it produced (an issue, a pull request, a channel post), never at the account.

A `[Specificate]` routine observed firing on a merged pull request is misconfigured — the merge is `[Implement]`'s event, and one event has one owner. Repairing a live routine's trigger is a human act in the routines UI; neither the setup sheet nor any script can see or fix it.

The scheduling consequence, **superseded 2026-08-10** (FB `20260810085032`/issue #336, ticket `20260810085347`): the 2026-08-06 ruling read as "settled" was that `[Implement]` stays merge-triggered because its survey already answers the clock argument (handoff resumption, lapsed claims, `/ticket`-written backlog have no merge event — every merge-started run offers *everything* claimable, so leftovers ride the next merge rather than a timer). That argument shows the survey **can** substitute for a timer, not that instant reaction is the better cadence — and the loop-engineering premise this repository was built on favors the timer: a bounded, predictable tick over a reactive one. `[Implement]` now fires on a fixed hourly schedule (`30 * * * *`) instead; the survey argument still holds as the reason this move is *safe* (nothing depended on the merge event for correctness), just not as the reason to prefer the merge event. The accepted cost: a merged proposal now waits up to an hour rather than starting instantly. (A shared `0,30 * * * *` was tried first and rejected by the API — `cron interval too short`, measured 2026-08-10; the minimum realizable interval is one hour, and a bare `:00` minute is silently rewritten to a server-chosen jitter minute — so `[Implement]` settled on the explicit non-zero minute `:30`.) A machine-local cron remains available as a fallback shape outside the routines product (`docs/drive-loop-runbook.md`), a developer's act to stand up.

**`[Specificate]` moved too, on the developer's explicit correction the same day.** A first pass of this ticket kept `[Specificate]` on its GitHub assignment trigger, reasoning that a schedule fire carries no issue in hand and `/specificate`'s whole design is *the ask in hand* — converting it looked like either a `nothing_in_hand` no-op every tick or a resurrection of the swept-backlog `[Propose Batch]` design retired below. The developer's ask covered both routines from the start (FB `20260810085032`'s literal text), and restated it live on PR #345 after seeing only `[Implement]` move. `fb.md` now carries the same `trigger_kind: schedule` as `implement.md`, on its own realizable hourly minute (`cron_expression: 15 * * * *`, distinct from `implement.md`'s `30 * * * *` so the two never collide). The conflict the first pass raised was real and **unresolved by the move alone**: a `[Specificate]` tick fired purely by the clock, with nothing else handing it an ask, reported `nothing_in_hand` and ended — the schedule did not give `/specificate` new input. **Closed 2026-08-12, on the developer's instruction**: the migration was always meant to include the discovery half — search the repository's open GitHub issues filtered to the developer's own assignment, instead of requiring a specific issue URL or ID handed in. `/specificate` now owns that as its *Clock-fired discovery* (`specificate/scripts/list-inbound-issues.sh`): open issues assigned to the session's own identity, oldest-first, minus those a feedback record already names, each taken as an ask through the full run. Two boundaries decided there rather than left open: it never takes **unassigned** issues (every developer's copy fires hourly, so an unassigned issue offered to all copies is the P8 race — a human hands those to `/specificate` by hand), and it applies **no title filter** (an `[FB]`-style prefix was considered and rejected: issues arrive here from humans in the GitHub UI and from other tools that carry no such prefix — measured 2026-08-12, 1 of 9 human-filed issues did — so a title filter would drop exactly the asks the loop exists to ingest. The rejection was originally justified by `/fb`'s own crossing adding no prefix to the issues it opens; since issue #411 the crossing does stamp `[FB] `, and the boundary stands unchanged on the inbound-mix reason, because the crossing was never the only sender).

## The schedule field, re-verified for a session (2026-08-10)

FB `20260810085032`/issue #336 asked to revisit both "routines are never cron" and "`/setup-routines` manages nothing," specifically for `cron_expression` — unlike a GitHub event, it **is** a genuine, API-visible field on a routine record (line 9 above), so the 2026-08-06 retirement's premise ("the wiring is invisible to the API") does not obviously carry over. Re-verified directly rather than assumed (ticket `20260810085351`): `ToolSearch` over this session's entire tool surface, queried by name and by keyword (`RemoteTrigger`, "routine", "trigger", "schedule", "cron"), found no `RemoteTrigger`-family tool at all. The only scheduling tools present — `CronCreate`/`CronList`/`CronDelete` — are explicitly documented as session-only and in-memory ("Jobs live only in this Claude session — nothing is written to disk, and the job is gone when Claude exits"), a different mechanism entirely from an account-level routine record, which persists across sessions and devices and is what actually fires `[Specificate]`/`[Implement]`. So while `cron_expression` is a *field* the API could in principle expose, no tool in this session's surface reads or writes it — the retirement's conclusion holds for a schedule trigger for the same reason it holds for a GitHub one, even though the underlying reason (no field at all vs. a field with no session-facing tool) differs. This finding is scoped to what was checked: an **unattended, routine-fired session** — the exact class `[Implement]` runs in. Nothing here rules out a `RemoteTrigger`-class tool being available to a *developer's own* interactive `claude.ai` session; that would need its own re-verification from inside such a session, not an assumption in either direction.

**That re-verification happened, and found the tool present** (FB `20260810214929`, ticket `20260810130703`, 2026-08-10): a live interactive session listed this repository's two routines via a `RemoteTrigger`-family tool, found both carrying an empty (unscheduled) `cron_expression`, and wrote working hourly schedules onto both. So "manages nothing" was never a property of `/setup-routines` itself — it was a property of the session class every check to date had run in. `/setup-routines` therefore **attempts the configuration every time** (`workaholic:workaholify` SKILL.md §5, *Configuring the routines is the job; `no_transport` is its one refusal*) and converges routine wiring directly; when its session can reach no account routine it reports `no_transport: RemoteTrigger-family tool` and renders the sheet as that refusal's recovery path — the sheet's content unchanged, its standing no longer that of an equal branch (issue #408, 2026-08-12: reporting a successful configuration as an accident of the tool surface was itself the defect). The account-management surface (digest gate, drift/fleet reports, §*The management surface is retired* below) stays retired regardless: the direct-apply path converges to the plugin's own templates on the spot, it does not survey or report drift as a standalone act, and it is reachable only through a developer's own interactive invocation of `/setup-routines` — never wired into `[Implement]`/`[Specificate]`, so it never runs unattended.

The practical consequence: `/setup-routines` already is the "revived `/set-routines`" — its copy-paste sheet (`render-setup-sheet.sh`) already derives a **Trigger** step from a template's `cron_expression` (the branch existed before this ticket, for exactly this case), so no new *sheet-rendering* command was written; what was added is the direct configuration above. Fabricating a `cron_expression`-writing command with nothing behind it to call would still repeat the exact mistake the 2026-08-06 retirement corrected — a tool that manages what it cannot verify — which is why the command *attempts* the write through a real transport and, finding none, says `no_transport` rather than pretending to have configured anything.

## The tool surface is session-class-dependent, and the live wiring has drifted (2026-08-10)

The line above is scoped to what was checked: an **unattended, routine-fired session** — the exact class `[Implement]` runs in. A separate, local **attended** session (ticket `20260810104620`) measured the opposite on its own tool surface: `RemoteTrigger` (`list`/`get`/`create`/`update`/`run`/`create_webhook_trigger`) was present, and `list` returned both live routine records (`[Specificate] workaholic`, `[Implement] workaholic`) in full — prompt, model, repository, connectors, `cron_expression`. Nothing here rules out a `RemoteTrigger`-class tool being available to a *developer's own* interactive `claude.ai` session; that was never checked from inside an unattended run and could not have been. The two findings are not in tension — they are answers to different questions, scoped to different session classes, and a reader who needs to know which applies to their own session has to check it directly rather than assume either direction.

The same reading also surfaced the second half of what an attended session can see but not fix: both live routine records carried `cron_expression: ""`, not the designed `0,30 * * * *`, and both prompts differed from the committed templates (`{repo}` placeholders, older wording, `next_run_at` unset). This is a **currently-manual, developer-facing gap**, not a defect this repository's tooling can close — no tool confirmed available to any session class here can write a routine's `cron_expression` or prompt; only an attended session was found able to *read* it. Repairing the drift is a human act: re-enter the schedule and re-paste the current template prompt in the routines UI at <https://claude.ai/code/routines>, or from within an attended session where a `RemoteTrigger`-class tool is confirmed present. Whether `/setup-routines` should eventually gain read/drift-check/create-update capability where the tool is confirmed present is a larger design decision, left open here.

## Auto-fix pull requests: a real API field, found by toggling the UI (2026-08-12)

The routine form's **Auto-fix pull requests** option (プルリクエストの自動修正) is stored at `job_config.ccr.session_context.autofix_on_pr_create` on the trigger record. It is not documented anywhere — the routines docs describe Auto-fix only as a per-PR toggle (CI status bar / `/autofix-pr`) — and it was found empirically: the API **silently drops unknown fields** (an update carrying a fabricated `autofix: true` returns HTTP 200 with the field absent from the record), so probing field names is inconclusive and the discovery route was the developer toggling the option in the UI on `[Implement] workaholic` and this side re-reading the record with `get`. Both consequences are standing rules: a `RemoteTrigger` write is confirmed by **reading the record back**, never by the 200; and the templates declare the option as `autofix_on_pr_create: true` frontmatter, which the direct-apply path converges (`session_context.autofix_on_pr_create`) and the setup sheet renders as a UI step.

## Per-developer routines: two mechanisms, not one (P6, 2026-08-06)

A repository has several developers, each with their own copy of both routines, and the trigger filter alone cannot answer "whose run is this" — a trigger is a UI setting nothing in the plugin can read or verify. So the filter bounds the cost (N−1 sessions per event find nothing to do and end `ok`) and the data decides the ownership: `/specificate` writes the triggering issue's assignee onto every artifact it emits (`--assignee`, `workaholic:specificate`), so the identity enters once at the trigger and rides the chain. Ownership is the load-bearing half — it lives in the repository, every runner reads it through one oracle, and it holds even when a trigger is misconfigured. Before it existed, a proposal-born artifact was unowned (correctly meaning "claimable by anyone"), so every developer's runner raced for it and whose push landed first decided whose job it was. Neither trigger narrows to a person: the routines UI offers no assignee filter, which killed the original `assignee = the developer` design; an `author` filter on `[Implement]` was tried and dropped with it.

## The retired routines

- `[Propose Batch]` existed for part of 2026-08-04: proposing belongs in the session that receives the ask, not in a sweep over what has already merged (`docs/proposal-loop-runbook.md` §7).
- `[Consent]` (the merge announcement, retired 2026-08-06) posted a merge — the approval, in this workflow — into the merged item's feedback thread. The stated cost: a human-merged pull request is now announced by nobody, since `[Implement]` posts only for the units it ran (and, since the start post's own retirement on 2026-08-11, only at the finish — a merged proposal that `[Implement]` never claims produces no post of its own at all). What softens the cost is that every merge remains readable on GitHub. The whole point of the reduction is that a third standing process costs more, per project, than the line it produced.
- `[Drive]`'s 141-line prompt (against the other templates' ~55) is why a template is a thin pointer: the restated run procedure had drifted into instructing a hand-filter for mission ownership that `plan-units.sh` had performed for weeks. The routine is what runs, and nothing rebuilds it from the skill.

## Prompt form

Keeping the prompt as readable markdown rather than an embedded JSON string is deliberate: the prompt *is* the routine, and a prompt nobody can read in a diff is a prompt nobody will keep current. Measured across the live account before P7: the `[FB]` prompt was byte-identical across seven repositories, differing only in which repository it pointed at — which is why the prompts now carry no repository name at all. The renderer accepts the repository URL in any spelling (`https://github.com/owner/name`, `git@github.com:owner/name`, `ssh://git@github.com/owner/name`, each ± `.git` and a trailing slash) and renders identically; the sheet's Repository field renders the https form (a link a person clicks), and a URL already carrying a scheme is passed through untouched, so a proxied `http://…` remote is never rewritten.

## Where the configuration lives (decided 2026-08-03)

Three places, one kind of fact each, and the repository declares nothing: the **plugin** holds what a routine *should* be (the templates, one set for every repository); the **account** holds what a routine *is* (the live routine); the **repository** holds nothing new — the setup sheet's Repository field and a routine's `{repo_name}` both derive from its own git remote. A repository was never short of a config file; it was short of an answer, so the fix was a reader (`/setup-routines`), not a directory — no `.workaholic/` area is introduced and no closed-layout amendment is involved. Rejected: per-repository declarations (one copy per repo, identical everywhere but its URL, each free to drift, none authoritative); a selection manifest (the closest call — but the selection is uniform across the fleet, and since P3 there is no per-repository choice left to record); a committed snapshot of the live routines (goes stale silently, and a stale snapshot reading as healthy is exactly the failure §4 exists to catch). Full record: `.workaholic/feedbacks/20260803213008-where-routine-configuration-lives-and-what-an-agent-may-apply-unattended.md`.

## The management surface is retired, and why it must not grow back (2026-08-06)

`plan-routine-change.sh` / `authorize-routine-change.sh` (the digest gate) and `compare-routines.sh` / `list-routines.sh` (drift and fleet reporting) were deleted with their tests. They managed the half of a routine the API exposes while blind to the half that decides whether it runs at all; the measured cost was two wrong answers in one day — a paginated `list` (20 rows, `has_more` unread) surveyed as the whole account, and six duplicate records carefully refreshed through the digest gate while the real, wired `[Specificate]` ran a stale prompt beyond page one, with a "drift-free fleet" verdict reported both times. Three things survive the machinery: the digest gate's reasoning (it closed *substitution* and *batching*; the bar is not weakened — the acts it gated no longer exist; record: `.workaholic/feedbacks/20260806143907-routine-setup-is-a-human-act-the-plugin-makes-cheap.md`), the rule that "could not check" is never "does not exist" (still governing `check-slack-channel.sh`), and the fact that the account has no delete — removing a routine is a human act at <https://claude.ai/code/routines>, and always was. That failure class had already cost the project once before: a survey concluded "no routines are installed" from an empty crontab, on a machine whose routines run in the cloud. Absence of evidence is not evidence of absence.
