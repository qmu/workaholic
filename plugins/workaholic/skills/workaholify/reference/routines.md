# Routine reference — trigger wiring, ownership, where configuration lives

Companion to `SKILL.md` §5. The standing rules live in the SKILL; this file carries the measurements, the retirement records, and the rejected alternatives.

## The trigger surface, measured (2026-08-05/06)

The product's documentation ([Routines](https://code.claude.com/docs/en/routines), *Add a GitHub trigger*) states: "GitHub triggers are configured from the web UI only." Supported event categories are Pull request and Release, narrowable by AND-combined filters (author, title, body, base/head branch, labels, is-draft, is-merged); `matches regex` tests the whole value, so substring matching wants `contains`. An API trigger's token is likewise generated in the UI only and fires `POST /v1/claude_code/routines/<id>/fire` with an optional `text` payload.

Read back over the live account, a routine record's whole trigger surface is three fields — `cron_expression`, `run_once_at`, and `api_token_hint`/`api_token_created_at` (an external caller POSTing `/v1/code/triggers/<id>/run`). There is no event-subscription field of any kind, so the GitHub wiring is unreadable, unwritable and unverifiable from a session; `trigger: event` in the templates became `trigger: invoked` accordingly, and the `trigger_*` keys declare the *designed* wiring for the reader and the setup-sheet renderer.

`last_fired_at` is populated for a cron fire and absent for a GitHub-triggered one — `[Propose] workaholic` turned issue #266 into PR #267 at 2026-08-06T03:23Z and its record still carries no such key. Two prior readings of the account failed the same way, by treating the record as able to answer a question it does not carry: an absent `last_fired_at` was read as "never fired", then the absent event field was read as "no event path exists". A reader who needs to know whether a routine ran looks at what it produced (an issue, a pull request, a channel post), never at the account.

A `[Propose]` routine observed firing on a merged pull request is misconfigured — the merge is `[Implement]`'s event, and one event has one owner. Repairing a live routine's trigger is a human act in the routines UI; neither the setup sheet nor any script can see or fix it.

The scheduling consequence, **superseded 2026-08-10** (FB `20260810085032`/issue #336, ticket `20260810085347`): the 2026-08-06 ruling read as "settled" was that `[Implement]` stays merge-triggered because its survey already answers the clock argument (handoff resumption, lapsed claims, `/ticket`-written backlog have no merge event — every merge-started run offers *everything* claimable, so leftovers ride the next merge rather than a timer). That argument shows the survey **can** substitute for a timer, not that instant reaction is the better cadence — and the loop-engineering premise this repository was built on favors the timer: a bounded, predictable tick over a reactive one. `[Implement]` now fires on a fixed hourly schedule (`30 * * * *`) instead; the survey argument still holds as the reason this move is *safe* (nothing depended on the merge event for correctness), just not as the reason to prefer the merge event. The accepted cost: a merged proposal now waits up to an hour rather than starting instantly. (A shared `0,30 * * * *` was tried first and rejected by the API — `cron interval too short`, measured 2026-08-10; the minimum realizable interval is one hour, and a bare `:00` minute is silently rewritten to a server-chosen jitter minute — so `[Implement]` settled on the explicit non-zero minute `:30`.) A machine-local cron remains available as a fallback shape outside the routines product (`docs/drive-loop-runbook.md`), a developer's act to stand up.

**`[Propose]` moved too, on the developer's explicit correction the same day.** A first pass of this ticket kept `[Propose]` on its GitHub assignment trigger, reasoning that a schedule fire carries no issue in hand and `/propose`'s whole design is *the ask in hand* — converting it looked like either a `nothing_in_hand` no-op every tick or a resurrection of the swept-backlog `[Propose Batch]` design retired below. The developer's ask covered both routines from the start (FB `20260810085032`'s literal text), and restated it live on PR #345 after seeing only `[Implement]` move. `fb.md` now carries the same `trigger_kind: schedule` as `implement.md`, on its own realizable hourly minute (`cron_expression: 15 * * * *`, distinct from `implement.md`'s `30 * * * *` so the two never collide). The conflict the first pass raised is real and **unresolved by this move alone**: a `[Propose]` tick fired purely by the clock, with nothing else handing it an ask, still reports `nothing_in_hand` and ends — the schedule does not give `/propose` new input, only a periodic chance to act on whatever *is* already in hand by some other means. Whether `/propose` should grow its own clock-compatible discovery is a separate, unscoped question, not assumed answered by this ticket.

## The schedule field, re-verified for a session (2026-08-10)

FB `20260810085032`/issue #336 asked to revisit both "routines are never cron" and "`/setup-routines` manages nothing," specifically for `cron_expression` — unlike a GitHub event, it **is** a genuine, API-visible field on a routine record (line 9 above), so the 2026-08-06 retirement's premise ("the wiring is invisible to the API") does not obviously carry over. Re-verified directly rather than assumed (ticket `20260810085351`): `ToolSearch` over this session's entire tool surface, queried by name and by keyword (`RemoteTrigger`, "routine", "trigger", "schedule", "cron"), found no `RemoteTrigger`-family tool at all. The only scheduling tools present — `CronCreate`/`CronList`/`CronDelete` — are explicitly documented as session-only and in-memory ("Jobs live only in this Claude session — nothing is written to disk, and the job is gone when Claude exits"), a different mechanism entirely from an account-level routine record, which persists across sessions and devices and is what actually fires `[Propose]`/`[Implement]`. So while `cron_expression` is a *field* the API could in principle expose, no tool in this session's surface reads or writes it — the retirement's conclusion holds for a schedule trigger for the same reason it holds for a GitHub one, even though the underlying reason (no field at all vs. a field with no session-facing tool) differs. This finding is scoped to what was checked: an **unattended, routine-fired session** — the exact class `[Implement]` runs in. Nothing here rules out a `RemoteTrigger`-class tool being available to a *developer's own* interactive `claude.ai` session; that would need its own re-verification from inside such a session, not an assumption in either direction.

The practical consequence: `/setup-routines` already is the "revived `/set-routines`" — its copy-paste sheet (`render-setup-sheet.sh`) already derives a **Trigger** step from a template's `cron_expression` (the branch existed before this ticket, for exactly this case), so no new command was written. Fabricating a `cron_expression`-writing command with nothing behind it to call would repeat the exact mistake the 2026-08-06 retirement corrected — a tool that manages what it cannot verify.

## Per-developer routines: two mechanisms, not one (P6, 2026-08-06)

A repository has several developers, each with their own copy of both routines, and the trigger filter alone cannot answer "whose run is this" — a trigger is a UI setting nothing in the plugin can read or verify. So the filter bounds the cost (N−1 sessions per event find nothing to do and end `ok`) and the data decides the ownership: `/propose` writes the triggering issue's assignee onto every artifact it emits (`--assignee`, `workaholic:propose`), so the identity enters once at the trigger and rides the chain. Ownership is the load-bearing half — it lives in the repository, every runner reads it through one oracle, and it holds even when a trigger is misconfigured. Before it existed, a proposal-born artifact was unowned (correctly meaning "claimable by anyone"), so every developer's runner raced for it and whose push landed first decided whose job it was. Neither trigger narrows to a person: the routines UI offers no assignee filter, which killed the original `assignee = the developer` design; an `author` filter on `[Implement]` was tried and dropped with it.

## The retired routines

- `[Propose Batch]` existed for part of 2026-08-04: proposing belongs in the session that receives the ask, not in a sweep over what has already merged (`docs/proposal-loop-runbook.md` §7).
- `[Consent]` (the merge announcement, retired 2026-08-06) posted a merge — the approval, in this workflow — into the merged item's feedback thread. The stated cost: a human-merged pull request is now announced by nobody, since `[Implement]` posts only for the units it ran (and, since the start post's own retirement on 2026-08-11, only at the finish — a merged proposal that `[Implement]` never claims produces no post of its own at all). What softens the cost is that every merge remains readable on GitHub. The whole point of the reduction is that a third standing process costs more, per project, than the line it produced.
- `[Drive]`'s 141-line prompt (against the other templates' ~55) is why a template is a thin pointer: the restated run procedure had drifted into instructing a hand-filter for mission ownership that `plan-units.sh` had performed for weeks. The routine is what runs, and nothing rebuilds it from the skill.

## Prompt form

Keeping the prompt as readable markdown rather than an embedded JSON string is deliberate: the prompt *is* the routine, and a prompt nobody can read in a diff is a prompt nobody will keep current. Measured across the live account before P7: the `[FB]` prompt was byte-identical across seven repositories, differing only in which repository it pointed at — which is why the prompts now carry no repository name at all. The renderer accepts the repository URL in any spelling (`https://github.com/owner/name`, `git@github.com:owner/name`, `ssh://git@github.com/owner/name`, each ± `.git` and a trailing slash) and renders identically; the sheet's Repository field renders the https form (a link a person clicks), and a URL already carrying a scheme is passed through untouched, so a proxied `http://…` remote is never rewritten.

## Where the configuration lives (decided 2026-08-03)

Three places, one kind of fact each, and the repository declares nothing: the **plugin** holds what a routine *should* be (the templates, one set for every repository); the **account** holds what a routine *is* (the live routine); the **repository** holds nothing new — the setup sheet's Repository field and a routine's `{repo_name}` both derive from its own git remote. A repository was never short of a config file; it was short of an answer, so the fix was a reader (`/setup-routines`), not a directory — no `.workaholic/` area is introduced and no closed-layout amendment is involved. Rejected: per-repository declarations (one copy per repo, identical everywhere but its URL, each free to drift, none authoritative); a selection manifest (the closest call — but the selection is uniform across the fleet, and since P3 there is no per-repository choice left to record); a committed snapshot of the live routines (goes stale silently, and a stale snapshot reading as healthy is exactly the failure §4 exists to catch). Full record: `.workaholic/feedbacks/20260803213008-where-routine-configuration-lives-and-what-an-agent-may-apply-unattended.md`.

## The management surface is retired, and why it must not grow back (2026-08-06)

`plan-routine-change.sh` / `authorize-routine-change.sh` (the digest gate) and `compare-routines.sh` / `list-routines.sh` (drift and fleet reporting) were deleted with their tests. They managed the half of a routine the API exposes while blind to the half that decides whether it runs at all; the measured cost was two wrong answers in one day — a paginated `list` (20 rows, `has_more` unread) surveyed as the whole account, and six duplicate records carefully refreshed through the digest gate while the real, wired `[Propose]` ran a stale prompt beyond page one, with a "drift-free fleet" verdict reported both times. Three things survive the machinery: the digest gate's reasoning (it closed *substitution* and *batching*; the bar is not weakened — the acts it gated no longer exist; record: `.workaholic/feedbacks/20260806143907-routine-setup-is-a-human-act-the-plugin-makes-cheap.md`), the rule that "could not check" is never "does not exist" (still governing `check-slack-channel.sh`), and the fact that the account has no delete — removing a routine is a human act at <https://claude.ai/code/routines>, and always was. That failure class had already cost the project once before: a survey concluded "no routines are installed" from an empty crontab, on a machine whose routines run in the cloud. Absence of evidence is not evidence of absence.
